# src/components フォルダ

Cockpitの日付横の天候は`hud/WeatherStatus.tsx`と`useWeather.ts`が担当する。Unityの`weather:state`を正として表示し、テンプレートモードでは標準selectから`weather:set`を送る。高さ76pxの独立WebViewをはみ出す候補にはCSSメニューを使わず、画面下端で上に開けるネイティブポップアップを使う。Cockpitは`AmbienceVolumeSync`で音量設定だけをUnityへ送る。環境音はUnityが再生する。

ドメイン別のUIコンポーネント置き場。コンポーネントごとに`.tsx`と対応する`.css`を並べる。
表示文字列は必ずi18n(`t("key")`、`src/i18n/`配下のドメイン別JSONの全7言語に追加)を使うこと。

**他コンポーネントのCSSのクラスを借りるときは、そのCSSを明示的に`import`すること。** パネルは`App.tsx`で`lazy()`されておりCSSもチャンク単位で分割されるため、`import`しないと「そのチャンクを既に読み込んだウィンドウでだけスタイルが当たる」という再現性の低い崩れになる(ポップアップウィンドウは`window_type`をまたいで使い回されるので、直前に何を開いたかで結果が変わる)。全パネル共通のレイアウト(`.agent-detail`など)は`App.css`にあるのでこれに当たらない。

## hud/ の常駐パネル(ゲーム中に画面へ出ているUI)

- **公共サービス充足度メータ(`hud/PublicServiceGauges`)**は、電力・水道などの需給を縦棒で常時表示する(棒の枠の高さ=供給キャパシティ、塗り=需要量。生産量は描かない)。逼迫は色だけで示し(80%以上=黄・100%以上=赤)、文字は出さず棒の下にアイコンだけを置く。**棒の隙間を含むウィジェット全体が1つのボタン**で、押すと公共施設ウィンドウ(`public_facilities`)を開く(棒ごとのクリック分岐はしない)。データ源は`GET /api/v1/city/public-service-supply`(公共施設ウィンドウの需給ドーナツと同一エンドポイント。**価格の概念を持たないインフラ財=高圧電力/高圧水道も含む**ので、価格用の`/public-service-prices`ではなくこちらを使う)。並べる製品は`local-constants.COCKPIT_PUBLIC_SERVICE_PRODUCTS`、表示名はコックピットが`MasterDataContext`の外にあるためi18n(`publicServiceGauge.services.<製品ID>`)に持つ。アイコンは専用画像が未用意のため同ファイル内のインラインSVGのプレースホルダ(製品ID→図形の対応表1箇所を`<img>`へ差し替えれば移行できる)。
- **共有部品**: `useHudSession`(session-stateの受信=表示可否/都市名/日付/テンプレートモード/市庁舎ロック/エポック実行中)、`useTutorialHighlight`(チュートリアルのハイライト対象)、`hudCommon.ts`(アイコン定義とウィンドウを開くヘルパ)、`hudMode.ts`。
- **地区編集の「地区の統合」の確定は `IconPanel` が中継して専用の小ウィンドウに出す**: 地区編集モードは自前のウィンドウを持たない常駐モードでUnityから直接ウィンドウを開けないため、Unityが3Dビューで統合元・統合先を決めた時点で送る `edit_zone:request_merge` を、常駐している `IconPanel` が受けて `zone_merge` ウィンドウ(`zone/ZoneMergeConfirmWindow`)を `params.extra.pendingMerge` 付きで開く。確定時は `POST /api/v1/zones/{id}/merge` を送って結果を `sendEditZoneFinishMerge(true)` でUnityへ返す。**イベントを投げてからウィンドウを開く順序ではパネルの購読が間に合わない**ため、統合内容はイベントではなくウィンドウコンテキストで渡している。**×で閉じられた場合の取消送信は Rust 側(`window.rs` のクローズ処理で `edit_zone:finish_merge {merged:0}`)が担う**(ウィンドウは非表示になるだけでReactのアンマウント処理が走らず、パネル任せだとUnityが統合待ちのまま取り残されるため)。
- **建物建設パネルの施設情報カード(`building/BuildingFacilityInfoCard`)は稼働後のランニングコストを内訳つきで表示する**: TYPE_STANDARD(一般施設)のバリアント選択+敷地確定時、`POST /buildings/construction-cost`が返す`estimated_operating_cost`(総額)/`operating_wage_cost`(人件費)/`operating_material_cost`(原料費)/`operating_cost_category`(支出元予算カテゴリ=LEDGER_*)を、推定生産量・雇用人数と同じグリッドに表示する。総額=人件費+原料費(専用建物のため家賃なし。算出はバックエンドのcalc_rough_costに一元化されておりUI側で計算しない)。費目行は`utils/ledgerIcon.resolveLedgerIcon`+`budget.category.{id}`のi18nで予算ウィンドウと同じアイコン・名称を使う。注記(1エポック(n日)あたり・フル稼働時)の日数はレスポンスの`simulation_days`。修繕費は意図的に含めない(建設時に意識していなかったコストが後からのしかかるゲーム体験を残すため)。
- **建物の構造種別(`structure`)**: 建物建設パネル(`building/BuildingConstructionPanel`)は、バリアントの `structures`(許可構造ID一覧)が非空なら構造セレクタを出し、既定は最上位(`defaultStructureOf`=max。バックエンドの既定と同じ)。選択値は建設コスト見積・確定送信(`structure`)・Unityへの `STATE_EDIT_BUILDING` パラメータと `edit_building:update_structure` IPC に載せ、階数ステッパーの上限は「バリアントの `max_floors` と構造の `max_floors`(0=無制限)の小さい方」。構造名は `masterData.structures`(GET /master/structures)から引き、建物詳細(`agent/BuildingInfoPanel`)は `structure>0` のときだけ行を出す。規制側は `parcel/RestrictionFields` に最低構造種別セレクタ(`min_structure`。0=制限なし、それ以外は「{{name}}以上」)があり、地区/土地区画パネルと都市規制ウィンドウ(`regulation/tabs/BuildingRegulationTab`。`BUILDING_REG_KEYS` に含む)が共用する。文言は全7言語の parcel.json / publicService.json / construction.json / building.json。
- **建物直接配置の民間区画オーバーラップは自動用地買収の確認ウィンドウを挟む**: `BuildingConstructionPanel`の直接配置モードで`preview-direct`が`requires_acquisition=True`(民間区画とのみ重なる)を返すと、確定ボタンは押せるが即送信せず`building_direct_acquisition`ウィンドウ(`building/BuildingDirectAcquisitionConfirmWindow`)を`params.extra.pendingAcquisition`(件数+買収費見積)付きで開く。OKでクロスウィンドウイベント`building_direct:acquisition_confirmed`が発火し、パネルが`acknowledge_acquisition=true`付きで`POST /buildings/direct`を送る(キャンセル/×は何も送らない=パネル側に確定待ち状態が無いためRustのクローズ特別処理は不要)。重なり区画・建物は`preview-direct`の`interference`を`sendHighlightObjects(_, "building_construction")`で道路敷設と同配色の3Dハイライトに流し、クリアはプレビュー消滅/キャンセル/確定成功時+ウィンドウクローズ時のRust側(`window.rs`)で行う。
- **ブルドーザ(コックピット)と地区編集(アイコンパネル)は排他の常駐モード**だが、別ウィンドウにボタンがある。状態はTauriのグローバルイベント `hud:mode_changed` を真実源として `hudMode.ts` が全HUDウィンドウで同期する。**モードの副作用(Unityへの`STATE_*`送信・ヒントバー文言・セッションリロード)は操作した側のコンポーネントが実行し、他ウィンドウは表示を合わせるだけ**。ブルドーザON中はコックピットのパネル背景を工事現場風の黄黒斜線(`Cockpit.css`の`.cockpit--bulldozer`)に切り替える(解除し忘れによる誤削除を防ぐため、アイコンのアクティブ表示だけに頼らない)。**ブルドーザの確認付き削除(範囲配置プロップ=森ごと撤去)は`Cockpit`が受け持つ**: Unityからの`remove_object:request_confirm`(`{object_type, id, prop_type}`)を受けて`window.confirm`(`taskbar.bulldozerConfirmScatter`。種別名は`masterData.prop_types`)を出し、結果を`sendRemoveObjectConfirmResult`で必ず返す(取消でも返さないとUnityが確認待ちのまま次の範囲配置クリックを受けない)。DELETEはUnity側が発行する。
- **アイコンパネルの高さはReactの実測値でウィンドウに反映する**(`ResizeObserver` → Tauriコマンド `resize_icon_panel`)。アイコン数がテンプレートモードで変わるため。`IconPanel.css`で高さを固定してはならない(ウィンドウ丈との相互参照でリサイズが往復する)。
- **BGM再生と3Dビューのオブジェクト選択受信は`Cockpit`が受け持つ**。HUD3枚で同じ処理を走らせると多重再生・多重オープンになるため、常に1枚だけ存在するウィンドウに寄せている。
- チュートリアルのハイライト対象ID(`road` / `budget` / `land` / `construction` / `district` / `track` / `transport` / `visibility` / `execute`)はHUDのウィンドウをまたぐが、各ウィンドウは自分が持つIDにだけ反応する。**IDの持ち主はアイコンパネルとは限らない**(`budget`=コックピットの予算ミニメータ、`visibility`/`execute`=コックピット)。アイコンを削除・移動するときは`tutorial/tutorialSteps.ts`の`targetElementId`が指す先が消えていないか確認すること(消えるとハイライトがどこにも出ないまま進行する)。
- **チュートリアルのステップは`prepare`(検証前)→`validate`(判定)→`onComplete`(合格後)の順に呼ばれる**(`tutorial/Tutorial.tsx`の`handleComplete`)。**パスの端点ノード(`start_node_id`/`end_node_id`)はパスが稼働中になった瞬間にしか割り当たらない**ため、「施設の接続端子ノードに線が繋がっているか」を条件にするステップ(送電線・引き込み線)は、工期スキップの`activatePathsWhere`を`onComplete`ではなく**`prepare`に置かないと永久に条件を満たせない**(プレイヤーが正しく敷設しても、判定時点のパスは建設中で端点が`-1`のまま)。`onComplete`は「合格のご褒美として代行する処理」専用。

## 新しいウィンドウの追加手順

1. 適切なドメインフォルダにコンポーネントを作成
2. `App.tsx`にimportを追加し、`SPECIALIZED_PANEL_TYPES`にウィンドウタイプ名を追加して分岐を書く
3. `src-tauri/config/window-registry.json`にウィンドウ定義(タイトル、サイズ、インスタンスポリシー)を追加
4. 排他にしたいウィンドウがあれば`window-mutex-groups.json`にも追加

## 建設・編集パネルの確定送信の責務分担

作成/建設/編集パネル(建物・パス・土地区画・資源・公共交通・プロップ)の「確定」は、**UIが直接バックエンドへPOST/PATCHする**(`fetchApi`使用)。Unityは形状の組み立てと `edit_*:update_*` 系IPCによる逐次通知のみを担い、UIは送信成功後に `edit_*:finish` 系IPC(建物のように専用イベントが無いものは `sendSessionReload`)+`STATE_NORMAL` でUnityの編集状態をリセットして再描画させる。エラーは `ApiError.code` を `errors.{code}` のi18nキーへマップして `showNotification` で表示する。例外は3Dジェスチャで完結する操作(地区の即時割当、接続端子ノードのドラッグ移動)で、これらはUnityが直接バックエンドへ送信する。

### 公共/公営施設コントロールパネル(agent/PublicFacilityPanel)

`AgentDetailPanel`は`agent.public_facility`のときだけ操作UIをこのカードへ差し替える(非公共は`AgentOperationPanel`+稼働率目標カードのまま)。**操作はすべて`.operation-panel`のアイコンボタン1列に並べる**(修繕/再建・着工保留・停止/開始・放棄・取り壊し。計画中は着工保留・編集・削除)。停止/開始・着工/保留・放棄は同じボタンの状態が入れ替わるトグルで、押下状態は`.operation-btn--active`(橙)+`aria-pressed`で示す。**チェックボックスなど別形式のコントロールを混ぜないこと**。

**稼働率目標(建設中は建設スピード)も同じ列の右端に置く**(`.operation-btn--util`。`margin-left:auto`で右寄せ)。閉じている間はラベルを持たず「メーターアイコン+現在値%」だけを出し(名称はツールチップ)、押すと列の下にスライダーが開く(`aria-expanded`)。**キャプション「稼働率目標」/「建設スピード」はスライダーを開いたときだけスライダーの左に出す**。アイコンは専用画像が未用意のためコンポーネント内のインラインSVG(`UtilizationIcon`)で、画像ができたら`<img>`へ差し替える。

**放棄(`PATCH {abandoned}`)中は放棄解除以外の操作ボタンをすべて無効化する**(修繕・停止/開始・取り壊しはいずれも維持している施設への操作のため)。放棄トグル自体は放棄中も押せる状態を保つ(でないと解除できなくなる)。バックエンドが`abandoned`を許すのは建物(is_bd=1)かつSTATUS_ACTIVE/STATUS_PAUSEDのときだけなので、UI側も同条件で活性化する。放棄すると稼働中の施設はバックエンド側でSTATUS_PAUSEDへ落ちる(解除しても自動再稼働はしない)。

### 土地区画詳細パネルの環境セクション(parcel/ParcelEnvironmentSection)

`ParcelDetailPanel`の基本情報の直後に、区画固有の環境スコアを`common/Meter`で4本表示する。データ源は**都市全体のヒートマップAPI(`/city/noise`等)ではなく`GET /api/v1/parcels/{id}/environment`**(詳細パネルのたびに全区画分を取得しないための単体取得口)。返る値はいずれも`[0,1]`の**悪さ度合い**(0=理想、1=最悪)なので、大気汚染・騒音・犯罪は値そのままで`polarity="negative"`、**日照だけは「影の時間割合」なので`1 - value`に反転して**日当たりの良さとして描く。エポック未実行だと全要素nullで返るため、その場合はメーターを出さず注記を出す。

### 土地区画作成パネル(parcel/ParcelCreationPanel)の作成方法はUnity側が真実源

**ウィンドウを開いた時点で`STATE_EDIT_PARCEL`(既定=`empty_area`)へ入る**(3DビューのCtrlラジアルメニューは作成モード中しか開かないため、タイルを押すまでモードに入らないと「ホイールが出ない」)。作成方法の真実源はUnity(`ParcelEditorManager.CurrentMode`)で、**Unity起点の切り替えだけが`edit_parcel:set_mode`で届く**(パネルのタイルは`world:change_state`で依頼しつつ楽観的に自分の状態も更新する。両方向で通知すると往復ループになる)。同じモードで`set_mode`が届いたら「選択のリセット」(3DビューでEsc/同じ方法を選び直した)の意味で、選択状態だけ捨てて幅・奥行き等の入力値は保持する(モードが変わったときだけ`SIZE_INPUT_PRESETS`の初期値へ戻す——モードによって幅/奥行きの意味と桁が違うため)。**確定してもモードから抜けない**: 成功後は`STATE_NORMAL`を送らず、`edit_parcel:reset_selection`で3D側の選択も捨てて連続作成に戻る(パネルを閉じたときだけ`STATE_NORMAL`)。地点指定系では幅・奥行きを`edit_parcel:set_rect_params`でUnityへ送り、角度ドラッグ中のローカル矩形プレビューを入力値に合わせる。

### 道路建設・インフラ建設パネル(path/PathConstructionPanel)は1コンポーネント2ウィンドウ

`path_build`(道路=自動車専用道路/街路/歩道)と`infra_build`(インフラ=電気/水道)は**同じ`PathConstructionPanel`を`category` propだけ変えて使う**(`App.tsx`で固定)。入力UI・フローが同一なのでコードは共有するが、プレイヤーには道路と電線・水道管は別の道具に見えるため入口(アイコンパネルのボタン)とウィンドウは分けている。**パネル内にカテゴリ切替UIを復活させないこと。** 既存パスの編集(パス詳細パネル起点の`editPathId`付き起動)は種別を問わず`path_build`で行い、その場合のカテゴリはパス取得時に`usePathConstruction.onTypeChange`が種別から補完した値を使う。Rust側の`EDIT_MODE_WINDOW_TYPES`とクローズ時のグリッド/ハイライト消去は両ウィンドウ種別で同じ扱い。

### 道路建設パネル(path/)の設定系はUnity移管済み

曲線/直線・吸着5種の設定UIは`PathConstructionPanel`に**無い**(Unity側のCtrlラジアルメニュー・カーソルHUDが担う)。復活させないこと。曲線モード(`usePathConstruction`の`curveMode`)は`edit_path:update_shape`の`is_curved`受信が唯一の書き込み元で、確定送信の`curved`・コスト見積り・形状プレビューがこれを参照する。**標高・盛土のステッパーはパネルに残す**(既存ノードを選んで数値で微調整する用途のため)。表示値は`edit_path:select_node`受信で選択ノード(node_id=-1は次回配置値)の値に同期し、ステッパー変更を`sendEditPathChangeNode`/`sendEditPathChangeEmbankment`でUnityへ送り返す双方向同期(Unityのキー操作でもHUD・パネル双方に反映される)。パネルが持つのは種別/バリアント選択・標高/盛土・ホーム設置側・グリッド設定(サイズ/角度。表示状態はUnityの`view:grid_toggled`受信で同期)・形状プレビュー・コスト・確定/キャンセル・「2Dで編集」(`path_shape_editor`を開く。曲線モードでの右クリック確定時は`usePathConstruction`が自動で開き、確定ボタンで閉じる)。軌道複線(線路数≥2)は確定時にUI側が中心線を平行な単線パス群へ展開して一括POSTするが、Unityの3Dプレビューにも複線が見えるよう、各線の横オフセット列を`STATE_EDIT_PATH`の`lateral_offsets` params(初期値)と`edit_path:change_lateral_offsets`(線路数変更時の逐次通知。配置中ノードは維持される)でUnityへ渡す(`usePathConstruction`の`lateralOffsetsForVariant`とrailComponents監視effect)。

### 2Dパス形状編集パネル(path/PathShapeEditorPanel = `path_shape_editor`)

敷設中パスのノード・ベジエ制御点を`CityMapCanvas`の上で真上から編集する。**形状の真実源はUnity(`RoadPlanManager`)のまま**で、パネルは`edit_path:update_shape`(全WebViewへブロードキャスト。型は`pathBuildConstants.ts`の`PathShapeUpdatePayload`)を受けて描き、操作の結果だけを`sendEditPathShapeCommand`(`edit_path:shape_command`。move_node/move_control/insert_node/remove_node/select_node)で**ドラッグ終了時に1回**送る。XZのみ編集し、標高・盛土は敷設パネルのステッパーに任せる(ノード選択は3Dと同期)。ドラッグ中のプレビューと楽観的更新(`applyDragPreview`/`applyLocalMove`)、ヒット判定(制御点>ノード>辺)、描画はReact非依存の`path/pathShapeOverlay.ts`。制御点の補完はしない(曲線モードではUnityが全制御点を送る)。曲率・勾配は`update_shape.alignment`(Unityのローカル推定を5m間引き)で中心線を色分けし、3Dと同じ区間ラベルを描く。**高さ編集可能バリアント(`update_shape.height_editable`。線路は全種)では地図の下に縦断面ストリップ`path/PathProfileStrip`を出す**(横軸=曲線を伸ばした距離、縦軸=標高。路面・地盤は`alignment.samples`の距離/路面/地盤、アンカー位置は`alignment.nodes`。モデル・描画・ヒット判定は`path/pathProfile.ts`。無ければ折れ線長+相対高さの相対表示)。ストリップではノードを上下ドラッグで高さだけ変え、ドラッグ終了時に既存の`sendEditPathChangeNode`を1回送る(横方向は動かせない。`min_height`でクランプ)。ノード番号(1始まり)は地図・ストリップ・Unity 3Dで共通。マウント時に`sendEditPathQueryShape`で現在形状を要求し(開くたびに再マウントされるため)、`phase=inactive`を受けたら自分を閉じる。開閉の条件はdocs `IPC連携の整理.md`「2Dパス形状編集パネルの同期」。ウィンドウは`right_top`レイアウト(既定はモニター幅の1/3の正方形。`width_ratio`)。地図は最初の形状(無ければカメラ位置)から`initialBounds`を決めてからマウントする(先に`fitBounds`を呼んでも地形ロード後の`resetView`で都市全体に戻されるため)。

### パス詳細パネルの結合・分割(path/PathTopologyEditPanel)

`PathDetailPanel`の操作パネル(`PathOperationPanel`)には、**稼働中(`STATUS_ACTIVE`)のパスにだけ**結合ボタン(`path_merge.svg`)と分割ボタン(`path_split.svg`)が出る。押すと`PathDetailPanel`の`topologyEditMode`(`"merge"`|`"split"`|`null`)が立ち、`PathTopologyEditPanel`セクションが開く(同じボタンの再押下・キャンセルで閉じる。モード切替時は`key`でリマウントして選択状態を持ち越さない)。

このセクションが「Unityでの対象選択→長さ確認→確定」の一連を持つ。マウント時に`sendStartPathMerge`/`sendStartPathSplit`(=`STATE_MERGE_PATH`/`STATE_SPLIT_PATH`、params`path_id`)でUnityを対象選択モードにし、**アンマウント時は必ず`sendEndPathTopologyEdit`(=`STATE_NORMAL`)で戻す**(候補パスの着色・分割点マーカーが残るため)。選択結果は`IPC_EVENT_EDIT_PATH_SELECT_MERGE_TARGET`(`{path_id, path_name}`)/`IPC_EVENT_EDIT_PATH_SELECT_SPLIT_POINT`(`{point:[x,y,z]}`)で受け取り、`POST /api/v1/paths/merge`・`POST /api/v1/paths/{id}/split`を**`dry_run=true`で叩いて長さを表示**してから、確定ボタンで同じボディを`dry_run`なしで再送する→**`sendFinishPathTopologyEdit(removedPathId)`を1発だけ送る**(`sendSessionReload`+`STATE_NORMAL`の2発に分けると、Unityの非同期な差分リロードへ状態遷移が割り込んで形状が更新されない・消えたパスが残る)+パス詳細の再取得。確定成功時はアンマウント時のキャンセル送信を`finishedRef`で抑止する。結合では`path_id_a`=開いているパス(結合後に残るsurvivor)・`path_id_b`=Unityで選んだパス(削除される)。**結合不可・分割不可の理由(偏向角・通行方向の矛盾・端点に近すぎる等)はバックエンドがdry_runで返すメッセージをそのまま表示する**(条件がケースごとに異なりエラーコードへ潰すと情報が失われるため、`errors.{code}`へのマップはしない)。

### 軌道建設パネル(path/TrackConstructionPanel)は簡易/詳細の2モード

`track_build`ウィンドウは最上段に**パネル全体のモード切替(簡易/詳細。既定=簡易)**を持ち、モードでタブ構成が変わる。

- **簡易モード**: 「軌道」+「駅」の2タブ。駅タブは**プラットフォーム複線(相対式=対面ホーム固定)と駅舎をまとめて1クリックで置くパッケージ**で、プレイヤーが指定するのは**ホーム長(両数)・高さ・角度・駅舎の種類**だけ。プラットフォームを曲げる・本数を変える・ホーム設置側を変える・建屋の配置端を変えることはできない(詳細モードを使う)。
- **詳細モード**: 従来の「軌道 / プラットフォーム / 駅舎」の3タブ。1本ずつ自由に敷設する。

駅タブの中身は `path/StationBuildSections`(規格プルダウン → 説明 → 駅舎の種類プルダウン → 両数/高さ/角度 → 費用カード → 確定)で、状態は `path/useStationConstruction` が持つ。**`usePathConstruction` は一切使わない**(敷設セッションの持ち主がUnityの `StationPlanManager` のため)。形状の真実源はUnityで、`edit_station:placement_state` が `platforms`(複線2本) / `house`(駅舎1本) の中心線を `[始点, 終点]` の `[x, 相対高さ, z]` で返すので、**UI側に幾何計算を持たせない**。逆にホーム長・高さ・角度の変更は `sendStationPlacementCommand`(`edit_station:placement_command`)でUnityへ送り、3Dの操作(中ボタン回転・PageUp/PageDown)で変わった値は `placement_state` でステッパーへ書き戻す(エコーしない)。確定は `POST /api/v1/paths` にプラットフォーム2本(`platform_side=PLATFORM_SIDE_OUTSIDE`)+駅舎1本(`house_ends="both"`)を `align_station_tracks: true` で一括送信し、成功後に `sendEditPathFinish()` → `continuePlacement()` で `STATE_EDIT_STATION` へ入り直して連続設置する。両数→m の換算は `local-constants.stationPlatformLength`(1両20m+余裕10m)。検証・費用は詳細モードと同じ `/paths/validate` / `/paths/construction-cost` を3本ぶん使い、費用は合計・工期は最長で集約する。

詳細モードの3タブは上から **鉄道種別プルダウン(鉄道/モノレール/ロープウェイ。タブより上位の選択で、タブを切り替えても保持する) → タブ(軌道=通常/橋梁 ・ プラットフォーム=駅 ・ 駅舎) → 規格プルダウン** の3段で敷設対象を絞り込む。**構造(通常/橋梁)・電化/非電化は独立した設定を持たず、すべて「規格」プルダウンの選択肢(=パスバリアント)として並べる**(表示はマスターの`display_name`そのまま)。したがって敷設対象の唯一の正は`usePathConstruction`の`selectedVariant`で、フック側にtrack_type・電化の状態は持たせない(復活させないこと)。候補一覧は`railBuild.railVariantsForTrackTypes`、鉄道種別の一覧は`railBuild.availableRailTypes`が返し、鉄道種別の変更・タブ切り替えで候補が入れ替わったらパネルのeffectが候補の先頭を`selectVariant`し直す。セクションの並びは **種別プルダウン → タブ → 規格プルダウン(`RailVariantSelector`) → 説明カード(`PathVariantDescription`) → 複線構成(`RailTrackLayoutSettings`=線路数・進行方向・線路間隔) → 形状以下(`PathBuildSections`)** で、区切り線は各`pc-section`の下罫線。**説明カードは道路建設パネルとは表示位置が違う(道路=バリアント選択の直下)ため`PathBuildSections`には入れず独立コンポーネントにしてある**。**駅舎タブも通常のパス敷設フロー**: 候補は`masterData.paths`のtype=PATH_STATION_HOUSEのバリアント(鉄道種別に依存しないため種別プルダウンは非表示)、カテゴリはnullのまま`selectVariant`→`confirmPath`で単一パスとして確定する(複線構成・ホーム設置側なし)。駅舎の専有エリア(建屋)の位置はバックエンドとUnityが線形・周辺線路から同一アルゴリズムで導出するため、形状セクションの「建屋の配置」1行で両端・始点・終点を選ぶ。`StationHouseEndsSelect`は`pc-settings-row`・`pc-settings-label`・`pc-select`を共用し、端点や内外配置の説明文は表示しない。**駅舎バリアントの敷設中はUnity側(`RoadPlanManager.SnappingSuppressed`)が既存の地物への吸着を全て実効OFFにする**(グリッド吸着のみ有効)ので、駅舎の線が線路に引き寄せられることはない。

## 道路設備パネル

path/PathEquipmentPanelは道路詳細から設備4項目を編集する。マスターの*_allowedで選択肢を制限し、適用時にPATCHしてsession:reloadを通知する。初期値の再適用はせず、取得したPathの保存値を表示する。文言は全7言語のpathEquipment.json。

道路詳細はAgentDetailPanelのタブ用CSSを明示的に読み込み、「基本情報（所属地区・物理状態）」「交通」「道路設備」に分ける。設備タブは設置可能または既設の設備がある場合のみ表示する。駅舎には駅情報、計画中・建設中・解体中には建設工事タブを追加する。着工前は基本情報・交通・設備を省略し、初期選択は着工前・建設中なら建設工事、それ以外は基本情報。タブ内容はhiddenで切り替えて未保存の設備・速度入力を保持する。設備欄はagent-detail-section/title/grid/label/valueと既存の地区選択・交通保存ボタンのスタイルを使う。

## 駅の同時敷設の標高

`path/usePathConstruction.ts` はホームを持つ鉄道コンポーネントの一括POSTに `align_station_tracks: true` を付ける。共通標高の計算・保存はバックエンドに任せる。単線や既存駅を自動補正する指定ではない。

PathConstructionPanel/TrackConstructionPanelの継続配置は間隔・進行方向・ホーム側・高さ・盛土・曲線・地形追従を保持する。continuePlacementはinitial_*と既存の設定パラメータをSTATE_EDIT_PATHへ渡し、座標・制御点・見積りだけをクリアする。PathBuildSectionsの高さ入力は小数対応、0.1mステップ。

## 土地区画作成パネル

`parcel/ParcelCreationPanel.tsx` の新規作成項目は道路沿い・ブロック一括・ランダム・単一区画の順でUnityの `ParcelEditorManager.Modes` と一致させる。ブロック一括は探索幅/高さ・間口・奥行き・ばらつきのみで、中央埋め用平均面積は持たない。プレビューが0件なら生成不能の案内を表示し、取得中・0件では確定できない。既存区画の分割と `ParcelDetailPanel` の頂点編集は独立した機能。

## 建物配置パネルの同期

`BuildingConstructionPanel`の配置方法はUnityのCtrlメニューから`edit_building:placement_state`で受ける。自由/道路沿い配置では地点未固定でも間口・奥行き・階数を表示する。寸法ステッパーは`sendBuildingPlacementCommand`で変更フィールドだけを送り、スナップ補正済みのposition/width/depth/angle/revisionを一括受信する。受信値のエコー送信は禁止。直接配置の設置可否は現在の要求キー(variant/revision/位置/寸法/角度/階数)に対応する応答だけで確定を許可し、`update_shape`にもplacement_revisionを渡す。Escとパネル取消しは位置のみリセットし、寸法と配置方法を維持する。道路沿いでは角度入力を無効化。Ctrl/HUD文言は全言語のconstruction.jsonからlabelsとして送る。忠実コピー開始時のSTATE_EDIT_BUILDINGにはcopy_source_agent_idを渡し、区画配置専用にする。市庁舎未設置ゲートの自動選択(`VARIANT_CITY`)では`placement_mode: "free"`を渡し、道路も区画も無い創設時に自由配置から始める(以後の配置方法はUnityの`placement_state`に追従するだけで、パネルは初期値を保持しない)。

## 達成目標と住民満足度

`achievement/AchievementsWindow`は左にシナリオ紹介と目標カード（active→locked→completed→failed）、右に住民満足度スコアを配置し、左右を独立スクロールする。主指標は減点後の1世帯あたりスコア（最大2点）。都市合計の内訳は数値で示す。履歴は生活水準と住環境の積み上げ棒・負方向の倒壊減点・減点後の確定値の線を単一軸で描き、世帯平均/都市合計を切り替える。APIのhistoryに含む同一エポックの内訳と世帯数を使う。満足度4項目は説明付きメーター、当期の焼失・倒壊は折りたたみ。詳細は公開ドキュメントの`programs/達成目標ウィンドウ.md`。

### 満足度の顔と配色

`common/SatisfactionFace`は`value`（0〜1）と任意の`size`（px、既定32）で5段階の絵文字（😵→😢→😐→😊→🥰）を表示する。補正後の値が0のときだけ☠️を表示する。`getSatisfactionAppearance`が範囲補正・段階・色を共通で返す。境界は0.2/0.4/0.6/0.8で、上側の段階に含める。非有限値は0扱い。画像に置換するときはこのコンポーネント内の表示を差し替える。文言は全7言語のsatisfaction.json。達成目標の半円メーターは世帯スコア÷2を渡し、4項目の横棒は`common/Meter`のcolorに同じ配色を指定する。世帯未集計時は顔を表示しない。

StationHouseEndsSelectは駅舎の両端/A端/B端の共通選択UI。建設はusePathConstruction→IPCでプレビュー反映、駅詳細は単独PATCH後に再取得とsession:reloadを行う。Aは始点、Bは終点。

道路・軌道共通の `PathBuildSections` の盛土・切土入力は -5〜+5m、ボタン0.1m刻み、手入力はそれより細かい小数も許可する。`NumberStepper` の `integerOnly={false}` は増減時の末尾誤差を有効15桁で除くが、手入力をステップ幅へ丸めない。

## プロップの高さ指定

PropPlacementPanelの個別配置は全種別共通で地面相対高さ(m)を小数・負値で設定できる。heightを初期化・設定変更IPCへ渡し、Unityから受ける各インスタンスのyをそのままPOSTする。高さ変更は次のゴーストだけに適用し、すでに打点したインスタンスは個別の高さを保つ。3D側の中ボタン回転・PageUp/PageDownで変わった値は`edit_prop:placement_settings`(`{rotation, height}`)で届き、パネルは`setRotation`/`setHeight`だけを呼んで`sendEditPropChangeSettings`へエコーしない(往復ループ防止)。既存プロップの削除はこのパネルではなくコックピットのブルドーザ。

道路・軌道の共通確定ボタンは `usePathConstruction.canConfirm` を使う。Unityからの `can_confirm` と、確定と同じ `constructionBody` 全線の `/paths/validate` 成功をANDする。事前検証は150msのデバウンスで行い、応答を送信形状キーで照合して古い結果を破棄する。取得失敗・検証待ち・交差中は確定不可。confirmPath自身もガードし、送信直前に再検証する。複線の先頭1本だけの検証は禁止。

パス確定不可の理由は `path/pathValidation.ts` で全線検証の `alignment_violations`（線番号と始点からの距離区間）・パス干渉・川横断を区別して表示する。API例外はメッセージを保持して再試行を提供し、干渉と表示しない。形状キーが一致する結果だけを表示・採用し、送信直前の再検証にも同じ説明を使う。ハイライトIPC失敗を検証失敗へ置き換えない。建設費用欄はノードが2点以上なら確定可否にかかわらず表示する。


全線validateのalignmentsが現在の形状キーで取得できたら、費用カードの線形値とalignmentOkにはその最悪値を優先する。個別のconstruction-costは駅共通標高を含まないため、取得済み全線結果を上書きしない。

## 河川の接岸と谷への補正

`terrainRiver.ts`の`computeOneSurfaceProfile`は、流量からの目安幅を横断地形で0.6〜1.4倍に補正し、河道・なじみ帯・格子余裕の最低標高より0.7m下に水位上限を置く。下流方向のmin走査で単調性を保ち、尾根の高さを上流水位へ伝播しない。河口の水位は海・湖・本流の境界条件を優先するため、不適切な経路は確定前に補正する。深さ係数は川底だけに作用する。

`fitRiverRouteToValley`は左右の探索帯（UI既定100m）で標高・逆勾配・迂回のコストが小さい連続経路を選び、両端を固定した制御点を返す。UIの`fitRiverRoute`はUndoを保存してから`applyRiverControlPoints`へ渡し、合流先を保って支流も更新する。彫り込み済み・読み込んだ川は対象外。川幅入力は地形補正前の目安である。

`buildRiverPolygon`は乾いた点の水位差も補間し、簡略化誤差はspacing×0.02。保存済みポリゴンを上限とする場合は境界までの符号付き距離で再計算による膨張を防ぐ。`buildRiverSurfaceMesh`は描画専用に隣接1セルを加えて岸へ埋めるが、保存範囲は広げない。Unityの`RiverRecord.SurfaceCellIncluded`と同じ規則。回帰検証は`tools/river-valley-regression-test.ts`と`tools/river-raster-regression-test.ts`（tsx）。

## 経路提案UI

`path/useRouteProposal.ts`はUnityの編集世代を保持して読み取り専用propose-route APIを呼び、同じ形状・設定への応答だけをshape_commandで反映する。`RouteProposalControls`は`PathShapeEditorPanel`のツールバーへ高さ固定/調整・提案・取消し・復元を表示し、形状同期の`route_proposal`から探索条件を受け取る。制御点Yは`ControlPoint.y`とwaypoint_controlsから保持し、複線展開時にもアンカー高さへ置き換えない。翻訳は各言語のroute-proposal.json。詳細は公開`programs/経路提案.md`。
