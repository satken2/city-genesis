# Genesis UI 仕様書

## 1. 概要

本プロジェクトは、`Tauri + React` により Windows 向けデスクトップ UI アプリケーションを実装するものである。  
このアプリケーションは、都市シミュレーションゲーム本体とは別プロセスで動作し、主に以下を担う。

- ゲーム空間上のオブジェクト選択に応じたポップアップ UI の表示
- 設定画面や補助 UI の表示
- ローカルまたはリモート API から取得した情報の表示
- UI 操作結果の親プロセスへのフィードバック

当面の親プロセスは Unity 製アプリケーションを想定するが、将来的に Unity 以外の技術へ置き換わる可能性がある。そのため、親子間の連携は特定エンジン依存ではなく、一定の規約を持つ IPC プロトコルとして設計する。

## 2. 目的

- Unity ゲーム上で必要となる各種ポップアップ UI を Windows ネイティブな別ウィンドウとして表示する
- オブジェクト種別ごとに異なる UI レイアウト、サイズ、位置、取得 API を柔軟に切り替えられるようにする
- 将来的に新しいウィンドウ種別を容易に追加できる土台を先に整備する
- 親プロセスの実装が Unity 以外へ変わっても流用できる IPC 規約を用意する
- 動作確認用の疑似親プロセスを用意し、UI 単体開発や IPC 検証を容易にする

## 3. 前提条件

- 対象 OS は Windows
- UI フレームワークは `React`
- デスクトップアプリ基盤は `Tauri`
- 親プロセスは当面 Unity アプリケーション
- ゲームのコアロジックおよびデータソースは、別ローカルプロセスまたはリモートサーバー上に存在する(コアモジュール)
- Tauri 側は必要に応じてコアモジュールの REST API を呼び出して表示内容を取得する

## 4. 想定ユースケース

### 4.1 ゲームオブジェクト選択

1. ユーザーが Unity の 3D 空間上のオブジェクトをクリックする
2. 親プロセスが、クリック対象のオブジェクト種別・識別子・補助パラメーターを IPC で Tauri に通知する
3. Tauri がオブジェクト種別に対応するウィンドウ定義を参照する
4. 必要なコアモジュールの REST API を呼び出して表示データを取得する
5. 対応するポップアップウィンドウを生成または更新して表示する

例:

- 道路をクリックした場合、`/api/v1/paths/{path_id}` を取得して道路情報を表示する

### 4.2 設定画面表示

1. 親プロセスまたは Tauri 内部操作により設定画面表示要求が発生する
2. Tauri が設定画面用ウィンドウを表示する
3. 必要な設定値を REST API から取得する
4. ユーザー操作結果を API または IPC で反映する

### 4.3 UI から親プロセスへの操作指示

1. ユーザーがポップアップ上で何らかの操作を行う
2. 操作内容に応じて Tauri が親プロセスへ IPC メッセージを送信する
3. 親プロセスはゲーム内処理を実行する

例:

- 指定座標または対象 ID へカメラ移動
- 対象オブジェクトのハイライト
- モード切替

## 5. スコープ

### 5.1 本フェーズで実現したいこと

- Tauri アプリのベースアーキテクチャ構築
- IPC の送受信基盤構築
- 複数ウィンドウ管理基盤構築
- ウィンドウ種別ごとの定義駆動な描画基盤構築
- REST API 取得基盤構築
- 親終了時の子終了制御
- 疑似親プロセスの実装

## 6. 非機能方針

### 6.1 拡張性

- 新規ウィンドウ種別追加時に、既存のウィンドウ管理や IPC コアを大きく改修しなくてよい構造にする
- オブジェクト種別ごとの差異は、できるだけ設定ファイルまたは定義オブジェクトで吸収する

### 6.2 保守性

- IPC メッセージ形式は型定義可能な明示的スキーマとする
- UI の共通レイアウト、開閉、読み込み、エラー処理を共通化する

### 6.3 置換容易性

- 親プロセスが Unity 固有でなくても接続できるよう、IPC 規約を定義する
- Tauri 側では「親プロセスは規約に従ってメッセージを送受信する外部クライアント」として扱う

### 6.4 ユーザー体験

- Windows 標準タイトルバーは極力避け、見た目をカスタマイズ可能にする
- ただし、透明フルスクリーンオーバーレイを常時使う方式ではなく、基本は個別の Windows ウィンドウを表示する
- ゲームの上に重ねる、または別ディスプレイへ移動するなど、運用上の柔軟性を持たせる

## 7. システム構成

主要コンポーネントは以下の通り。

- 親プロセス
  - 当面は Unity アプリ
  - オブジェクトクリックやゲームイベントを IPC で通知する
  - Tauri からの操作要求を受け取る
- Tauri ホスト
  - IPC サーバーまたはクライアント機能を持つ
  - ウィンドウ生成、ライフサイクル管理を担う
  - REST API クライアントを持つ
- React UI
  - 各ウィンドウの表示ロジックを担う
  - 共通フレーム、各種画面コンポーネントを提供する
- データ API
  - ローカルプロセスまたはリモートサーバー
  - オブジェクト詳細や設定値を返す
- 疑似親プロセス
  - 開発・検証用ツール
  - 任意の IPC メッセージを送受信できる

## 8. ウィンドウ表示方針

### 8.1 基本方針

- Tauri 起動直後は、ユーザーに見えるウィンドウを表示しない
- 透明ウィンドウを常時全面表示するのではなく、必要なときに個別ウィンドウを表示する
- すべてのウィンドウが閉じても、Tauri プロセス自体は終了しない
- 親プロセスからの次の通知に備えて待機状態へ戻る

### 8.2 複数ウィンドウ

- 複数のウィンドウを同時表示可能とする
- ただし、特定の種類のウィンドウは同時表示不可とする
- 同時表示可否ルールはコード直書きではなくコンフィグで定義可能にする

例:

```window-mutex-groups.json
{
    "settings": ["settings"], // settingsは同時に2つ存在できない
    "path_detail": ["path_detail", "zone_detail"] // 地区ウィンドウを表示すると道路ウィンドウが消える
}
```

### 8.3 サイズ・位置

- ウィンドウサイズはオブジェクト種別またはウィンドウ種別ごとに定義できること
- 初期表示位置は以下の情報を元に決定できること
  - デフォルト値
  - 画面中央
  - 親から渡された座標や推奨位置
  - 最後に表示した位置
- 別ディスプレイへ移動可能であること
- Unity ウィンドウ上に重なることもある

### 8.4 外観

- タイトルバーやフレームはカスタマイズ可能とする
- Windows 標準の見た目をそのまま使わず、アプリ独自の見た目に寄せられること
- ただし、タイトル文、アイコン設定、移動、リサイズ、最小化、閉じるなどの基本操作性は共通化すること

## *. IPC 要件

### 9.1 目的

- 親プロセスからの UI 表示要求を受ける
- Tauri から親プロセスへ UI 操作結果を返す
- 親子プロセスの生存監視を行う
- 将来的な親実装の差し替えに耐える共通規約を定める

### 9.2 候補トランスポート

通信方式は `Named Pipe` とする。  

### 9.3 IPC 層の設計方針

トランスポートとメッセージ仕様を分離する。

- 下位層: 通信手段
  - Named Pipe など
- 上位層: メッセージ仕様
  - JSON ベースの共通イベント形式

これにより、将来トランスポートを差し替えてもアプリケーション層の変更を最小化する。

### 9.4 メッセージ形式

メッセージは JSON ベースの封筒形式とし、最低限以下の項目を持つ。

```json
{
  "version": "1.0",
  "request_id": "uuid-or-sequence",
  "timestamp": "2026-03-27T12:34:56Z",
  "source": "parent",
  "destination": "tauri",
  "event": "ui.open_window",
  "payload": {}
}
```

必須項目候補:

- `version`
  - IPC 規約バージョン
- `request_id`
  - 要求追跡用 ID
- `timestamp`
  - 送信時刻
- `source`
  - 送信元
- `destination`
  - 送信先
- `event`
  - イベント種別
- `payload`
  - 本文

### 9.5 規約として定義したいイベント

親 -> Tauri:

- `world.select_object`
- `system.ping`
- `system.shutdown`
- `game.time_update`

Tauri -> 親:

- `ui.action`
- `ui.window_opened`
- `ui.window_closed`
- `ui.error`
- `system.pong`
- `system.ready`

### 9.6 `world.select_object` の例

```json
{
  "version": "1.0",
  "request_id": "req-001",
  "timestamp": "2026-03-27T12:34:56Z",
  "source": "parent",
  "destination": "tauri",
  "event": "world.select_object",
  "payload": {
    "window_type": "road-detail",
    "entity": {
      "type": "path",
      "id": "path-123"
    },
    "params": {
      "preferred_position": {
        "mode": "screen_point",
        "x": 1200,
        "y": 300
      }
    }
  }
}
```

### 9.7 `ui.action` の例

```json
{
  "version": "1.0",
  "request_id": "req-101",
  "timestamp": "2026-03-27T12:35:20Z",
  "source": "tauri",
  "destination": "parent",
  "event": "ui.action",
  "payload": {
    "action": "camera.move_to_entity",
    "window_type": "road-detail",
    "entity": {
      "type": "path",
      "id": "path-123"
    },
    "params": {}
  }
}
```

### 9.8 生存監視

以下のいずれか、または組み合わせで親生存を監視する。

- 接続断による終了検知
- 定期 `ping/pong`
- 親プロセス ID 監視

要件:

- 親プロセスが終了したら、Tauri は自動終了したい
- 親が異常終了し、子のみ残る状態を可能な限り避ける
- 通信断が一定時間継続した場合の扱いを定義する

想定方針:

- 明示的 `system.shutdown` を受けた場合は即時終了
- 接続断を検知した場合は一定猶予後に自動終了
- `ping/pong` タイムアウト時も異常終了候補として扱う

## 10. REST API 連携要件

### 10.1 基本方針

- 表示内容は Tauri がコアモジュールの REST API を直接呼んで取得する
- API エンドポイントはウィンドウ種別またはオブジェクト種別に応じて切り替える
- API ベース URL は環境設定で差し替え可能とする

### 10.2 例

- 道路詳細: `GET /api/v1/paths/{path_id}`
- 建物詳細: `GET /api/v1/buildings/{building_id}`
- 設定取得: `GET /api/v1/settings`

### 10.3 API 定義の持ち方

オブジェクト種別ごとに、以下を紐づけられるようにする。

- `window_type`
- 対象エンティティ種別
- API エンドポイント生成ルール
- 使用する React 画面コンポーネント
- ウィンドウサイズ、配置方針
- 排他制御ポリシー

### 10.4 エラー時の扱い

- API 通信失敗時はウィンドウ内にエラー状態を表示する
- 再試行可能であること
- 対象が存在しない場合の表示を定義する
- API ロード中のローディング表示を共通化する

## 11. 疑似親プロセス要件

開発・検証のため、Tauri とは別に疑似親プロセスを実装する。

### 11.1 目的

- Unity 未起動でも IPC の送受信を検証できるようにする
- UI 開発をゲーム本体から切り離して進められるようにする
- 親からの表示要求と、子からの応答内容を可視化する

### 11.2 必須機能

- IPC 接続開始
- 送信イベント種別の選択
- `window_type` の入力
- 対象 ID や任意パラメーターの入力
- 送信ボタン
- Tauri から返ってきた IPC メッセージの一覧表示
- 接続状態表示

### 11.3 望ましい機能

- 定型メッセージテンプレート
- 送受信履歴保存
- 再送
- `ping/pong` 検証
- 複数ウィンドウ同時表示の確認

## 11 初期実装で先に作るべきベース

初期フェーズでは、個別画面を大量に作る前に以下を優先する。

1. IPC 抽象レイヤー
2. メッセージスキーマ定義
3. 親生存監視
4. ウィンドウ管理基盤
5. 設定駆動レジストリ
6. 共通ウィンドウフレーム
7. API クライアント
8. 疑似親プロセス
9. サンプルとして 1 から 2 種類のウィンドウ実装
