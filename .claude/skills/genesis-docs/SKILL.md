# City Genesisの文書整理

説明は、公開docs・非公開docs・ソースのコメントの3か所に分けて書く。作業中に知ったことをすべて残すための文書にしない。

パスは `city-genesis` と `genesis-core` を並べたワークディレクトリ起点。対象のAGENTS.mdを先に読み、非公開コアが手元にない場合は公開契約で確認できる範囲を扱う。このSkillは `city-genesis`・`genesis-core`・ワークディレクトリ直下に同じ内容で置く。変えるときは3か所を揃える。

## 書く場所の判断

段落ごとに、次の問いに上から順に当てはめる。どれにも当たらない内容は書かない。

| 置き場 | 判定の問い |
| --- | --- |
| 公開docs `city-genesis/docs/docs/` | コアのソースを読めない Unity・Tauri の開発者が、これを知らないとフロントを正しく書けないか |
| 非公開docs `genesis-core/docs/` | コアを触る人が、ソースを開く前に頭に入れておくべき全体的な考え方や処理順序か |
| ソースのコメント | 上の2つに当たらず、コードから読み取れない意図や編集時の注意点があるか |

公開docsには、シミュレーションの概念、API・IPC の項目が何を意味するか、フロントの全体構成と共通の仕組み、座標・単位・命名などモジュール間で共有する約束を書く。コアの処理ロジックや、フロントから見えない内部の名前は書かない。

`AGENTS.md` にはディレクトリの概要と配下の作業全体に適用する横断的なルール、`README.md` には対象の概要・入口・実行やビルドの案内を書く。

## 書かないもの

- 実装を日本語に置き換えただけの説明、コードや擬似コード・式の写し、関数一覧、逐次処理の列挙。
- 個別の機能・画面・パネル・イベント・バリアントの仕様、閾値・係数・既定値などの調整値。必要なら該当ソースのコメントに書く。
- モデルの作り方(パーツの原点・向き・寸法・著作のしかた)。コードがその約束を前提にしているなら、パーツを置くコードのコメントに書く。
- TODO、計画、構想、作業記録、検証の作業ログ、作成手順書。
- 過去の仕様、廃止した名前、不採用案、試行錯誤、今回の変更経緯、修正前の不具合の筋書き。

外部契約を説明するための名前(API・IPC の項目、フロントが読むマスターの項目、同期される共有定数、アセットの命名規則)は残してよい。部品の名前と役割の対応は短い表にしてよい。

不要な文章を別ページ・付録・ソースコメントへ丸ごと移して温存しない。コメントに移すのは実装を読んでも分からない意図だけで、そのソースに同じ意図のコメントが既にあれば移さない。作業中の気付きはワークスペースの `TODO.md` に必要なものだけ残す。

## 粒度

- 1ページは、全体の考え方と、概念ごとの短い節が数個。個別の挙動ごとに見出しを立てない。
- 「〜のときは〜する」という個別の挙動や例外の列挙が続くなら、その仕組みの考え方を1〜2文にまとめ、列挙はソースのコメントに任せる。
- 他のページの見出しや節番号を本文で参照しない。ページ単位でリンクする。ソースのコメントから文書を参照するときもページ単位にする。
- ソースのコメントは、その変数・関数を編集する人が知るべき意図と注意点を1〜3行で書く。

## 更新と確認

ソースを変えても、上の基準で書くべき内容が変わらなければ文書は更新しない。更新するときは既存の説明を直し、他のページからは参照する。追記の前に、重複する節や主題から外れる文章を削れるか確認する。文書の整理に合わせて実装の機能を追加しない。

見出し・リンク・説明先を変更したら関係する参照を揃える。公開ページの追加・削除時は `city-genesis/docs/mkdocs.yml` のnavも合わせる。生成API資料は手編集しない。

公開docsは `city-genesis/docs/README.md` の方法でMkDocsをビルドし、変更ページの表示とリンクを確認する。完了前に各段落を上の判定で読み直す。
