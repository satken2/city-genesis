# City Genesisの文書整理

現行仕様を初めて読む開発者に必要な説明を、その主題の正となる場所へ簡潔に書く。作業中に知ったことをすべて残すための文書にしない。

パスは `city-genesis` と `genesis-core` を並べたワークディレクトリ起点。対象のAGENTS.mdを先に読み、非公開コアが手元にない場合は公開契約で確認できる範囲を扱う。

## 追記するかの判断

次の3点で、文章を残す必要があるか判断する。

- 現在の実装を初めて読む開発者に必要か。
- このページの主題を説明しているか。
- ここを説明の正にする必要があるか。

既存の説明があればそこを修正し、他のページは参照にする。ソースを変更したという理由だけで、文書に変更内容を追記しない。既存の説明が現行仕様を正しく表していれば、無理に文章を増やさない。

## 文書の役割

| 配置 | 書く内容 |
| --- | --- |
| `city-genesis/docs/docs/economics/` | ゲームの概念、データの意味、観測できるルール |
| `city-genesis/docs/docs/geometries/` | 形状・描画の仕組み、座標・単位・命名などの共通規約 |
| `city-genesis/docs/docs/programs/` | フロントの責務、UIの仕様、API・IPCなどの共有契約 |
| `genesis-core/docs/` | 非公開コアの内部ロジック |
| `AGENTS.md` | ディレクトリの概要と、配下の作業全体に適用する横断的なルール |
| `README.md` | 対象の概要、入口、実行・ビルドなど利用に必要な案内 |

概念ページに具体的なクリック手順や画面の細部を混ぜない。公開文書に非公開コアの実装ファイル・関数・内部計算を載せない。READMEや制作手順など、操作案内自体が主題の文書では必要な手順を書く。

## 仕様文書から除くもの

- TODO、未実装の構想、作業予定、進捗、検証の作業ログ。
- 過去の仕様、廃止した名前、不採用案、試行錯誤、今回の変更経緯。現行仕様の理由は、過去の会話を知らなくても読める形で説明する。
- コードから読み取れる関数一覧・逐次処理・分岐・細かな調整値、実装をそのまま写した長いコード例。

具体的な名前や値を一律に禁止しない。外部契約のフィールド、単位、命名規則、状態遷移など、利用側が共有する必要のある情報は残す。個別アセットを差し替えても変わらない仕組みや管理方針を説明する。

個別の値や対応表は既存のコード・設定・素材台帳を正とし、仕様文書ではその所在を示す。外部素材の出所と表記は `city-genesis/tauri/src/data/credits.ts`、原本・加工条件は素材フォルダの記録で管理する。

不要な文章を別ページ・付録・ソースコメントへ丸ごと移して温存しない。コメントに必要なのは実装を読んでも分からない意図だけである。作業中の気付きはワークスペースの `TODO.md` に必要なものだけ残す。正規の素材台帳や制作記録まで、この基準で削らない。

## 更新と確認

対象の文書と関連する実装・契約を確認し、古い説明や矛盾は現行仕様の文章に置き換える。追記の前に、重複する節や主題から外れる文章を削れるか確認する。文書の整理に合わせて実装の機能を追加しない。

見出し・リンク・説明先を変更したら関係する参照を揃える。公開ページの追加・削除時は `city-genesis/docs/mkdocs.yml` のnavも合わせる。生成API資料は手編集しない。

公開docsは `city-genesis/docs/README.md` の方法でMkDocsをビルドし、変更ページの表示とリンクを確認する。完了前に追加した各段落を3つの判断基準で読み直し、説明の重複や作業記録が混ざっていないことを確認する。
