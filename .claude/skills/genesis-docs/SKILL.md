# City Genesisの文書整理

説明は読み手と用途に応じて、公開docs・通常の非公開docs・非公開OKF・ソースコメントに分ける。現在の意味と設計理由を扱い、作業中に知ったことをすべて複写するための文書にしない。

公開側のパスは `city-genesis` リポジトリのルート起点。`genesis-core/` で始まる参照は非公開コアのリポジトリ内のパスを表し、並置を前提としない。対象のAGENTS.mdを先に読み、非公開コアが手元にない場合は公開契約で確認できる範囲を扱う。

公開文書は日本語原本を先に編集し、対応する英訳を同じ変更で揃える。README の原本は `README.ja.md`、本文の原本は `docs/ja/`。GitHub の英語の入口にかかわらず、意味が食い違えば日本語を正とする。

## 書く場所の判断

段落ごとに、次の読み手と用途に合う置き場を選ぶ。どれにも当たらない内容は書かない。OKFへ整理する場合の粒度は後述の専用規約に従う。

| 置き場 | 判定の問い |
| --- | --- |
| 公開docs `docs/ja/`（原本）・`en/`（英訳） | コアのソースを読めない Unity・Tauri の開発者が、これを知らないとフロントを正しく書けないか |
| 通常の非公開docs `genesis-core/docs/`（`okf/`を除く） | コアを触る人が、ソースを開く前に頭に入れておくべき全体的な考え方や処理順序か |
| 非公開OKF `genesis-core/docs/okf/` | 概念・実装の責務・データや属性の意味を、相互関係と根拠から辿るための知識か |
| ソースのコメント | そのコードを編集する人が知るべき、コードから読み取れない意図や注意点か |

公開docsには、シミュレーションの概念、フロントの全体構成と共通の仕組み、座標・単位・命名などモジュール間で共有する約束といった全体的な考え方を書く。API・IPC の項目は網羅せず、読み違えやすい重要な項目だけを考え方の説明の中で書く(項目の一覧は API 資料、IPC はソースのコメントで読む前提)。コアの処理ロジックや、フロントから見えない内部の名前は書かない。

`AGENTS.md` にはディレクトリの概要と配下の作業全体に適用する横断的なルール、`README.md` には対象の概要・入口・実行やビルドの案内を書く。

## OKFとの役割分担

OKFの作成・更新・移行は、非公開コアの `genesis-core/.claude/skills/genesis-okf/SKILL.md` に従う。非公開側が手元にない公開リポジトリでの作業は、公開契約で確認できる範囲を扱い、OKFを必須の参照先にしない。

以下の「通常のdocsに書かないもの」と「通常のdocsとコメントの粒度」は公開docs・通常の非公開docs・ソースコメントの基準である。OKFでは専用規約に従い、ソースの責務、データの属性一覧、属性の単位・時間的意味・更新元などを記載できる。この例外で公開docsの範囲を広げない。

非公開docsからOKFへ移す主題は詳しい説明先を一本化し、旧ページや索引から案内する。公開docsは公開読者向けの説明として維持し、非公開OKFへのリンクで代用しない。ソースコメントには、そのコードを編集する人が必要な意図と注意点を残す。Skillの作業手順とAGENTS.mdの横断的な規則は原本を参照する。

## 通常のdocsに書かないもの

- 実装を日本語に置き換えただけの説明、コードや擬似コード・式の写し、関数一覧、逐次処理の列挙。
- 個別の機能・画面・パネル・イベント・バリアントの仕様、閾値・係数・既定値などの調整値。必要なら該当ソースのコメントに書く。
- モデルの作り方(パーツの原点・向き・寸法・著作のしかた)。コードがその約束を前提にしているなら、パーツを置くコードのコメントに書く。
- TODO、計画、構想、作業記録、検証の作業ログ、作成手順書。
- 過去の仕様、廃止した名前、不採用案、試行錯誤、今回の変更経緯、修正前の不具合の筋書き。

外部契約を説明するための名前(API・IPC の項目、フロントが読むマスターの項目、同期される共有定数、アセットの命名規則)は残してよい。部品の名前と役割の対応は短い表にしてよい。

不要な文章を別ページ・付録・ソースコメントへ丸ごと移して温存しない。コメントに移すのは実装を読んでも分からない意図だけで、そのソースに同じ意図のコメントが既にあれば移さない。作業中の気付きはワークスペースの `TODO.md` に必要なものだけ残す。

## 通常のdocsとコメントの粒度

- 1ページは、全体の考え方と、概念ごとの短い節が数個。個別の挙動ごとに見出しを立てない。
- 「〜のときは〜する」という個別の挙動や例外の列挙が続くなら、その仕組みの考え方を1〜2文にまとめ、列挙はソースのコメントに任せる。
- 他のページの見出しや節番号を本文で参照しない。ページ単位でリンクする。ソースのコメントから文書を参照するときもページ単位にする。
- ソースのコメントは、その変数・関数を編集する人が知るべき意図と注意点を1〜3行で書く。

## 更新と確認

ソースを変更したら、関連する文書と既存OKFの更新要否を確認し、記載対象の意味や関係が変わった箇所を同じ変更で更新する。記載内容に影響しなければ機械的に更新しない。通常の文書・ソース編集だけでOKFの新規構築や一括移行を始めない。更新するときは既存の説明を直し、他のページからは参照する。追記の前に、重複する節や主題から外れる文章を削れるか確認する。文書の整理に合わせて実装の機能を追加しない。

見出し・リンク・説明先を変更したら関係する参照を揃える。公開ページの追加・削除時は `docs/ja/README.md` と `en/README.md` の目次も合わせる。

公開docsは GitHub 上で Markdown を直接読む。本文・画像を保持し、相対リンクが実ファイルを指すことと、両言語のページの対応を確認する。サイトのビルド環境は使わない。完了前に各段落を上の判定で読み直す。
