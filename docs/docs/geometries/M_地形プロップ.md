# M. 地形プロップ（装飾オブジェクト）

## M.1. 地形プロップとは

地形プロップは、森・茂み・岩などの装飾オブジェクトをのっぺりした地形の上に載せ、都市の外側の自然地形に密度感を与えるための仕組みである。

プロップは**純粋な装飾**であり、経済シミュレーションには一切影響しない。配置コスト・維持費は発生せず、天然資源（森林資源など）とも紐づかない。ゼロコストの装飾であるため、テンプレート作成モードに限らず通常プレイ中もいつでも配置・撤去できる。また、土地区画や天然資源と異なり**未開放（未取得）の地形セルにも配置できる**。都市の外に広がる自然の森を表現することが主用途だからである。

プロップの種別（針葉樹・広葉樹・岩・茂みなど）はマスタデータ `prop_master` で定義され、表示名や対応するプレハブ（3Dモデル）の情報を持つ。

## M.2. 2つのデータ型

プロップは配置のしかたによって2つのデータ型に分かれる。ジオメトリの表現・重なり除去の処理・削除の単位がまったく異なるため、別々のエンティティ（別テーブル）として管理される。

| | 範囲散布（`PropScatter`） | 個別配置（`PropInstance`） |
| --- | --- | --- |
| 用途 | 森・岩場など「範囲と密度」で表す装飾の集まり | ランドマーク的な1本木・岩など1個ずつ置く装飾 |
| 1レコード | 散布範囲1つ | **配置オブジェクト1個** |
| 位置情報 | `region`（穴つきMultiPolygon座標） | 座標1点 + 回転 + スケール |
| 個々のオブジェクトの座標 | 保持しない（グラフィック側が `seed` から生成） | レコードそのもの |

### 範囲散布（PropScatter）のデータモデル

- **`prop_type`**: 種別。`prop_master` のキー。
- **`region`**: 散布範囲。GeoJSON MultiPolygon の `coordinates` 形式（`[[[外周リング], [穴リング], ...], ...]`）。穴・複数塊を1レコードで表現できる。
- **`density`**: 散布密度（本/ヘクタール）。
- **`seed`**: 散布生成用の乱数シード（整数）。
- **`center_point`**: `region` 全体の重心。
- **`version`**: 見た目に関わるプロパティ（`region` / `density` / `seed` / `prop_type`）が変わるたびに増える差分更新用バージョン。

### 個別配置（PropInstance）のデータモデル

- **`prop_type`**: 種別。`prop_master` のキー。
- **`x` / `z`**: 配置位置。
- **`rotation`**: Y軸回転（度）。
- **`scale`**: スケール倍率（1.0 = 原寸）。

どちらの型も**標高（Y座標）を持たない**。プロップは常に地表に貼り付いているものとして扱い、実際の高さはグラフィック側が自前の地形メッシュからサンプルする（「Y座標の考え方」と同じ原則）。

## M.3. シード方式による散布生成（グラフィック側との契約）

範囲散布プロップについて、バックエンドは範囲・密度・シードのみを保持し、**木1本1本の座標・回転・スケールはグラフィック側（Unity）が `seed` を初期値とする決定的な乱数で生成する**。数万本の森でもデータは数百バイトで済み、セーブデータも肥大化しない。

グラフィック側の実装が守るべき契約は以下のとおり。

- 散布する点の数は `region` の面積 × `density` を目安とする。散布アルゴリズム（グリッドジッター、Poisson-diskなど）は実装の自由。
- 散布点は「**外周リングの内側にあり、かつ、どの穴リングの内側にも入らない**」場所にのみ生成する。`region` は区画や道路による刳り抜きでドーナツ形（穴つき）や複数塊になり得る。
- 各点の標高は地形メッシュからサンプルして地表に配置する。
- `version` が変わったレコードだけ散布を再生成する（他エンティティと同じ version 差分更新の慣習）。
- **シードの厳密な再現性は保証されない仕様である。** 重なり除去などで `region` が変わると、同じ `seed` でも散布結果が多少変わってよい（`region` 更新時に `seed` は据え置かれる）。「森の見た目が完全に不変であること」より「データの小ささと処理の単純さ」を優先している。

## M.4. API

エンドポイントは `/api/v1/props` に統一されている。取得は1リクエストで両タイプを返す。

| メソッド | パス | 説明 |
| --- | --- | --- |
| GET | `/api/v1/props` | 範囲散布と個別配置の両方を取得。`?bbox=x1,z1,x2,z2` で範囲検索可能。散布プロップは散布範囲全体を覆うbboxで空間インデックスに登録されているため、「中心は範囲外だが散布範囲は重なる」プロップも漏れなくヒットする |
| POST | `/api/v1/props/scatters` | 範囲散布を作成。`polygon`（単純ポリゴン `[[x, z], ...]`）/ `prop_type` / `density` 必須、`seed` 任意（未指定はサーバ採番）。入力の単純ポリゴンはサーバ側でMultiPolygon座標の `region` に正規化される |
| PATCH | `/api/v1/props/scatters/{id}` | `polygon` / `density` / `seed` の編集 |
| DELETE | `/api/v1/props/scatters/{id}` | 範囲散布の撤去 |
| POST | `/api/v1/props/instances` | 個別配置の一括作成。`instances: [{x, z, rotation, scale, prop_type}, ...]`。配置パネルで複数打点→確定を1リクエストで送る想定 |
| DELETE | `/api/v1/props/instances/{id}` | 個別配置を1個撤去 |

GET のレスポンス例:

```json
{
  "scatters": [
    {
      "prop_scatter_id": 1,
      "prop_type": 1,
      "region": [[[[0, 0], [300, 0], [300, 300], [0, 300], [0, 0]],
                  [[100, 100], [200, 100], [200, 200], [100, 200], [100, 100]]]],
      "center_point": [150.0, 150.0],
      "density": 400.0,
      "seed": 12345,
      "version": 3
    }
  ],
  "instances": [
    {
      "prop_instance_id": 1,
      "prop_type": 2,
      "x": 500.0,
      "z": 600.0,
      "rotation": 90.0,
      "scale": 1.5,
      "version": 0
    }
  ]
}
```

上の例の `region` は「外周＋穴1つ」のドーナツ形（1パート・リング2本）である。

## M.5. 重なり除去（イベント駆動）

都市の開発によってプロップの上に区画や道路が作られた場合、重なったプロップは自動的に除去される。除去は以下の**イベント発生時にのみ**行われる。

- 土地区画の作成
- 土地区画の形状変更（作り直しを含む）
- パス（道路など）の作成。ただし完全に地下のパス（トンネル）は地表の装飾に影響しないため除去しない

除去のされかたはデータ型ごとに異なる。

- **範囲散布**: 散布範囲から区画・道路の占有ポリゴンが刳り抜かれる（`region` がドーナツ形やMultiPolygonになる）。範囲が完全になくなればレコードごと削除される。`region` の変更で `version` が上がり、グラフィック側が再散布する。
- **個別配置**: 範囲内に位置するレコードが削除される。

以下は**除去されない**（仕様）。

- **建物の作成**では除去しない。建物は区画の中に建つため、区画作成の時点で除去済みだからである。
- **区画作成「後」にユーザーが後付けしたプロップ**は、たとえ区画と重なっていても除去されない。イベント発生時にのみ除去が走るためである。区画を削除して同じ場所に作り直せば、その時点で再び除去される。

## M.6. グラフィック側の実装状況

**配置UIは実装済み**。プロップ配置パネル（UI `prop_placement`）と Unity のプロップ配置モード（`STATE_EDIT_PROP` → `PropPlacementManager`）により、個別配置（1クリック=1個、配置前は半透明ゴースト／確定で不透明）と範囲散布（ポリゴンを描いて `density`/`seed` を設定、seedベースの簡易散布プレビューを半透明表示）を行える。確定送信（個別=`POST /api/v1/props/instances`、範囲=`POST /api/v1/props/scatters`）はUI側が行う。プロップの選択肢は `prop_master`（`GET /api/v1/master/prop_types`）から取得し、モデルは Unity が種別IDごとに `Resources/Models/Props/{prop_type}` から読み込む。詳細なIPC契約は [IPC連携の整理](../programs/IPC連携の整理.md) の `STATE_EDIT_PROP` を参照。

**永続レンダラは実装済み**（Unity `PropManager`）。カメラ周辺セルのマージBBOXで `GET /api/v1/props?bbox=` を一括取得し、`version` 差分更新の慣習に従ってレコード単位で生成・破棄する（散布レコードは範囲が複数セルに跨っても1回だけ実体化される）。散布点は M.3 の契約どおり `seed` を初期値とする決定的な乱数で生成され、穴リング・複数塊を考慮して「外周の内側かつどの穴にも入らない」場所にのみ置かれる。個々の標高は地形（CPU高さ配列）からサンプルし、地形のロード・更新後には建物・道路と同じ地形追従フローでY座標が再調整される（[Unity差分ロード整理](K_Unity差分ロード整理.md) 参照）。

**未実装（別タスク）**: GPUインスタンシング等による数万本規模の軽量描画（現状は1オブジェクト=1GameObjectのため、1散布レコードあたり5000個の生成上限がある）、および既存プロップの削除UI。また `master.yaml` の `prop_master` セクション（種別ID→表示名／prefab）の生成はジェネレータ側の対応が必要。
