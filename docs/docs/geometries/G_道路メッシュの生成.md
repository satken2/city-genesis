# 道路メッシュの生成

## 概要

バックエンドの Path データから、道路の外観メッシュを組み立てて配置する仕様。

道路の経路は始点・終点・ウェイポイントというアンカー点と、それらの間を結ぶ三次ベジエ曲線で定義される。フロントエンドではこのベジエ曲線を多数の点にサンプリングし、その点群をもとにメッシュを生成する。

カーブを含む道路の描画には **Dreamteck Splines** ライブラリを使用し、サンプリング点群からスプラインを構築してメッシュパーツを配置する。

### パスの種類とジェネレータの対応

`PathMeshFactory` がジェネレータの振り分けを行う。ジェネレータの選択は **`path_master` の `model_type`** で決まる（`path_type` ではない）。まず `path_variant` に固有のジェネレータがあれば最優先し、なければ `model_type` で切り替える。

| model_type | ジェネレータ    | 生成方式                     |
| ---------- | --------- | ------------------------ |
| `default`  | RoadPath  | スプライン + SplineMesh       |
| `track`    | TrackPath | スプライン + SplineMesh（線路構成） |
| `none`     | （なし）      | メッシュ生成なし（経路探索専用パス・公共交通の路線等） |

`model_type` が未設定（旧マスター）の場合は `path_type` から推論する（PATH_TRACK/PATH_MONORAIL → `track`、それ以外 → `default`）。これは後方互換のための過渡措置であり、`master.yaml` の再生成後は `model_type` が正とする。

本ドキュメントでは主に **RoadPath**（道路のスプライン方式）の詳細を説明する。線路・モノレール向けの **TrackPath** は同じ仕組みの上に線路固有のパーツ構成を持ち、[N_線路メッシュの生成](N_線路メッシュの生成.md) で説明する。

## 1. データフロー

```
バックエンド API
       │
       ▼
  PathSummary（APIレスポンス）
       ├─ path_id            一意識別子
       ├─ path_type          パスの種類
       ├─ path_variant       パスのバリアント
       ├─ status             状態（active 等）
       ├─ start_point        始点座標 [x, y, z]
       ├─ end_point          終点座標 [x, y, z]
       ├─ waypoints          ウェイポイント配列（位置 + 制御点）
       ├─ polygon            道路の占有ポリゴン（衝突判定用、描画には使わない）
       ├─ width              道路幅
       └─ ...
       │
       ▼
  PathManager.CreateOrUpdatePath()
       │
       ├─ CalculatePathPoints()
       │    ├─ アンカー点と制御点から三次ベジエ曲線を構築
       │    ├─ 各セグメントを約1m間隔（TERRAIN_SAMPLE_INTERVAL）でサンプリング
       │    └─ 各点のY座標を地形標高に追従させる
       │
       ├─ PathMeshFactory.GeneratePathMesh(path, points)
       │    ├─ ジェネレータ選択（variant → type の順）
       │    │
       │    ▼
       │    RoadPath.Generate()
       │         1. マスターデータから寸法を取得
       │         2. 点群から Dreamteck スプラインを構築
       │         3. パーツの解決とフォールバック
       │         4. 各パーツを SplineMesh で配置
       │         5. 街路樹の配置
       │         6. コライダーメッシュの生成
       │         │
       │         ▼
       │    PathMeshResult (Mesh + ModulesCreated + GeneratedObject)
       │
       ├─ MeshCollider にコライダーメッシュを設定
       ├─ PathInputHandler を追加（クリック判定用）
       └─ LOD判定に基づき Near/Far 表示を切り替え
```

### 1.1 polygon について

`PathSummary.polygon` はバックエンドで計算された**道路の占有領域ポリゴン**である。土地区画との重複判定などの幾何学的計算に使われ、フロントエンドの道路描画には直接使われない。道路の描画形状は `start_point` / `end_point` / `waypoints` から三次ベジエ曲線を再構築して生成する。

## 2. 三次ベジエ曲線による点群生成

### 2.1 アンカー点と制御点

パスの形状はアンカー点と制御点の組で定義される。アンカー点は曲線が必ず通過する点であり、制御点は曲線の入り・出りの方向と張りを制御する。

各セグメントは三次ベジエ曲線 B(t) = (1-t)³·P0 + 3(1-t)²·t·P1 + 3(1-t)·t²·P2 + t³·P3 で表現される：

- P0 = セグメント始点の位置
- P1 = セグメント始点の出口制御点（`control_out` または自動計算）
- P2 = セグメント終点の入口制御点（`control_in` または自動計算）
- P3 = セグメント終点の位置

制御点が未指定の場合は自動計算する。ウェイポイントのないパスは始点と終点を 1/3・2/3 に内分した位置（実質的に直線）、ウェイポイントを挟むアンカーは Catmull-Rom スプラインの接線（`T_i = P_{i+1} − P_{i-1}`、テンション 1/6、端点は片側接線）から計算する。これはバックエンドの制御点自動補完（`A_パス形状.md` の「制御点の自動補完」参照）と同一ロジックであり、バックエンドが永続化したウェイポイントの制御点（`control_in` / `control_out`）が API に含まれる場合はそれを優先使用する。

### 2.2 セグメント構成

ウェイポイントがない場合は始点→終点の単一セグメント、ウェイポイントがN個の場合はN+1セグメントになる。

```
始点 → ウェイポイント0 → ウェイポイント1 → ... → 終点
  セグメント0    セグメント1       ...      セグメントN
```

### 2.3 サンプリングと地形追従

`PathManager.CalculatePathPoints()` は各セグメントを約1m間隔（`TERRAIN_SAMPLE_INTERVAL`）でサンプリングする。相対Y=0のアンカーで挟まれた区間では、サンプリングされた各点のY座標を地形標高＋`RoadPartHeights.ROAD_SPLINE_OFFSET`（0.1m）に追従させる。これにより、道路の中心線が地形の起伏に沿うようになる。相対Y≠0（高架・地下）の区間は地形追従せず、アンカーと制御点のY座標をそのままベジエ補間する。

中心線サンプリングとExtrudeタイル長はともに1mを基準とし、Dynamic地形の格子間の小さな尾根を長い弦でまたぐことによる埋没を抑える。これは描画用近似の密度であり、保存されたアンカー・制御点や相対高さの意味は変更しない。高架・地下・`single_span`の追従除外規則も維持する。

地形の高さキャッシュは同一XZ座標のみを共有する。1m単位に座標を丸めて別地点の高さを使い回すと、傾斜地で問い合わせ順によって路面が変わるため行わない。道路全幅の横断方向の造成はバックエンドが担い、描画側で縁石や断面を地形へ個別に吸着させることはしない。

## 3. LOD（Level of Detail）

### 3.1 Near / Far の2段階

カメラ位置からの距離に応じて、パスの描画品質を切り替える。`LodTier.Near`（カメラに近いセル）と `LodTier.Far`（カメラから遠いセル）の2段階がある。

判定基準はパスの始点または終点がNearセルに含まれるかどうかである。セル境界を跨ぐパスの場合、片方の端がNearセルにあればフル詳細で描画する。

### 3.2 Near（フル詳細）

`CreateOrUpdatePath()` で通常のパスオブジェクトを生成する。ベジエサンプリング→スプライン構築→SplineMesh配置のフルパイプラインが実行される。

### 3.3 Far（簡易表示）

`CreateOrUpdateFarPath()` で簡易パスオブジェクトを生成する。始点と終点の2点だけの `BuildStripMesh` で単純なストリップメッシュを作る。ウェイポイントやベジエサンプリングは行わない。マテリアルはノード用マテリアルを流用する。

セルのアンロード時はオブジェクトを破棄せず非アクティブにしてプーリングし、他のロード対象セルに跨っているパスは非表示にしない。これによりセル境界を跨ぐ道路がカメラ移動時に一瞬消えるチラつきを防止する。

## 4. スプラインによる道路形状の定義（RoadPath）

### 4.1 描画点列と補間

`CalculatePathPoints` が保存された三次ベジエをサンプリングする。交差点の切断は、この点列上の経路距離で行う。保存されたアンカー・制御点を移動して曲線を作り直すことはしない。

### 4.2 スプラインの構築

`RoadPath.BuildSpline` は曲線の点列を明示的な三次ベジエハンドルで補間する。内部はCatmull-Rom相当の接線、両端は残存点列の最初・最後の区間方向を使う。交差点も同じ区間方向を参照するため、別々の再補間による入口の回転を防げる。折れ線はLinearを使う。`single_span` は交差点計算でもアンカー間の直線として評価する。

点列はワールド座標で渡し、`Uniform`サンプリングと`RebuildImmediate`で直後の長さ・位置評価を確定する。この補間は描画用の近似であり、バックエンドの保存曲線や占有ポリゴンを変更しない。
### 4.3 SplineMesh によるパーツの配置

スプラインが構築できたら、各パーツ（道路本体、区画線、歩道）をスプラインに沿って配置する。これには Dreamteck Splines の **SplineMesh** コンポーネントを使用する。

SplineMesh の考え方は以下の通り：

- **メッシュパーツをスプラインに沿って並べる** という基本的なアプローチ
- パーツはスプラインの形状に合わせて自動的に変形（曲げ）される
- 1つのパーツが短すぎてスプライン全体を覆えない場合、**タイリング（繰り返し配置）** される
- SplineMesh はタイル内の頂点Z位置でしかスプラインを評価しないため、Z方向の分割が粗いパーツはタイルが弦（直線）近似になる。縦カーブ（尾根・谷）でパーツ同士が上下にずれて貫通・浮きが起きないよう、**タイル長には上限（`MAX_EXTRUDE_TILE_LENGTH`=1m）を設け、タイル数を明示的に決める**（メッシュ実寸ベースの `autoCount` は使わない）。

### 4.4 スケールとオフセット

SplineMesh に渡すパーツは、元のメッシュの寸法と道路の設計寸法が異なるため、適切にスケールを調整する必要がある。

- **X 方向のスケール**: `設計幅 / メッシュの元の幅` を計算する。body は最上面から2mm以内の頂点の横幅と中心を使い、下部の桁やスカートの張り出しを除く（`GetBodySurfaceBounds`）。他パーツは全体の bounds を使う。body の上面は生成用の共有メッシュで Y=0 に補正するため、FBX の微小な原点誤差も接合に持ち込まない。歩道とラインも、実際に採用したモデル系列のbody上面Yを引く（`GetRoadPartMesh`）。p2のように路面高0.5mが付属パーツにも含まれるモデルで、路面だけが下がって付属パーツが浮くことを防ぐ。フォールバック時は採用したパーツ側の系列を参照する。
- **横方向オフセット**: スプラインの中心線から左右にどれだけずらすかを、**パーツの中心の位置**として指定する。プレハブのピボットが中心にない場合（縁石原点の歩道など）は、メッシュ bounds の中心が指定位置に一致するよう生成側（`RoadPath.CreateSplineMesh`）が自動補正する。このため、プレハブのピボット位置が配置結果に影響することはない
- **Y 方向オフセット**: スプラインからの高さ。値は `RoadPartHeights` の定数に集約されている（下表）

#### 高さの層構造（RoadPartHeights）

道路は「スプライン点（地形+0.1m）」の上に各パーツをオフセットで重ねる2層構造で描画される。

| 定数 | 値 | 意味 |
|---|---|---|
| `ROAD_SPLINE_OFFSET` | 0.1m | 地形追従スプライン点の地形からの浮かせ量（地形メッシュへの埋没回避） |
| `BODY_ABOVE_SPLINE` | 0.1m | 道路本体のスプラインからの高さ。**bodyプレハブの上面＝ピボット平面**の規約なので、路面上面はこの平面（地表道路なら地形+0.2m）になる |
| `LINE_ABOVE_SPLINE` | 0.12m | 区画線・センターラインの高さ（body上面の2cm上） |
| `CENTER_LINE_EXTRA` | 0.005m | 中央の線を側線よりさらに浮かせる量 |
| `SIDEWALK_ABOVE_SPLINE` | 0.1m | 歩道の下端の高さ（body上面と同一平面。縁石の立ち上がりはプレハブ形状） |
| `WALL_ABOVE_SPLINE` | 0.1m | 防音壁・ガードレールの下端の高さ |

交差点メッシュもこの体系に従う（[§11](#11-交差点と断面の接合)）。

## 5. マスターデータと寸法パラメータ

### 5.1 寸法の取得

道路の寸法は `MasterDataStore` のパスマスターデータ（`PathMasterItem`）から取得する。`path_variant` をキーにしてマスターデータを検索し、以下のパラメータを得る。

| パラメータ | フィールド | 単位 | デフォルト |
|---|---|---|---|
| 道路幅 | `width` | m | 4.0 |
| 歩道幅 | `sidewalk_width` | m | 0.5 |
| 区画線幅 | `side_width` | m | 0.5 |
| 防音壁・ガードレール幅 | `wall_width` | m | null（配置なし） |
| 中央分離帯幅 | `center_width` | m | null（配置なし） |
| 街路樹の標準間隔 | `tree_spacing` | m | null/0なら20m（設置有無はPathの選択） |

歩道幅・区画線幅・防音壁幅・中央分離帯幅・街路樹間隔は null 許容であり、null の場合はデフォルト値を使用するか、その機能をスキップする。街路樹の有無は間隔とは独立し、Pathの保存値で決まる（§8.6）。

### 5.2 オフセットの計算

道路は中心線に対して左右対称に構成される。各パーツの配置位置は以下の考え方で計算する。

`width` は**道路全体の幅**である。歩道は道路の端に覆いかぶさるように配置する（歩道幅を道路幅に足すのではなく、道路幅の中に歩道が含まれる）。

```
中心線
    │
    ├──────────── width ────────────┤
    │                               │
    区画線  歩道    道路本体    歩道  区画線
```

各パーツのオフセット（中心線からパーツ中心までの距離）：

| パーツ | オフセット計算 | 値の例 (width=4, sidewalk=0.5, side=0.5, wall=0.3, center=0.6) |
|---|---|---|
| 道路本体 | 0 | 0 |
| 中央分離帯 | 0 | 0 |
| 歩道 | `(width/2) - (sidewalkWidth/2)` | 1.75 |
| 区画線 | `(width/2) - sidewalkWidth - (sideWidth/2)` | 1.25 |
| 防音壁・ガードレール | `(width/2) + (wallWidth/2)` | 2.15 |

オフセットは絶対値で計算し、左右それぞれに +オフセット と -オフセット で配置する。オフセットは常に**パーツの中心**の位置を表す（プレハブのピボットが端にあっても生成側で bounds 中心基準に補正される）。

#### 左右非対称パーツのミラーリング規約

**歩道は左側用**（縁石＝道路中心側が +X）で、左側が原型・右側がXミラー。**壁は右側用**（道路中心側が -X）で、右側が原型・左側がXミラー。交差点内でもこの向きを維持する。

### 5.3 歩道付き道路橋（p223）

幅12m、両側歩道各2.5mの2車線コンクリート桁橋。`model_type=default` の `RoadPath` で組み立て、`single_span=false` として曲線を維持する。`height_editable=true`、`follow_terrain=false` が既定で、橋脚間隔は40m。接道可否は `frontage_allowed=false` とし、地表に置いても沿道区画生成や接道指定の対象にはしない。Unityはマスターの同属性を参照し、沿道生成モードのクリック・ホバー対象から除外する。

| パーツ | 構成・著作寸法 |
| --- | --- |
| `body` | 幅12mの舗装・床版と4本の縦桁。路面上面が原点、最下部は-1.05m |
| `sidewalk` | 幅2.5m、歩道上面0.20m、車道側縁石0.23m。左側用（中心側+X） |
| `line` | 幅0.5mの区画線。既存街路の区画線マテリアルを共有 |
| `wall` | 幅0.3mの地覆と金属製高欄。路面から約1.3m、右側用 |
| `pillar` | 左右2本のコンクリート柱。天端0mから下へ4mの一様断面で、地盤まで高さ倍率を掛ける |
| `pillar_cap` | 幅10mの受け梁。路面原点から下へ1.9mまで、実寸のまま配置 |

連続パーツは進行方向2.5mのタイルとし、既存の `PATH_ASPHALT`・`PATH_CONCRETE`・`PATH_METAL` を共有する。道路設備（街路樹・街灯・柵・電柱）の個別設定は許可しない。高欄は道路設備の柵ではなく、常設の `wall` パーツである。

制作元は `genesis-gallery/library/paths.blend` の `p223/*` コレクション。著作ジョブは `pipeline/jobs/build_p223.py`、書き出し先は `Assets/Models/Paths/p223/`。Unityのミラープレハブは通常の自動生成に従う。

## 6. アセットの命名規則とフォルダ構成

### 6.1 リソースパスの構成

道路パーツはプレハブとして `Assets/Resources/Models/Paths/` に配置する。`ModelManager` が glTF ファイル（`persistentDataPath`）を優先的に探し、なければ `Resources.Load` でプレハブを読み込む。

```
Models/Paths/p{path_variant}/{position}
```

| 構成要素             | 値                                                    | 説明      |
| ---------------- | ---------------------------------------------------- | ------- |
| **path_variant** | `p{path_variant}`                                    | バリアント番号 |
| **position**     | `body`, `line`, `sidewalk`, `tree`, `wall`, `center` | パーツの種類  |

### 6.2 命名例

```
Models/Paths/p1/body         タイプ1の道路ボディ
Models/Paths/p1/line         タイプ1の区画線
Models/Paths/p1/sidewalk     タイプ1の歩道
Models/Paths/p1/tree         タイプ1の街路樹
Models/Paths/p1/wall         タイプ1の防音壁・ガードレール
Models/Paths/p1/center       タイプ1の中央分離帯
Models/Paths/p100/body       バリアント100の道路ボディ
Models/Paths/p100/sidewalk   バリアント100の歩道
```

### 6.3 パーツの種類

| position     | 役割         | 配置数   | 備考                                                                    |
| ------------ | ---------- | ----- | --------------------------------------------------------------------- |
| `body`       | 道路本体       | 1     | スプライン中心に配置                                                            |
| `center`     | 中央分離帯      | 1     | スプライン中心に配置。パーツがない場合は `line` にフォールバック                                  |
| `line`       | 区画線        | 2（左右） | 道路端、歩道の内側に配置                                                          |
| `sidewalk`   | 歩道         | 2（左右） | 道路端に配置。右側は左右反転                                                        |
| `wall`       | 防音壁・ガードレール | 2（左右） | 道路の左右端に配置。右側は左右反転                                                     |
| `tree`       | 街路樹        | 任意    | 歩道に沿って一定間隔で配置                                                         |
| `pillar`     | 柱          | 任意    | 高架道路等の路面支持用。height_editable=true のバリアントに対してのみ配置。地下パス（負の相対Yを持つ）には配置しない |
| `pillar_cap` | 柱のキャップ     | 任意    | 高架の柱の上部を保護または装飾するキャップパーツ。Y方向には拡大（スケール）されない。地下パスには配置しない                |
| `portal`     | 坑口         | 任意    | 地下パスの描画区間⇔トンネル区間の境界（坑口）に配置。プレハブはローカル+Zがトンネル内部を向く前提                    |

### 6.4 パーツプレハブのモデリング規約

生成側はプレハブメッシュの bounds を実測して配置を補正するため、横方向のピボット位置は自由だが、以下の規約は守る必要がある。

| 項目 | 規約 | 理由 |
|---|---|---|
| bodyの高さ方向ピボット | **路面の上面**（厚みは下方向に伸ばす） | 区画線のオフセット（body上面+2cm）や交差点アスファルトの高さがこの前提で決まる |
| line/sidewalk/wallの高さ方向ピボット | **下端**（上方向に伸ばす） | パーツの下端が配置面（`RoadPartHeights` の各オフセット）に接する |
| 左右非対称パーツ（sidewalk/wall）の向き | 歩道は左側用（中心側+X）、壁は右側用（中心側-X） | 歩道は右側、壁は左側をXミラーで配置する |
| Z方向（進行方向）の長さ | 1タイルとして繰り返される単位。10m程度でよい | タイル長は生成側が `MAX_EXTRUDE_TILE_LENGTH`（2.5m）に分割するため、Z方向の細かい分割は必須ではない |
| tree/pillar/pillar_cap/portal | Instantiate配置のため原点＝接地点（pillar/pillar_capは路面原点） | スケール・回転が原点基準で適用される |

## 7. フォールバック機能

### 7.1 基本考え方

建物のフォールバックと同様に、まずバリアント固有のパーツを探し、見つからなければタイプのパーツにフォールバックする。

### 7.2 フォールバック階層

パーツごとに以下の順序で検索し、最初に見つかったものを使用する。

```
1. バリアント固有パーツ: Models/Paths/p{path_variant}/{position}
       ↓ ない場合
2. タイプパーツ: Models/Paths/p{path_type}/{position}
       ↓ ない場合
3. そのパーツをスキップ（道路本体以外）
```

ここで、`path_type` は `PathMasterItem.type` から取得する。

道路本体（body）が見つからない場合は、道路形状（スプライン）に沿った白い板（ストリップメッシュ）を動的生成して描画し、ゲームプレイが継続できるようにフォールバックする。その他のパーツはオプショナルであり、パーツがなくても道路本体（または白い板）だけでも機能する。

#### 中央分離帯（center）の特別なフォールバック

中央分離帯のパーツ（`center`）が見つからない場合、センターラインのパーツ（`line`）を代わりに使用する。これにより、中央分離帯の3Dモデルを用意しなくても、区画線で中央の分離を表現できる。

## 8. 各パーツの生成詳細

### 8.1 道路本体（body）

スプラインの中心線に沿って、道路全体の幅で配置する。

- **リソースパス**: `Models/Paths/p{variant}/body`（フォールバックあり）
- **幅**: マスターデータの `width`
- **オフセット**: なし（中心）
- **高さオフセット**: `BODY_ABOVE_SPLINE`（0.1m）。bodyプレハブはピボット＝路面上面の規約なので、路面上面がスプライン+0.1m（地表道路なら地形+0.2m）になる
- **SplineMesh の設定**:
  - X スケール = `width / メッシュの元の幅`
  - タイル数 = `スプライン長 / min(メッシュZ長, MAX_EXTRUDE_TILE_LENGTH(=2.5m))`（縦カーブの弦誤差を抑えるため明示指定）

#### single_span モード（`single_span = true`）

`single_span` が true のバリアントでは、body の配置方法が変わる。地形追従で2.5mごとに細分化配置するのではなく、**柱（アンカー点）間を1枚のbody引き延ばしで接ぐ**。高架橋や桁橋のように、路面が地形の起伏に関わらず支柱間で水平に架かる構造物を表現するために使う。

- **スプラインの構築**: アンカー点（始点・ウェイポイント・終点）のみでスプラインを構築し、地形追従の細分化（`SubdividePointsWithTerrain`）を行わない。曲線パス（`curved=true`）も `single_span` の場合は直線セグメント化して扱う（ベジエ曲線の水平形状は無視され、アンカー点間の直線になる）。
- **body のタイル数**: `count = 1`。SplineMesh はメッシュのZ頂点をスプライン始点・終点に写像するため、body は両端を結ぶ弦（直線スパン）になる。Z方向の分割を持たないプレハブ（bodyは10mの箱）では、アンカー点間の直線的な床板として描画される。
- **その他のパーツ**（line / sidewalk / wall 等）: body と同じスプライン（アンカー点のみ）に沿って配置されるため、body と一貫して地形に追従しない。タイル数は通常通り `MAX_EXTRUDE_TILE_LENGTH` に基づく。
- **ウェイポイントがある場合**: セグメントごとに独立したスプラインが作られ（`GenerateLinearPathWithCorners` と同じフロー）、各セグメントの body が `count = 1` で柱間を接ぐ。

### 8.2 中央分離帯（center）

道路の中央に配置する分離帯。中央分離帯がある場合、センターラインは省略され、代わりに中央分離帯と側線の間にレーン境界の点線が配置される。

- **リソースパス**: `Models/Paths/p{variant}/center`（フォールバックあり。パーツがない場合は `line` を代用）
- **幅**: マスターデータの `center_width`
- **オフセット**: なし（中心）
- **高さオフセット**: 0.1m
- **レーン境界線**: 中央分離帯の端から側線までの距離を片側レーン数で等分し、各境界に点線を配置する。例えば4車線なら片側2レーンなので1本、6車線なら片側3レーンなので2本の点線を配置する。

### 8.3 区画線（line）

道路の端、歩道の内側に配置する細いライン。左右2本。中央分離帯がない場合は、センターラインや車線境界線としても使用される。

`side_width` が0の道路（未舗装路など、区画線を持たない道路）では、側線・センターライン・車線境界線のいずれも配置しない。線の太さを `side_width` から導くため、0の場合は描いても潰れたメッシュになる。

- **リソースパス**: `Models/Paths/p{variant}/line`（フォールバックあり）
- **幅**: マスターデータの `side_width` の3割（`side_width * 0.3`）
- **オフセット**: `±((width/2) - sidewalkWidth - (sideWidth/2))`
- **高さオフセット**: `LINE_ABOVE_SPLINE`（0.12m）。body上面（0.1m）の2cm上でZファイティングを回避。中央の線はさらに `CENTER_LINE_EXTRA`（0.005m）浮かせる
- **左右対称**: 同じメッシュを +オフセット と -オフセット に2つ配置

#### 中央分離帯がない場合の中央線・車線境界線

マスターデータの `lanes`（車線数）に応じて、道路中央と各車線境界に線を配置する。車線幅は `width / lanes` で等分する。

| `lanes` | 中央 | 車線境界 |
|---|---|---|
| 1以下 | なし | なし |
| 2 | 点線 | なし |
| 4以上の偶数 | 実線 | 片側 `lanes/2 - 1` 本の点線を左右対称に配置 |
| 3以上の奇数 | 点線 | 片側 `lanes/2`（切り捨て）本の点線を左右対称に配置 |

1車線の道路（未舗装路など）は分ける対向車線が存在しないため、中央線を引かない。

#### 点線（車線境界線・センターライン）

センターラインと車線境界線は SplineMesh の **Place モード**で、長さ2m（`dashLength`）のダッシュを4m周期（`dashSpacing`）で等間隔配置する。

- ダッシュのZ方向ピボットが端にあっても中心が配置点に一致するよう、Z方向のピボット補正を行う
- ダッシュが道路の端（交差点の切断面）から突き出さないよう、配置区間を両端から `dashLength/2` ずつ内側に制限する（`clipFrom`/`clipTo`）
- ダッシュ2個分に満たない短い区間には中央に1個だけ配置する

### 8.4 歩道（sidewalk）

道路の端に配置する。歩道は左右で形状を対称にするため、右側はメッシュを X 軸で反転させる。

- **リソースパス**: `Models/Paths/p{variant}/sidewalk`（フォールバックあり）
- **幅**: マスターデータの `sidewalk_width`
- **左側オフセット**: `-(width/2) + (sidewalkWidth/2)` = `-(width/2 - sidewalkWidth/2)`
- **右側オフセット**: `+(width/2 - sidewalkWidth/2)`
- **高さオフセット**: `SIDEWALK_ABOVE_SPLINE`（0.1m）。下端がbody上面と同一平面に接し、縁石の立ち上がりはプレハブ形状で表現する

#### 歩道のミラーリング

歩道パーツは**左側用**（縁石＝道路中心側の面が +X 側）として作り、左側はそのまま、右側は X 軸で反転（ミラー）して配置する。壁の右側用規約とは異なる。

ミラーリングの処理内容：
1. **頂点の反転**: 全頂点の X 座標を -1 倍する
2. **法線の反転**: 全法線の X 成分を -1 倍する（面の向きを正しく保つ）
3. **三角形の反転**: 三角形インデックスの順序を反転させる（カリング方向を修正する）

この3つの処理を組み合わせることで、反転後も面が正しい向きを向く。頂点反転で裏返った面を、三角形反転で元に戻すという考え方である。

### 8.5 防音壁・ガードレール（wall）

道路の左右端に配置する壁または柵。歩道の外側に設置される。

- **リソースパス**: `Models/Paths/p{variant}/wall`（フォールバックあり）
- **幅**: マスターデータの `wall_width`
- **オフセット**: `±((width/2) + (wallWidth/2))`
- **高さオフセット**: `WALL_ABOVE_SPLINE`（0.1m）
- **左右対称**: 右側用パーツの規約。右側はそのまま、左側は X 軸で反転（ミラー）して配置する
- **オプショナル**: `wall_width` が未設定（0以下）の場合は描画しない

### 8.6 道路ごとの付帯設備

付帯設備は `Path` の `streetlight_type`（街灯）、`fence_type`（歩車道境界の柵）、`street_tree_type`（街路樹）、`utility_mode`（配線方式）で選択する。各値は保存対象で、0は明示的な「なし」。種類は現在0/1（なし/標準）、配線方式だけ0/1/2（なし/架空/地中）を持つ。費用・治安・電力供給への効果はまだ持たない。

道路マスターは各項目の `*_allowed` と `default_*` を持つ。初期値は新設時にエンティティへ確定保存し、以後のマスター初期値変更で既存道路の設備は変わらない。`tree_spacing` は有無ではなく標準の配置間隔で、未設定または0なら20mを使う。基本断面（歩道幅など）と外側の構造壁 `wall` は従来どおり道路マスターで決まる。

`RoadEquipmentGenerator` は切断済みスプラインの両端から3mを空け、距離に基づいて配置する。街灯は24m間隔・開始位相6mで両側、電柱は32m間隔で右側、地上機器ボックスは64m間隔で右側、街路樹は標準間隔の半分だけ開始位相をずらして両側に配置する。ここでの右側はパスの始点→終点を基準とする。個別の左右指定は持たず、向きを反転して結合した場合は再配置される。

電柱/ボックス→街灯→街路樹の順に位置を確定する。3mグリッドの近傍検索で既存設備から2m（街路樹は3m）未満の候補を省略する。歩道がある道路では歩道中央、なければ道路端から0.3m内側に置き、接地高さは路面原点へ補正済みの床メッシュを使い、設置する横位置で三角形の上面を求める。bodyの未補正bounds上面や、歩道全体の最高点（縁石）を使ってはいけない。歩道の原点補正は採用モデルと同系列のbodyで行い、道路本体と同じ `GetRoadPartMesh` を使う。スプラインからの高さオフセットはワールド上方向、歩道の立ち上がりは断面法線方向に加える。設備は道路の勾配によらずワールド上方向へ直立する。長さ6m以下の描画区間には配置しない。

柵は歩道に含めず、歩車道境界から歩道側へ0.12mの位置に独立生成する。支柱は最大2m間隔で直立し、横桟は支柱間を結ぶ。終端では支柱と桟を閉じ、交差点内部の歩道コネクタへは接続しない。交差点・折れ線の角・地下道の描画区間分割では、それぞれの描画区間に端部余白を設ける。既存の外側 `wall` の交差点接続は変わらない。

モデルは `Models/Paths/p{variant}/{part}` → `p{type}/{part}` の順で解決する。点配置パーツは `streetlight` / `utility_pole` / `utility_box` / `tree`。点設備は接地面を原点に実寸で著作する。Blenderでは右側用として灯具を-Xへ向けるが、FBXの軸変換でUnityのX符号が変わるため、配置時は読み込み後のbounds中心Xから張り出し側を判定し、道路内側へ向ける。左側はさらにヨー180度回転する。旧共通モデルの原点ずれも考慮し、点設備のメッシュ下端を床へ合わせる。`fence` は支柱を含まない横桟/パネルで、高さ・横幅を保持しZ方向だけ支柱間長へ合わせる。標準支柱はコード生成される。

モデルがない設備は簡易形状で表示する。簡易形状は道路・材質ごとに結合し、生成Meshは `IntersectionMeshOwner` が解放する。専用マテリアルは `PATH_EQUIPMENT_METAL` / `CONCRETE` / `LAMP` / `LEAVES`（いずれも接頭辞 `PATH_EQUIPMENT_`）で差し替え可能。設備にクリック用Colliderやリアルタイム光源は追加しない。遠景は従来の簡易道路表示のみ。

架空配線の電線は同一描画区間内で隣接する実配置電柱の接地点+7.6mを結び、中央で0.4m垂らす。専用電柱もこの接続高さに合わせる。交差点を跨ぐ接続、建物への引き込み線、地中配線との接続設備は生成しない。地中配線では電柱と電線を省き、ボックスだけを別間隔で置く。

道路詳細パネルの「道路設備」タブで選択し、「適用」でPATCH後に差分リロードする。変更は設備選択のみに作用し、道路の基本断面・経済値を変えない。分割時は両側に設定を継承し、異なる設備設定の結合は拒否する。造り替え先に設置できない設備がある場合は、先に設備を外す必要がある。

道路詳細は経済主体詳細と共通のタブ表示を使う。「基本情報」に所属地区・物理状態、「交通」に制限速度・交通量、「道路設備」に設備設定をまとめる。設備非対応で既設設備もないパスでは設備タブを表示しない。駅舎には「駅情報」、計画中・建設中・解体中には「建設工事」を追加する。着工前は基本情報・交通・設備を省略し、着工前・建設中の初期選択は建設工事とする。タブ切り替えだけでは設備・速度の未保存の入力を破棄しない。

#### 設備モデルの収録範囲

設備を設置できる道路バリアントには、以下の専用FBXを `Assets/Models/Paths/p{variant}` に収録する。

| パーツ | バリアント | 外観 |
| --- | --- | --- |
| `streetlight` | 100 / 101 / 201 / 211 / 212 / 221 / 222 / 231 / 301 | 高規格道路は大型照明、細い道路は短いアーム、歩行者専用道路は低いランタン型 |
| `utility_pole` / `utility_box` | 201 / 211 / 212 / 221 / 222 / 231 | 木柱・コンクリート柱、碍子、変圧器、扉・通風口付き地上機器 |
| `fence` / `tree` | 221 / 222 / 231 | 横桟または縦格子のパネル、歩道幅に収まる樹冠の広葉樹 |

合計27点。柵パネルは長さ2m、高さ1m以下で、支柱は含まない。点設備は接地面を原点にした1メッシュで、道路本体のin-place高さオフセットを焼き込まない。
既存の共通街路樹 `p1/tree` / `p2/tree` はフォールバック用として保持する。
モデルの存在だけで設備は有効にならず、描画は個別道路の設備設定に従う。
FBXのインポート時に `ModelPrefabGenerator` がResources側のプレハブを生成する。

### 8.7 柱（pillar）とキャップ（pillar_cap）

高架道路など、路面が地面から離れているパスに対して、路面を支持する柱（およびキャップ）を配置する。これらは `height_editable=true` のバリアントに対してのみ配置される。

- **リソースパス**: 
  - 柱: `Models/Paths/p{variant}/pillar`（フォールバックあり）
  - キャップ: `Models/Paths/p{variant}/pillar_cap`（フォールバックあり）
- **配置対象**: `height_editable=true` かつ `pillar_spacing` が設定されているバリアント。地下パスには配置しない。

#### 配置間隔

スプラインに沿って配置する。各セグメント（始点→ウェイポイント、ウェイポイント→ウェイポイント、ウェイポイント→終点）について以下のルールで配置する。

- **パス全体の開始点と、各セグメントの終点に配置する（これにより、開始点・中間アンカー点・終了点のすべてに配置される）**
- セグメントのスプライン上の長さが `pillar_spacing` を超える場合は、その間隔で追加配置する

#### 柱とキャップの配置とスケール

- **垂直保持**: 柱・キャップとも地形の傾斜に追従して斜めに立たず、**常にワールド上方向に対して垂直に立つ**。回転は進行方向の水平成分から導出したYawのみ（ピッチ・ロールは0）とする。
- **キャップ（pillar_cap）の配置**:
  - プレハブが存在する場合、スプライン上の路面位置（`sample.position`）にYスケールを変更せずにそのまま配置する。
  - 原点（ピボット）は路面原点（上端）とし、モデルは `-Y` 方向に厚みを持つものとする。
  - キャップの厚み `capThickness` は、プレハブの `MeshFilter` の `bounds` から `-bounds.min.y` として動的に計算される。
- **柱（pillar）の配置**:
  - プレハブが存在する場合、キャップがあるときは `capThickness` 分だけ下方向（常に `Vector3.down`）にオフセットした位置に配置する。
  - 柱の原点（ピボット）も路面原点（上端）とする。
  - Yaw-only 回転でローカルY軸がワールド上方向と一致するため、Yスケールにオフセット後の位置から地面（Y=0）までの高さをそのまま適用し、柱の下端が地面に接するようにする。
  - 残りの高さ（柱を配置すべき高さ）が `0.1m` 未満の場合は、柱（pillar）本体は配置せず、キャップのみを配置する。

#### プレハブの著作規約（Yスケールの帰結）

Yスケールは「柱を配置すべき高さ（m）」**そのもの**を倍率として掛ける。著作寸法がそのまま倍率になるため、モデル側は次の作法で作る必要がある。

- **柱（pillar）の天端は必ず原点（ローカル Y=0）に置く。** 天端を原点より下に著作すると、そのオフセットにも倍率が掛かって沈むため、`天端Y × 高さ < −高さ` が常に成り立ち、**どんな高さの高架でも橋脚が丸ごと地面より下に潜って一切描画されなくなる**。
- **柱の下端は、想定する最大の高架高さぶん（既存アセットは 2〜8m）だけ下方向へ伸ばしておけばよい。** 倍率で伸びすぎたぶんは地中に隠れるだけで実害が無い。柱は一様断面（またはゆるいテーパー）にしておくと、倍率が変わっても見た目が破綻しない。
- **Yスケールを掛けたくない造形（橋脚梁・パイルキャップ・ハンチ・門型ラーメンの横梁）は `pillar_cap` 側へ分ける。** キャップは実寸のまま路面位置に置かれ、その厚みぶん柱が下げられるので、キャップの最深部と柱の天端（Y=0）が自動的に噛み合う。

この規約は `genesis-gallery` のバリデータ（`pillar-top-offset`）で機械検査している。

#### base_height（3D描画用の高さオフセット）

`base_height` は**3D描画のみに影響する高さオフセット(m)** で、ゲームロジック（経済シミュレーション・経路探索・交差判定等）には一切影響しない。

パスの相対高さ(relY)から `base_height` を引いた値を「3D描画用の実効高さ」として扱い、`CalculatePathPoints` が返す全サンプル点のY座標から `base_height` を引く。これにより、スプライン・メッシュ・柱がすべて `relY - base_height` の高さで描画される。

```
3D描画用の実効高さ = relY - base_height
```

- `base_height = 0`（既定）: シフトなし。従来動作。
- `base_height = 20`（例: 高圧送電線）: `relY=20` で敷いたパスは3D上は高さ0m（地面）として描画される。プレハブモデル自体が20mの高さを持つことで、送電線が地上を這わずに適切な高さに見える。`relY=25` にすれば3D上は5mの高さとして描画され、柱が5m分伸びる。

バックエンドのロジック・交差判定は `CalculatePathPoints` を使わず、パスデータの `relY` をそのまま使用するため、`base_height` の影響を受けない。

## 8.8 地下パス（トンネル）の描画区間分割

負の相対Yを持つアンカーがあるパス（地下パス）は、点列をそのまま1本のスプラインにせず、サンプル点ごとのトンネル判定で「描画する連続区間」に分割してから、区間ごとに通常のメッシュ生成器（RoadPath / TrackPath）を呼ぶ（`PathManager.GenerateUndergroundPathMesh` / `TunnelSectionUtil`）。

- **トンネル判定**: サンプル点で `現在の地形標高 − 道路Y > クリアランス高さ（マスターの height）` ならトンネル区間。両端点がともに地表に張り付いている（|地形−Y| ≤ 0.5m）区間は地形追従区間とみなし、深さ0（描画対象）として扱う。
- **開削区間との整合**: バックエンドは着工時に開削区間（深さ ≤ height）の地形を道路標高まで掘削する。掘削後の地形ではその区間の深さが約0になるため、Unity側の判定は自動的に「開削区間＝描画、トンネル区間＝非描画」となり、バックエンドの区間分類（[3_道路網](../economics/3_道路網.md)参照）と整合する。建設前（PENDING・プレビュー）は元地形に対する判定となり、これもバックエンドの分類と一致する。
- **境界と坑口**: 区間の境界は深さがちょうど height になる位置を隣接サンプル間の線形補間で求める。各境界には `portal` パーツ（バリアント→タイプのフォールバック）を、トンネル内部方向を向けて配置する。プレハブ未整備時はスキップされる（オプショナルパーツ）。
- **コライダー**: 描画区間のストリップメッシュを結合したものになる。トンネル区間はクリック判定を持たない。
- **Farティア**: 地下パスは遠景の簡易表示（始点終点の直線ストリップ）を行わない。直線ストリップは埋設区間を無視して地表を横切ってしまうため、Farティアでは非表示とする。
- **柱（pillar）**: 地下パスには配置しない。

## 9. マテリアルの割り当て

SplineMesh でパーツを配置する際、プレハブに設定されたマテリアル情報を引き継ぐ。ただし、FBX からインポートされたマテリアルは Unity 内のマテリアルアセットと対応が取れない場合があるため、以下の再割り当てロジックを使用する。

1. プレハブの `MeshRenderer.sharedMaterials` から元のマテリアル配列を取得する
2. 各マテリアルについて、その名前で `Resources.Load<Material>()` を試みる
3. Resources に同名のマテリアルがあればそちらを使用し、なければ FBX 由来のマテリアルをそのまま使用する

これにより、Blender 等の DCC ツールで設定したマテリアル名と同名の Unity プロジェクト内マテリアルが自動的に対応付けられる。**Resources 側にマテリアルを置くことが、コードを変更せずに路面の見た目（シェーダーを含む）を差し替える唯一の口**である（未舗装路の `PATH_SAND` はこの仕組みで専用シェーダーを当てている。§16 参照）。

## 10. コライダーメッシュの生成

### 10.1 目的

SplineMesh は子オブジェクトとして生成されるため、親オブジェクトの `MeshCollider` には自動的には反映されない。クリック判定等の物理用途のために、道路全体を覆う簡易的なコライダーメッシュを別途生成する。

### 10.2 RoadPath の場合

1. 構築済みの `SplineComputer` に沿って等間隔（1m間隔）でサンプリングし、`List<Vector3>` を得る
2. `PathMeshFactory.BuildStripMesh()` にサンプリング点と道路幅を渡してストリップメッシュを生成する

### 10.3 BuildStripMesh のアルゴリズム

ポイント列を折れ線とみなし、各点で進行方向に垂直な方向に左右 `width/2` ずつ頂点を置いてストリップ状のメッシュを構築する。各点での方向ベクトルは、前後の点とのベクトルを平均してスムージングする。UV座標は累積距離に基づいて割り当てる。

### 10.4 返却

生成されたコライダーメッシュは `PathMeshResult.Mesh` として返される。`PathMeshResult.ModulesCreated` は `true`（SplineMesh が視覚的メッシュを担当しているため親の MeshRenderer は不要）、`GeneratedObject` は道路のルートコンテナである。`PathManager.CreateOrUpdatePath()` で `MeshCollider` コンポーネントにこのメッシュが設定される。

## 11. 交差点と断面の接合

### 11.1 共通の切断断面

`PathManager` は交差点の影響を受けない描画点列を `CalculatePathPoints(path, false)` で生成し、`NodeMeshFactory` に渡す。`IntersectionPolygonUtil` はこの点列上に `PathEndSection`（ワールド位置、外向き接線、法線、全幅、切断距離）を作る。点列が供給されないテストや仮想ノードでは `SamplePlan` が端点制御点・ウェイポイントを評価する。

`ConnectionPoints` はこの断面の中心を返す。本線は `Trim` によって元の点列の必要区間だけを保持する。車道・歩道・壁・レールは同じ切断断面を参照し、保存データの端点を移動しない。

ウェイポイントのない直線も、地形追従のサンプリングを切断前に行う。描画時に切断後の長さでサンプリングし直さない。折れ線道路の角は前後のアンカーから仮想入口を作り、各スパンの45%を上限に接合する。歩道がない場合も壁・中央分離帯のコネクタを生成する。

### 11.2 外周と路面

入口断面を外向き方向の角度順に並べ、隣接する入口の外縁を端部接線付きの三次ベジエで結ぶ。`IntersectionCorner` の点列・方向を路面、歩道、壁が共用する。凸包で外周を塗り潰さないため、曲がった壁の外に余分な舗装が残らない。

一直線の2本でも移行区間を生成する。異幅の入口間では外周が滑らかに変化し、幅変更を1点の段差にしない。三角形化は耳切り法で行い、失敗時に凹多角形をファンで埋めることはしない。

路面高さは本線の切断断面を境界条件として補間する。入口では本線と同じワールド上方向の `BODY_ABOVE_SPLINE` を適用し、坂道でも境界を合わせる。モデル自体の厚みは断面法線方向に向ける。bodyプレハブの全高から底面・外周の小口も作る。これは汎用の厚み補間であり、橋桁の内部構造を再現するものではない。

### 11.3 歩道・壁・中央分離帯

幾何情報は互換性のため `SidewalkConnectorSpec` に集約し、`Part` が `sidewalk` / `wall` / `center` / `line` を区別する。`RoadPath.CreateSidewalkConnectorObject` は通常道路と同じプレハブを細かいタイルとして変形して生成する。

- 歩道は共通外周の内側、壁は外側に配置する。幅を滑らかに補間し、端の向きは本線の断面に合わせる。
- 歩道幅の補間はX方向だけに適用する。`SplinePoint.size`で縁石の高さまで拡大縮小しない。
- 歩道が途切れる場合は、切断面の道路外縁を中心に、半径＝歩道幅の四分円の扇形を作る。縁石を道路外側へ90度回し、幅をゼロに絞った尖端にはしない。本線の歩道を別距離で後退させない。壁・中央分離帯の片側終端は先細りとする。
- 異なるプレハブ間では開始側の形状を使用し、高さを相手側のbounds高さへ補間する。異なる装飾や断面トポロジーの完全な形状モーフィングは行わない。
- ほぼ対向する2本道路の中央分離帯は接続し、多叉交差点では各入口で先細り終端にする。
- 2本道路の移行部では側線を接続する。中央分離帯が無い場合は車線境界の横位置を対応付け、車線数の変化を表現する。
- 駅ホーム側の壁は生成しない。交差点内のレール通路に干渉する壁コネクタも除外する。

生成メッシュは `IntersectionMeshOwner` が所有し、オブジェクト削除・再生成時に解放する。

### 11.4 線路と踏切

レールの配置位置も共通断面から求める。軌道数が異なる場合は、横位置順を保つ多対一対応で実際の各軌道端へ接続する。中心線1本への置き換えは行わない。曲線端部には本線の方向と勾配を適用し、軌間は伸縮しない。

転回可否は保存された論理端点の接線で判定し、切断後の描画接線とは区別する。曲線は端点制御点を優先し、折れ線は隣接アンカー方向を使う（バックエンド `path_end_tangent` と同じ）。線路とモノレールの間にレール接続は作らない。道路×線路では道路の路面材質を優先し、その上に通行可能な線路ペアのレールを配置する。

### 11.5 接合距離と縮退配置

切断距離は幅・進入角度・外周の移行余裕から求める。反対側にも交差点があるパスでは、各端に全長の45%までを予約して切断区間の逆転を防ぐ。反対側が終端なら95%まで使用できる。折れ線・single_spanでは次のアンカーを越えない。

この範囲に入口断面が収まらず外周が自己交差する場合、`RequiresMoreSpace` として接合を見送る。無効なポリゴン修復で入口を欠落させず、古い切断情報を解除して本線を元のノードまで描く。**近接交差点の自動一体化は未実装**であり、幅に対して極端に短い枝や同方向の重複パスではパーツ同士の重なりが残り得る。

### 11.6 材質と検証

材質は道路を線路より優先し、同分類では最大variantの `body_material`、bodyプレハブ、共通路面の順に解決する。交差点を複数材質へ領域分割する処理はない。UVに依存する路面テクスチャには従来の制限が残る。頂点カラーは白（α=1）を明示する。

`unity/Tests/Intersections/run.ps1` はUnity生成csprojで本体をビルドしてから、実際の幾何計算を.NET上で検証する。幅・角度・枝数・長さの組合せ、入口の境界一致、入力順への非依存性、切断による内部点の保持、保存制御点の優先順位、空間不足時の安全な失敗を確認する。

`run-unity.ps1` は独立した検証用Unityで実際の描画コードとFBXを使い、傾斜三叉路の路面・付属パーツの端を本線の頂点と比較する。道路と線路の混在、複線→単線、歩道なしの折れ点の壁も検査する。全モデル・全地形・全LODを網羅するものではない。実行条件と出力先は同ディレクトリのREADMEを参照する。

## 14. max_span バリデーション

### 14.1 概要

`height_editable=true` のバリアントに対して、始点・終点・ウェイポイント間の1区画の長さが `max_span` を超えないように制限する。これは柱（pillar）を持つ高架道路などの構造上の制約であり、過度に長い区画ができないようにする。

### 14.2 計算方法

バリデーションでは**水平距離（XZ平面）**を計算する。高さ方向（Y軸）の差分は距離計算に含めない。曲線の長さは考慮せず、アンカー点間の直線距離で判定する。

### 14.3 フロントエンド（Unity）

道路エディタ（`RoadPlanManager`）では、ユーザーがポイントを移動した時点でリアルタイムに `max_span` をチェックする。`max_span` を超えるセグメントが存在する場合は以下のフィードバックを行う。

- **視覚的フィードバック**: 違反セグメントを赤色の太線でハイライトする
- **テキスト警告**: 画面上部に「セグメントの長さが制限を超えています（最大 {max_span}m）」という赤色のテキストを表示する

### 14.4 バックエンド（Python）

パスの作成（`POST /api/v1/paths`）と更新（`PATCH /api/v1/paths/{path_id}`）時に `max_span` バリデーションを行う。`height_editable=true` のバリアントに対してのみチェックする。

バリデーションに失敗した場合は `ValidationError` を発生させ、エラーメッセージには超過しているセグメントのインデックスと長さを含める。

## 15. 工事中（STATUS_CONSTRUCTING）のパス表示

status が `STATUS_CONSTRUCTING` のパスは、完成品のパーツ（body / line / sidewalk 等）を一切描画せず、専用の「工事現場」表示で描画される。分岐は `PathManager.CreateOrUpdatePath` のメッシュ生成部にあり、`model_type` に関わらず全パス種（道路・線路）に適用される。ただし **`model_type = "none"`（公共交通の路線等、完成時も描画しないパス）は工事中も非表示のまま**である。

なお、旧仕様の「完成品メッシュに黄色い建設中マテリアルを上塗りする」表示は廃止された。

### 15.1 土ストリップ

経路全体を、厚みとランダムな凹凸を持つ土の帯で覆う（`ConstructionMeshUtil.BuildDirtStripMesh`）。

- **高さは常に地表**: 各サンプル点のY座標はパスの相対高さを使わず、そのXZ位置の地形標高 + `ROAD_SPLINE_OFFSET` に置く。**高架のパスでも土は地表に盛られ、柱だけが立っている**工事現場の見た目になる
- **幅** = マスターの `width` + 余白（1m）を基準に、低周波ノイズで左右独立に±15%揺らす（直線的な輪郭を崩し、盛り土らしい不定形の縁にする）
- **断面**は「左右端2頂点（地表に接地）+ 中央寄り2頂点（厚み + 土ノイズで盛り上げ）」の台形マウンド。左右端が接地するため地形との隙間ができない。両端は端面キャップで閉じる
- **凹凸**は多オクターブのPerlinノイズ（fbm。波長 約6.7m / 2.5m / 1.1m の3オクターブ）で、大きなうねりと細かい起伏を重ねる。建物の土マウンドと共通の `ConstructionMeshUtil.DirtNoise`。ノイズ入力はワールド座標なので再生成しても模様は安定する
- **UV**はワールドXZ座標ベース（×0.1）。マテリアル側の模様が経路の伸縮で歪まず、隣接区間とも連続する
- **マテリアル**は建物の土マウンドと共用の `Resources/ConstructionDirt`（未配置時は `ConstructionMaterial`（黄色）→ デフォルトにフォールバック）。`RoadPath.GetOrCreateRoadMaterial` のキャッシュを経由し、renderQueue 補正（Z-fighting 対策）にも相乗りする

### 15.2 高架の柱

`height_editable=true` かつ `pillar_spacing` を持つバリアントは、完成時と同じ `RoadPath.GeneratePillars` で **pillar / pillar_cap パーツだけ**を配置する。柱の配置位置・垂直保持・キャップの扱いは §8.7 と同一で、柱高が 0.1m 以下になる地上区間には柱が立たないため、高架区間にだけ柱が並ぶ。

### 15.3 トンネル

地下パスは完成時と同じ描画区間分割（§8.8）を行い、**描画区間には土ストリップを、区間境界には portal パーツを**配置する。トンネル区間は何も描画しない（＝工事中のトンネルは「坑口と、その手前の土」だけが見える）。

### 15.4 進捗・コライダー・その他の扱い

- **進捗による見た目の変化はない**（静的な表示）。建物と異なり、パスの version は進捗では上がらない。status の変化（着工・完成）で必ず再生成され、完成時は通常メッシュへ自動的に切り替わる
- **コライダー**は土ストリップの結合メッシュ。クリック（詳細ウィンドウ）は工事中も機能する
- **Farティア**は現状のまま（通常の簡易表示。遠景では工事中の見分けを行わない）
- **交差点メッシュ**（§11）も現状のまま生成される。工事中パスも切断点で端点が切り詰められ、土ストリップは切断済みの点列から作られるため整合する。交差点のアスファルトが工事中でも描かれるのは既知の割り切り

## 16. 未舗装路の路面表現（Custom/PathDirt）

未舗装路（`path_variant` 201）の body は、舗装路のような「端までベタ塗りの帯」ではなく、**地面に踏み固められた土の道**として描く。テクスチャは使わず、ワールドXZ座標の手続きノイズと頂点カラーだけで表現する。

- シェーダー定義: `Assets/Resources/Shaders/PathDirt.shader`（パス構成）
- 本体: `Assets/Shaders/PathDirt.hlsl`（シェーディング）
- マテリアル: `Assets/Resources/PATH_SAND.mat`

### 16.1 3つの層

| 層 | 内容 |
| --- | --- |
| 土の色ムラ | 大スケールの fbm で主色↔副色を混ぜ、細スケールの fbm で明るい砂利の斑を散らす |
| 細かい凹凸 | 同じ細スケールノイズの勾配で法線を微小に傾け、平面のノッペリ感を消す |
| 縁の侵食 | 頂点カラーのアルファを縁マスクとして、ワールド座標のノイズでアルファクリップし、路肩をギザギザに溶かす |

ノイズの入力はすべてワールドXZ座標なので、**UV・タイリング・頂点密度に依存しない**。SplineMesh の Extrude はタイル（既定 2.5m）ごとに UV を繰り返すため、UV ベースの模様だとタイル周期の反復が目に見える。

### 16.2 頂点カラーの規約（モデル側の契約）

body プレハブは、路面の外側に**下向きに垂れる「なじませスカート」**を持ち、その頂点にアルファを塗る。

| 頂点カラーのα | 意味 |
| --- | --- |
| 1.0 | 路面の中核。絶対に抜けない |
| 0.0 | スカートの外端。ほぼ完全に抜ける |
| 中間 | スカートを横断する線形グラデーション |

路面上面は地形+0.2m（§4.4 / `RoadPartHeights`）にあるため、スカートの外端をローカルY −0.3m 程度まで垂らすと平地でも確実に地形へ潜る。これにより**見える境界が「スカートと地形の交線」**になって直線でなくなり、その上にノイズの侵食が乗って砂利が草に食われるような縁になる。

Dreamteck の SplineMesh は元メッシュの頂点カラーをそのまま出力へ透過するため（`SplineMesh.cs` のチャンネル書き込み）、Extrude されたタイル列でも規約が保たれる。

body の公称幅は最上面の幅（§4.4）であり、下向きのスカートや桁の張り出しは含めない。スカートを広げても路面幅は変わらない。

### 16.3 アルファブレンドではなくクリップである理由

路面は地形から浮いた板なので、半透明にすると板の下の隙間が透ける。クリップ（cutout）なら抜けた部分は地形がそのまま見えるだけで済み、**不透明キューのままなので `GetOrCreateRoadMaterial` の renderQueue 補正や ZWrite の前提も壊れない**。キューは `AlphaTest`（RenderType は `TransparentCutout`）。

### 16.4 パス構成と切り抜きの一貫性

ForwardLit / ShadowCaster / DepthOnly / **DepthNormals** の4パス構成。DepthNormals は `PC_Renderer` の SSAO（Source = DepthNormals）が前段パスとして要求するため必須で、省くと未舗装路だけ SSAO と深度テクスチャから抜け落ちる（水面シェーダーの深度参照にも影響する）。

**全パスが同じ切り抜き関数（`PathDirtClip`）を通る。** パスごとに輪郭が食い違うと、抜けたはずの路肩が影や SSAO に残る。

### 16.5 遠景でのチラつき対策

プロジェクトは MSAA 無効（`PC_RPAsset`）のため、クリップ境界はアンチエイリアスされない。遠景ではノイズの粒がピクセル以下になってチラつくので、カメラ距離に応じて**ノイズを平均値（0.5）へ寄せて**縁を滑らかな線に戻す（`_EdgeDetailFadeDistance`）。侵食量そのものを0へ戻すのではなく平均へ寄せるため、**縁の平均位置が変わらず、遠近で道路幅が太った／痩せたように見えるポップが起きない**。

### 16.6 適用範囲の制限

**このシェーダーは規約どおりに頂点カラーを持つメッシュ専用**で、他の道路 body へ流用してはいけない（頂点カラーのない body に適用すると縁マスクが不定になる）。

交差点ポリゴン（§11）はこのマテリアルを共有しうる（未舗装路と舗装路が接続するノードでは variant 番号が大きい未舗装路側が代表に選ばれ、そのマスターの `body_material`＝`PATH_SAND` が交差点にも適用される）。`ConvertGeometryToMesh` は依存を明示するため**白（α=1＝侵食なし）を明示設定する**。既定値に依存すると交差点が丸ごと切り抜かれて消える事故になりうる。

maxTileLengthを0以下にして著作周期を保つ連続パーツは、頂点数上限時に整数タイル単位で別SplineMeshへ分割する。区間全体のタイル数を減らして造形を引き伸ばさない。通常の道路用タイル上限やsingle_spanにはこの分割を適用しない。
