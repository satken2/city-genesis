# O. 車両の走行描画

## O.1. 概要

道路の上を車が走る様子を描画する仕組みである。カメラ周辺の道路ごとに、パスの**交通量（`path_traffic`）**から求めた**目標台数**（物理的な同時存在台数 × 演出倍率、O.4 参照）を定め、不足分を道路上のランダムな地点（沿道の建物から出てきた車を表す）へ補充スポーンする。車は**走行方向（`travel_direction`）**を尊重して走り、交差点で交通量に応じて確率的に分岐する。乗り換え先の道路が目標台数を超えている場合は「沿道の建物に到着した」とみなして途中降車（デスポーン）し、範囲外に出た車もデスポーンする。

この目標密度への自己調整により、各道路の車の密度は常に `path_traffic` に比例した水準に保たれる。実世界の交通と同じく、車は道路の途中で発生・消滅する（建物への出入り）。`path_traffic` は地区間ルートに沿って加算される負荷であり、ルートの起終点で交通が発生・消滅する情報を含むため、下流ほど交通量が減る道路では描画上も車が減っていく。また、カメラを遠くへジャンプさせた場合も、移動先の道路が即座に適正密度まで充填される。

この描画は**純粋な演出**であり、経済シミュレーションには一切影響しない。バックエンドは車を1台ずつシミュレートしておらず（[事故と災害](../economics/20_事故と災害.md) 参照）、車の位置・台数はクライアント（Unity）側で手続き的に生成する短命オブジェクトである。したがって：

- サーバー永続エンティティではないため、パス（[パス形状](A_パス形状.md)）や建物のようなセル単位のロード/アンロードには載せない。
- 他の車との**当たり判定は行わない**。信号待ちも考慮しない。
- ロードするのは `PathManager` が既に取得済みのパスデータ（`pathDataCache`）であり、車描画専用のAPI取得は行わない（通行方向の取得を除く。O.6 参照）。

当面はすべて単純な箱で描画するが、将来的に「車種ごとに異なる fbx」「同一車種内でもランダムに複数 fbx」へ拡張できる構造を持つ（O.5）。設計は[追加コンテンツとアセットパック](../programs/追加コンテンツとアセットパック.md) の `ModelManager` 解決層（論理パス → 物理アセット）と整合する。

## O.2. 入力データ

車描画は既存のパスデータ2種と都市設定1つを入力とする。いずれも新規のバックエンド構造は増やさない。

### 交通量 `path_traffic`

パスごとに記録される**車種別**の交通量。`VEHICLE_*`（`VEHICLE_STANDARD=10` 乗用車 / `VEHICLE_TRUCK=11` トラック / `VEHICLE_BUS=12` バス / `VEHICLE_COMMERCIAL=13` 商用車 …）をキーとする dict で、値は**1日あたりにそのパスを通過するトリップ数**（台/日、[道路網](../economics/3_道路網.md) 参照）である。この値が目標台数と交差点での分岐確率の重みになる。

- **目標台数**: 範囲内パス（O.4）× 車種ごとに目標台数を定める（計算式は O.4 参照）。スポーン・途中降車はこの目標との差分で駆動される。
- **分岐の重み**: 交差点で次のパスを選ぶとき、各候補パスの `path_traffic[車種]` を重みにした重み付きランダムで曲がる方向を決める。

!!! note "バルク配信について"
    `path_traffic` はパス詳細（`PathData`）とバルクのパス一覧（bbox の `PathSummary`）の両方に含まれる。Unity 側は**リフレクションで読み取り、フィールドが無いスキーマでも落ちない**（無ければ集計値 `utilization` を乗用車の代替として使う暫定 degrade）実装になっている。

### 走行方向 `travel_direction`

パスのジオメトリ方向（`start_point → end_point`）に対する通行可否。`DIR_BOTH=0`（双方向）/ `DIR_FORWARD=1`（start→end のみ）/ `DIR_BACKWARD=2`（end→start のみ）。スポーン時・交差点分岐時に、そのパスへ入る向きが許可されるかの判定に使う（O.4）。`PathSummary` に既に含まれる。

### 通行方向（左側/右側） `traffic_hand`

車をどちらの車線に寄せるかの都市設定。`city` の `traffic_hand`（`0`=左側通行 / `1`=右側通行、既定=左）。`GET /api/v1/city` で配信し、Unity は起動時に一度取得する（取得失敗時は既定=左側通行）。変更UIは後日実装予定。

## O.3. 描画範囲

「カメラから一定距離」の範囲は、**カメラ注視点を中心とした半径**で定義する。

- 中心: `CameraCellChecker.CurrentWorldPosition`（カメラ中央のレイと地面 y=0 平面の交点）。
- 半径: `renderRadius`（既定 400m ≒ [LOD処理](E_LOD処理.md) の Dynamic 相当）。
- デスポーン: 車のワールド座標（XZ距離）が `renderRadius + despawnMargin`（既定 +80m）を超えたらデスポーンする。

判定は XZ 平面距離のみ（高さは無視）で行う。

## O.4. スポーン・走行・デスポーン

### 範囲内パスの抽出と目標台数

一定間隔（`rangeScanInterval`、既定 0.5 秒）で「範囲内パス」を再スキャンしてキャッシュする。範囲内パスとは、ロード済みの走行可能な道路（`PATH_MOTORWAY` / `PATH_STREET`、`STATUS_ACTIVE`）で、中心線が描画円と交わるものを指す。

- 中心線のうち円内にある区間 `[sIn, sOut]` を求める（円との交点は隣接頂点の距離を線形補間して近似）。円を複数回出入りするパスは「最初の進入点〜最後の退出点」で1区間に丸める。
- 範囲内パス × 車種ごとに **目標台数** = 物理的な同時存在台数 × `timeExaggeration` を算出する。物理台数は「流量[台/s]（= `path_traffic[車種]`[台/日] ÷ 活動秒数（`activeHoursPerDay` × 3600））× 円内区間の通過時間[s]（= 円内区間の長さ ÷ 車種の走行速度）」の期待値で、実スケールではほぼ0台になるため、演出倍率 `timeExaggeration` で時間を圧縮して見た目の賑わいを作る。円外にはみ出す部分は目標に含めない。
- あわせて、(パス, 車種) ごとの**現在の走行台数**をスポーン・乗り換え・デスポーンの各時点で増減カウントし、常に維持する。

### スポーン（不足補充）

範囲内パス × 車種ごとに、不足分 = 目標台数 − 現在台数 を計算し、毎フレーム確率 `p = 不足分 × spawnFillRate × Δt` でスポーンを抽選する（フレームレート非依存のポアソン過程）。不足分が大きいほど速く補充され、目標密度へ指数的に収束する。同時存在数が `maxActiveVehicles`（既定 300）に達したら抑止する。

- スポーン位置は円内区間 `[sIn, sOut]` 上の**ランダムな地点**とする（沿道の建物から道路に出てきた車を表す）。
- 走行向きは `travel_direction` が許す向き。双方向ならランダムに選ぶ。
- カメラを大きく動かした直後は、移動先の範囲内パスがすべて不足状態になるため、数秒で適正密度まで一気に充填される。

生成した車には車種係数（トラック/バスは遅め）と個体ばらつきを掛けた速度を与える。

### 走行

各フレーム、車は中心線に沿って進行方向へ距離を進める。位置は中心線を距離パラメータで補間して求め、**進行方向に対して `traffic_hand` の側へ横オフセット**（左側通行なら進行方向左）した車線中心に配置し、接線方向へ向ける。

### 交差点での分岐

パスの端（ノード）へ到達したら、次のパスへ乗り換える。

- 候補は `PathManager.GetPathsConnectedToNode(nodeId)` で得た、そのノードに接続する走行可能な道路。**現在のパスは除外**（Uターン回避）。
- 各候補について、ノードが `start_node_id` 側なら前進・`end_node_id` 側なら後退で入るものとし、その向きを `travel_direction` が許可するものだけ残す。
- 残った候補を `path_traffic[車種]` を重みにした重み付きランダムで1つ選ぶ。全候補が交通量0の場合のみ均等ランダムで選ぶ（交通量0の道路は「他に行き先が無いときの逃げ道」であり、通常時の分岐先には混ぜない）。
- 有効な候補が無い（行き止まり等）ときはデスポーンする。

### 途中降車（目標超過デスポーン）

分岐先を決めた後、その乗り換え先パスが描画範囲内で、乗り換え後の台数が目標台数を超える場合、超過度に応じた確率 `p = arrivalDespawnStrength × (1 − 目標台数 / 乗り換え後台数)` で「沿道の建物に到着した」とみなしてデスポーンする。

この仕組みにより各パスの車密度が目標（= `path_traffic` 比例）へ自己調整される。交通量の少ない道路には車が滞留せず、下流ほど交通量が減る道路では実際に車が減っていく。交通量0のパス（目標0）へ乗り換える車は、`arrivalDespawnStrength = 1` ならほぼ確実に降車する。

### travel_direction フィルタ

ノード N からパスへ入れるかの判定：

| 入る向き | 許可される `travel_direction` |
| --- | --- |
| 前進（N が `start_node_id`、start→end） | `DIR_BOTH` または `DIR_FORWARD` |
| 後退（N が `end_node_id`、end→start） | `DIR_BOTH` または `DIR_BACKWARD` |

## O.5. モデル解決と拡張性

車種（+バリアント）から描画用オブジェクトを解決する層を持ち、[建物メッシュ](F_建物メッシュの生成.md)・[地形プロップ](M_地形プロップ.md) と同じく `ModelManager.GetModel(論理パス)` を単一の入口とする。解決順は次のとおり：

1. `Models/Vehicles/{車種}/{バリアント}`（車種内で複数モデルを持つ場合）
2. `Models/Vehicles/{車種}`（車種単一モデル）
3. `Models/Vehicles/{VEHICLE_STANDARD}`（汎用車フォールバック）
4. いずれも無ければ**単純な箱**（車寸の Cube、車種別に色分け。fbx 導入までの暫定）

車種内の複数バリアントは、[地形プロップ](M_地形プロップ.md) の `seed` 方式と同様に、車1台の乱数シードから決定的に1つを選ぶ。どの車種にどのバリアントがあるかは任意の設定ファイル（`Resources/Config/vehicle_model_config.yaml`、`agent_model_config.yaml` と同形式）で「車種ID → バリアント一覧」を宣言する。未定義の車種は上記フォールバックで動作する。

この設計により、**箱 → 車種別 fbx → 車種内ランダム複数 fbx** を段階的に拡張できる。物理配置は将来のコンテンツパック（[追加コンテンツとアセットパック](../programs/追加コンテンツとアセットパック.md)）の論理パス解決にそのまま乗る。

生成した車は車種+バリアント単位でプールし、デスポーン時に破棄せず再利用する。

## O.6. データフローと関連コンポーネント

```
GET /api/v1/city ─ traffic_hand ─┐
                                 ▼
PathManager（取得済み pathDataCache: path_traffic / travel_direction / ノードグラフ / 中心線）
   │  GetAllPaths / TryGetPathPolyline / GetPathData / GetPathsConnectedToNode
   ▼
VehicleManager（毎フレーム: 範囲内パス抽出+目標台数算出 → 不足補充スポーン → 走行 → 交差点分岐/途中降車 → 範囲外デスポーン, プール管理）
   │  ModelManager.GetModel("Models/Vehicles/{車種}/{バリアント}")
   ▼
車オブジェクト（箱 or fbx）を中心線上に配置
```

- 中心線・ノードグラフ・パス属性はすべて `PathManager`（[バックエンドデータロード](H_バックエンドデータロード.md)）が既に取得済みのものを再利用する。中心線は curved パスではベジエサンプリング済み・地形追従済みの点列（[パス形状](A_パス形状.md)）。
- 描画範囲の中心は `CameraCellChecker`、範囲区分の目安は[LOD処理](E_LOD処理.md) の Dynamic 距離に準じる。

## O.7. 調整パラメータ

| パラメータ | 既定 | 意味 |
| --- | --- | --- |
| `renderRadius` | 400m | 車を走らせる半径 |
| `despawnMargin` | 80m | この余白を超えたらデスポーン |
| `timeExaggeration` | 60 | 時間圧縮の演出倍率。1=物理的に正確な同時存在台数（ほぼ0台） |
| `activeHoursPerDay` | 15h | 交通が流れる1日の活動時間。バックエンドの `PATH_ACTIVE_HOURS` に合わせる |
| `spawnFillRate` | 1.0 /s | 目標台数への不足分を1秒あたりに埋める割合 |
| `arrivalDespawnStrength` | 1.0 | 目標超過パスへ乗り換えた車が途中降車する確率の強さ（0=無効） |
| `maxActiveVehicles` | 300 | 同時存在数の上限 |
| `rangeScanInterval` | 0.5s | 範囲内パスの再スキャン間隔 |
| `baseSpeed` | 12 m/s | 基準速度（車種係数・個体ばらつきが乗る） |
| `laneOffset` | 2.5m | 中心線からの車線オフセット |

`path_traffic` は1日あたりの通過トリップ数（台/日）である。1日34台の道路を物理的に正確に描くとほぼ常に0台で画面が死ぬため、`timeExaggeration` で時間を圧縮して賑わいを誇張する。倍率を1に近づけるほどリアルに、大きくするほど賑やかになる。見た目が適切になるよう `maxActiveVehicles` とあわせて調整する前提である。

## O.8. 現在の実装状況と今後

- 実装済み: 目標密度ベースの不足補充スポーン（道路途中からの発生）／中心線走行（左側通行のレーンオフセット）／交差点の確率分岐（`travel_direction` 尊重）／目標超過時の途中降車デスポーン／範囲外デスポーン／プール／箱フォールバック描画／`traffic_hand` の city 設定・配信。
- 未実装（拡張余地）: 車種別・車種内ランダムの fbx プレハブ（`Models/Vehicles/...` と `vehicle_model_config.yaml` の実データ）／通行方向（左右）の変更UI／線路上の車両描画（同じ仕組みを `RAIL_VEHICLE_KEYS` と線路型に差し替えて拡張可能）。
