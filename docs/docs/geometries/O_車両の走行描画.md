# O. 車両の走行描画

## O.1. 概要

道路の上を車が走る様子を描画する仕組みである。カメラ周辺の道路ごとに、パスの**交通量（`path_traffic`）**から求めた**目標台数**（物理的な同時存在台数 × 演出倍率、O.5 参照）を定め、不足分を道路上のランダムな地点（沿道の建物から出てきた車を表す）へ補充スポーンする。車は道路の寸法から求めた**車線**（O.4）の中心を、**走行方向（`travel_direction`）**を尊重して走り、交差点では交通量に応じて確率的に分岐し、通過曲線に沿って次の道路へ移る（O.6）。乗り換え先の道路が目標台数を超えている場合は「沿道の建物に到着する」車として、その道路を少し走ってから降車（デスポーン）し、範囲外に出た車もデスポーンする。

この目標密度への自己調整により、各道路の車の密度は常に `path_traffic` に比例した水準に保たれる。実世界の交通と同じく、車は道路の途中で発生・消滅する（建物への出入り）。`path_traffic` は地区間ルートに沿って加算される負荷であり、ルートの起終点で交通が発生・消滅する情報を含むため、下流ほど交通量が減る道路では描画上も車が減っていく。また、カメラを遠くへジャンプさせた場合も、移動先の道路が即座に適正密度まで充填される。

この描画は**純粋な演出**であり、経済シミュレーションには一切影響しない。バックエンドは車を1台ずつシミュレートしておらず（[事故と災害](../economics/20_事故と災害.md) 参照）、車の位置・台数はクライアント（Unity）側で手続き的に生成する短命オブジェクトである。したがって：

- サーバー永続エンティティではないため、パス（[パス形状](A_パス形状.md)）や建物のようなセル単位のロード/アンロードには載せない。
- 他の車との**当たり判定は行わない**。信号待ちも考慮しない。したがって追い越し・車線変更・車間の詰まりは発生せず、車線が変わるのは交差点だけである。
- ロードするのは `PathManager` が既に取得済みのパスデータ（`pathDataCache`）とパスマスター（道路の寸法）であり、車描画専用のAPI取得は行わない。

当面はすべて単純な箱で描画するが、将来的に「車種ごとに異なる fbx」「同一車種内でもランダムに複数 fbx」へ拡張できる構造を持つ（O.7）。設計は[追加コンテンツとアセットパック](../programs/追加コンテンツとアセットパック.md) の `ModelManager` 解決層（論理パス → 物理アセット）と整合する。

## O.2. 入力データ

車描画は既存のパスデータ・パスマスターと都市設定1つを入力とする。いずれも新規のバックエンド構造は増やさない。

### 交通量 `path_traffic`

パスごとに記録される**車種別**の交通量。`VEHICLE_*`（`VEHICLE_STANDARD=10` 乗用車 / `VEHICLE_TRUCK=11` トラック / `VEHICLE_BUS=12` バス / `VEHICLE_COMMERCIAL=13` 商用車 …）をキーとする dict で、値は**1日あたりにそのパスを通過するトリップ数**（台/日、[道路網](../economics/3_道路網.md) 参照）である。この値が目標台数と交差点での分岐確率の重みになる。

- **目標台数**: 範囲内パス（O.5）× 車種ごとに目標台数を定める（計算式は O.5 参照）。スポーン・途中降車はこの目標との差分で駆動される。
- **分岐の重み**: 交差点で次のパスを選ぶとき、各候補パスの `path_traffic[車種]` を重みにした重み付きランダムで曲がる方向を決める。

交通量は**パス単位であって車線単位ではない**。目標台数は道路全体に対して定め、その車をどの車線へ置くかは O.4 の車線モデルが独立に決める。

!!! note "バルク配信について"
    `path_traffic` はパス詳細（`PathData`）とバルクのパス一覧（bbox の `PathSummary`）の両方に含まれる。Unity 側は**リフレクションで読み取り、フィールドが無いスキーマでも落ちない**（無ければ集計値 `utilization` を乗用車の代替として使う暫定 degrade）実装になっている。

### 走行方向 `travel_direction`

パスのジオメトリ方向（`start_point → end_point`）に対する通行可否。`DIR_BOTH=0`（双方向）/ `DIR_FORWARD=1`（start→end のみ）/ `DIR_BACKWARD=2`（end→start のみ）。スポーン時・交差点分岐時に、そのパスへ入る向きが許可されるかの判定に使い（O.5）、あわせて車線の割り当て（対向車線を持つか、全車線を一方向に使うか）を決める（O.4）。`PathSummary` に既に含まれる。

### 道路の寸法（パスマスター）

車線の位置は、道路メッシュと同じパスマスター（`MasterDataStore.GetPathMaster(path_variant)`、取得は `RoadPath.GetPathMasterParams` に集約）の寸法から求める。使うのは次の4つで、意味は[道路メッシュの生成](G_道路メッシュの生成.md) §5 と同一である。

| フィールド | 意味 |
| --- | --- |
| `width` | 道路全体の幅[m]。**歩道を含む**（歩道は道路の端に覆いかぶさる帯） |
| `sidewalk_width` | 片側の歩道幅[m]。0 なら歩道なし |
| `side_width` | 区画線の幅[m]。0 は「区画線を持たない道路」（未舗装路など） |
| `center_width` | 中央分離帯の幅[m]。0 ならなし |
| `lanes` | 車線数。0/1 はどちらも「1車線」として扱う |

パス個別の `width` ではなくマスターの値を正とする（交差点メッシュの幅決定と同じ規約）。

### 通行方向（左側/右側） `traffic_hand`

車をどちらの車線群に寄せるかの都市設定。`city` の `traffic_hand`（`0`=左側通行 / `1`=右側通行、既定=左）。`GET /api/v1/city` で配信し、Unity では `CityInfoStore`（`DataLoaders/`）がゲーム開始時に一度だけ取得して保持する（取得失敗時は既定=左側通行）。駅のプラットフォーム設置側の解決と同じ値を共有する。変更UIは後日実装予定。

## O.3. 描画範囲

「カメラから一定距離」の範囲は、**カメラ注視点を中心とした半径**で定義する。

- 中心: `CameraCellChecker.CurrentWorldPosition`（カメラ中央のレイと地面 y=0 平面の交点）。
- 半径: `renderRadius`（既定 400m ≒ [LOD処理](E_LOD処理.md) の Dynamic 相当）。
- デスポーン: 車のワールド座標（XZ距離）が `renderRadius + despawnMargin`（既定 +80m）を超えたらデスポーンする。

判定は XZ 平面距離のみ（高さは無視）で行う。

## O.4. 車線モデル

車は中心線をそのままなぞるのではなく、道路の寸法から求めた**車線の中心**を走る。1車線の道路なら道路の真ん中を、対向車線を持つ道路なら通行方向側の車線を、多車線ならその1本を占める。ここで定義するオフセットは道路メッシュの区画線・車線境界線（[道路メッシュの生成](G_道路メッシュの生成.md) §8.3）と**同一の定義**であり、車は必ず引かれた線の間に収まる。線の描画と車の配置は同じ車線オフセット計算を共有し、二重定義しない。

### O.4.1. 走行帯の定義

記号は O.2 のマスター値（`W`=width / `SW`=sidewalk_width / `SL`=side_width / `CW`=center_width / `L`=lanes）とする。中心線から進行方向右向きを正とした横オフセットで表す。

```
            ←──────── R_out ────────→
 ┌────────┬───┬───────────┬───┬───────────┬───┬────────┐
 │  歩道  │側 │   車線1   │中 │   車線1   │ 側│  歩道  │
 │        │線 │─── 車線0 ─│央 │─ 車線0 ───│ 線│        │
 └────────┴───┴───────────┴───┴───────────┴───┴────────┘
 ←────────────────────── W ──────────────────────────→
                        ↑中心線（オフセット0）
```

- **走行帯の外側境界** `R_out = W/2 − SW − (SL>0 ? SL/2 : 0)`
  歩道の内側かつ側線の中心。ここより外側は走らない。
- **走行帯の内側境界** `R_in = CW/2`（中央分離帯がなければ 0）
- **片側走行帯幅** `band = R_out − R_in`

`band` が0以下になる異常なマスター値（歩道が広すぎる等）では1車線扱い（オフセット0）へフォールバックし、車が歩道の上を走らないようにする。

### O.4.2. 車線中心オフセット

**双方向（`DIR_BOTH`）の場合**

- `L ≤ 1`: 車線は1本。**オフセット = 0**（中心線の真上、道路のど真ん中を走る）。対向車も同じ線上を走るが、当たり判定を持たないため見た目は成立する。センターラインを持たない道路（1車線）で片側に寄って走らないのは、この分岐による。
- `L ≥ 2`: 片側車線数 `n = L / 2`（切り捨て）。
    - `laneWidth = band / n`
    - 車線 `j`（`0`=中央側、`n−1`=路肩側）の中心 = `R_in + laneWidth × (j + 0.5)`
    - 符号は通行方向側に付ける。左側通行なら進行方向の左、右側通行なら進行方向の右。
    - 奇数車線（3以上）の余り1本は中央の右左折レーンとみなし、走行には使わない。

**一方通行（`DIR_FORWARD` / `DIR_BACKWARD`）の場合**

全車線を進行方向に使う（対向車線が無いため）。帯 `[−R_out, +R_out]` を `L` 等分し、`laneWidth = 2·R_out / L`、路肩側から数えて `k` 番目（`0`=路肩側）の車線の中心 = `R_out − laneWidth × (k + 0.5)` を通行方向側の符号で置く。中央分離帯を持つ一方通行はマスターに存在しないため `CW` は無視する。

### O.4.3. 寸法から求まる車線位置の例

| バリアント | `W` | `SW` | `SL` | `CW` | `L` | `R_out` | 片側車線数 | 車線中心オフセット |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 未舗装路 | 3.0 | 0 | 0 | 0 | 1 | 1.50 | 1 | 0（中央） |
| 極小路地 | 3.0 | 0 | 0.5 | 0 | 1 | 1.25 | 1 | 0（中央） |
| 1車線生活道路 | 6.0 | 0 | 0.5 | 0 | 1 | 2.75 | 1 | 0（中央） |

| 2車線生活道路 | 12.0 | 2.5 | 0.5 | 0 | 2 | 3.25 | 1 | ±1.63 |

### O.4.4. 車線の選択と維持

- **スポーン時**: 使用可能な車線からランダムに1本選ぶ。ただしトラック・バスは路肩側の車線（`k=0`）を `heavyVehicleOuterLaneBias` の確率で選ぶ（大型車が第1走行車線を走る見え方）。
- **乗り換え時**: 路肩側から数えた車線番号 `k` を維持し、乗り換え先の片側車線数でクランプする。片側1車線の道から4車線の道へ出た車は路肩側の車線に入り、逆に多車線から1車線へ入る車は唯一の車線に収まる。
- **車線変更はしない**: 当たり判定を持たないため追い越しに意味がなく、車線が変わるのは交差点の乗り換え時だけである。
- **横オフセットは瞬間移動させない**: 車線オフセットが変わる場面（交差点の通過、到着直前の路肩寄せ）では `laneBlendDistance` の走行距離をかけて線形補間する。

## O.5. スポーン・走行・デスポーン

### 範囲内パスの抽出と目標台数

一定間隔（`rangeScanInterval`、既定 0.5 秒）で「範囲内パス」を再スキャンしてキャッシュする。範囲内パスとは、ロード済みの走行可能な道路（`PATH_MOTORWAY` / `PATH_STREET`、`STATUS_ACTIVE`）で、中心線が描画円と交わるものを指す。

- 中心線のうち円内にある区間 `[sIn, sOut]` を求める（円との交点は隣接頂点の距離を線形補間して近似）。円を複数回出入りするパスは「最初の進入点〜最後の退出点」で1区間に丸める。
- 範囲内パス × 車種ごとに **目標台数** = 物理的な同時存在台数 × `timeExaggeration` を算出する。物理台数は「流量[台/s]（= `path_traffic[車種]`[台/日] ÷ 活動秒数（`activeHoursPerDay` × 3600））× 円内区間の通過時間[s]（= 円内区間の長さ ÷ 車種の走行速度）」の期待値で、実スケールではほぼ0台になるため、演出倍率 `timeExaggeration` で時間を圧縮して見た目の賑わいを作る。円外にはみ出す部分は目標に含めない。
- あわせて、(パス, 車種) ごとの**現在の走行台数**をスポーン・乗り換え・デスポーンの各時点で増減カウントし、常に維持する。交差点を通過中の車とフェード中の車も、乗り換え先パスの台数に数える（二重補充の防止）。

### スポーン（不足補充）

範囲内パス × 車種ごとに、不足分 = 目標台数 − 現在台数 を計算し、毎フレーム確率 `p = 不足分 × spawnFillRate × Δt` でスポーンを抽選する（フレームレート非依存のポアソン過程）。不足分が大きいほど速く補充され、目標密度へ指数的に収束する。同時存在数が `maxActiveVehicles`（既定 300）に達したら抑止する。

- スポーン位置は円内区間 `[sIn, sOut]` 上の**ランダムな地点**とする（沿道の建物から道路に出てきた車を表す）。
- 走行向きは `travel_direction` が許す向き。双方向ならランダムに選ぶ。走る車線は O.4.4 に従って選ぶ。
- **沿道から出てくる演出**: 横オフセットは路肩（`R_out`）から車線中心へ `laneBlendDistance` かけてブレンドし、スケールは `fadeDuration` かけて 0 → 1 に立ち上げる。スケールで出入りさせるのは、マテリアルの差し替え（半透明化）を伴わずプールした実体をそのまま使えるためである。
- カメラを大きく動かした直後は、移動先の範囲内パスがすべて不足状態になるため、数秒で適正密度まで一気に充填される。

生成した車には車種係数（トラック/バスは遅め）と個体ばらつきを掛けた速度を与える。

### 走行

各フレーム、車は中心線に沿って進行方向へ距離を進める。位置は中心線を距離パラメータで補間して求め、**進行方向に対して現在の車線の横オフセット**（O.4）だけ横へずらした点に置き、接線方向へ向ける。

### 交差点での分岐

パスの端（ノード）へ到達したら、次のパスへ乗り換える。乗り換えの幾何（通過曲線）は O.6 に従う。

- 候補は `PathManager.GetPathsConnectedToNode(nodeId)` で得た、そのノードに接続する走行可能な道路。**現在のパスは除外**（Uターン回避）。
- 各候補について、ノードが `start_node_id` 側なら前進・`end_node_id` 側なら後退で入るものとし、その向きを `travel_direction` が許可するものだけ残す。
- 残った候補を `path_traffic[車種]` を重みにした重み付きランダムで1つ選ぶ。全候補が交通量0の場合のみ均等ランダムで選ぶ（交通量0の道路は「他に行き先が無いときの逃げ道」であり、通常時の分岐先には混ぜない）。
- **候補が1本も無い（行き止まり）ときは U ターンする**: 現在のパスを逆走する向きが `travel_direction` で許されるならそのまま折り返し、許されない（一方通行の行き止まり）ときだけデスポーンする。行き止まりのたびに車が消えると、袋小路の突き当たりで車が湧いて消えるだけの絵になるため。

### 途中降車（目標超過デスポーン）

分岐先を決めた後、その乗り換え先パスが描画範囲内で、乗り換え後の台数が目標台数を超える場合、超過度に応じた確率 `p = arrivalDespawnStrength × (1 − 目標台数 / 乗り換え後台数)` で「沿道の建物に到着する」車として降車を予約する。

**降車は交差点の上では起こさない**。予約された車は乗り換え先のパスへ普通に進入し、進行方向へ `arrivalRunDistance`（既定 10〜60m のランダム、パス長でクランプ）走った地点を到着点とする。到着点の手前 `laneBlendDistance` から横オフセットを路肩（`R_out`）へブレンドしながら減速し、到着点で `fadeDuration` かけてスケールを 0 へ縮めて消える。沿道の敷地へ入っていったように見せるための扱いであり、交差点の中央で車が突然消える見え方を避ける。

この仕組みにより各パスの車密度が目標（= `path_traffic` 比例）へ自己調整される。交通量の少ない道路には車が滞留せず、下流ほど交通量が減る道路では実際に車が減っていく。交通量0のパス（目標0）へ乗り換える車は、`arrivalDespawnStrength = 1` ならほぼ確実に降車する。

### デスポーンの3経路

| 経路 | 契機 | 見え方 |
| --- | --- | --- |
| 沿道到着 | 乗り換え先が目標超過 | 乗り換え先を少し走り、路肩へ寄ってフェードアウト |
| 行き止まり | Uターンも許されない一方通行の末端 | 即座に消える（稀。突き当たりのため目立たない） |
| 範囲外 | `renderRadius + despawnMargin` 超過 | 即座に消える（描画円の外なので画面に映らない） |

### travel_direction フィルタ

ノード N からパスへ入れるかの判定：

| 入る向き | 許可される `travel_direction` |
| --- | --- |
| 前進（N が `start_node_id`、start→end） | `DIR_BOTH` または `DIR_FORWARD` |
| 後退（N が `end_node_id`、end→start） | `DIR_BOTH` または `DIR_BACKWARD` |

## O.6. 交差点の通過

パスの中心線は交差点ハルの切断点（`NodeMeshResult.ConnectionPoints`。[パスの交差処理](J_パスの交差処理.md)）まで切り詰められており、ノード中心までは伸びていない。したがって隣り合うパスの端点の間には交差点アスファルトぶんの空白があり、さらに両パスの車線オフセットも一般に異なる。車はここを直線で飛ばず、**通過曲線**に沿って走る。

- **退出点** `P0` = 現在パスの端点 + 現在の車線オフセット、**退出接線** `T0` = そこでの進行方向。
- **進入点** `P1` = 乗り換え先パスの端点 + 選んだ車線（O.4.4）のオフセット、**進入接線** `T1` = そこでの進行方向。
- 通過曲線は三次ベジエ `P0, P0 + T0·d, P1 − T1·d, P1`（`d = |P1 − P0| × intersectionCurveTension`）。制御点を接線の交点で求めないのは、直進・180°折り返しのように接線が平行な配置でも破綻させないためである。
- 高さは `P0` と `P1` の線形補間（交差点は同一平面）。
- 通過中の速度には、偏向角に応じた係数（直進で 1.0、90°以上の転回で `intersectionSpeedFactor`）を掛ける。
- 台数カウントは通過を開始した時点で乗り換え先パスへ移す。
- 乗り換え先の点列が取得できない等で通過曲線を作れない場合のみ、その場でデスポーンする。

信号待ち、交差点内での他車との干渉、右折待ちの停止は考慮しない（O.1 の当たり判定なしの方針どおり）。

## O.7. モデル解決と拡張性

車種（+バリアント）から描画用オブジェクトを解決する層を持ち、[建物メッシュ](F_建物メッシュの生成.md)・[地形プロップ](M_地形プロップ.md) と同じく `ModelManager.GetModel(論理パス)` を単一の入口とする。解決順は次のとおり：

1. `Models/Vehicles/{車種}/{バリアント}`（車種内で複数モデルを持つ場合）
2. `Models/Vehicles/{車種}`（車種単一モデル）
3. `Models/Vehicles/{VEHICLE_STANDARD}`（汎用車フォールバック）
4. いずれも無ければ**単純な箱**（車寸の Cube、車種別に色分け。fbx 導入までの暫定）

車種内の複数バリアントは、[地形プロップ](M_地形プロップ.md) の `seed` 方式と同様に、車1台の乱数シードから決定的に1つを選ぶ。どの車種にどのバリアントがあるかは任意の設定ファイル（`Resources/Config/vehicle_model_config.yaml`、`agent_model_config.yaml` と同形式）で「車種ID → バリアント一覧」を宣言する。未定義の車種は上記フォールバックで動作する。

モデルの寸法は車線幅に合わせない（実寸のまま配置する）。狭い車線に大型車が入って多少はみ出すのは許容し、スケールで縮めない。

この設計により、**箱 → 車種別 fbx → 車種内ランダム複数 fbx** を段階的に拡張できる。物理配置は将来のコンテンツパック（[追加コンテンツとアセットパック](../programs/追加コンテンツとアセットパック.md)）の論理パス解決にそのまま乗る。

生成した車は車種+バリアント単位でプールし、デスポーン時に破棄せず再利用する（フェードで縮めたスケールはプールから取り出す時に戻す）。

## O.8. データフローと関連コンポーネント

```
CityInfoStore（traffic_hand）─────────────┐
MasterDataStore（width/lanes/歩道/分離帯）─┤
                                          ▼
PathManager（取得済み pathDataCache: path_traffic / travel_direction / ノードグラフ / 中心線）
   │  GetAllPaths / TryGetPathPolyline / GetPathData / GetPathsConnectedToNode
   ▼
VehicleManager（毎フレーム: 範囲内パス抽出+目標台数算出 → 不足補充スポーン → 車線に沿った走行
                → 交差点分岐/通過曲線/沿道到着 → 範囲外デスポーン, プール管理）
   │  ModelManager.GetModel("Models/Vehicles/{車種}/{バリアント}")
   ▼
車オブジェクト（箱 or fbx）を車線中心に配置
```

- 中心線・ノードグラフ・パス属性はすべて `PathManager`（[バックエンドデータロード](H_バックエンドデータロード.md)）が既に取得済みのものを再利用する。中心線は curved パスではベジエサンプリング済み・地形追従済みで、**両端は交差点ハルの切断点まで切り詰められた**点列（[パス形状](A_パス形状.md)）。
- 車線オフセットの計算は道路メッシュの区画線描画と共有する（[道路メッシュの生成](G_道路メッシュの生成.md) §8.3）。片方だけ式を変えると車が線をまたいで走る。
- 描画範囲の中心は `CameraCellChecker`、範囲区分の目安は[LOD処理](E_LOD処理.md) の Dynamic 距離に準じる。

## O.9. 調整パラメータ

| パラメータ | 既定 | 意味 |
| --- | --- | --- |
| `renderRadius` | 400m | 車を走らせる半径 |
| `despawnMargin` | 80m | この余白を超えたらデスポーン |
| `timeExaggeration` | 60 | 時間圧縮の演出倍率。1=物理的に正確な同時存在台数（ほぼ0台） |
| `activeHoursPerDay` | 15h | 交通が流れる1日の活動時間。バックエンドの `PATH_ACTIVE_HOURS` に合わせる |
| `spawnFillRate` | 1.0 /s | 目標台数への不足分を1秒あたりに埋める割合 |
| `arrivalDespawnStrength` | 1.0 | 目標超過パスへ乗り換えた車が沿道到着する確率の強さ（0=無効） |
| `arrivalRunDistance` | 10〜60m | 沿道到着が決まった車が、乗り換え先を走ってから消えるまでの距離 |
| `maxActiveVehicles` | 300 | 同時存在数の上限 |
| `rangeScanInterval` | 0.5s | 範囲内パスの再スキャン間隔 |
| `baseSpeed` | 12 m/s | 基準速度（車種係数・個体ばらつきが乗る） |
| `laneBlendDistance` | 15m | 車線の横オフセットを補間する走行距離（交差点通過・路肩寄せ） |
| `heavyVehicleOuterLaneBias` | 0.7 | トラック・バスが路肩側の車線を選ぶ確率 |
| `intersectionCurveTension` | 0.4 | 通過曲線の制御点の張り出し（退出点〜進入点の距離に対する比） |
| `intersectionSpeedFactor` | 0.5 | 90°以上の転回時の速度係数（直進は 1.0、間は偏向角で線形） |
| `fadeDuration` | 0.4s | スポーン/デスポーン時にスケールを立ち上げ・縮小する時間 |

車線の位置はパラメータではなくマスターの寸法から決まる（O.4）。中心線からの固定オフセットは持たない。

`path_traffic` は1日あたりの通過トリップ数（台/日）である。1日34台の道路を物理的に正確に描くとほぼ常に0台で画面が死ぬため、`timeExaggeration` で時間を圧縮して賑わいを誇張する。倍率を1に近づけるほどリアルに、大きくするほど賑やかになる。見た目が適切になるよう `maxActiveVehicles` とあわせて調整する前提である。

## O.10. 現在の実装状況と今後

- 実装済み: 目標密度ベースの不足補充スポーン（道路途中からの発生）／中心線に沿った走行／交差点の確率分岐（`travel_direction` 尊重）／目標超過時の途中降車デスポーン／範囲外デスポーン／プール／箱フォールバック描画／`traffic_hand` の city 設定・配信。
- 未実装（O.4 の車線モデル）: 現状は通行方向側へ固定量（2.5m）寄せるだけで、`width` / `lanes` / `sidewalk_width` / `center_width` を参照していない。そのため1車線の道路でも路肩寄りを走り、多車線の道路でも全車が同じ位置を走る。車線番号の維持・大型車の車線選好・横オフセットのブレンドも未実装。
- 未実装（O.6 の交差点通過）: 現状はパス端点から次パス端点へ瞬間移動する。あわせて、沿道到着デスポーンが乗り換えの決定と同時に発生するため車が交差点上で消える。行き止まりの U ターンとスポーン/デスポーンのフェードも未実装。
- 未実装（区画線側の追従）: 道路メッシュの車線境界線は走行帯（歩道・側線を除いた幅）ではなく `width / lanes` で等分している。車線オフセットの共通化にあわせて揃える必要がある（[道路メッシュの生成](G_道路メッシュの生成.md) §8.3）。
- 未実装（その他）: 車種別・車種内ランダムの fbx プレハブ（`Models/Vehicles/...` と `vehicle_model_config.yaml` の実データ）／通行方向（左右）の変更UI／`traffic_hand` の取得を `CityInfoStore` へ寄せる（現状は `VehicleManager` が独自に `GET /api/v1/city` を叩く）／線路上の車両描画（同じ仕組みを `RAIL_VEHICLE_KEYS` と線路型に差し替えて拡張可能）。
