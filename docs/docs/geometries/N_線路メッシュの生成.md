# 線路メッシュの生成

## 概要

線路（path_type=4 PATH_TRACK）とモノレール（path_type=5 PATH_MONORAIL）の外観メッシュを組み立てて配置する仕様。生成器は **TrackPath** で、`PathMeshFactory` により path_type から振り分けられる。

データフロー（ベジエサンプリング → スプライン構築 → SplineMesh によるパーツ配置）、LOD、コライダー生成、地下パスの区間分割、フォールバック階層は道路（[G_道路メッシュの生成](G_道路メッシュの生成.md)）とすべて共通であり、本ドキュメントでは**線路固有の部分だけ**を説明する。

道路との本質的な違いは次の3点である。

1. **幅方向に引き伸ばせないパーツがある**。レールの軌間（ゲージ）や架線の断面はバリアントの幅が変わっても不変でなければならない。このため線路のパーツは「引き伸ばすパーツ（道床）」と「実寸で並べるパーツ（軌道・架線）」に分かれる。
2. **ノード（交差点）が分岐器（ポイント）になる**。道路のように全方向が舗装で繋がるのではなく、線路の敷設形状から通行可能な方向にだけレールが繋がる。
3. **近接して並走する線路は結合して描画する**。ゲームの内部データに「複線線路」という単位は無く、複線は一方通行の単線線路2本として表現される。そのままでは単線が2本並ぶだけの見た目になるため、近接する線路どうしは道床・防音壁・架線柱・架線ビームを結合した1つのコリドーとして描画する（§8）。

## 1. パーツ構成

プレハブは道路と同じ命名規則 `Models/Paths/p{path_variant}/{パーツ名}`（無ければ `p{path_type}` にフォールバック）で配置する。

| パーツ        | 役割             | 配置数     | Xスケール                   | 備考                                                                                    |
| ---------- | -------------- | ------- | ----------------------- | ------------------------------------------------------------------------------------- |
| `body`     | 道床             | 1       | 全幅に引き伸ばす                | 地上線路ではバラスト（砕石）の台形断面。**高架・橋梁バリアントではプレハブ自体を「桁＋道床」の断面にする**ことで高架床を表現する（deck等の専用スロットは持たない）。鉄道橋梁（403）は下路トラス橋のため、body は薄い床組（鋼床版＋横桁）だけを持ち、桁としての構造高は wall のトラスが受け持つ |
| `track`    | 1軌道分（レール2本＋枕木） | lanes本  | **実寸（スケールなし）**          | 軌間1.435mの断面で作る。モノレールでは軌道桁1本のモデルを同じスロットに置く                                             |
| `rail`     | レールのみ（枕木なし）    | —       | 実寸                      | ノード内のレールコネクタ専用（§4）。未配置時は `track` で代用される                                               |
| `wire`     | 架線（トロリ線＋吊架線）   | lanes本  | 実寸                      | 電化バリアントのみ（§2）。トロリ線の高さ（レール面上約5m）はプレハブ形状が持つ                                             |
| `pole`     | 架線柱（柱）         | 間隔配置×左右 | 実寸                      | 電化バリアントのみ。Instantiate 配置                                                              |
| `beam`     | 架線ビーム（門型梁）     | 間隔配置    | 柱間に引き伸ばす                | 電化バリアントのみ。pole と同位置に配置                                                                |
| `wall`     | 防音壁・主構       | 2（左右）   | 道路と同じ                   | 道路の wall スロットをそのまま共用（`wall_width`）。プラットフォームがある側には立てない（§7）。**鉄道橋梁（403）はこのスロットで主構（ポニートラス）を表現する**（左右独立に配置されるスロットなので上部横構は持てない）                   |
| `pillar`   | 高架橋脚           | 間隔配置    | 道路と同じ                   | 道路の pillar と共通処理（`pillar_spacing`、height_editable時のみ、地下は除外）。**道路と同じくYaw-only回転で垂直保持** |
| `portal`   | 坑口             | 境界ごと    | 道路と同じ                   | 地下パスの描画区間境界（PathManager側の共通処理）                                                        |
| `platform` | ホームの淵（線路側）    | 片側/両側   | **実寸（スケールなし）**          | 駅パスのみ（§7）。黄線・点字ブロック・ホームドア・縁の垂直面・支柱。原点＝線路中心線・線路面で配置し、縁（中心線から±1.5m固定）への横位置と立ち上がりはプレハブ形状が持つ。「右側用」規約（左側はXミラー）。未配置ならスキップ |
| `platform_wall` | ホームの外縁（壁・柵・ベンチ） | 片側/両側 | **実寸（スケールなし）**   | 駅パスのみ（§7）。原点＝線路中心線・線路面で配置し、外縁（±(width/2+platform_width)）への横位置はプレハブ形状が持つ。島式結合区間・他線路近接区間では省略（§7.4）。「右側用」規約（左側はXミラー）。未配置ならスキップ |
| `platform_panel` | ホーム上面のマテリアル採取用 | 配置なし | —                    | 駅パスのみ（§7）。デッキ（ホーム上面）はコードが動的生成し、このプレハブの**マテリアルだけ**を使う。未配置なら共通コンクリートにフォールバック |

「路盤」の専用パーツは存在しない。地上線路の路盤は地形そのもの＋バラスト断面（裾野込み）で表現し、盛土は `embankment_heights` による地形変形が担う。高架の床も deck スロットを設けず、高架バリアント専用の body プレハブの断面で表す（バリアントは地上/高架で固定なので、断面をプレハブに焼き込める）。

### 1.1 軌道オフセットの導出

軌道の中心位置はマスターデータから導出し、専用のパラメータを持たない。道路の車線と同じ考え方で、全幅（`width`）を軌道数（`lanes`）で等分した各帯の中央に軌道を置く。

```
offset_i = -width/2 + (width/lanes) × (i + 0.5)
```

| バリアント例 | width | lanes | 軌道中心 |
|---|---|---|---|
| 単線線路(401) | 5 | 1 | 0 |
| 複線線路(411) | 11 | 2 | ±2.75 |
| 複々線線路(421) | 16 | 4 | ±2, ±6 |

`lanes` は線路では**軌道数**を意味する（単線=1、複線=2、複々線=4）。この導出は本線（`TrackPath.GetTrackCenterOffset`）とノード内のレールコネクタ（§4）で共有され、交差点の縁で本線の軌道位置とコネクタが正確に一致する。

### 1.2 高さの層構造とプレハブのピボット規約

道路の高さ体系（`RoadPartHeights`、[G_道路メッシュの生成](G_道路メッシュの生成.md) §4.4）に以下を追加する。

| 定数 | 値 | 説明 |
|---|---|---|
| `BODY_ABOVE_SPLINE` | 0.1m | 道床（body）のスプラインからの高さ。道路と共通。**bodyプレハブのピボット＝道床の上面**（厚みは下方向）の規約なので、道床天端はこの平面になる |
| `TRACK_ABOVE_SPLINE` | 0.12m | 軌道（track）・レールコネクタ（rail）の下端の高さ。道床天端の2cm上（Zファイティング回避） |
| `OVERHEAD_ABOVE_SPLINE` | 0.12m | 架線（wire）・架線柱（pole）・架線ビーム（beam）の基準面の高さ |
| `PLATFORM_BASE_ABOVE_SPLINE` | 0m | プラットフォームプレハブ（platform / platform_wall）の設置面（原点＝線路中心線・線路面）の高さ。スプライン基準面と同一平面 |
| `PLATFORM_SURFACE_ABOVE_SPLINE` | 1.5m | ホーム面（デッキ上面の公称高さ）。レール踏面（≒スプライン+0.3m）から約1.2mに相当。デッキの実面はここから2cm沈む（淵の上面造形とのZファイティング回避）。**プレハブのホーム面の立ち上がりはこの値と一致させて造形する**（§1.2） |

プレハブのモデリング規約（この規約が崩れると高さ定数が意味を失う）:

- `track` / `rail`: ピボット＝**枕木の下面**（道床に接する面）。レール踏面までの立ち上がりはプレハブ形状が持つ
- `wire`: ピボット＝軌道と同じ基準面。トロリ線・吊架線はプレハブ内でレール面上約5mの高さに造形する（**コードは架線高さのパラメータを持たない**）
- `pole`: ピボット＝設置面（軌道と同じ基準面）。柱は+Y方向に伸ばす。**「右側用」**として作り、腕金・張り出しは -X（軌道中心）方向を向ける。左側はY軸180°回転で配置される
- `beam`: ピボット＝スプライン中心の設置面。梁本体はプレハブ内で柱の高さに造形する。X幅が柱間（全幅＋マージン×2）に一致するよう引き伸ばされる
- `platform`（淵）: **原点＝線路中心線・線路面**（X＝スプライン中心、Y＝スプライン基準面 `PLATFORM_BASE_ABOVE_SPLINE`）。**「右側用」**として作り、縁の造形をプレハブ内で **X=+1.5m（`PLATFORM_EDGE_OFFSET`。バリアントの width に依存しない固定値。道床コリドー端 width/2 より線路側に突き出した乗降縁）**に置く。ホーム面までの立ち上がり（縁の垂直面）と**ホームを支える支柱**もプレハブ形状が持ち（デッキは厚さ15cmの浮いた板で支柱を生成しない）、**黄線・点字ブロック・ホームドア等の上面造形は原点から `PLATFORM_SURFACE_ABOVE_SPLINE` と同じ高さ（1.5m）に造形する**（ずれるとデッキと淵の上面が食い違う。デッキ実面はその2cm下）。支柱・スカートの下端は地形の微起伏に埋まる余裕として原点より少し下（-0.5m程度）まで伸ばす。左側はXミラーで配置される（原点が中心線にあるためミラーは中心線対称になる）。実寸配置（Xスケール・ピボット補正なし）
- `platform_wall`（外縁）: **原点＝線路中心線・線路面**。**「右側用」**として作り、壁・柵・ベンチの本体をプレハブ内で X=+(width/2+platform_width)（ホーム外縁）、ホーム面の高さ（1.5m）から上に造形する。デッキの外縁の小口（板の側面）と同一平面になる垂直面は持たせない（Zファイティング防止）。左側はXミラーで配置される。実寸配置
- 淵・外縁とも造形の横位置・立ち上がり高さをバリアントのマスター値（width / platform_width）・高さ定数に一致させて作る（ずれるとデッキと食い違う）
- `platform_panel`: 配置されないマテリアル参照専用パーツ（切妻屋根の `generic-wall` と同じ扱い）。デッキ（ホーム上面）の動的生成メッシュにこのプレハブのマテリアルが割り当てられる。UVはメートル基準（4mで1タイル）

架線柱の設置面はスプライン（路面）基準なので、高架では桁の上に立つ。地面まで伸びる橋脚（pillar）とは役割が異なる（pillar は道路と同じく、配置位置のY座標をスケールにして地面まで伸ばす）。

## 2. 電化（架線・架線柱）

マスターデータの **`wire_spacing`**（架線柱の設置間隔、m）で制御する。null（シート空欄）は非電化を意味し、`wire` / `pole` / `beam` は一切描画されない。

- `wire` は各軌道の中心に SplineMesh で曲げて配置する（実寸、軌道と同じオフセット）
- `pole`（左右1組）と `beam`（1本）は `wire_spacing` 間隔で Instantiate 配置する。交差点の切断面ぎりぎりに柱が立たないよう、両端から間隔の半分だけ内側に寄せる（街路樹の端部クリアランスと同じ考え方）。プラットフォームがある側（§7）では、柱がホームを突き抜けないようホーム外縁＋マージンの位置に立てる（梁は柱間全幅に引き伸ばされる）
- `pole` だけ配置して `beam` を置かない（片持ち柱をプレハブで表現する）ことも、その逆も可能（各パーツはオプショナル）
- **垂直保持**: 架線柱・架線ビームとも地形の傾斜に追従して斜めに立たず、**常にワールド上方向に対して垂直に立つ**。回転は進行方向の水平成分から導出したYawのみ（ピッチ・ロールは0）。これにより坂道・カント上でも架線柱が直立する。

## 3. フォールバック

各パーツはバリアント→タイプの順でプレハブを探し、無ければスキップする（道路と同じ）。ただし道床（body）と軌道（track）が**両方とも**無い場合のみ、白いストリップメッシュにフォールバックしてゲームプレイを継続する。

- 道床のみ（track未整備）: バラストの帯だけが描かれる
- 軌道のみ（body未整備）: 軌道だけが描かれる。**モノレールのように道床が不要なバリアントでは、bodyプレハブを置かないことが正常な構成**である

## 4. ポイント（分岐器）・平面交差の表現

### 4.1 道床ハル

線路どうしのノードにも道路と同じ交差点凸包（[G_道路メッシュの生成](G_道路メッシュの生成.md) §11）が生成され、各線路の端点はハルの縁（切断点）まで切り詰められる。ハルのマテリアルは代表バリアントの body プレハブから解決されるため、線路ノードでは自動的に**道床（バラスト）の見た目**になる。

### 4.2 レールコネクタと転回制約

ハルの上に、**通行可能な線路ペアにのみ** `rail` パーツを短いコネクタスプラインで敷く。これがポイント・ダイヤモンドクロッシングの表現である。

通行可能かどうかは、シミュレーション側の転回制約（[6_公共交通機関](../economics/6_公共交通機関.md)参照。交差点での進行方向の連続性）と同じ幾何ルールで判定する:

- ノードでパスAからパスBへ進むときの**偏向角**（Aの到着方向とBの発進方向のなす角。直進=0°、折り返し=180°）が **RAIL_MAX_TURN_ANGLE_DEG（既定45°）以下**のペアにのみレールを敷く
- 端点の接線方向は、ノード側アンカーから最寄りのウェイポイント（無ければ反対側端点）へ向かう方向から導出する

これにより見た目と経路探索の挙動が一致する:

- **Y字合流**: なめらかに合流する2方向にはレールが繋がり、折り返し側（偏向角≈180°）にはレールが無い
- **ダイヤモンドクロッシング（90°平面交差）**: 直進方向どうしだけレールが交差し、90°曲がる向きにはレールが無い
- **踏切（道路×線路の混在ノード）**: ハルは道路の舗装を優先し、その上を直進レールが横切る

閾値はバックエンド `parameters.yaml` の `RAIL_MAX_TURN_ANGLE_DEG` と同じ値を Unity 側の定数（`LocalConstants.RAIL_MAX_TURN_ANGLE_DEG`）に持つ。プレイヤーがパラメータを書き換えた場合に見た目と経路探索がずれるのは既知の制限である。

### 4.3 軌道の対応付け

- 軌道数が同じペア: 走行フレーム（A→Bへ進む向きの右手方向）での横位置順に1対1で結ぶ（複線の直進では右側軌道どうし・左側軌道どうしが繋がる）。軌道オフセットは本線と同じ導出（§1.1）なので、切断点で本線の軌道と正確に繋がる
- 軌道数が異なるペア: 中心線1本のコネクタで近似する（簡易表現）

コネクタの形状は、両側の切断点を端点接線をハンドルにした三次ベジエで滑らかに結ぶ。レールは実寸配置（Xスケール1固定）で、`rail` プレハブが無ければ `track` プレハブで代用し、それも無ければスキップされる（道床ハルだけが描かれる）。

### 4.4 実装の役割分担

歩道コネクタと同じ「幾何情報と実体化の分離」パターンに従う。

- `TrackIntersectionMeshGenerator.BuildRailConnectorSpecs`: 通行可能ペアの判定とコネクタ点列（`RailConnectorSpec`）の計算。`RoadIntersectionMeshGenerator.Generate` から呼ばれ、`NodeMeshResult.RailConnectors` として返る
- `TrackPath.CreateRailConnectorObject`: レールプレハブを SplineMesh で曲げて実体化。`PathManager.UpdateNodeRailMesh` が NodeMesh の子（`Rail`）として生成する

### 4.5 防音壁の接続（壁コネクタ）

線路の点列（と防音壁）は交差点ハルの縁で切り詰められるため、何もしないとノードのたびに壁がハルの長さ分だけ途切れる。浅い角度で合流する線路のハルは細長くなるため、合流部では特に目立つ。これを、ハルを跨いで壁どうしを繋ぐ**壁コネクタ**で埋める。

- ノードに接続する線路を外向き方向の**角度順**に並べ、隣り合うペアの間の扇形（他の線路が入らない領域）ごとに、その扇形に面する壁端どうし（切断点＋道床半幅＋壁半幅の横オフセット）を端点接線をハンドルにした三次ベジエで結ぶ（歩道コネクタと同じ「角度順の隣接ペア」方式）
- 以下の扇形にはコネクタを張らない:
    - ペアのどちらかに壁が無い（`wall_width` が null）
    - ペアのどちらかの壁端がプラットフォームの設置側（その側の壁は立たない。§7.3）
    - 扇形角が `TRACK_MERGE_MAX_CONVERGE_ANGLE_DEG`（45°）以下（合流・分岐で収束するペア。本線側の壁も結合描画（§8）で省略されており、繋ぐべき壁端が存在しない）
    - 扇形の中に線路以外の接続パス（道路など）が入っている（踏切で壁が道路を塞がない）
    - コネクタ経路が交差点内のレールコネクタに近づきすぎる（走行する列車の経路を壁が横切らない）
    - コネクタ経路の近くを、このノードに**接続しない**別の線路が通っている（複線の相方・合流相手の並走線路。その側の壁は結合描画で省略される側。判定閾値は§8.1の結合判定と同じ）
- 実装は `TrackIntersectionMeshGenerator.BuildWallConnectorSpecs`（幾何計算。`NodeMeshResult.WallConnectors`）と `TrackPath.CreateWallConnectorObject`（実体化。NodeMesh の子 `Wall`）
- 接続しない近隣線路の敷設・撤去で遮蔽状態が変わってもノード自身のデータは変わらないため、近接線路の再生成（§8.3）と同時に両端ノードの交差点メッシュも描き直される

## 5. マスターデータ

線路の描画に使う `path_master` のパラメータ。

| フィールド | 型 | 説明 |
|---|---|---|
| `width` | float | 全幅（m）。道床の幅であり、軌道オフセットの導出にも使う。**駅パスも通常線路と同じ幅**（§7） |
| `lanes` | int | 軌道数（単線=1、複線=2、複々線=4） |
| `wire_spacing` | float? | 架線柱の設置間隔（m）。null は非電化（架線・架線柱なし） |
| `wall_width` | float? | 防音壁（橋梁バリアントでは主構トラス）の幅（m）。null・0 は配置なし。高架線路・橋梁のバリアントに設定する。**0 にすると鉄道橋梁のトラスも消える**ので、プレハブの見付け幅と一致させること |
| `pillar_spacing` | float? | 高架橋脚の間隔（m）。height_editable=true のバリアントのみ有効 |
| `height_editable` | bool | 高架（高さ編集可能）バリアントか |
| `min_height` | float? | 負の値を持つバリアント（地下鉄用線路など）だけが地下に建設できる |
| `platform_width` | float? | プラットフォームの幅（m）。駅バリアントのみ設定。null はホームなし。敷地・コライダー・柱位置に加えて**デッキ（ホーム上面）の外縁位置（width/2+platform_width）**にも使う（淵側のエッジは中心線から1.5mの固定値。§7.3） |

---

## 6. LOD・コライダー・地下

道路と共通の仕組みに乗る。

- **Far ティア**: 始点終点を結ぶ簡易ストリップ（地下パスは非表示）
- **コライダー**: 全幅のストリップメッシュ（クリック判定用）
- **地下パス**: 描画区間分割・`portal` 配置・柱の抑制は PathManager 側の共通処理（[G_道路メッシュの生成](G_道路メッシュの生成.md) §8.8）

## 7. 駅パス（プラットフォーム）

地上鉄道駅（451等）の駅パスも path_type=4 の線路バリアントであり、同じ TrackPath で生成される。

**駅パスの `width` は通常の線路と同じ「線路コリドーの幅」**（単線駅なら5m）である。このため道床・軌道・架線・交差点ハル・レールコネクタはすべて通常線路とまったく同じに描かれ、駅パスの中心線は前後の線路とシームレスに繋がる（位置合わせのための特別な処理は存在しない）。プラットフォームは道床の外側に `platform_width` ぶん張り出す付帯構造で、3つの要素で構成される（§7.3）。

### 7.1 platform_width と platform_side

- マスターの `platform_width`（§5）がホームの幅。null は通常の線路（ホームなし）。この値は敷地ポリゴン・クリック判定コライダー・架線柱の位置算出と**デッキ（ホーム上面）の外縁位置**に使う（デッキは外縁 width/2+platform_width から、道床コリドー端を越えて中心線から1.5mの固定淵ラインまで張られる）。張り出し幅の正はマスター、淵ライン・デッキ高さの正はコードの定数（§1.2）であり、**敷地と見た目は構造的に一致する**。
- **どちら側に張り出すかはパスのプロパティ `platform_side`** で決まる。建設時にプレイヤーが指定し、建設後の変更はできない。値は共有定数:

| 値 | 意味 |
|---|---|
| `PLATFORM_SIDE_OUTSIDE`（既定） | 進行方向の**外側**（複線の相手線路と反対側） |
| `PLATFORM_SIDE_INSIDE` | 進行方向の**内側**（複線の線路間） |
| `PLATFORM_SIDE_BOTH` | 両側 |

- 「内側/外側」は絶対的な左右ではなく、**都市の通行方向（`GET /api/v1/city` の `traffic_hand`）と線路の走行方向（`travel_direction`）を基準に左右へ解決する**。複線（一方通行の単線線路2本）では、左側通行なら相手線路が走行方向の右側に来るため 内側=走行方向右。右側通行なら 内側=走行方向左。`traffic_hand` はゲーム開始後変化しないため、セッション開始時に一度取得してキャッシュしてよい。
- 内側/外側は走行方向基準の概念なので、走行フレームで解決した左右を幾何フレーム（start→end 方向）へ変換する。**`DIR_BACKWARD` の線路は幾何の end→start 方向へ走行するため左右が反転する**。複線の上下線は幾何方向が同じで走行方向だけ逆のため、この反転が無いと外側指定でも両線のホームが同じ側に出てしまう。双方向（`DIR_BOTH`）は幾何方向をそのまま走行方向とみなす（§7.2 の単式ホーム）。
- この解決ロジック（`TrackPath.ResolvePlatformExtents`）は**バックエンドの敷地ポリゴン算出と鏡写し**であり、駅パスの敷地（土地の占有・区画判定）もホームのぶんだけ同じ側へ非対称に拡張される。片方だけ変えると敷地と見た目が食い違う。

### 7.2 複線駅の組み立て（相対式・島式）

「複線＝単線2本」の表現（§8）がそのまま駅にも適用される。複線の駅は単線の駅パスを2本並べて作り、専用の複線駅バリアントは持たない。

- **相対式ホーム**: 上下線とも `PLATFORM_SIDE_OUTSIDE` → 外側に2面
- **島式ホーム**: 上下線とも `PLATFORM_SIDE_INSIDE` → 線路間で向き合うホームが1枚の島に結合して描画される（§7.4）
- **単式（棒線駅）**: 双方向の単線1本＋片側ホーム。双方向単線では敷設方向に運行上の意味がないため、描く向きでもホームの側を選べる

### 7.3 描画仕様

プラットフォームは片側ごとに3つの要素で構成される。高さの正は `PLATFORM_SURFACE_ABOVE_SPLINE`（§1.2）。

| 要素 | 実体 | 位置 |
|---|---|---|
| 淵（線路側） | `platform` プレハブを SplineMesh 配置 | 原点＝線路中心線・線路面。縁（中心線から±1.5m固定）への横位置・立ち上がり・ホームを支える支柱はプレハブ形状（§1.2） |
| デッキ（上面） | 動的生成の厚さ15cmの板（上面＋底面＋外縁・妻面の小口） | 淵（中心線から1.5m固定）からホーム外縁（width/2+platform_width）まで、上面＝ホーム面-2cm。宙に浮いたスラブで、支柱は生成しない |
| 外縁 | `platform_wall` プレハブを SplineMesh 配置 | 原点＝線路中心線・線路面。外縁（±(width/2+platform_width)）への横位置はプレハブ形状（§1.2） |

- 淵・外縁は「右側用パーツ」規約（§1.2）の実寸配置（X引き伸ばし・ピボット補正なし）。プレハブ未配置ならその要素だけスキップされる
- デッキのマテリアルは `platform_panel` プレハブから採取する。**platform_panel が未配置でも共通コンクリートで描画される**（ホームは駅の視認性の本体のため、スキップにしない）
- ホームがある側では、架線柱（pole）はホーム外縁＋マージンの外側に立つ（§2）。防音壁（`wall_width` 設定時）は**ホームがある側には立てない**（乗降空間を防音壁で塞がないため。外縁の壁・柵は `platform_wall` が担う）。ホームの無い側は通常どおり立つ
- ホームがある側では道床の結合描画（§8のバラスト充填・壁省略・柱コリドー化）は行わない（ホームの下にバラスト充填帯が張られるのを防ぐ）。代わりにホームどうしの結合を判定する（§7.4）
- クリック判定コライダーはホーム込みの非対称ストリップ（幅= width＋左右のホーム幅、中心をホーム側へオフセット）
- 着工時の地形平坦化は、ホームが地形の起伏に埋もれないようホーム幅ぶん広げて均される（バックエンド側の処理。左右対称の近似）

### 7.4 島式ホームの結合描画

互いに向き合うホームを持つ2本の駅パス（上下線とも `PLATFORM_SIDE_INSIDE` 等）は、ホームを1枚の島として結合描画する。結合は近接線路の結合描画（§8）と同じくサンプル点単位・描画専用で、バックエンドのデータには影響しない。

判定（`TrackAdjacency.Compute`）: 自線路のホーム側サンプル点ごとに、以下をすべて満たす相手がいれば島式結合区間となる。

| 条件 | 閾値 |
|---|---|
| 相手が自分側を向いたホームを持つ駅パス | `platform_side` の左右解決後の値で判定 |
| 接線方向がほぼ平行 | `TRACK_MERGE_MAX_ANGLE_DEG`（20°）以下（§8.1と同じ） |
| Y差 | `TRACK_MERGE_MAX_DY`（1m）以下（§8.1と同じ） |
| 道床エッジ間ギャップ | 両ホームの `platform_width` の合計以下（＝デッキが届き合う距離） |

結合区間での挙動:

- **デッキ**: path_idの小さい側が、自分の淵から**相手の淵ライン（相手中心線から1.5mの固定位置）まで**全幅のデッキを1枚張り、相手側はその区間のデッキを張らない（バラスト充填の担当ルールと同じ二重生成防止）。デッキ幅が線路間隔から動的に決まるため、複線の間隔調整（敷設UI）にもそのまま追従する
- **platform_wall**: 両側とも省略される（島の中央に外縁の壁・柵が立たない）
- **架線柱・架線ビーム**: コリドー内で最小path_idの線路（主線路）だけが、**島全幅**（相手線路の外縁側ホーム込み）の左右端＋マージンに柱を立てて梁を渡す（§8.2の柱コリドー化と同じ主線路方式）。島の中央に柱は立たない
- 淵（`platform`）と軌道・架線は各線路が従来どおり自分の分を描く（島の両縁に黄線が出る）

島式が成立しない近接（ギャップが両ホーム幅の合計を超える、または向き合うホームが無いのに他線路の道床がホーム外縁に掛かる等）では、その区間の `platform_wall` を省略し、デッキを相手道床の手前までクランプする（壁・デッキが他線路の本体に被るのを防ぐ。§8.2の壁の物理ブロック判定と同じ考え方）。

敷設プレビュー（§8.4）はプレビューの線どうしに結合を適用しないため、島式駅のプレビューでは2枚のデッキが独立に描かれ、確定時に1枚の島へ切り替わる。隣接線路の新設・撤去による結合状態の更新は §8.3 の再生成機構に乗る。

## 8. 近接線路の結合描画（複線見え化）

内部データに「複線線路」という単位は存在せず、複線は**一方通行の単線線路を2本並べたもの**として表現される。そのまま描画すると防音壁や架線柱が線路の間にも立つ「単線×2」の見た目になるため、近接して並走する線路どうしを1つの**コリドー**とみなし、パーツを結合して描画する。この結合は**描画専用**であり、バックエンドのデータ・経路探索・転回制約には一切影響しない。

### 8.1 結合の判定

自線路の描画点列（約5m間隔サンプル）の各点で、近傍の**同じ path_type** の線路への最近接点を求め、以下をすべて満たす場合に「その側に隣接線路がいる」とみなす（`TrackAdjacency.Compute`）。

| 条件 | 閾値（`LocalConstants`） |
|---|---|
| 道床エッジ間のXZギャップ（中心線間距離ではない） | `TRACK_MERGE_MAX_EDGE_GAP`（4m）以下 |
| Y差（描画点列＝地形追従済みの高さで比較。高架と地上は結合しない） | `TRACK_MERGE_MAX_DY`（1m）以下 |
| 接線方向の角度差（内積の絶対値で判定。上り線・下り線で敷設方向が逆でもよい） | `TRACK_MERGE_MAX_ANGLE_DEG`（20°）以下 |

接線方向の条件には例外があり、**合流・分岐で収束中の線路**（角度差が `TRACK_MERGE_MAX_CONVERGE_ANGLE_DEG`（45°。ノードの転回制約 `RAIL_MAX_TURN_ANGLE_DEG` と同値）以下）は、道床エッジ間ギャップが結合閾値以下まで近づいていれば接線が揃う前でも結合を開始する。接線が20°以下に揃いきるのを待つと、複線どうしの合流では道床が重なり始めてからようやく路盤結合が始まり、線路間の防音壁が相手の線路本体に被ってしまうため、結合は合流の手前から始める。

また、最近接点が**相手線路の端点へのクランプ**（交差点ハルで切り詰められた相手の端点が、自線路の中心線近傍——反対側＝外側のこともある——へ投影されたもの）で、かつ道床どうしが重なる距離の場合は、幾何的な虚像として隣接に採用しない。これを許すと合流ノードの手前で外側の防音壁が数mだけ抜け落ちる（壁の途切れ）。

隣接はエッジギャップの**チェーン連結**で束ねられ、3本以上の並走も1つのコリドーになる。判定は点ごとに行われるため、分岐で徐々に離れていく線路は閾値を超えた地点から自然に結合が解ける（防音壁・架線柱がそこから復活する）。工事中（STATUS_CONSTRUCTING）の線路は完成パーツを描画しないため、結合相手に含めない。

### 8.2 パーツごとの結合内容

| パーツ | 結合区間での挙動 |
|---|---|
| `body` | 道床どうしの隙間を、道床マテリアルを共有する水平のバラスト帯（ギャップフィラー）で埋めて一体の道床に見せる。二重生成を防ぐため**path_idの小さい側**が充填を担当する。フィラーは両側の道床に0.5m食い込ませ（裂け目防止）、道床天端から2cm沈めて（Zファイティング防止）バラストの肩の下に潜り込ませる |
| `wall` | 結合している側（線路間）の防音壁を区間クリップ（`clipFrom`/`clipTo`）で省略する。外側の壁は各線路が従来どおり自分の分を立てる。加えて結合判定とは**独立の角度不問の判定**として、他線路の道床が壁の位置に物理的に掛かる区間（合流の喉元・浅い角度の平面交差など、壁が相手の線路本体を横切ってしまう場所）でも壁を省略する。また、パスの端（ハルの切断面）に接する短い壁区間は「相手の点列がハル縁で終わることによる結合の取りこぼし」とみなして生成しない（交差点の分岐フラン上に壁スタブが立つのを防ぐ。その側が全長無結合のパスには適用されない） |
| `pole` / `beam` | コリドー内で**最小path_idの線路（主線路）**だけが、コリドー全幅の左右端＋マージンに柱を立て、柱間に梁を渡す（梁は柱間中央へ横移動し、柱間の幅に引き伸ばされる）。他の線路は結合区間では柱・梁を置かない。主線路と他線路で `wire_spacing` の位相は揃わないが、結合区間では他線路の柱自体が消えるため問題にならない |
| `track` / `wire` | 結合しない。各線路が自分の軌道・架線を従来どおり描く（軌間・架線位置は不変） |

道床（body）プレハブが無いバリアント（モノレール等）ではギャップフィラーも生成されない。

### 8.3 隣接線路の再生成（結合状態の更新）

線路が新設・変更・撤去されても、並走する既存線路の version は変わらないため、そのままでは既存線路の結合状態（線路間に残った防音壁など）が古いまま残る。PathManager は線路のデータ変更（新規・version変化・削除）を検知すると、その通過セル＋隣接セルにある同種線路を再生成キュー（地形追従と同じ視野優先・フレーム予算制ワーカー）へ積んで描き直す。隣接線路の点列・幅・ホーム張り出し幅（島式結合の判定用。§7.4）は `TrackAdjacency.NeighborProvider`（PathManager が実装を提供）経由で取得され、プロバイダ未設定の環境（メッシュ確認用テストシーン等）では従来どおり単独描画になる（ホームは自幅の単独デッキ）。

### 8.4 敷設プレビューでの複線表示

UIの建設パネルで複線（線路数≥2）を選んで敷設している間の3Dプレビューも「単線パス群の平行配置」として描かれる。UIが各線の横オフセット（`lateral_offsets`）と進行方向（`travel_directions`。IPC仕様は [IPC連携の整理](../programs/IPC連携の整理.md) 参照）をUnityへ渡し、プレビュー生成（`RoadRenderer`）が中心線をオフセットした点列ごとに本節と同じ `TrackPath` でメッシュを1本ずつ生成する。進行方向は各線の仮 PathSummary の `travel_direction` に載るため、駅バリアントのホーム設置側（§7.1）と進行方向矢印（§9）は確定後と同じ見た目でプレビューされる。プレビューは仮データのため、結合描画（§8.1〜8.2）や交差点処理はプレビューの線どうしには適用されず、確定して実パスになった時点で通常の結合描画に切り替わる。

## 9. 進行方向矢印（一方通行線路の編集支援表示）

一方通行の線路（`travel_direction` が DIR_FORWARD / DIR_BACKWARD）には、進行方向を示す平板の矢印オーバーレイ（`TrackDirectionArrows`）が線路コンテナの子として生成される。双方向（DIR_BOTH）の線路には何も付かない。

- **表示は道路敷設モード（STATE_EDIT_PATH）のみ**。既存の一方通行線路に向きの対（複線化）を作って接続する際の編集支援表示であり、通常プレイ中は非表示。表示切替は `IpcStateCoordinator` がステート変更時に `TrackDirectionArrows.SetVisible` を呼び、登録済み全インスタンスを一括で active/inactive にする（敷設モード中に再生成された線路の矢印も生成時に現在の表示フラグへ従う）
- **描画**: スプラインに沿って25m間隔（両端から半間隔のクリアランス。短い線路は中央に1枚）で、進行方向へ向けた矢印を1枚の結合メッシュとして生成する。DIR_BACKWARD は幾何の終点→始点方向の通行なので接線を反転して向ける。高さは `RoadPartHeights.DIRECTION_ARROW_ABOVE_SPLINE`（レール踏面より上）
- **色は固有色（黄色）を維持する**: 矢印のレンダラーは `VisualModeObject` のマテリアル変更対象外（`ShouldPreventMaterialChange`）なので、ホバーハイライトや計画中（灰色塗り）でも矢印の色は変わらない
- 敷設中のプレビュー（§8.4）にも、UIから渡された各線の `travel_directions` に従って矢印が付く（一方通行の線のみ。進行方向トグルの切り替えが即座にプレビューへ反映される）
