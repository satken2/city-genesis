# マテリアルの解決

## 概要

メッシュ生成器が組み立てたジオメトリに、**どのマテリアル実体を割り当てるか**を決める仕組み。
建物（[F_建物メッシュの生成](F_建物メッシュの生成.md)）・道路（[G_道路メッシュの生成](G_道路メッシュの生成.md)）・線路（[N_線路メッシュの生成](N_線路メッシュの生成.md)）・
駅舎パス（[Q_駅舎パスのメッシュ生成](Q_駅舎パスのメッシュ生成.md)）が共通で従う規約を記述する。

マテリアルの供給元は3種類しかない。

| 供給元 | 実体 | 使う場面 |
| --- | --- | --- |
| **パーツプレハブ** | プレハブの `MeshRenderer.sharedMaterials` | 壁・角・道路本体・歩道など、アセットとして存在するパーツ |
| **Resources 直下の共通マテリアル** | `Assets/Resources/*.mat` | プロシージャル生成した面（基盤・土マウンド・交差点アスファルト等）と、全フォールバックの終着点 |
| **動的生成（複製）** | 実行時に `new Material(...)` | Resources にも見つからないときの保険（白い箱・白い板） |

「マテリアルを持たない面」は原則として作らない。どの経路でも最終的に何らかのマテリアルへ落ちる
（唯一の例外が地面パネル。§3.3）。

なお本ドキュメントは**メッシュ生成時の解決**を扱う。生成後にホバー・地区色分け・ヒートマップで
マテリアルを差し替える層は別系統で、§6 に概要だけ記す。
マテリアルを**複数アセット間で共有**するための命名規約とエクスポート手順は
[P_マテリアル共有とエクスポート](P_マテリアル共有とエクスポート.md) を参照。

## 1. 2つの解決方式

建物とパスで方式が異なる。**この違いが本ドキュメントで最も重要な点**である。

| | 建物 | パス（道路・線路・駅舎） |
| --- | --- | --- |
| 方式 | プレハブの `sharedMaterials` を**そのまま**使う | マテリアル**名**をキーにした共有プールを必ず経由する |
| 入口 | `BuildingMeshUtils.GetModuleMaterials` / `CombineModuleMeshes` | `RoadPath.GetOrCreateRoadMaterial` |
| 同名 `.mat` の探索 | しない | する（`Resources.Load<Material>(名前)`） |
| 複製 | しない（アセットの実体を共有） | する（必ず複製を作り、それを共有） |
| 描画設定の補正 | なし | `renderQueue` を +1（Zファイティング回避） |

建物側で同名マテリアルが1実体に寄るかどうかは、**Unity の FBX インポート設定（`materialSearch: RecursiveUp`）に
依存する**（[FBXのインポート](P_マテリアル共有とエクスポート.md#fbxとラッパープレハブ)）。コード側では名前解決を行わない。

## 2. パスのマテリアル解決（名前キーの共有プール）

### 2.1 GetOrCreateRoadMaterial

道路パーツのマテリアルは、必ず `RoadPath.GetOrCreateRoadMaterial(source)` を通す。

```
source（プレハブの sharedMaterial 等）
  │
  ├─ static キャッシュに source.name のキーがある → それを返す（以降ずっと共有）
  │
  ├─ Resources.Load<Material>(source.name) が成功 → そのアセットの複製を作る
  │
  └─ 失敗                                        → source の複製を作る
        │
        ▼
  renderQueue = （元の値）+ 1 を一度だけ適用してキャッシュへ登録
```

要点：

- **キーはマテリアル名**。異なるプレハブが同名マテリアルを持てば、実体は1つに集約される。
- **必ず複製を作る**。`renderQueue` を書き換えるため、Resources のアセット実体をそのまま使うと
  プロジェクトのアセットを汚してしまう。「同名 `.mat` があればそれ**を使う**」ではなく
  「同名 `.mat` があればそれ**を元に複製する**」が正確な挙動。
- キャッシュは static なので、パスの再生成（LOD切替・交差点更新・敷設プレビュー）を繰り返しても
  マテリアルは増えない。
- **プレハブの `sharedMaterials` を直接レンダラーへ渡してはならない。** 通常道路と
  交差点・歩道コネクタで解決結果がずれ、交差点の中だけ色味や描画順が変わる。

### 2.2 部位ごとの解決順

| 部位 | 解決順 |
| --- | --- |
| 道路本体・区画線・歩道・防音壁・中央分離帯・街路樹・柱・坑口 | パーツプレハブのマテリアル → `GetOrCreateRoadMaterial` |
| パス本体のプレハブが無いとき（明灰色の板フォールバック）・パーツの材質配列が空のとき | URP対応の `Resources/BuildingMaterial` → `GetOrCreateRoadMaterialByName` の共有プール |
| 交差点アスファルト | 代表バリアントのマスターの `body_material`（§2.3）→ 代表バリアントの `body` プレハブ → `Resources/PATH_ASPHALT` → `Resources/NodeMaterial` |
| 遠景モデル（`far`） | パーツプレハブのマテリアル → `GetOrCreateRoadMaterial` の `DepthOffsetLit` 版（元マテリアルごとに共有） |
| 遠景モデルの無いパスの遠景の板・沿道アクセスの路面・高速道路の結合部の埋め面 | マスターの `body_material`（§2.3）→ `body` プレハブの代表材質。遠景の板はどちらも無ければ `Resources/Road` で、`DepthOffsetLit` 版を使う |
| 交差点の歩道コネクタ・エンドキャップ | 通常道路と同じ `sidewalk` プレハブ → `GetOrCreateRoadMaterial` |
| 駅ホームのデッキ | `platform_panel` プレハブのマテリアル → `GetOrCreateRoadMaterial`。プレハブが無いときは共通コンクリート（§3.4） |
| LRT停留所のホームの簡易スラブ（`lrt_platform` パーツが無いときの代替） | 共通コンクリート（§3.4） |
| 工事中パスの土ストリップ | 建物と共通の土マテリアル（§3.4）→ `GetOrCreateRoadMaterial` |
| 一方通行線路の進行方向矢印 | `Resources/PathColorMaterial` の複製に色を焼き込んだ専用マテリアル（静的キャッシュ） |
| ノードマーカー | `Resources/NodeMaterial` |

交差点の代表バリアント選択（踏切では道路側を優先）は [G_道路メッシュの生成](G_道路メッシュの生成.md) §11.5 を参照。

### 2.3 マスターデータからの名指し（body_material）

パスマスターの `body_material` は、そのバリアントの路面を代表するマテリアル名
（`Assets/Resources/` 直下の `.mat` 名）である。プレハブを介さず**名前だけ**で共有プールを引く経路で、
`RoadPath.GetOrCreateRoadMaterialByName` が入口になる。解決の中身は §2.1 と同じ
（キャッシュ → `Resources.Load` → 複製 → `renderQueue` +1）で、Resources に同名の `.mat` が
無ければ null を返し、呼び出し側がプレハブ経由の解決へフォールバックする。

交差点、遠景モデルの無いパスの遠景の板、沿道アクセスの路面、高速道路の結合部の埋め面で使う。
これらの生成面が代表する路面材質を、マスターデータで宣言する（舗装路 `PATH_ASPHALT` /
未舗装路 `PATH_SAND` など）。遠景の板は、この設定をバリアントごとに1度解決して保持する。
通常・接写の道路本体は body プレハブのサブメッシュごとの材質で描くため、路面と側面などの
材質の区別を保つ（`body_material` は詳細モデルの見た目を上書きしない）。

## 3. 建物のマテリアル解決

### 3.1 パーツから来るマテリアル

壁・角・フェンス・塔屋・エントランス・既成建物パーツ・マッシュアップのサブ建物・
工事中の足場とクレーンは、**プレハブのサブメッシュ構成をそのまま持ち込む**。

- `CombineModuleMeshes` がプレハブ配下の全メッシュを結合し、サブメッシュと同じ順序で
  マテリアル配列を返す。サブメッシュ数がマテリアル数を超える場合は最後の要素を繰り返す。
- 返すのは `sharedMaterials` の参照であり、複製しない。同じパーツを使う建物どうしは
  `ModelManager` のパス単位キャッシュ（§5）を介して**同一のマテリアル実体を共有**する。
- パーツが見つからない場合はマテリアル解決以前にジオメトリが生成されない
  （パーツのフォールバック階層は [F_建物メッシュの生成](F_建物メッシュの生成.md) §5）。

### 3.2 マテリアル参照専用パーツ

プロシージャルに張る面（屋根面・妻壁・地面パネル・岸壁スラブ）には形状となるパーツが存在しない。
そこで、**形状は使わずマテリアルだけを供給するパーツ**を置く規約になっている。

| パーツ | 供給先の面 | 解決順 |
| --- | --- | --- |
| `ceil` | 平屋根の屋上パネル、住宅風三角屋根・切妻屋根・片流れ屋根の屋根面、施工済み階の天面、岸壁の側面・下面 | `ceil` パーツ → 呼び出し側が渡すフォールバック配列（＝躯体の壁マテリアル）の先頭の非 null → `Resources/BuildingMaterial` |
| `generic-wall` | 切妻屋根・片流れ屋根の妻壁 | `generic-wall` パーツ → フォールバック配列 → `Resources/BuildingMaterial` |
| `floor` | 地面パネル、岸壁の上面 | §3.3 |

これらは建物本体と同じ閾値フォルダ（[F_建物メッシュの生成](F_建物メッシュの生成.md) §4）から取得する。

### 3.3 地面パネル（floor）だけの特別扱い

地面パネルは「描かない」という選択肢を持つ唯一の面である。マスターデータの `draw_floor=yes` の
建物だけが対象で、マテリアルは次の順で解決する。

```
a{variant} の floor パーツ
    ↓ 無い
b{bd_type} の floor パーツ     ※ a と b が同じプレフィックスに解決される場合はスキップ
    ↓ 無い
Models/Buildings/common/floor  ※ common は閾値フォルダを挟まない
    ↓ 無い
null → 地面パネルを描画しない（既定マテリアルへはフォールバックしない）
```

既定マテリアルへ落とさないのは、地面パネルが不要な地面アセット（タイルだけを置くソーラー発電所など）に
意図しないスラブが敷かれるのを防ぐため。各段の閾値フォルダは `floor` パーツ単独で走査する
（建物本体の閾値とは独立）。この解決は駅舎パスの専有エリアの地面パネルとも共有している
（[Q_駅舎パスのメッシュ生成](Q_駅舎パスのメッシュ生成.md) §1。ただし駅舎パスに `draw_floor` 相当のフラグは無く、パーツの有無だけで決まる）。

### 3.4 全建物共通の Resources マテリアル

パーツに依存しない面は、Resources 直下の共通マテリアルを静的キャッシュして使う。
どれも1実体を全建物で共有する。

| 用途 | 解決順 |
| --- | --- |
| 既定の建物マテリアル（白い箱・遠景の建物・全フォールバックの終着点） | `Resources/BuildingMaterial` |
| 共通コンクリート（`BuildingMeshBuilder.GetCommonConcreteMaterial`） | `Resources/COMMON_CONCRETE` → `Resources/BuildingMaterial`（`.mat` が無いときは警告を出す） |
| 工事現場の土（建物の土マウンド／パスの土ストリップ共用） | `Resources/ConstructionDirt` → `Resources/ConstructionMaterial` → `Resources/BuildingMaterial` |

共通コンクリート（無彩色のグレー）を使う面は次のとおり。

- コンクリート基盤（傾斜地の谷側を埋める柱状の押し出し。[F_建物メッシュの生成](F_建物メッシュの生成.md) §8.2）
- オープンスペースの面のうち、`floor` パーツも床材の指定も無いもの（[F10_オープンスペースのメッシュ生成](F10_オープンスペースのメッシュ生成.md)）
- 駅ホームのデッキ（`platform_panel` プレハブが無いとき）と、LRT停留所のホームの簡易スラブ（`lrt_platform` パーツが無いとき）
- 埋立地の岸壁の天端と垂直の面（[D_地形形状](D_地形形状.md) §D.17.5）。地形より手前に描くため、建物と同じ共有の DepthOffset 版（`BuildingManager.GetSharedDepthOffsetMaterials`）にして使う

### 3.5 最終保険とサブメッシュ統合

- **`EnsureMaterials`** — `BuildingMeshBuilder.Generate` の戻り値に対して必ず走る最後の保険。
  マテリアル配列が null／空なら `Resources/BuildingMaterial` を1つ割り当て、配列内の null 要素も
  同じもので置き換える。したがって**建物のサブメッシュがマテリアル無しで出てくることはない**。
- **`MergeSubMeshes`** — 同じマテリアルのサブメッシュを1つに統合してドローコールを減らす。
  同一判定のキーは**マテリアルの実体ID**であり、名前ではない。**同名でも別インスタンスなら統合されない**
  ため、共有が効いているかどうかがそのまま描画負荷に出る（[共有の単位](P_マテリアル共有とエクスポート.md#共有の単位)）。

## 4. 解決結果の適用

- **建物** — `BuildingMeshResult` の `Materials`（サブメッシュと同順の配列）を
  `MeshRenderer.sharedMaterials` へそのまま設定する。
- **パス** — 生成器がパーツごとの子オブジェクトを作り、その `MeshRenderer` へ設定する。
  親オブジェクトの `MeshRenderer` は使わない（`PathMeshResult.Mesh` はコライダー専用）。

## 5. モデルのロード経路

マテリアルの供給元であるプレハブは `ModelManager.GetModel(リソースパス)` が解決する。

1. `persistentDataPath` 配下の glTF（`.glb`）を探し、あれば実行時インポートする
2. 無ければ `Resources.Load<GameObject>(リソースパス)` でプレハブを読む
3. 結果は**リソースパス単位**でキャッシュする（見つからなかったパスも記録し、再探索しない）

キャッシュがパス単位であることは共有の粒度をそのまま決める。**同じパーツを使う建物・道路は
マテリアルまで含めて1実体を共有するが、別ファイルの同名マテリアルは（パス側の名前プールを通らない限り）
別実体になる**。glTF 経路の制約と対策は [共有の単位](P_マテリアル共有とエクスポート.md#共有の単位) を参照。

## 6. 生成後のマテリアル上書き（別系統）

ホバーハイライト、status（計画中・工事中）の色、地区色分け、数値ベースのヒートマップは、
**メッシュ生成後に `VisualModeObject` がレンダラーのマテリアルを差し替える**ことで表現する。

- 生成直後の `sharedMaterials` を「元のマテリアル」として記憶し、モード解除時に復元する。
- 上書き用マテリアル（`HighlightMaterial` / `PendingMaterial` / `PlannedMaterial` /
  `ConstructionMaterial` / `PreviewBuildingMaterial` / `ZoneMaterial1`〜`4` /
  `PathColorMaterial` / `BuildingColorMaterial` 等）はいずれも Resources 直下のアセット。
- スプライトや文字、進行方向矢印のように固有色を保つべきレンダラーは上書き対象から除外される。

したがって、本ドキュメントで解決したマテリアルは「素の見た目」であり、表示モードによっては
画面に出ないことがある。表示モードの詳細は UI・表示モード側のドキュメントを参照。

## 7. 新しい生成器を書くときの規約

- パス系のメッシュを描くなら、**マテリアルは必ず `RoadPath.GetOrCreateRoadMaterial` を経由**する。
  プレハブの `sharedMaterials` を直接使うと、隣接する通常道路と見た目がずれる。
- 建物系でプロシージャルな面を張るなら、**マテリアル参照専用パーツ（`ceil` / `floor` /
  `generic-wall`）か共通 Resources マテリアルのどちらかに寄せる**。生成器ごとに独自の
  `Resources.Load` を増やさない。
- **`new Material(...)` を毎回呼ばない。** 複製が必要な場合も静的キャッシュに載せ、名前や用途を
  キーに1実体へ集約する。
- 共有を効かせたいマテリアルは、まず**名前を揃える**（[マテリアル名](P_マテリアル共有とエクスポート.md#マテリアル名)）。
  実体の共有は名前の一致を起点にしか成立しない。
