# D. 地形形状

地形データを管理する `Terrain` シングルトンと、3段階のLOD（Level of Detail）を持つ標高マップについて。

## D.1. 何のためのデータか

地形形状は、都市ワールドの標高をグリッドデータ（ラスター）として保持し、3D描画のLODや道路・建物の工事による地形変更を支える。遠景は常に描画し、視点周辺は近景で描画する。超近景はさらに細かく、道路の盛土・切土などランタイムでの地形変更を反映する。

## D.2. Terrainシングルトン

地形データは `Terrain` クラス（`app/entities/terrain.py`）のシングルトンで管理される。CityやGameData3と同じ `__new__` パターンで、プログラム起動時に1つのインスタンスが作られる。

### D.2.1. 設定値

| プロパティ                 | 意味           |
| --------------------- | ------------ |
| `map_height`          | マップの高さ(m)    |
| `map_width`           | マップの幅(m)     |
| `cell_size`           | セル分割サイズ(m)   |
| `far_map_spacing`     | 遠景グリッド間隔(m)  |
| `near_map_spacing`    | 近景グリッド間隔(m)  |
| `dynamic_map_spacing` | 超近景グリッド間隔(m) |

これらの値はユーザーが任意に設定できるが、`check_settings_integrity` で整合性が検証される。具体的には、全ての値が正の整数であること、マップの縦横がセルサイズの整数倍であること、遠景間隔が近景間隔の整数倍であることなど。

### D.2.2. 計算で導かれる値

設定値から以下が計算される:
- `cells_x = map_width / cell_size`（横方向のセル数）
- `cells_y = map_height / cell_size`（縦方向のセル数）
- `far_map_shape`（遠景マップのピクセルサイズ）
- `near_map_shape`（近景マップのピクセルサイズ）
- `dynamic_map_cell_shape`（超近景マップ1セル分のピクセルサイズ）

## D.3. 3段階のLOD

### D.3.1. 遠景（far_map）

最も粗いグリッド間隔の標高マップ。マップ全体をカバーし、常に全て描画される。ランタイムでは変更されない。`np.float16` の2次元配列。

### D.3.2. 近景（near_map）

中程度のグリッド間隔の標高マップ。マップ全体をカバーし、視点中心とその周辺セルの描画に使用する。ランタイムでは変更されない。`np.float16` の2次元配列。

### D.3.3. 超近景（dynamic_map）

最も細かいグリッド間隔の標高マップ。セル単位で管理され、道路の敷設や建物の建設によって地形が変更される。例えば傾斜地に道路を引くと、道路範囲内が平坦になり、周辺が盛土や切土になる。

遠景と近景がマップ全体を1つの配列で持つのに対し、超近景はセルごとに独立した配列として管理される。これは、マップ全体を超近景の解像度で一括保持するとデータ量が膨大になるため（例: 100km四方 × 1m間隔）。

## D.4. セルの概念

マップ全体を `cell_size` (m) 四方の「セル」に分割する。セルは3D描画におけるロード・アンロードの単位であり、Cities: Skylinesなどの都市シミュレーションゲームと同様の考え方。

セルの位置は `(cell_x, cell_y)` のインデックスで指定し、左下（または下）が (0, 0)。セルIDは `cell_y * cells_x + cell_x` で計算される。

#### D.4.4. フロントエンド（Unity）とのセルインデックス対応関係
バックエンドのセルインデックス `(bx, by)` は常に 0-based の非負の値（`(0, 0)` がマップの左下隅）である。
一方、フロントエンド（Unity）側ではワールド原点 `(0, 0, 0)` をマップの中央としているため、Unityのセルインデックス `(ux, uy)` は負の値も含み、以下のように一対一で正確にマッピングされる。
- `ux = bx - offsetX`
- `uy = by - offsetY`
ここで、オフセット値 `offsetX = map_width / (2 * cell_size)`、`offsetY = map_height / (2 * cell_size)` である。
整合性ルールによりマップサイズはセルサイズの2倍の整数倍であることが保証されているため、このオフセットは常に整数となり、セル同士が一対一でズレなく完全に対応する。

### D.4.1. セルの確保と解放

超近景マップは最初から全セル分が存在するわけではなく、プレイヤーがセルを使い始めたときに初めて作られる。`acquire_cell` でセルを確保し、`release_cell` で解放する。

### D.4.2. 超近景のスワッピング

メモリ上にキャッシュできるセル数には上限（`MAX_REAL_MAP_CACHED`）がある。上限を超えると、最も古いアクセスのセルがディスクに書き出され、メモリから解放される。再度アクセスされた場合はディスクから読み込まれる。このLRU（Least Recently Used）ベースのスワッピングにより、広いマップでもメモリ効率よく超近景データを扱う。

### D.4.3. dirty管理

超近景データが道路工事等で変更されると、該当セルはdirtyとしてマークされる。dirtyセルは解放時にディスクに書き出され、明示的な `flush_cell` や `flush_all` でも書き出される。

## D.5. 任意範囲の切り出し

`extract_region` は、座標（メートル単位）で指定した任意の矩形範囲の超近景標高マップを切り出す。複数セルにまたがる場合は、必要な全セルをロードして結合する。セルをまたぐ道路の敷設などで使用される。

## D.6. 標高マップの更新

`update_dynamic_map` は、指定位置に超近景データを書き込む。道路の敷設や建物の建設による標高変更に使用する。書き込み後、該当セルはdirtyとしてマークされ、メモリとディスクの両方が即時更新される。

## D.7. フロントエンドとの通信

標高マップはfloat16（半精度浮動小数点）リトルエンディアンのrawバイナリとしてフロントエンドに提供する。16bit PNGを使わずrawバイナリを選ぶ理由は、Unity側で受信バイト列から半精度→単精度への変換を行いつつ `float[,]` → `TerrainData.SetHeights()` へ変換でき、PNGデコードのオーバーヘッドや精度ロスを回避できるため。HTTPレベルのgzip圧縈により転送量は自動的に削減される。

APIエンドポイントは以下の通り:

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/api/v1/terrain/far` | 遠景（float16 LE raw） |
| GET | `/api/v1/terrain/near` | 近景（float16 LE raw） |
| GET | `/api/v1/terrain/dynamic` | 超近景（float16 LE raw、セル指定・範囲指定） |
| PUT | `/api/v1/terrain/dynamic/rect` | 超近景更新（float16 LE raw、rows/colsで形状指定） |
| GET | `/api/v1/terrain/water` | 水面（海面以外の湖など）のポリゴン一覧 |
| GET | `/api/v1/terrain/settings` | 設定値取得 |
| PATCH | `/api/v1/terrain/settings` | 設定変更 |
| POST | `/api/v1/terrain/acquire-cell` | セル確保 |
| POST | `/api/v1/terrain/release-cell` | セル解放 |

### D.7.1. 標高の表現範囲

データフォーマット自体に実質的な標高上限はない。`far_map`/`near_map`/`dynamic_map` はいずれも `float16` で、`Terrain.load_heightmap_data` が外部標高データを読み込む際に `±65504`（float16が表現できる範囲）へクリップするのみである。

一方、Unity側の描画では地形タイル生成時に標高（メートル）を0〜1へ正規化してから `TerrainData.SetHeights()` に渡しており、この正規化に使う垂直スパン（`TerrainManager.terrainSize.y`、既定1200m）を超える標高は描画上1.0に張り付き、それより上の起伏が失われてフラットに見える。この値は現在ゲームに登録されている地形マップ（青ヶ島の最高標高423mなど）に対して十分な余裕を持たせてあるが、より標高の高い地形マップを追加する場合はこの値を引き上げる必要がある（詳細は `city-genesis/unity` の `DataLoaders/AGENTS.md` を参照）。

## D.8. セーブ・ロード

地形データのセーブ・ロードは `terrain_serializer.py` で処理される。セーブZIP内の `terrain/` ディレクトリに設定値・遠景・近景・超近景セルが格納される。詳細は [[ii.セーブ・ロード]] を参照。

## D.9. 初期化

`init_game` で `Terrain` の `_init` と `init_maps` が呼ばれ、遠景・近景マップがゼロ初期化される。その後 `initialize_data` で中央セル1つ分の超近景マップが `acquire_cell` で確保される。実際の標高データはフロントエンドや外部ツールから設定される想定。

## D.10. 水面（海面以外の湖など）

標高0mの海面（ワールドY=0の板ポリゴン）とは別に、任意の場所に「水面ポリゴン」を配置できる。山上湖や貯水池のように、海面とは異なる標高（水位）を持つ平らな水面を3D上で表現するためのものである。

### D.10.1. データモデル

水面は1枚ごとに以下のフィールドを持つ、GeoJSONライクなオブジェクトである。

| フィールド | 意味 |
| --- | --- |
| `id` | マップ内で一意な識別子 |
| `water_level` | 水面のY標高(m)。heightmap と同じ絶対標高フレームで、海面が0。湖はそれぞれの水位を持つ |
| `kind` | 種別ラベル（任意。将来の見た目分岐用。現状は `"lake"`） |
| `polygon` | 水面の平面形状。`{"type": "Polygon"｜"MultiPolygon", "coordinates": [...]}`。座標はワールド座標（マップ中心が(0,0)）のXZ平面。穴（内周リング）も表現可能 |

水面は海岸線と同様に「マップ固有のオーサリング済み静的データ」で、near_map から導出できない。そのため地形マップの `.npy` と同じディレクトリ・同名（拡張子だけ `.water.json`）のサイドカーJSONに永続化され（サムネイルPNGと同じ命名規則）、`init_game` 実行時に読み込まれて `city.terrains["water_surfaces"]` にキャッシュされる。セーブデータにも保存され、ロード時に復元される。

### D.10.2. APIとレンダリング

フロントエンド（Unity）は `GET /api/v1/terrain/water` で水面一覧を取得し、各ポリゴンを `water_level` のY標高に置いた水平メッシュとして描画する（`WaterSurfaceManager`）。マテリアルとシェーダーは海面板と同じもの（`Custom/DepthOffsetLit`、`Offset -1,-1`）を用いるため、湖底（per-cellタイル）とのZ-fightingは海面と同じ深度オフセット階層で回避される。岸（水面より高い地形）では地形がワールドYの差で自然に手前へ描画される。詳細は [[E_LOD処理]] の「海面・水面の描画と深度オフセット」を参照。

### D.10.3. 海岸線への反映（穴あき形状）

水面は海岸線ポリゴンから差し引かれて「穴」になり、その上には土地区画や建物を作れなくなる（`is_within_coastline` 等の判定が水面を非陸地として扱う）。

このとき穴になるのは、オーサリングされた `polygon`（footprint）そのものではなく、**footprint の範囲内で地形標高が `water_level` を下回る領域だけ**である。footprint はあくまで「その水面が存在しうる範囲の上限」であり、その内側でも `water_level` より高い地形は陸地として残る（例えば水面の中に頭を出す小島や、水位より高い岸辺は陸地のまま）。これは、海面（`water_level` に相当する標高が0）が海岸線を形作るのと同じ考え方を、湖ごとの水位に対して適用したものである。したがって水位を上げれば水面（穴）は広がり、下げれば狭まる。

海岸線のGeoJSONは穴（Polygonの内周リング）とMultiPolygonを表現でき、Unity側の陸地内外判定（`CoastlineStore.IsLand`）も全リングへのeven-odd判定で穴を尊重する。

なお、川（次節）は水面（`water_surfaces`）には含めない。水面の契約は「単一の `water_level` を持つ水平面」であり、流下方向に水面標高が変化する川とは互換性が無いためである。

## D.11. 川（rivers）

地形エディタ（`city-genesis/tauri` の「川編集」タブ）で自動生成される河川。川床の彫り込み自体は標高データ（near_map の `.npy`）へ直接焼き込まれるため、ランタイムから見た「地形の谷」は通常の標高と区別されない。この節で定義するのは、その上へ水面を描画するための数値データ（流路スプライン＋深さ＋幅）と、建設不可判定用の平面形状である。

### D.11.1. データモデル

川は1本ごとに以下のフィールドを持つ。

| フィールド | 意味 |
| --- | --- |
| `id` | マップ内で一意な識別子 |
| `kind` | 種別ラベル。常に `"river"` |
| `centerline` | 川床中心線（タルウェグ）の3D点列 `[[x, y, z], ...]`（上流→下流）。x/z はワールド座標（マップ中心が(0,0)）、y は川床の絶対標高(m)（海面=0） |
| `widths` | 各点の川幅(m)。`centerline` と同じ要素数 |
| `surface_offsets` | 各点の水面オフセット(m)。**水面のY標高 = `centerline[i][1] + surface_offsets[i]`**。水面標高は流下方向に単調非増加 |
| `footprint` | 建設不可判定用の帯ポリゴン（中心線を左右に幅/2 だけオフセットした閉リング）。`{"type": "Polygon", "coordinates": [...]}`。座標系は水面の `polygon` と同じ |

### D.11.2. 永続化

水面（§D.10.1）と同じ方式で、地形マップの `.npy` と同じディレクトリ・同名（拡張子だけ `.rivers.json`）のサイドカーJSON（`{"version": 1, "rivers": [...]}`）に永続化される。地形エディタの作業コピーでは `meta.json` の `rivers` フィールドに保持される。エクスポート時は川が無くてもファイルを書き出し、以前のエクスポートで残った古い川が読まれ続けるのを防ぐ。

### D.11.3. 生成（地形エディタ）

流路はハイトマップから自動特定される。年間雨量と降雨範囲（選択マスク）をパラメータとして流量集積（flow accumulation）を計算し、流量が閾値を超えたセル列を川とする。流量は年平均ではなく豊水期（bankfull）相当の河道形成流量で、川幅・深さのスケーリング（hydraulic geometry）もこの流量に対して適用される。合流点では流量最大の枝が本流として通過し、他の枝は支流として合流終端する。既存の湖（water_surfaces）に流入する川は湖で分断され、溢出点から先は別の川になる。

流路には曲率駆動の蛇行進化シミュレーション（平地で蛇行が発達し、山地の急流や峡谷では直進する）が適用され、川床は流量に応じた幅・深さ（hydraulic geometry）で標高へ彫り込まれる。断面はカーブ外岸側が深く急峻な非対称形状で、低勾配・大流量の区間では中州（網状流路）が作られる。切断された蛇行ループを三日月湖として残す処理は現状スコープ外（将来拡張）。アルゴリズムの実装は `city-genesis/tauri/src/components/terrain/terrainRiver.ts`。

### D.11.4. レンダリング（将来実装）

ゲーム本体（Unity）での川の水面描画は未実装。実装方針は「`centerline` を Catmull-Rom スプライン（`RoadPath.BuildSpline`）で補間し、`widths` の幅を持つリボンメッシュ（`MeshFactory.BuildStripMesh` と同構成）を水面標高（`centerline[i][1] + surface_offsets[i]`）に張る」。地形エディタの3Dプレビュー（`Terrain3DPreviewCanvas`）が同じ構成のリボンを実装済みで、データ形式の参照実装を兼ねる。

### D.11.5. 海岸線への反映（将来実装）

`footprint` は水面の polygon と同列に `Terrain.compute_coastline_polygon` の穴あけ入力として使える平面形状であり、バックエンドが `.rivers.json` を読み込んで水面と同様に difference すれば、川の上は建設不可になる（バックエンド側の読み込みは未実装）。
