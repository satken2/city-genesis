# D. 地形形状

地形データを管理する `Terrain` シングルトンと、3段階のLOD（Level of Detail）を持つ標高マップについて。

## D.1. 何のためのデータか

地形形状は、都市ワールドの標高をグリッドデータ（ラスター）として保持し、3D描画のLODや道路・建物の工事による地形変更を支える。遠景は常に描画し、視点周辺は近景で描画する。超近景はさらに細かく、道路の盛土・切土などランタイムでの地形変更を反映する。

## D.2. Terrainシングルトン

地形データは `Terrain` クラス（`app/entities/terrain.py`）のシングルトンで管理される。CityやGameData3と同じ `__new__` パターンで、プログラム起動時に1つのインスタンスが作られる。

### D.2.1. 設定値

| プロパティ                 | 意味           |
| --------------------- | ------------ |
| `map_height`          | マップの高さ(m)    |
| `map_width`           | マップの幅(m)     |
| `cell_size`           | セル分割サイズ(m)   |
| `far_map_spacing`     | 遠景グリッド間隔(m)  |
| `near_map_spacing`    | 近景グリッド間隔(m)  |
| `dynamic_map_spacing` | 超近景グリッド間隔(m) |

これらの値はユーザーが任意に設定できるが、`check_settings_integrity` で整合性が検証される。具体的には、全ての値が正の整数であること、マップの縦横がセルサイズの整数倍であること、遠景間隔が近景間隔の整数倍であることなど。

### D.2.2. 計算で導かれる値

設定値から以下が計算される:
- `cells_x = map_width / cell_size`（横方向のセル数）
- `cells_y = map_height / cell_size`（縦方向のセル数）
- `far_map_shape`（遠景マップのピクセルサイズ）
- `near_map_shape`（近景マップのピクセルサイズ）
- `dynamic_map_cell_shape`（超近景マップ1セル分のピクセルサイズ）

## D.3. 標高データと描画LOD

初期自然地形near_mapと編集済みセルが標高の正となる。共通サンプラーが全域に固定した格子で補間し、編集標高を反映する。far/near/dynamicは保存・互換APIの名前であり、カメラ距離で別の地面へ切り替える描画ティアではない。

Unityは同じ標高から作った513格子のTerrainタイルを使用する。地形自身の画面上の細分化はUnity Terrainに任せ、建物・道路・プロップの描画LODは独立に選択する。詳細は [E_LOD処理](E_LOD処理.md)。

### D.3.1. 配列の向きと方位

ワールド座標は東が`+X`、北が`+Z`、上が`+Y`で、原点はマップ中心である。標高配列(近景・遠景・超近景・背景とも)は行0がZ最小の南端、列0がX最小の西端で、行が増えるほど北へ、列が増えるほど東へ進む。したがって配列の`[0, 0]`は南西隅に当たる。この並びはUnityの俯瞰(北を上にしたとき`+Z`が画面上)・コンパス・カメラyaw(北=`+Z`を0とする時計回り)と一致する。

外部の標高データ(画像やDEMは北→南の行順)は、取り込みツールが行を並べ替えてからこの向きで保存する。ゲーム内に行を反転する処理は持たないので、新しい取り込み経路を足すときも保存前に並べ替えること。

表示側で向きを合わせる箇所は2つある。都市マップと地形エディタの2D表示はCanvasのY軸が下向きなので、ビュー変換のY倍率を負にして`+Z`を画面の上に描く(文字だけはその描画でY反転を打ち消す)。地形エディタの3Dプレビューとサムネイルはthree.js(右手系)で描くので、ワールド座標のままでは東西が鏡像になる。地形・水面をZ倍率-1のグループに入れて鏡像を打ち消す。

## D.4. セル

セルは標高データの保存単位であり、Unityが地形タイルを作る単位でもある。ゲームルール上の意味は持たず、道路・建物・土地区画・資源はマップ全域のどこにでも置ける。

セルサイズは設定から取得する。バックエンドは左下原点の非負セル番号、Unityはマップ中心原点のため負の番号もある。変換はTerrainManagerの変換APIを使う。

編集用のfloat32配列はセル単位で持ち、そのセルの地形が実際に編集されるときにだけ生成される（無ければ共通サンプラーから作る）。新規都市は編集用配列を1つも持たずに始まり、描画は全域共通の `/terrain/surface` が担う。編集セルの共有辺・角の格子点は隣接セルへ同じ高さで反映する。

## D.5. 任意範囲の切り出し

バックエンドの `extract_region` は指定セル領域をfloat32で組み立てる。Unity描画には `/terrain/surface` を使用する。保存用配列やnear_mapをクライアントが独自補間して接地標高を作らない。

## D.6. 標高マップの更新

`update_dynamic_map` は入力を検証後、編集セルと共有格子点を持つ隣接セルへ反映し、版を増やす。変更したセルを保存対象にする。描画APIは版と標高を同じ読取ロック内で取得する。

## D.7. フロントエンドとの通信

| API | 内容 |
|---|---|
| GET /terrain/settings | マップ寸法・セルサイズ・標高範囲 |
| GET /terrain/surface | cell_x、cell_z、resolutionで指定する現在標高。little-endian float32、行Z・列X(行0が南端。D.3.1) |
| GET /terrain/cell-versions | 版を持つセルとその3x3近傍の描画版。一覧に無いセルは版0として扱う |
| GET /terrain/far | 現在標高の全域overview。互換形式float16 |
| GET /terrain/near | 初期地形の互換・編集用取得 |

surfaceは `X-Grid-Rows`、`X-Grid-Cols`、`X-Cell-Version` を返す。Unityは完成前のデータを公開せず、全帯の適用後に置換して高さキャッシュを無効化する。

## D.8. セーブ・ロード

初期地形と編集セルを保存する。標高はfloat32で復元し、編集精度をfloat16へ落とさない。表示用タイル・UnityのLODキャッシュは保存せず再生成する。

## D.9. 初期化

初期標高を読み込み、地形設定とnear/far配列を生成する。ロード・設定変更時は共通サンプラーの派生キャッシュを初期化する。海岸線の抽出は初期near_mapを基準とする。

## D.10. 水面（海面以外の湖など）

標高0mの海面（ワールドY=0の板ポリゴン）とは別に、任意の場所に「水面ポリゴン」を配置できる。山上湖や貯水池のように、海面とは異なる標高（水位）を持つ平らな水面を3D上で表現するためのものである。

### D.10.1. データモデル

水面は1枚ごとに以下のフィールドを持つ、GeoJSONライクなオブジェクトである。

| フィールド | 意味 |
| --- | --- |
| `id` | マップ内で一意な識別子 |
| `water_level` | 水面のY標高(m)。heightmap と同じ絶対標高フレームで、海面が0。湖はそれぞれの水位を持つ |
| `kind` | 種別ラベル（任意。将来の見た目分岐用。現状は `"lake"`） |
| `polygon` | 水面の平面形状。`{"type": "Polygon"｜"MultiPolygon", "coordinates": [...]}`。座標はワールド座標（マップ中心が(0,0)）のXZ平面。穴（内周リング）も表現可能 |

水面は海岸線と同様に「マップ固有のオーサリング済み静的データ」で、near_map から導出できない。そのため地形マップの `.npy` と同じディレクトリ・同名（拡張子だけ `.water.json`）のサイドカーJSONに永続化され（サムネイルPNGと同じ命名規則）、`init_game` 実行時に読み込まれて `city.terrains["water_surfaces"]` にキャッシュされる。セーブデータにも保存され、ロード時に復元される。

### D.10.2. APIとレンダリング

フロントエンド（Unity）は `GET /api/v1/terrain/water` で水面一覧を取得し、各ポリゴンを `water_level` のY標高に置いた水平メッシュとして描画する（`WaterSurfaceManager`）。マテリアルとシェーダーは海面板と同じもの（`Custom/DepthOffsetLit`、`Offset -1,-1`）を用いるため、湖底（per-cellタイル）とのZ-fightingは海面と同じ深度オフセット階層で回避される。岸（水面より高い地形）では地形がワールドYの差で自然に手前へ描画される。詳細は [[E_LOD処理]] の「海面・水面の描画と深度オフセット」を参照。

### D.10.3. 海岸線への反映（穴あき形状）

水面は海岸線ポリゴンから差し引かれて「穴」になり、陸地として扱われなくなる。穴の上に作られた土地区画は海上区画（`PARCEL_WATER`）になり、陸地を要求する通常の建物は建てられない（[B_土地形状](B_土地形状.md) B.5）。

このとき穴になるのは、オーサリングされた `polygon`（footprint）そのものではなく、**footprint の範囲内で地形標高が `water_level` を下回る領域だけ**である。footprint はあくまで「その水面が存在しうる範囲の上限」であり、その内側でも `water_level` より高い地形は陸地として残る（例えば水面の中に頭を出す小島や、水位より高い岸辺は陸地のまま）。これは、海面（`water_level` に相当する標高が0）が海岸線を形作るのと同じ考え方を、湖ごとの水位に対して適用したものである。したがって水位を上げれば水面（穴）は広がり、下げれば狭まる。

海岸線のGeoJSONは穴（Polygonの内周リング）とMultiPolygonを表現でき、Unity側の陸地内外判定（`CoastlineStore.IsLand`）も全リングへのeven-odd判定で穴を尊重する。

なお、川（次節）は水面（`water_surfaces`）には含めない。水面の契約は「単一の `water_level` を持つ水平面」であり、流下方向に水面標高が変化する川とは互換性が無いためである。

## D.11. 川（rivers）

地形エディタ（`city-genesis/tauri` の「川編集」タブ）で自動生成される河川。川床の彫り込み自体は標高データ（near_map の `.npy`）へ直接焼き込まれるため、ランタイムから見た「地形の谷」は通常の標高と区別されない。この節で定義するのは、その上に存在する「川」の実体、すなわち**範囲ポリゴン**と**水面標高のプロファイル線**である。流路スプライン（幅・深さ）は彫り込みのためのエディタ内部の中間データであり、ゲーム側には渡さない。

### D.11.1. データモデル

川は1本ごとに以下のフィールドを持つ。

| フィールド | 意味 |
| --- | --- |
| `id` | マップ内で一意な識別子 |
| `kind` | 種別ラベル。常に `"river"` |
| `polygon` | 川の範囲。`{"type": "Polygon"｜"MultiPolygon", "coordinates": [...]}`。座標系は水面の `polygon` と同じ（ワールド座標XZ、マップ中心が(0,0)）。中州・島は穴（内周リング）になる |
| `profile` | 水面標高のプロファイル線 `[[x, y, z], ...]`（上流→下流）。y は海面=0 の絶対標高(m)で、流下方向に単調非増加 |

**範囲内の任意地点の水面標高は「`profile` 折れ線上の最近点の y（線分内は線形補間）」で決まる。** この規則は地形エディタ（`riverGeometry.ts` の `RiverProfileSampler`）・バックエンド（`geo_rivers.py`）・Unity（`RiverStore`）で共通の契約であり、水面メッシュの頂点標高、パスの横断判定の水面標高はすべてこれで求める。

### D.11.2. 永続化

水面（§D.10.1）と同じ方式で、地形マップの `.npy` と同じディレクトリ・同名（拡張子だけ `.rivers.json`）のサイドカーJSON（`{"version": 2, "rivers": [...]}`）に永続化される。地形エディタの作業コピーでは `meta.json` の `rivers` フィールドに保持される。エクスポート時は川が無くてもファイルを書き出し、以前のエクスポートで残った古い川が読まれ続けるのを防ぐ。バックエンドは `version` が 2 未満のファイル（スプライン帯方式の旧形式）を読まない。

バックエンドは新規都市の初期化時（`init_game`）にサイドカーを読み込んで `city.terrains["rivers"]` にキャッシュし、セーブデータ（`city.json`）にも含める。

### D.11.3. 生成（地形エディタ）

流路はハイトマップから自動特定される。年間雨量と降雨範囲（選択マスク）をパラメータとして流量集積（flow accumulation）を計算し、流量が閾値を超えたセル列を川とする。流量は年平均ではなく豊水期（bankfull）相当の河道形成流量で、川幅・深さのスケーリング（hydraulic geometry）もこの流量に対して適用される。合流点では流量最大の枝が本流として通過し、他の枝は支流として合流終端する。既存の湖（water_surfaces）に流入する川は湖で分断され、溢出点から先は別の川になる。

流路には曲率駆動の蛇行進化シミュレーション（平地で蛇行が発達し、山地の急流や峡谷では直進する）が適用され、川床は流量に応じた目安の幅・深さ（hydraulic geometry）をもとに標高へ彫り込まれる。幅は横断地形の起伏と深さの比から目安の0.6〜1.4倍へ補正し、前後区間で平滑化する。狭い谷・横断斜面では細く、平坦な場所では広くなる。断面はカーブ外岸側が深く急峻な非対称形状で、低勾配・大流量の区間では中州（網状流路）が作られる。切断された蛇行ループを三日月湖として残す処理は現状スコープ外（将来拡張）。アルゴリズムの実装は `city-genesis/tauri/src/components/terrain/terrainRiver.ts`。

**川幅に下限は無く、小川や用水路も作れる。** ただし地形は格子点（near_map、既定10m間隔）の標高でしか表現できないため、格子間隔を下回る幅を指定しても、実際に彫られる溝と描画される水面の幅は1格子ぶんで頭打ちになる（指定幅は深さと流量には効き続ける）。彫り込みでは中心線までの距離から格子の半対角幅（spacing/√2）を差し引いて断面を評価する。中心線を覆う格子点に連続した川底を刻み、流路と格子の位置関係で深さが脈動するのを防ぐ。この補正は川幅によらず適用する。

**流路は手動でも作図・編集できる。** 川編集タブのポインタ操作は「降雨範囲の選択（自動生成用）」「川を描く」「ノード編集」の3モードで、「川を描く」は上流から下流の順に頂点を置いて右クリックで確定し、頂点を通る滑らかな曲線（centripetal Catmull-Rom）が流路になる。手動の川の流量は上流端・下流端の川幅から hydraulic geometry の逆算で決め、制御点での目安の幅は弧長で線形補間し、制御点間では逆算した流量を補間する。実際の河道幅には横断地形の補正が加わる。河口は終点の位置から自動判定する（海＝周辺の地形が0m以下、湖＝水面ポリゴンの内側、合流＝他の川の中心線から吸着半径以内（終点を相手の中心線上へ吸着）、それ以外＝接続なし）。彫り込み前の川はすべて「制御点」を持ち（自動生成した川は蛇行進化後の中心線を Douglas-Peucker で間引いたもの。合流点の流量段差は残す）、「ノード編集」で制御点のドラッグ移動・流路上クリックによる追加・右クリックによる削除ができる。編集のたびに制御点から中心線・河口・水面プロファイルを作り直し（標高は変えない）、本流を動かした場合はそこへ合流する支流の終点も新しい中心線へ吸着し直す。彫り込み済みの川と保存データから読み込んだ川は地形が既に変わっているためノード編集の対象外（Ctrl+Z で彫り込み前に戻す）。

**谷に沿った経路補正。** 未彫り込みの川の「谷に沿って経路を補正」は、現在の流路の左右に指定した探索距離（既定100m、10〜500m）の帯を取り、各横断面を順に通る連続経路を動的計画法で選ぶ。評価は低い標高を優先し、逆勾配・線分途中の尾根・迂回量・横移動の急変にペナルティを与える。始点・終点を固定し、既存の河口と合流先を保つ。戻り値は通常の制御点再構築へ渡すため、支流の吸着・プレビュー・Undoを共用する。補正自体では標高を書き換えず、補正後もノード編集できる。地図全域の最低経路を探すものではなく、ユーザーが描いた経路の周辺に限定する。

**水位と接岸。** 水面の基準は彫り込み前の地形。補正済みの川幅に格子の半対角幅・岸のなじみ帯・1格子の余裕を加えた横断範囲を半格子以下の間隔で調べ、前後半区間も含む最低標高から0.7m下に水面の上限を置く。前後平均で平滑化してもこの上限を超えず、下流方向のmin走査で水位を下げる。途中の尾根を越すために上流の水位を引き上げる処理は行わない。河口は海・湖・合流先の水位に合わせ、必要な背水区間はその境界水位を下限とする。したがって、不適切な経路のまま確定すると尾根を深く切り通すことがある。先に経路補正とプレビューで形を確認する。

川床はその水位から流量・深さ係数・曲率による深さを引いて求め、岸肩は水面+0.7mから元の地形へなじませる。標高は下げる方向にだけ更新する。中州判定の後に幅を追加拡大せず、調査済みの岸の範囲内に冠水砂州を作る。深さ係数の変更は川底に作用し、水位の再計算は行わない。

**範囲ポリゴンは彫り込み後の地形から抽出する。** 河道から連結して到達でき、水面プロファイルより低い格子点をMarching Squaresで閉リング化し、外周と穴に分類する。指定幅そのもので水面を切らず、岸のなじみ帯と格子の余裕まで水際を探す。乾いた格子点の実際の水位との差も補間に使い、岸線の簡略化誤差は格子間隔の0.02倍に抑える。これにより河道幅に沿った人工的な端ではなく、地形との交点で水面を閉じる。探索範囲には上限があり、海（地形標高0m以下）・既存の湖の水位以下・先に処理した大流量の川の領域は除外する。

「川の範囲を再計算」は現在の地形から水没部分を取り直す。スプラインが残っている川は調査帯を使用し、保存データから読み込んだ川は前回の範囲を上限とする。保存済み範囲の境界では岸線までの符号付き距離も使い、再計算のたびに水面が外へ膨らむのを防ぐ。

地形エディタは2Dキャンバスに範囲ポリゴンの塗り（穴は抜く）を、3Dプレビューに水面メッシュ（§D.11.4 と同構成）を表示し、ゲーム本体でどの範囲に水面が描かれるかを確認できる。彫り込み前の川は「彫り込みプレビュー」として、標高データを変えずに現在の深さ係数で彫った地形と、その上の水面範囲を表示する。深さ係数を変えるとプレビューが更新され、「確定して彫る」で初めて標高データへ焼き込まれる。水面表示を切ると川底の地形だけを確認できる。各川には2Dキャンバス上に一覧と同じ番号が付く。

検証: `tauri/tools/river-raster-regression-test.ts` は幅0〜60mの川底の連続性と範囲再計算を確認する。`tauri/tools/river-valley-regression-test.ts` は平地・斜面・尾根・変化する谷幅・山腹の曲線について水位、接岸、描画メッシュ外縁、谷への経路補正、非破壊性、海・湖・本流への水位接続を確認する。

### D.11.4. レンダリング（Unity）

Unity は `GET /api/v1/terrain/rivers` で川の一覧を取得し（`RiverSurfaceManager`）、川ごとに「範囲ポリゴンを覆う格子面」の水面メッシュを作る。格子間隔は 4m（`RiverStore.GRID_STEP`）。各頂点の Y は「その地点のプロファイル標高 + 微小な持ち上げ」で、湖の水平面と違い流下方向に沿って下る。ポリゴンを頂点ごとに三角形分割しないのは、細長く蛇行する川では外周頂点を結ぶ三角形が流下方向に長く伸び、頂点間の線形補間が実際の水面勾配から乖離するためである。描画は「4隅のいずれかが範囲内」のセルとその隣接1セルを採用し、岸線から最大2セルの余白を岸へ埋める。地形と水面の格子・三角形が異なる曲線区間でも水の板の端を露出させないためで、保存ポリゴン・川床マスク・干渉の占有範囲は拡大しない。Tauriの3Dプレビューも同じ描画規則を使う。

マテリアルは海面板（`Custom/WaterLit`）の複製で、流れモード（`_FlowEnabled`）を有効にし、頂点の UV2 に載せた流下方向（プロファイル線の最近線分の接線）へさざ波と泡を流す。深度オフセットや水際の扱いは湖と同じ（[E_LOD処理](E_LOD処理.md) の「海面・水面の描画と深度オフセット」）。

川床と川岸の地表は地形シェーダー側で表現する。`RiverSurfaceManager` は同じ4m格子で全域マスク（R＝川床、G＝カーブ内岸の砂地）を生成してグローバルテクスチャとして渡し、地形シェーダーが川床を濡れた岩、内岸の岸帯を砂地として塗る（[E_LOD処理](E_LOD処理.md) の「地表のスタイライズ表現」）。

### D.11.5. 海岸線への反映とパスの横断

範囲ポリゴンは水面と同列に `Terrain.compute_coastline_polygon` の穴あけ入力になり、そのまま difference される（湖のような水位判定は行わない。範囲が既に「水面より低い領域」だからである）。したがって川の上に作られた土地区画は海上区画（`PARCEL_WATER`）になって陸地を要求する建物は建てられず、パスの端点・ウェイポイントも置けず（`over_water_allowed` のバリアントを除く。[A_パス形状](A_パス形状.md) A.9）、プロップの範囲散布も除外される。

川の範囲を**跨ぐ**パスには追加の制約がある。範囲内の各地点で「路面の絶対標高が水面標高 + `RIVER_BRIDGE_MIN_CLEARANCE`（`consts.py`、0.5m）以上（橋）」か「深さ（地形標高 − 路面標高）がバリアントのクリアランス高さを超える（完全埋設トンネル）」のいずれかでなければ敷設できない。地形追従スパンは路面が川床（水面より下）になるため必ず拒否され、既定の街路で川を渡ろうとすると警告になる（橋バリアントか非追従設定、または地下で渡す）。電線・導水管・パイプラインなどのインフラパスは地表を占有しないため対象外。判定の詳細は [J_パスの交差処理](J_パスの交差処理.md) の「川の横断」を参照。

## D.12. 天然資源エリア（resources）

地形エディタ（`city-genesis/tauri` の「資源編集」タブ）でオーサリングされる天然資源エリア（鉱脈・油田などのポリゴン領域）。天然資源は経済シミュレーションのエンティティ（[[../economics/21_天然資源]] 参照）だが、埋蔵資源の分布は地形と密接に結び付くマップ固有のデータであるため、水面・川と同じサイドカー方式で地形マップに付随させる。

### D.12.1. データモデル

資源エリアは1件ごとに以下のフィールドを持つ。

| フィールド | 意味 |
| --- | --- |
| `id` | マップ内で一意な識別子 |
| `resource_type` | 資源種別（`resource_master` のキー）。提供物資（`product_id`）は種別からバックエンドが導出する |
| `max_amount` | 埋蔵量上限。配置直後の埋蔵量はこの値と同値（満タン）で初期化される |
| `recovery_rate` | 埋蔵量上限に対する1日あたりの回復割合。`0.0` は回復しない非再生資源（鉱脈・油田など） |
| `polygon` | 資源エリアの平面形状。`{"type": "Polygon", "coordinates": [...]}`。座標系は水面の `polygon` と同じ（ワールド座標XZ、マップ中心が(0,0)） |

### D.12.2. 永続化

水面（§D.10.1）と同じ方式で、地形マップの `.npy` と同じディレクトリ・同名（拡張子だけ `.resources.json`）のサイドカーJSON（`{"version": 1, "resources": [...]}`）に永続化される。地形エディタの作業コピーでは `meta.json` の `resources` フィールドに保持される。エクスポート時は資源が無くてもファイルを書き出し、以前のエクスポートで残った古い資源が読まれ続けるのを防ぐ。

### D.12.3. 新規都市への反映

水面が `city.terrains` の静的データとして読み込まれるのと異なり、資源はシミュレーションのエンティティである。バックエンドは新規都市の初期化時（`init_game`）に一度だけサイドカーを読み込み、各定義を天然資源エンティティ（`Resource`）として配置する。以後の埋蔵量の増減はセーブデータ側が正となり、ロード時にサイドカーを再読込することはない。

テンプレート作成モードの資源編集（`POST /api/v1/resources`、[[../economics/21_天然資源]] §21.7）とは併存する。サイドカー由来の資源は「そのマップで都市を始めたときの初期賦存」を、テンプレートモードの編集は「シナリオ固有の追加・調整」を表す。

## D.13. カメラ初期状態（camera）

地形エディタ（「カメラ」タブ）でオーサリングされる、そのマップで新規都市を始めたときの3Dカメラの位置と向き。マップに1つだけ持ち、未設定でもよい。

### D.13.1. データモデル

| フィールド | 意味 |
| --- | --- |
| `x`, `z` | カメラ位置のワールド座標XZ（m）。水面・資源の `polygon` と同じ座標系（マップ中心が(0,0)） |
| `y` | カメラの高さ（m）。標高と同じ絶対高さフレーム（海面=0） |
| `yaw` | 視線の方位（度）。北（ワールド+Z）を0とする時計回り。`camera:state` IPC の `yaw` と同じ |
| `pitch` | 見下ろし角（度）。正で下向き（90=真下）、0で水平。ロールは常に0 |

### D.13.2. 永続化と都市への反映

水面・川・資源のようなサイドカーJSONではなく、`terrain_maps.yaml` のマップエントリの `camera` キーに5つのスカラーとして書かれる（地形エディタのエクスポートが自動追記する。未設定ならキー自体を書かない）。地形エディタの作業コピーでは `meta.json` の `camera` フィールドに保持される。

バックエンドは新規都市の初期化時（`init_game`）にマップ定義の `camera` を都市のカメラ状態（`City.camera`、`GET /api/v1/city` の `camera`）へコピーする。以後はグラフィック（Unity）がカメラの静止時に `PATCH /api/v1/city` の `camera` で更新し、セーブデータ（`city.json`）に含まれる。ロード時はグラフィックが `game:start` 受信後に `GET /api/v1/city` を読んで視点を復元する。`camera` が `null`（マップ定義にも無い）の都市は、グラフィック側の既定視点（原点＝マップ中心の上空、シーン配置時の向き）で始まる。


### 地形エディタの共通操作

マップID、遠景グリッド間隔、セルサイズ、マップサイズ変更は編集対象から独立したメタデータである。「3Dプレビューを開く」の右隣にある「メタデータ編集」からモーダルダイアログを開いて編集する。閉じるボタンまたはEscapeで編集画面に戻り、変更した値は保持する。編集結果は編集パネル下部のエクスポートボタンで書き出す。

編集対象には地形・水面・川・資源・プロップ・カメラがある。左パネルは幅300pxで、残りの幅は地図へ割り当てる。地形は「自動編集」「手動編集」のタブで切り替え（初期表示は手動編集）、選択範囲と設定値は切り替えても保持する。その他も対象の編集カードを1列で表示する。プロップの配置・保存契約は [M_地形プロップ](M_地形プロップ.md) を参照。

基盤マップを作業コピーへ取り込む際は、`GET /api/v1/terrain/maps/{map_id}/resources` で同名の `.resources.json` も取得する。資源のID・種別・埋蔵量上限・回復率・GeoJSON範囲をmeta.jsonへ引き継ぐ。資源ファイルがないマップは空の一覧として開く。取得やJSON解析、resources配列の形式確認に失敗した場合は取り込みを中断し、空の資源で作業コピーを作り直さない。編集を始めるたびに選択したマップを取り込み、以前の編集途中データは開かない。

地形エディタのロード画面は「既存マップを編集」（川、資源、プロップなどを含みます）、「オリジナル地形」（純粋な地形データです）の順に表示する。既存マップの川・水面・カメラは `/terrain/maps/{id}/features` から、資源・プロップは各専用APIから取り込む。編集中の内容を残すにはエクスポートする。

## D.14. 編集禁止の地形原本

地形は `genesis-core/assets/terrains/` に集約する。`original/` には編集禁止の標高 `.npy` だけを置き、川の経路・水面・資源・プロップ・カメラ・サムネイルを含めない。原本の寸法と解像度は同階層の `original_terrains.yaml` に独立して保持する。ゲーム用コピーのサイズ変更や上書きは原本設定に影響しない。

ニューゲームは `terrain_maps.yaml` に登録されたゲーム用コピーを読み込む。標高と付随JSONは `terrains/` 直下にあり、両登録表の `file_name` は `assets/` 基準である。川床は従来どおりゲーム用コピーへ彫り込む。

エディタの「オリジナル地形」は標高だけの新しい作業コピーを作り、原本と既存の作業コピーを変更しない。後から川を作り直したい場合は原本から再び複製する。コピー上のその他の加工を自動で再適用する仕組みではない。編集途中の保存・再開は行わず、「.npyへエクスポート」でゲーム用コピーと登録表を更新する。原本ディレクトリへのエクスポートは書き込み前に拒否する。

HTTPの `/terrain/maps` と `/terrain/maps/{id}/near` は `original=true` のときだけ原本用登録表を参照する。原本を書き換えるAPIは設けない。


## 都市外の背景地形

都市範囲は詳細標高マップの範囲と一致する。半島・大陸などは、都市の外側に任意の50m格子の背景地形を描いて表現する。背景は詳細地形の原本とセットで保存され、編集や造成の対象にはしない。境界の継ぎ目を補間する処理はない。

地形の登録情報に背景ファイル参照と左下のワールドXZ座標を保持する。原点指定が無ければ背景配列を都市原点の周囲に配置する。地形エディタは原本取り込みと既存マップの再保存で背景参照を引き継ぐ。背景標高は原本を参照し続け、編集した詳細地形へ焼き込まない。

UnityのTerrainManagerは `/api/v1/terrain/background` のfloat32 little-endian配列を取得する。行数・列数・格子間隔・原点は `X-Grid-Rows`、`X-Grid-Cols`、`X-Grid-Spacing`、`X-Origin-X`、`X-Origin-Z` で受け取り、未設定の204では背景を生成しない。背景を分割メッシュとして描き、都市内のセルには従来の詳細地形を使う。カメラ移動範囲と遠方クリップ距離は背景を含め、都市外の道路・建物も必要な周辺セルで取得する。

都市外への道路・線路・建物・土地区画の配置はテンプレートモード専用。道路は完成時に都市境界で分割され、都市外部分は共通の都市外地区に所属する。経路は境界を越えて接続できる。都市外地区は道路網が離れても分割されない。都市外では建物の自動発生や自動入居、道路の自動延伸、設備の老朽化・修繕は行わない。

variant 4「汎用建物」はテンプレート専用の建物で、TYPE_DEFAULT・is_bd=Trueとして扱う。通常の建物描画と区画所属を使い、火災・倒壊・自動閉鎖・自動解体の対象にはしない。輸出入や観光の発生機能は含まない。
