# アラートフラグ管理

## 概要

City Genesis では、建物(agent)・道路(path)のうち「ユーザーに知らせるべき状態」を一元的に表現するために、`alert` というビットフラグプロパティを両テーブルの SoA に持たせる。

アラートの例:

- 建設サービス財の調達不足で建設が滞っている
- 火災・失火・犯罪・交通事故が当エポックで発生した
- 稼働中のインフラ施設(発電所・変電所など)がインフラ網に未接続で、供給・受け取りができない
- 将来拡張: 倒壊リスク等
（※建設中・解体中といったステータスは `status` プロパティで表現されるため、アラートからは除外されている）

これらを個別の専用エンドポイントで都度計算するのではなく、**1つの `alert` ビットフィールド**に集約し、**1つのエンドポイント**で一括取得できるようにする。これにより:

- アラート種別の追加がビット定義の追加だけで完結する
- Unity側は単一の `AlertManager` と `AlertIconFactory` で全アラート種別を扱える
- エンドポイントの増殖を防げる

## 設計の核心: version 管理対象外

**`alert` プロパティは `VERSION_TRIGGER_PROPS` に含めない。** これが本仕様の最も重要な設計判断である。

### version 管理対象外とする理由

Unityの `BuildingManager` / `PathManager` はバックエンドの `version` をキャッシュし、version が変わったオブジェクトだけ3Dメッシュを再生成する(LOD差分ロード)。`version` は「見た目に関わる実体データが変わった」ことを示す。

アラートフラグは:

- メッシュ形状・テクスチャ・位置といった「3D実体」の変化ではなく、UIオーバーレイアイコンの表示・非表示の変化である
- 直近エポックの需給結果など、エポックごとに変わり得る揮発的な状態である
- 変化頻度が実体データの変化頻度と独立している(実体が変わらなくてもアラートだけ変わる)

もし `alert` を `VERSION_TRIGGER_PROPS` に入れてしまうと、アラートビットが変化するたびに建物・道路の version が上がり、毎エポック画面内の全建物・道路の3Dメッシュが再生成されてしまう。これは都市規模が大きくなった際に致命的なパフォーマンス劣化を招く。

### 代替の観測経路

代わりに、アラート専用のエンドポイント `GET /api/v1/alerts` を設け、Unity の `AlertManager` が独立してこれを観測する。`AlertManager` は version キャッシュを持たず、毎回フル再構築して `HashSet<string>` で前回セットとの差分を取ることで、3Dメッシュ再生成を伴わずにアイコン表示だけを更新する。

## データモデル

### SoA プロパティ

`agents` テーブルと `paths` テーブルそれぞれに以下の SoA プロパティを追加する:

| テーブル | プロパティ | dtype | SoA 種別 |
|---|---|---|---|
| `agents` | `alert` | int16 | 通常スカラー配列 |
| `paths`  | `alert` | int16 | 通常スカラー配列 |

dtype は int16 で16ビット分のアラート種別を表現できる(将来拡張を含めても十分)。

### version 連動しない仕組み

`alert` は `app/entities/agent.py` / `app/entities/path.py` の `VERSION_TRIGGER_PROPS` セットには登録しない。これにより、`alert` の SoA 配列を直接書き換えても `version` はインクリメントされない。`BuildingManager` / `PathManager` は `version` をキーに差分判定するため、alert の変化を無視する。

### セーブデータ

`alert` は `assets/save_exclusions.yaml` で除外指定しない = **セーブ対象**。ロード時にアラート状態が復元される。これは「建設中」などの状態はセーブ時点で継続しているため、ロード直後からアイコン表示が復元されるべきだからである。次のエポック実行で `ConstructionProgressPhase._recompute_alerts` が最新状態に再計算する。

## アラートビット定義

`consts.py` に定義する。agent と path で名前空間は独立しているが、**同じビット値を agent/path で別の意味に使ってよい**(ビット2 = 火災/交通事故)。これは agent/path でアラートの意味が同じでもアイコンを変えたいケースに対応するため、名前空間だけ分けてある。

```python
# consts.py
ALERT_AGENT_CONSTRUCTION_SHORTAGE  = 1   # 建設サービス財の調達不足
ALERT_AGENT_ON_FIRE                = 2   # 当エポックで火災が発生した建物
ALERT_AGENT_ACCIDENTAL_FIRE        = 4   # 当エポックで失火(小火)が発生した建物
ALERT_AGENT_CRIME                  = 8   # 当エポックで犯罪が発生した建物
ALERT_AGENT_CRIME_SIGN             = 16  # 当エポックで犯罪の兆候が発生した建物
ALERT_AGENT_INFRA_DISCONNECTED     = 32  # インフラ網に未接続の稼働中インフラ施設
ALERT_PATH_CONSTRUCTION_SHORTAGE   = 1   # 建設サービス財の調達不足
ALERT_PATH_ACCIDENT                = 2   # 当エポックで交通事故が発生した道路
```

ビット2は agent/path で名前空間が分かれており、agent では「火災中」、path では「交通事故発生」という別の意味を持つ。これは前述の「名前空間だけ分けてある」設計が活きる典型例である。

これらの定数は `tools/sync_consts.py` により `Constants.cs`(Unity)・`constants.ts`(Tauri)へ自動同期される。

| ビット値 | agent 定数 | path 定数 | 意味 | 計算元 |
|---|---|---|---|---|
| 1 | `ALERT_AGENT_CONSTRUCTION_SHORTAGE` | `ALERT_PATH_CONSTRUCTION_SHORTAGE` | 直近エポックで建設サービス財(`PRODUCT_CONSTRUCTION_SERVICE`)の調達が需要に満たなかった。`CONSTRUCTING` / `DEMOLISHING` ステータスに限定し、`cs_demand > cs_acquired` で判定。agent は `is_bd==1 & public_facility==1` に限定(民間建物はプレイヤーが建設指示を出せないため)。`ConstructionProgressPhase._recompute_alerts` が設定 | status + demand/acquired |
| 2 | `ALERT_AGENT_ON_FIRE` | `ALERT_PATH_ACCIDENT` | agent: 当エポックで火災が発生した建物(火災フェーズ`fire.py`が設定)。path: 当エポックで交通事故が発生した道路(`AccidentPhase` が設定)。**いずれも当エポック限りの揮発的イベントで、次エポック先頭のリセットで自動的に消える** | 火災判定 / 事故判定 |
| 4 | `ALERT_AGENT_ACCIDENTAL_FIRE` | - | 当エポックで失火(小火)が発生した建物(火災フェーズ`fire.py`が設定)。揮発的イベント | 火災判定 |
| 8 | `ALERT_AGENT_CRIME` | - | 当エポックで犯罪が発生した建物(被害度が閾値超。`CrimeResolvePhase`が設定)。揮発的イベント | 犯罪判定 |
| 16 | `ALERT_AGENT_CRIME_SIGN` | - | 当エポックで犯罪の兆候が発生した建物(被害度が閾値以下。`CrimeResolvePhase`が設定)。揮発的イベント | 犯罪判定 |
| 32 | `ALERT_AGENT_INFRA_DISCONNECTED` | - | 稼働中(`STATUS_ACTIVE`)のインフラ施設(variantがインフラ財を授受する)のうち、接続端子ノード(`infra_node_id`)に「その施設が授受する製品を流せる稼働中インフラパス」が1本も接続されていないもの(停電・断水シグナル)。建設中は配線猶予期間として警告しない。判定は`utility/infra_network.py`の`build_infra_node_sets`(製品別の稼働中互換パス端点ノード集合)への所属チェックで、`ConstructionProgressPhase._recompute_alerts`が毎エポック再計算する(O(パス数+インフラ施設数)のベクトル演算)。UI(Tauri)の経済主体詳細パネルは、このビットを「インフラ接続」セクションの接続済み/未接続バッジにも利用する | infra_node_id + インフラパス網 |

## 更新タイミングと計算ロジック

### ライフサイクル: エポック先頭で全リセット + 各担当フェーズが OR 加算

alert ビットのライフサイクルは以下の2段構えである。

1. **エポック先頭の全リセット**: `InitializePhase.proc()`(`app/services/simulation/initialize.py`)が、agents / paths の alert SoA を `fill(0)` で全クリアする。これにより「前エポックで立っていたが解消した」ビットは自動的に消灯する。
2. **担当フェーズによる OR 加算**: 各ビットの担当フェーズが、自分の担当ビットだけを `a_alert[mask] |= ビット値` で立てる。全再構築(zeros→一括代入)は行わないため、フェーズの実行順序によって他フェーズが立てたビットが消されることはない。

### 状態系ビットの計算場所: ConstructionProgressPhase の末尾

「イベント」ではなく「現在の状態」を表すビット(`CONSTRUCTION_SHORTAGE` / `INFRA_DISCONNECTED`)は、`app/services/simulation/building/progress.py` の `ConstructionProgressPhase.proc()` 末尾の `_recompute_alerts()` が毎エポック計算する。

このタイミングが選ばれた理由:

1. `MarketPhase` / `InfrastructureMarketPhase` が完了した後なので、直近エポックの `demand_amount` / `remain_amount` が確定している
2. `ConstructionProgressPhase` 内のステータス完了遷移(`CONSTRUCTING → ACTIVE` 等)が済んでいるので、最新ステータスが反映されている(当エポックに完成したインフラ施設の未接続判定も同エポック中に行える)
3. 既に status / demand / acquired の numpy 配列を `progress.py` が取得しているため、alert 計算も同じ配列を使い回せて効率的

```python
# CONSTRUCTION_SHORTAGE ビット(OR 加算。リセットは InitializePhase 任せ)
shortage_target = (status == CONSTRUCTING) | (status == DEMOLISHING)
shortage_mask = shortage_target & (cs_demand > cs_acquired)
a_alert[shortage_mask] |= np.int16(ALERT_*_CONSTRUCTION_SHORTAGE)

# INFRA_DISCONNECTED ビット(製品別の稼働中互換パス端点ノード集合への所属チェック)
node_sets = build_infra_node_sets()   # utility/infra_network.py
# variant ごとに授受製品の互換ノード集合を合算し、infra_node_id の np.isin で判定
```

### イベント系ビット(火災・失火・犯罪・交通事故)は各イベントフェーズが設定する

`ON_FIRE` / `ACCIDENTAL_FIRE`(火災フェーズ `fire.py`)、`CRIME` / `CRIME_SIGN`(`CrimeResolvePhase`)、`PATH_ACCIDENT`(`AccidentPhase`)は、「当エポックで発生したイベント」を表す揮発的フラグであり、各イベントフェーズが判定と同時に OR で立てる。各フェーズは冒頭で自ビットのみを `&= ~自ビット` でクリアしてから立て直す(エポック先頭の全リセットがあるため通常は冗長だが、同一エポック内でのフェーズ再実行に対する安全策)。いずれも「発生したエポックのみ点灯し、翌エポック先頭のリセットで自然に消灯する」挙動になる。

### 新規作成時の初期値

新規 agent/path は SoA の int デフォルトで `alert=0`。最初のエポックの `ConstructionProgressPhase` で必要に応じてビットが立つ。

`SCHEDULED_CONSTRUCTION` 直後(エポック前)にはアイコンが出ない期間ができるが、これは仕様である(エポック実行を前提としたフラグのため)。即時表示が必要な場合は、crud 側で status 設定時に alert も同時設定する追加ロジックが必要になるが、現状は不要としている。

## API

### `GET /api/v1/alerts`

`?bbox=x1,z1,x2,z2` を指定した場合は `center_point` がその範囲内にある対象のみ返す。省略時は都市全体。

#### レスポンス

```json
{
  "agents": [
    {
      "id": 123,
      "name": "第1小学校",
      "center_point": [120.5, 340.2],
      "status": 4,
      "alert": 3
    }
  ],
  "paths": [
    {
      "id": 456,
      "name": "主要道1号",
      "center_point": [200.0, 100.0],
      "status": 4,
      "alert": 1
    }
  ]
}
```

- `alert` は int16 のビット和。各ビットの意味は `consts.py` の `ALERT_AGENT_*` / `ALERT_PATH_*` 定数に対応
- 需要量・調達量などの詳細情報は含まない。それらはUI(Tauri)の建物詳細ウィンドウ等で別途取得することを前提とする
- フィルタ条件は `alert != 0` または `status == STATUS_COLLAPSED` (何かしらのアラートビットが立っている、あるいは倒壊しているものだけ返す)

#### レスポンスは endpoints.yaml 自動生成フローから外す

`alert` は version 管理外の派生プロパティであり、通常のエンティティスキーマ(`endpoints.yaml` 駆動)に載せると `BuildingManager` / `PathManager` が version 差分ロードの対象として誤解する恐れがある。そのため `app/controllers/alerts.py` で手書きの Pydantic モデルで定義する(`projects.py` や旧 `construction_warnings.py` と同じ方針)。

## Unity 側の消費

### AlertManager (`DataLoaders/AlertManager.cs`)

`ZoneManager` / `ResourceManager` と同じ ScreenSpaceOverlay Canvas + Image 方式で、各対象の `center_point` 上にビット種別ごとのビルボードアイコンを表示する。

特徴:

- **version キャッシュを持たない**: 毎回フル再構築し `HashSet<string>` で前回セットとの差分を取る(既存の `ConstructionWarningManager` と同じ方式)
- **1オブジェクトに複数ビットが立っている場合はアイコンを水平に並べる**: `ZoneManager.cs:763` と同じ `(i - (count-1)/2f) * alertIconHorizontalSpacing` 式で中央揃えファンアウト
- **建物/道路の子にはしない**: アイコンは Canvas 直下に置く。これにより VisualModeObject のステータス連動や LOD アンロードの影響を受けない
- **ワールド座標は `_worldPositions` 辞書にキャッシュ**: `Update()` で毎フレーム `BuildingManager` 等に問い合わせず、キャッシュした座標を `Camera.WorldToScreenPoint` でスクリーン座標に変換して `RectTransform.anchoredPosition` を更新する
- **カメラ移動が 1m / 2° 未満のフレームはスクリーン座標更新をスキップ** して間引き(`ZoneManager` と同じ基準)
- **Image.raycastTarget = false**: `InputHandler` の `Physics.RaycastAll` に干渉しない

リフレッシュタイミング:

- `CellDataLoader.ReloadAllData()` 完了後(エポック完了/編集確定後)
- `ForceReloadAllDataCoroutine()` 完了後(全量再取得、`forceRefresh=true`)
- `OnCameraCellChanged()` でティア変更セルがあるとき

`Refresh()` は `refreshCooldownSeconds`(既定0.5秒)で間引かれる。

### AlertIconFactory (`Utils/AlertIconFactory.cs`)

`BuildingIconFactory` / `AgentIconFactory` / `PathIconFactory` と同じパターンで、Inspector から名前付き `[SerializeField] Sprite` を割り当て、`Awake` で `Dictionary` を構築する。

agent と path で同じビット値(例: `CONSTRUCTION_SHORTAGE=1`)でも別のアイコンを割り当てられるよう、Dictionary のキーは `(string entityType, int bit)` の組とする。

```csharp
public Sprite GetIconForAgent(int bit);  // entityType="agent"
public Sprite GetIconForPath(int bit);   // entityType="path"
```

未設定ビットの Sprite は `null` になり、そのビットのアイコンはスキップされる。

### Canvas sortingOrder 階層

| sortingOrder | 用途 |
|---|---|
| 55 | `ResourceManager` ラベル |
| 60 | `ZoneManager` / `GridOverlay` / `ParcelBoundaryOverlay` |
| 70 | **`AlertManager`** (既定値。Inspector で調整可能) |
| 100 | `TooltipManager` (常に最前面) |

## 新しいアラートビットの追加手順(拡張ガイド)

新しいアラート種別を追加する場合は、以下の3ステップで完結する:

### 1. 定数追加

`genesis-core/consts.py` に `ALERT_AGENT_*` / `ALERT_PATH_*` 定数を追加する。ビット値は重複しない2のべき乗を選ぶ(agent 側は 1〜32 使用済みのため次は 64)。

```python
ALERT_AGENT_FLOOD_RISK    = 64   # 新しいビット
ALERT_PATH_FLOOD_RISK     = 4
```

その後 `python tools/sync_consts.py` を実行し、`Constants.cs` / `constants.ts` へ同期する。

### 2. 計算ロジック追加

状態系ビットは `ConstructionProgressPhase._recompute_agent_alerts` / `_recompute_path_alerts` に、イベント系ビットは該当イベントフェーズに、**OR 加算(`|=`)方式**で計算を追加する(リセットはエポック先頭の `InitializePhase` が一括で行うため、個別のクリア処理は不要)。ビットの計算に必要なデータが `ConstructionProgressPhase` のタイミングで揃わない場合は、別フェーズで計算することも検討する。

### 3. Unity アイコン追加

`Utils/AlertIconFactory.cs` に対応する `[SerializeField] Sprite` フィールドを追加し、`InitializeAlertIcons()` で Dictionary に登録する。シーンの IconFactory GameObject の Inspector から Sprite を割り当てる。
