# UI共通基盤

TauriのUIは複数のWebViewで構成する。Rustがウィンドウと共有状態を管理し、Reactが各画面の内容を描く。個別機能は共通の管理・通信・表示部品を利用する。

## ウィンドウの管理

ポップアップの種別・初期サイズ・配置・インスタンスポリシーは `src-tauri/config/window-registry.json`、同時に開けない組は `window-mutex-groups.json` で定義する。生成と表示は `open_window` を通し、初期データは `get_window_context` で受け取る。新しく開く画面へのデータはコンテキストに含め、購読開始前のイベントに依存しない。

閉じたポップアップは非表示のまま再利用される。再表示では `window-context-updated` と `open_seq` によってReactの状態を初期化する。閉じたときの編集終了・ハイライト解除はRustが担当し、Reactのアンマウントに依存しない。排他で閉じられる画面は、自分から追加の終了要求を送らない。

編集ウィンドウはUnityの一つの編集ステートを共有するため互いに排他である。編集画面を開くと、共通処理がHUDの常駐編集モードを解除する。

トップメニューの右上には、半透明グレーの正方形に横棒を描いた最小化ボタンを置く。Tauriの最小化APIを使い、権限はトップメニューのウィンドウだけに付与する。最小化の対象はトップメニュー自身で、右下の終了ボタンはアプリ全体の終了を担当する。

### 配置と表示先

常駐HUDはアイコンパネル・コックピット・システムトレイ・表示トレイの4ウィンドウに分かれる。透明なWebViewもクリックを受けるため、各ウィンドウはパネルの実面積に合わせる。

HUDはゲーム画面のモニターに置き、ポップアップは通常同じモニター、マルチディスプレイ設定では別のモニターに置く。同じモニターではHUDの占有領域を避ける。異なるDPIのモニターをまたぐ配置には物理座標を使い、非表示で配置してから表示する。

位置とサイズはプロセス起動中だけ種別ごとに記憶する。表示先の変更で記憶を破棄する。Unityのフォーカス通知やUIの表示・フォーカス変更時には、共通管理が表示中ウィンドウの最前面指定を整える。

## 共有データと通信

HTTPとIPCの窓口は[コンポーネント連携](コンポーネント連携.md)に従う。セッションと版情報を各画面へ複製せず、プレイモードは `usePlayMode` で参照する。受信したIPCの状態をそのまま再送して往復ループを作らない。

統計の取得はエポックと接続先に対応するキャッシュを使う。表示する値はAPIの確定値を使い、欠測と0を区別する。履歴の内訳に最新期の値を流用しない。

### コックピットの確定気候

スコア・予算の左側に、最後に開始したエポックの気温・降水量・日照強度・風速をアイコンと数値の2行2列で表示する。`GET /api/v1/city` の `city.epoch_temperature`（℃）・`epoch_precipitation`（月相当のmm）・`epoch_sunlight`（%）・`epoch_wind_speed`（m/s）を、既存の `session-state` の都市情報から受け取る。専用のポーリングは行わない。

未実行・未取得の値は「—」で表示し、0とは区別する。値の意味は [生産活動](../economics/9_生産活動.md#気候による生産変動) を参照。日付の横の天気表示はUnityの現在の描画状態を示す。

## 共通スタイル

配色・影・状態色は `App.css` の共通トークンを使う。トップメニュー系は `--flat-*`、設定フォームは `SettingsRow` と `SettingsForm.css`、タブは `FlatTabs` を利用する。個別画面で同じ意匠を再定義しない。

本文・通常の表の項目と値・入力欄・操作ラベルの文字サイズは、全画面で `1rem` に揃える。`FontSizeContext` がグローバル設定をルートの文字サイズへ反映するため、各画面で本文全体に拡大率を掛けない。見出しや主要な集計値は大きく、補足・バッジ・グラフの目盛りは小さくして情報の役割を区別する。これらもremで指定し、設定と同じ比率で拡縮する。

本文に連動する寸法はremで指定する。pxしか受け取らないグラフの寸法は `useRemPx` で換算する。固定サイズの常駐ウィンドウ、設定フォームの余白や操作部、位置計算に使うチュートリアルの強調表示は、それぞれの固定寸法に合わせる。

固定の段組みが入らない狭いウィンドウでは、CSSのメディアクエリでウィンドウの幅に応じて段組みを組み替える。判定はウィンドウの幅だけで行い、実行環境を見ない。

スクロールバーは `App.css` の共通指定を使う。右端の操作部を隠すオーバーレイ表示を避けるため、WebView2の `::-webkit-scrollbar` を用いる。

## 言語と作者のテキスト

UIの文言はi18nリソースを使い、全対応言語でキーを揃える。対応言語とIntlロケールは `utils/locale.ts` の定義を使う。

シナリオ紹介やクエストの名前・説明は作者が書く多言語テキストで、UIの翻訳リソースとは別に扱う。`resolveLocalizedText` は表示言語の文を選び、無ければ英語へ戻す。入力には `LocalizedTextFields` を使い、英語を必須とする。

## 個別機能の仕様

### 経済主体詳細の建物情報タブ

建物情報、フロア構成、駐車の順にセクションを並べる。建物情報は建物タイプ・階数・床面積・耐久度を表示し、フロア構成は家賃・フロアの占有量・入居者の右側に建物の断面図を表示する。公共施設など、家賃や入居情報を持たない建物でも、形状とフロア容量を取得できれば断面図を表示する。

駐車セクションは容量と昼間・夜間の使用量を別々のメーターで表示し、容量と両時間帯の使用量がすべて0なら省略する。駐車需要の意味は[建物の駐車](../economics/12_建物.md#1214-駐車)を参照。

### 統計ウィンドウの経済タブ

商品ごとの平均価格と生産量・消費量・輸出量・輸入量を表で表示する。表は小売製品（`GOODS_RETAIL`）と工業原料（`GOODS_MATERIAL`）のタブに分け、それ以外の種類の商品、規制製品（`regulated=true`）、4種類の数量がすべて0の商品は表示しない。数量セルの文字は数量と単位を示し、背景の棒グラフはその数量に同じ行の平均価格を掛けた金額で比較する。尺度はタブごとに持ち、表示中のタブの全商品・4列で最大の金額を100%とする。平均価格が0または未取得の商品は棒を塗りつぶさない。

行を押すと、その商品の平均価格と需給の推移、最新エポックの物資フローをタブの上に重ねて表示する。

### Tipsの処理中表示

表示するTipsは `components/tips/TipsWindow.tsx` の一覧で選び、タイトルと本文は各言語の `tutorial.json` 内の `tips.items` で管理する。画像は任意で、画像のないTipsも同じ一覧から表示する。

Tipsウィンドウの初期ロードとエポック実行中の状態表示は、本文より大きな文字で強調する。文字サイズはグローバル設定に連動させ、Tips本文は通常の本文サイズを使う。

### 公共交通の路線一覧

公共交通ウィンドウの一覧は閲覧専用の表で、路線種別のタブで絞り込める。運賃と目標運行間隔はラベルで表示し、運賃収入の右に同じエポックの収支（収入 − 車両リース支出）を表示する。縦横の罫線で項目を区切り、収支は黒字を緑、赤字を赤で示す。

行のどの列をクリックしても路線詳細を開く。キーボードでは路線名のボタンから開ける。設定の変更と路線の廃止は路線詳細で行い、新設は一覧のサイドバーから専用ウィンドウを開く。

### 市政府ウィンドウ

コックピットの都市名を押すと開く。左の3分の1に都市名と都市の概要、右の3分の2に公的な経済主体の一覧を並べる。都市名はここで変更し、セッションの定期取得を待たずにHUDへ反映するため、グローバルイベント `city:renamed` を送る。

一覧は `GET /api/v1/city/government-agents` が返すカテゴリ(不動産・公営施設・オープンスペース・教育機関・港湾施設・都市間輸送・市政府)をタブで切り替える。公共サービスを供給する施設は公共サービスウィンドウが扱い、ここには出ない。都市間輸送は、観光客が都市間旅客輸送を買いに向かう玄関口の施設である。列に出す指標は経済主体の種類(不動産・輸出入拠点・事業所)で決まる。列の見出しで並べ替え、行を押すと経済主体の詳細を開く。

### 公共サービスの需給推移

コックピットには電力と水道のメーターを各1本表示する。上限は電力なら変電所と発電所、水道なら配水所と取水施設の現在容量を同じ単位で比較した小さい方とし、通常の電力・水道の現在需要を緑で塗る。需要が上限を超える場合は棒を満杯にし、ツールチップで上限に対する比率を示す。

コックピットの公共サービスメーターから開くウィンドウは、サービスごとのタブの左側に料金設定と需給推移、右側に供給施設一覧を表示する。料金は固定価格なら入力欄の後ろに通貨単位、原価比率なら製造原価への乗率として示し、製造原価は入力欄の下の行に表示する。需給推移は `GET /api/v1/stats/market_price` の `total_order`（需要）と `total_production`（生産）の履歴に、`GET /api/v1/city/public-service-supply` の最新実績を加えて実線で描く。現在の施設容量 `supply_capacity` は、過去から未来まで共通の水平線として表示する。数量の単位は1エポックあたりで、日量への換算は行わない。

過去の実績は取得できた履歴をすべて表示する。需要見込みはフロントで対象期間の実績を直線回帰し、最新の需要量から点線で延ばす。回帰の対象期間と未来の表示期間は `publicServiceTrend.ts` で定め、それぞれ仮想暦の1年（360日）と `GET /api/v1/city` の `simulation_days` から期数に換算する。履歴が回帰の対象期間に満たなければ取得済みの実績を使い、2期未満なら見込みを描かない。横軸は現在からの年数、ツールチップと施設容量に到達するまでの目安は月数または年数で案内する。内部の期数はプレイヤー向け表示に使わない。この見込みは需要傾向の延長であり、施設の増設や稼働条件の変化は織り込まない。

電力・水道のタブは、それぞれ高圧電力・高圧水道の現在容量も水平線で示し、発電所・取水施設などを同じ施設一覧に含める。凡例は変電所・発電所、配水所・取水施設のキャパシティとして区別し、高圧財の実績や見込みはグラフに加えない。高圧財のMWh・KLはサービス側のkWh・Lに換算し、一覧の容量も同じ単位に揃える。縦軸は需要・生産・需要見込みと、小さい方の容量の最大値に余白を加えて定め、範囲外の大きい容量も凡例の数値で確認できる。容量到達の目安も小さい方の容量で判定する。グラフは左側の残りの高さを使う。製品の対応と換算は `publicServiceInfrastructure.ts` が定める。施設情報は需給APIの `include_facilities=true` で各製品の `facilities` に取得する。指定を省略したメーター用の応答は、施設一覧を含まない。
