# チュートリアル基盤

チュートリアルの進行はTauriが管理し、Unityには現在の案内と操作制限だけを送る。シナリオは `tauri/src/tutorial/definitions/*.json`、共通処理は `tauri/src/tutorial/` と `unity/Assets/Scripts/Tutorial/` に置く。シミュレーションの経済ルールは変更しない。

シナリオ作者向けの設計(基本・地区・インフラ・鉄道・埋立・用地買収)と部品表は、リポジトリの `docs/tutorials/` にある。これはMkDocsのソース階層外に置いた作業資料であり、本ページが公開サイト上の実装契約である。

## 開始と説明ウィンドウ

ニューゲームの教材一覧は `components/tutorial/tutorialSteps.ts` の `SCENARIO_ORDER` が定める学習順で表示し、基本操作編(`controls`)を基本編(`basic`)より先に置く。チュートリアルの見出しをクリックすると一覧を開閉できる。ウィンドウを開くたびに `GET /api/v1/profile` のクリア記録を取得し、ニューゲームに表示する全教材がクリア済みなら閉じた状態、未クリアの教材があれば開いた状態を初期状態にする。取得中は閉じ、取得に失敗した場合は開く。新規開始の一覧から外している旧教材(`acquisition`)は全クリア判定に含めない。開いている間の手動の開閉は、プロフィール取得によって上書きしない。

クリア済みの教材と通常シナリオは、タイルの右上と詳細パネルに `assets/images/ui/badge.png` のバッジを表示する。代替テキストとツールチップには翻訳済みの「クリア済み」を使う。

チュートリアルのプレイモードは `PLAY_MODE_TUTORIAL=2`。資金審査・市庁舎設置前のHUDロック・エポック実行制限だけを免除し、それ以外は通常モードと同じ判定・UIを使う。建築後はパネルを閉じる。左側の制作専用アイコンと右下の一括完成・路地作成・神モード切り替えは表示しない。モードごとの一覧は[テンプレート作成支援](プレイモード.md)。

チュートリアルの初期都市(支援の町と教材の施設・区画)は、教材ごとに組み立て済みの都市としてゲームに同梱されている(バックエンドの `assets/tutorials/<教材ID>.cg`)。舞台の地形は、インフラが与論島、採掘が与論島の既存都市MineCity2、鉄道がMetroCity、観光が与論島の既存都市Tourism City(港から遺跡へ続く曲線道路と沿道施設)、埋立が平地のない人工岩礁、ほかは平坦な検証用地形で、定義の座標はこの地形を前提にしている。ニューゲームのチュートリアル開始は `POST /api/v1/sessions?play_mode=2&tutorial_id=<id>` で、コアはこの都市をシナリオと同じ手順で開き(アプリの言語が都市の言語と違えば、住民・建物などの名前を付け直す)、チュートリアルモードで開始する。同梱の都市はシナリオの一覧には出ない。埋立編は支援の町なし・未創設で始まり、最後にプレイヤーが市庁舎を置く。埋立編以外は創設済みの状態で始まる。採掘・鉄道・観光編は原本の市庁舎を使い、ほかの教材は支援の町に市庁舎が置かれている([都市の創設](../economics/12_建物.md#都市の創設市庁舎の配置))。そのため、終了時に通常モードへ移行しても、そのまま通常のプレイを続けられる。エポックの実績を最初のステップから見せる教材(インフラ編で、世帯の電力の需要と獲得量)は、エポックを進めた状態の都市を同梱している。

最初のステップから始めるときは、Tutorialウィンドウがポップアップ `tutorial_intro` を開く。上半分にシナリオのサムネイル、下半分にタイトルと「市長へのお願い」(`tutorial.intro.heading`)の見出し、導入文(`tutorial.intro.<id>`)を表示する。開始ボタンでも×でも、閉じた通知(`tutorial:window_visibility`)を受けてから案内と操作制限を始める。閉じたことはセーブごとに記録し、同じセーブで再開したときは再表示しない。

### 導入文の書き方

導入文の前半は、町の人や事業者が置かれた架空の状況と、解決したい困りごとを書く。後半は「このチュートリアルでは、〜を学ぶことができます」という形で、達成することで身につく方法や一連の流れを具体的に伝える。たとえば採掘編は「島に貴重な資源があるが、山から港へ運ぶ手段がなく産業に生かせない」という状況に続けて、鉱山・貨物鉄道・港を整え、採掘から輸出までの流れを学べることを書く。

ニューゲームの短い説明も、困りごとに続けて学べる内容を伝える。翻訳の正は `tauri/src/i18n/ja/tutorial.json` の `tutorial.intro.<id>` と `tutorial.<id>.description`。基本編の短い説明だけは `paramSetup.json` の `newGame.tutorialDesc` を使う。対応する全言語で状況と学習内容を揃える。具体的なクリック方法や配置位置は各ステップの操作案内で説明する。

架空の状況は教材の初期配置と達成内容に合わせる。将来の交通増加への備えなどを動機にしても、教材で確認しない渋滞解消や利益増加を達成条件として約束しない。

## 進行と条件

専用Tutorialウィンドウの `useTutorialGuide` が定義を読み、`legacyStep` が現在の番号と一致したステップの案内と完了判定を担当する。全チュートリアルの全ステップを定義で書く。`components/tutorial/tutorialSteps.ts` は定義からニューゲームの一覧・説明ウィンドウ・進捗表示に使う情報(並び順、サムネイル、ステップのタイトル `tutorial.<シナリオID>.step<番号>.title`)を導くだけで、判定を持たない。

コアが作った初期都市の対象は、`GET /api/v1/tutorials` の `targets` から `support.<名前>`(支援の町)・`lesson.<名前>`(教材)の名前で束縛に取り込み、定義から直接参照できる(例: 詳細ウィンドウの表示条件の `target`)。教材ごとの達成判定は同じ応答の `checks.<キー>` を `entity` 条件(`resource: "tutorial"`)で読む。

鉄道編の路線開業と運行の判定では、指定した両方のプラットフォームに実際に停車する路線を調べる。ホーム上の停留所の位置は問わない。片方だけに停車する路線や運休中の路線は合格しない。運行確認では車両調達後に輸送力が正になることも必要。短い駅間では住民が徒歩を選ぶため、乗客数は必須条件にしない。

ステップは複数の操作段階に分かれる。表示中のウィンドウ、選択中の道路種別、配置頂点数、HUDの常駐モード(地区編集・ブルドーザ)から段階を再計算し、閉じる・取消・モードの解除では前の段階に戻る。最後の段階は説明を読んだ後の「次へ」ボタンで確定する。最終段階以外を説明のページにしたいときは、その段階の `until` を `page` 条件(`id` は定義内で一意)にする。「次へ」は最終段階でなければ、まずこのページを送り、前の段階へ戻ったときは戻り先以降のページ送りを未送信へ戻す(閉じたパネルを開き直すと説明を最初から読める)。`page` はステップの達成条件には使えない。達成条件を持つ複数段階のステップは、達成条件を満たしていれば最終段階として扱い、「次へ」は開いているパネルではなく達成条件そのものを確かめる(確定でパネルが閉じる建設の後でも進める)。建物・道路・鉄道・インフラの種別を選んで建てさせるステップと公共交通の路線の新設は、パネルを開く段階から確定までのすべての段階が `strict` で、案内した種別・カード・確定などの操作だけを許可する。

道路配置は「始点を左クリック→終点を左クリック→右クリックで形状確定→建設パネルで確定→チュートリアルの完了」の順で案内する。終点配置と形状確定は別の段階で、2点を置くだけではパネルの確定へ進まない。道路APIの `curved` は0/1で返るため、読み取りアダプタでbooleanへ揃えてから条件と比較する。他の項目の型や座標は厳密に比較する。

判定エンジンは都市の読み取りとローカルの対象ID束縛だけを行う。都市を変更する初期配置・完成代行は独立アクションであり、実行順は `setup` → 段階条件 → `beforeCheck` → `complete` → `afterCheck`。合格前に完成が必要な接続判定と、説明の読了後に行う工期スキップを区別できる。

名前付き対象と作成中の記録は `tutorial_runtime_v1:<scenario>:<saveId>` へ保存する。成功済みの作成を再実行しない。応答喪失などでPOSTの結果が不明な作成は記録を残して停止し、無条件の再POSTで重複を作らない。完成代行は対象の現状を確認してから実行する。書き込み直前には現在のセーブIDを確認する。都市データとlocalStorageを一括保存する仕組みではないため、削除された対象や結果不明の初期化を検出した場合は新しいチュートリアル都市で再開始する。

## UIへの適用

App直下の `TutorialLayer` が各WebViewで同じスナップショットを購読する。`highlight` は強調のみ、`related` は登録済み操作と指定ウィンドウ全体を許可、`strict` は登録済みの個別操作だけを許可する。対象は `data-guide`、HUDでは既存のボタンIDで解決し、翻訳文やCSS階層に依存しない。建設パネルのカテゴリのタイルやバリアントのカード、パス建設パネルの地形追従の選択肢、区画作成パネルの作成方法のタイルのように同じ操作名の要素が並ぶものは `data-guide-value`(カテゴリ番号・バリアント番号・地形追従の設定値・区画の作成方法の名前)も持ち、定義では `名前:値`(例: `building.variant:1054`、`parcel.mode:along_path`)で1つだけを指せる。値の無い名前はその名前の要素すべてを指す。強調の見た目(黄色の枠)もこの層だけが付け、各コンポーネントは独自の強調表示を持たない。押せない(`disabled`)要素には枠を付けない。

パス建設パネルの分類タブは、カードと同じ `data-guide="path.variant"` と、タブ内のバリアント番号を空白区切りで並べた `data-guide-values` を持つ。いずれかのカードが許可されていれば、そのカードを表示するタブも許可する。強調も同じ番号で解決し、キーボードによるタブ切り替えは無効化されたタブを飛ばす。

アイコンパネル(`icon-panel`)は各段階の操作の入口なので、方針に関わらず、その段階の `allow` と `highlight` に含まれるボタンだけを押せる。ほかのボタンは無効化の見た目になる。取り消しや作り直しのために段階をまたいで使うボタン(地区編集の切り替えなど)は `allow` に書く。

未許可の操作はDOMキャプチャと `inert` でクリック・キーボード・フォーム経路を止める。既存のdisabledを変更しない。終了時はこの層が設定した属性だけを解除する。タイトルバー、明示した離脱操作、チュートリアル・通知・Tipsは制限対象外。設定・保存・復旧・終了の経路を保つため、システムトレイ、設定、クレジット、セーブ/ロード、セーブ一覧、新規ゲーム、確認ダイアログも制限しない。除外は `dom.ts` が共通で適用し、シナリオの許可リストに左右されない。UI案内の状態はメモリ上だけに置き、アプリ再起動後に以前の制限を復元しない。

チュートリアルウィンドウのボタンはステップ中は「次へ」だけで、途中でやめる操作はシステムトレイ(終了・保存)に任せる。全ステップを終えると完了メッセージと「終了」ボタンを出す。「終了」はセッションを終えず、`PATCH /api/v1/sessions` でプレイモードを `PLAY_MODE_TUTORIAL` から `PLAY_MODE_NORMAL` へ変更してから、チュートリアルウィンドウを隠す。都市はそのまま通常のプレイとして続く。送信中だけボタンを無効化し、HTTPエラーや通信失敗では通知して再試行可能にする。終えたチュートリアルは同じセッションで再表示しない。セッション終了・別の都市への切替では送信中フラグと確認状態を戻し、常駐WebViewを非表示のまま再利用しても前の状態を持ち越さない。

WebViewは閉じても破棄されないことがある。表示状態の観測では `isVisible()` を確認し、Rustの `close_window_by_label` は `tutorial:window_visibility` をTutorialへ通知する。対象IDを含むので、別の建物の詳細や閉じたパネルで条件を満たさない。

## 通信

| 経路・イベント | 内容 |
| --- | --- |
| Tauri内部 `tutorial:guide_state` | 現在のステップ・段階・UI許可・Unity案内の全スナップショット |
| Tauri内部 `tutorial:guide_query` | 新しいWebViewの再同期、表示状態・道路編集中の状態の再観測 |
| Tauri内部 `tutorial:guide_observe` | 表示ウィンドウ、対象ID、道路種別・形状、保存成功した道路ID |
| Tauri内部 `hud:mode_changed` | HUDの常駐モード(`district` / `bulldozer` / `null`)。全HUDで共有される既存のイベントをTutorialが直接購読し、`hudMode` 条件の判定に使う |
| Rust→Tutorial `tutorial:window_visibility` | キャッシュされたポップアップの明示的な閉鎖通知 |
| Tauri→Unity `ui:action` / `tutorial:apply` | `params` に `active/runId/revision/saveId/scenario/stepId/phaseId/ui/world`。`world` はマーカー・道路制約・カメラの案内先 |
| Unity→Tauri `tutorial:applied` | 適用した `runId/revision`。RustからTutorialへ中継する |

同一実行内の古いrevisionと終了済みrunIdを捨てる。新しい実行中に届く以前の解除通知も無視する。段階変更時と `graphic-reconnected` でだけ送信し、周期送信は行わない。Unityの `session:reset` と `game:end`、Tauriの終了・ステップ変更・再試行では制限を解除する。

## Unityの操作制限

`TutorialRuntime` は最初の有効な指示で生成される。マーカーは `OverlayMeshRenderer` による描画物で、都市ノード・コライダー・PathManagerの実体に登録しない。マーカー座標は地面相対の `[x,y,z]`。

段階の `world.camera`(`target` は地面相対の `[x,y,z]`、`distance`、`yaw` は北を0とする時計回り、`pitch` は5〜89度の見下ろし角)を受け取ると、カメラをその注視点を見る位置へ1.5秒かけて滑らかに移動する。直前に移動した案内先と同じ値の再送(同じステップ内の段階の切り替え・Unityの再接続)では動かさず、プレイヤーが動かした視点を尊重する。移動中のキー・クリック・ホイール入力で中断し、ロード直後は保存された視点の適用が終わるまで待つ。

`world.mode` は `observe`、`blocked`、`path`。`blocked` では共通のワールド入力を止める。`path` ではパス(道路・駅のプラットフォームなど)の敷設エディタの入口で始点・終点の左クリックと半径を検査する。始点は水色、終点は黄色で実際の受理半径を表示し、クリック位置を定義の正確な座標へ吸着させる。点の高さ(地面からの相対Y)は点ごとに定義へ書け、吸着した点はその高さに置かれる(高架の高速道路など)。受理半径は地表上の水平距離で測るので、円は高架の点でも地表に描く。2点の配置後だけ右クリックを許可し、通常の道路編集と同じく最後の点を終点として形状確定する。この右クリックの位置は形状に影響しないため、円内に限定しない。

v1のパスは始終点2つの直線で、線路は1本だけ敷く。始終点の高さは定義の値に固定し、高さを付けられるのは高さ編集ができるバリアントだけ(それ以外は0)。`world.path` がある段階では、パス建設パネルで指定バリアント以外のカテゴリ・カードを選べない。追加頂点、曲線、高さ・盛土、ドラッグ、ラジアル設定、2D編集からの変更を制限する。通常の建設検証に加えてUnityの `can_confirm` とTauriのHTTP送信直前でも指定形状を検証する。対象バリアント・頂点・制御点・盛土・地形追従の上書きが条件から外れると確定しない。チュートリアルが無効なときはこれらの判定を素通りする。

カメラ操作をチュートリアルのワールド編集ゲートに含めない。Unityはシナリオの進捗や完了条件を判断せず、通常のステート遷移は既存の仕組みを使用する。

## 検証と拡張

JSON Schemaに加え、安定IDの重複、未登録の操作名、存在しない定数・束縛(`support.` / `lesson.` で始まるコアの対象名を除く)、パスの始終点の重なり、カメラの値域を検査する。

JSON Schemaの検証は、`schema.json` から Ajv の standalone 出力で事前生成した `src/tutorial/schemaValidator.generated.ts` で行う。実行時に Ajv でスキーマをコンパイルすると `new Function` を使い、UIのCSPで `eval` を許すことになるためである([コンポーネント連携](コンポーネント連携.md#corsとwebviewのcsp))。生成物は編集せず、`schema.json` を変えたら `npm run gen:tutorial-validator`(`tools/tutorial/generate-schema-validator.mjs`)で作り直す。`npm run dev`・`npm run build` の前処理も同じ生成を行い、`npm run test:tutorial` は最初に生成物が最新かを確かめる。Ajv は生成時だけ使う開発依存である。

`npm run test:tutorial` は条件・副作用・戻り方・DOM操作制限(アイコンパネルの無効化を含む)・解除・説明ウィンドウの表示・「次へ」と完了後の「終了」と、全定義の翻訳キー・ステップのタイトル・全シナリオの説明文・ウィンドウ名、作者向け設計書のステップIDと定義の一致を確認する。`unity/Tests/Tutorial/run-unity.ps1` は独立Unityプロジェクトで本編アセンブリを実行する。`Tests/Tutorial/README.md` に試験の範囲を記載する。

新しいシナリオを追加するときは、まず作者向け設計書と能力一覧を確認する。未登録のUI対象は通常コンポーネントに安定した属性を付けるだけにし、シナリオ固有の判断を持ち込まない。Unityで新しい種類の制約が必要な場合は、専用モジュールの型・Schema・受信側・編集の接点・試験をまとめて拡張する。

## 個別教材

教材ごとの舞台・手順・達成条件はサイト外の `docs/tutorials/` にある作者向け設計書と `tauri/src/tutorial/` の定義を参照する。基盤は教材固有の座標や操作手順を持たない。
