# IPC連携

Unity のグラフィック(以下 graphic)と Tauri の UI(以下 ui)は、編集の状態・選択・表示・ロードの進み具合をメッセージでやり取りする。都市のデータは両者がそれぞれコアの HTTP API から取り、IPC ではオブジェクトの ID、操作の指示、編集中の状態だけを運ぶ。

## 運び方

exe 版は、Windows の MemoryMappedFile(MMF)を方向ごとに1本ずつ使う。

| 方向 | MMF | Mutex | 書き込み通知(AutoResetEvent) |
| --- | --- | --- | --- |
| ui → graphic | `genesis-ipc-ui-to-graphic` | `genesis-ipc-mutex-utg` | `genesis-ipc-event-utg` |
| graphic → ui | `genesis-ipc-graphic-to-ui` | `genesis-ipc-mutex-gtu` | `genesis-ipc-event-gtu` |

各 MMF は長さ付きの UTF-8 の JSON を並べるリングバッファで、名前・容量・レイアウトは Rust(`tauri/src-tauri/src/ipc.rs`)と Unity(`unity/Assets/Scripts/IPC/IpcTransport.cs`)で一致させる。両側とも「無ければ作り、あれば開く」ので起動の順序は問わない。読み手がいない間の送信はバッファに溜まって読み手の起動後にまとめて読まれ、空きが無くなると送信は失敗する(`MMF buffer full`)。

名前は固定で、各方向の読み手は1つしか持てない。2つ目の Unity が同じ MMF を開くと ui からのメッセージを奪い合うので、[観察専用の起動](コンポーネント連携.md#観察専用の起動)の Unity は MMF を開かず、Unity の中の ui の代役とつなぐ。

[ブラウザ版](コンポーネント連携.md#ブラウザ版)では graphic と ui が同じページで動くので、MMF の代わりにページの JS で受け渡す(Unity 側は `IpcTransport` の窓口、ui 側は Web シェルの `__genesisGraphicBridge`)。Unity が受信を始める前の送信を MMF と同じ容量まで溜めておくことも含め、以降の取り決めはそのまま当てはまる。

## Envelope

メッセージは、送り手・宛先・イベント名・ペイロードを包む共通の JSON(Envelope)で、Unity の `IpcEnvelope.cs`、Rust の `messages.rs`、Web シェルで同じ構造に保つ。解析できないメッセージは捨てる。

- ui → graphic は、接続の確立に使う `system:ready` などを除き、すべて `ui:action` という1つのイベントに包み、イベント名(`action`)と引数(`params`)をペイロードに入れる。Rust はこれを中身を見ずに転送するので、イベントを足しても Rust の変更は要らない。Unity はペイロードの中のイベント名で振り分ける。
- graphic → ui は、`event` にイベント名をそのまま入れる。Rust が受け取り、多くは同名の Tauri イベントとして全ウィンドウへ流す(コックピットなど特定のウィンドウだけが扱うものは、そのウィンドウへだけ送る)。ウィンドウを開く・ui を隠す・ロードの進み具合を記録するなど、Rust 自身が処理するものもある。Rust に中継の分岐が無いイベントは、どの WebView にも届かない。

## イベントの命名と定義場所

イベント名は `対象:動作` のコロン区切りで、Unity・Rust・フロントエンドで同じ文字列を使う(例: `edit_path:select_node`)。対象の部分は、接続(`system:`)、都市の読み込み(`session:`・`game:`)、選択とステート(`world:`)、表示(`view:`・`camera:`)、編集モード(`edit_path:`・`edit_building:` など)の区分を表す。問い合わせ(`view:query_state` など)には、そのときの状態を1回返す。

各イベントの意味とペイロードは、このページに一覧を置かず、ソースのコメントに書く。

| 層 | 定義のある場所 |
| --- | --- |
| Tauri(フロントエンド) | `tauri/src/utils/ipc.ts` の送信関数と、受信するイベント名の定数(`IPC_EVENT_*`) |
| Rust | `tauri/src-tauri/src/ipc.rs` の受信の振り分け。ウィンドウを閉じたときやロード・エポック演出の進行で Rust 自身が送るものは `window.rs`・`lib.rs` |
| Unity | `unity/Assets/Scripts/IPC/IpcClient.cs` の受信イベント(`On*`)と送信(`Emit*`)。受けた後の処理は `IpcEventHandler`・`IpcStateCoordinator`・`IpcViewCoordinator` |

### イベントを追加・変更するときの変更箇所

1つのイベントは3か所にまたがる。どこかが欠けても実行時エラーにはならず、単に届かない。

- ui → graphic: `ipc.ts` に送信関数を足し、Unity の `IpcClient` で受ける。Rust は変えない。
- graphic → ui: Unity の `IpcClient` から送り、Rust の `ipc.rs` に中継の分岐を足し、フロントエンドが同名のイベントを受ける。
- 項目の削除や意味の変更など、相手の実装を変えないと壊れる変更では IPC の契約番号を上げる([バージョニングと互換性](バージョニングと互換性.md))。

## 同期の原則

- **周期的に送らない。** 受け手がいない間も送信は MMF に溜まり、やがて満杯にする。状態は変わったときと問い合わせを受けたときだけ送る。3D のカメラ位置のように絶えず変わる値は、要る側が問い合わせて1回だけ受け取る。
- **状態の正は片側に置く。** 表示の状態、オブジェクト単位の表示フィルタ、編集中の形状とその設定、建物の配置、天気などは Unity が正で、パネルは指示を送るだけで、表示は Unity の通知に合わせる。
- **通知は全体を、指示は差分を送る。** 状態の通知は差分でなく現在の全体を送り、取りこぼしても次の通知で揃うようにする。パネルからの指示は変えた項目だけを送り、補正された結果は Unity の通知で受け取る。
- **受け取った値を送り返さない。** パネルは Unity の通知を表示に反映するだけで、指示を送るのは利用者がパネルを操作したときに限る。送り返すと往復が止まらなくなる。
- **非同期の結果は世代で照合する。** Unity の編集状態をもとに ui がコアへ問い合わせた結果(検証・プレビュー)には、もとにした編集の世代を付けて返し、Unity は世代が一致するときだけ採用する。初期ロードも要求ごとの世代を付け、古いロードの完了通知を捨てる。
- **要求には失敗しても応える。** 応答を待つ側が止まらないよう、できなかったとき・取り消したときも応答を返す。
- **購読の前に届いた通知を当てにしない。** ウィンドウは購読を始めてから現在の状態を問い合わせる。変更時にしか届かない値(音量など)は、受け手が最後の値を覚えておく。

## 確定送信の責務分担

編集の確定をコアへ送るのは、確定の操作を持つ側である。パネルに確定ボタンがある編集(建物の建設、パスの敷設、土地区画、資源エリア、造成、公共交通、プロップの配置など)は ui がコアへ直接送り、Unity は形状を組み立てて ui へ通知するだけにする。3D の操作だけで完結する編集(接続端子ノードのドラッグ移動、ブルドーザでの削除)は Unity がコアへ直接送る。

確定後の後始末(編集状態の片付け、消えたオブジェクトの破棄、通常のステートへの復帰、データの取り直し)は、ui が送る `edit_*:finish` の1イベントにまとめ、Unity がその中で順に行う。`session:reload` と `world:change_state` を別々に送らない。データの取り直しは複数フレームにまたがるので、後から状態の遷移が割り込むと再生成と削除が中途半端に終わる。確定しない取り消しは `STATE_NORMAL` を送れば足りる。

ポップアップは閉じても破棄されずに隠れるだけで、React のアンマウント処理が走らない。そのため、ウィンドウを閉じたときの後始末は Rust のウィンドウ管理が送る。編集ステートに入るウィンドウなら `STATE_NORMAL` を、ほかの編集と同時に開けるウィンドウ(詳細パネルなど)なら、そのウィンドウが始めたモードだけを終える取り消しを送る。取り消しを受けた Unity は、そのモードの最中でなければ何もせず、併存するほかの操作を巻き込まない。

## グラフィックプログラムのステート

Unity は、3D 画面でいま何を操作しているかを表すステートを1つだけ持つ。通常の閲覧が `STATE_NORMAL` で、道路の敷設・建物の建設・土地区画の作成などの編集ごとに `STATE_EDIT_PATH` などのステートがある(一覧は `ipc.ts` の `GraphicState`)。

ステートは ui が `world:change_state` で切り替え、編集の初期条件(敷設するバリアント、編集する既存オブジェクトの ID など)を同じ `params` に載せる。ステートの中身は、オブジェクトの種類(土地区画・建物・パス・地形・地区など)ごとの入力モード(クリックやホバーで何をするか)と表示モード(どう見せるか)の組で、Unity がステートに入るときにまとめて適用する。ui は種類ごとの入力や表示を個別に指定しない([Unity入力制御](Unity入力制御.md)・[Unity表示モード](Unity表示モード.md))。

表示の正も Unity にある。Unity は利用者が通常のステートで選んだ表示(`view:change_view`)を覚えておき、`STATE_NORMAL` に戻るとそれを戻す。編集ステートが強制した表示は覚えない。専用のステートを持たないウィンドウが開いている間だけ表示を変えるときは、`view:change_view` ではなく `view:apply_preset` を使う(利用者の選んだ表示を上書きしないため)。

編集ステートは同時に1つなので、ステートに入るウィンドウどうしは同時に開けないようにする(`window.rs` の `EDIT_MODE_WINDOW_TYPES` と、ウィンドウの排他の設定)。Unity が Esc などで自分からモードを終えたときは、パネルの表示を合わせる必要があるモードに限り、Unity がモードの終わりを通知する。

## 起動・再接続

プロセスの起動の順序と接続先の受け渡しは[コンポーネント連携](コンポーネント連携.md#起動順序)による。Unity は起動して IPC を開くたびに `system:graphic_ready` で自分の版とコアとの互換の結果を伝え、ui は IPC の契約番号を照合して `system:ready` で受け入れの可否を返す。照合が通るまでは、接続と終了のためのイベント以外を送らず、届いても捨てる([バージョニングと互換性](バージョニングと互換性.md))。

`system:graphic_ready` はプロセスの準備ができた合図で、都市の描画が終わった合図ではない。Unity が落ちて起動し直したときは、これを起点に ui がポップアップを閉じ、設定を送り直し、必要ならロードの手順をやり直す。都市の状態は Unity が自分でコアから取り直す。Unity が正常に終わるときは `system:graphic_stopped` を送る(異常終了では届かない)。コアとの接続・互換の状態は ui が確かめ、変わったときに `system:backend_connection` で Unity へ知らせる。
