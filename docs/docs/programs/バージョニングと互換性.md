# バージョニングと互換性

本ページはコア・フロントのリリース規則と、実装されている版情報・ロード前検証・バックアップの契約を定める。基準版は双方 `1.0.0`。版情報のない内部開発用セーブは自動変換しない。[セーブデータ仕様](セーブデータ仕様.md)、[シナリオ制作と配布](シナリオ制作と配布.md)も参照する。

## 1. 分けて管理するもの

セーブを読み込めること、シミュレーションのルールが変わらないこと、3つのプログラムが正しく通信できることは、それぞれ異なる保証である。

| 管理対象 | 識別する情報 | 用途 |
| --- | --- | --- |
| コアのリリース | `core_version`（例: `1.12.5`） | セーブ互換性、バランス変更の区分、障害報告 |
| フロントのリリース | `frontend_version`（例: `1.0.0`） | TauriとUnityを組み合わせたUI・描画・操作の変更 |
| IPCの連携契約 | `ipc_contract_version`（正の整数） | TauriとUnityの接続可否 |

コアとフロントのリリース番号は独立して進める。フロントだけの更新でセーブの互換性区分を変えることはない。コアとフロントの接続可否はリリース番号のMAJORで決める（第4節）。IPCの互換番号は開発・診断用であり、通常のタイトル画面に並べる必要はない。

## 2. コアの番号

形式は `MAJOR.MINOR.PATCH` とし、各部分は非負の整数とする。比較は3つの整数の順で行い、文字列として大小比較しない。MINORを上げたらPATCHを0に、MAJORを上げたらMINOR・PATCHを0に戻す。

| 区分 | 上げる条件 | 例 |
| --- | --- | --- |
| PATCH | セーブ互換性を維持し、ゲームルールやバランスに影響しない修正 | 結果を変えない高速化、ログ修正、通信の不具合修正 |
| MINOR | セーブ互換性を維持する機能追加、またはゲームルール・バランスが変わる可能性のある修正 | 生産・消費・価格・人口の挙動変更、バランス係数の調整 |
| MAJOR | 従来のセーブを通常のロードで安全に引き継ぐ保証を維持できない変更 | 既存都市の意味を保存できないデータモデル変更、旧セーブ対応の終了 |

複数に該当するときは最も大きい区分を採る。**「バグ修正」という作業名だけでPATCHにしない。** 計算の誤りを直した結果として生産量や収支などが変わる場合はMINORにする。影響がないことを説明・検証できない場合もMINORを選ぶ。

MAJORが表すのは、ZIPの構造だけでなく、都市を意味のある状態で引き継げるかどうかである。互換性を保つ既定値補完や自動変換で対応できる形式変更は、必ずしもMAJORを必要としない。

同じMAJORの新しいコアは、そのMAJORで既に配布した古いセーブすべてを読み込めることを保証する。直前の版からの更新だけでなく、複数のMINORを飛ばした更新も対象とする。一方、新しいコアで保存したデータを古いコアで読み込むことは保証しない。

### コアの配布物に含める範囲

コアの番号は実行プログラムと、それが使うマスターデータ・標準パラメータを一体として識別する。コードを変えずに配布用の係数だけを調整した場合も、この規則で番号を上げる。同じリリース番号の配布物を、内容を差し替えて再公開しない。

開発ビルドやモックは製品版と識別できるビルド種別・ビルド識別子を持つ。モックかどうか、エポックを実行できるかはリリース番号の大小から推測せず、公開する機能情報で判定する。

## 3. フロントの番号

TauriとUnityは同一リポジトリで開発・配布するため、**フロント全体で1つの `MAJOR.MINOR.PATCH` を使う。** UIだけ、または描画だけの変更でも、公式に配布する組には同じ番号を付ける。

| 区分    | 上げる条件                                 |
| ----- | ------------------------------------- |
| PATCH | 表示崩れ、入力不具合、描画性能、翻訳などの修正               |
| MINOR | ウィンドウ・可視化・操作機能などの追加・拡張                |
| MAJOR | 従来の操作体系やフロントが保存するユーザー設定との互換性を維持できない変更、またはコアのMAJORが上がったときの追従 |

フロントのMAJORは、接続できるコアのMAJORの上限を決める（第4節）。

版の正は公開リポジトリ直下に`city-genesis/version.json` とする。`frontend_version`・`ipc_contract_version` をここに定義し、TauriとUnityの両方のビルドへ取り込む。Tauriの `package.json`・`Cargo.toml`・`tauri.conf.json` とUnityの製品バージョンはここから同期する。画面の文字列へ番号を直書きしない。開発起動時も同じ定義を使い、配布時は各成果物の番号と元の定義の一致を検査する。

コアの版はコア側の単一の定義からAPI応答・セーブメタデータ・実行ファイル情報へ反映する。フロントの共有定数へ接続先コアのリリース番号を焼き込まない。

フロントの表示番号が共通でも、実行中のTauriとUnityが同じ版とは限らない。開発中の組み替えや取り違えを診断するため、それぞれが自分の版情報を通知し、ログには両方を残す。

## 4. プログラム間の互換性

起動できる組み合わせは、次の2つの規則だけで決める。

- **コアとフロント（Tauri・Unity）**: フロントの `frontend_version` のMAJORが、コアの `core_version` のMAJOR未満なら起動できない。比較するのはMAJORだけで、MINOR・PATCHは見ない。フロントの方が新しい分には構わない。
- **TauriとUnity**: `ipc_contract_version`（正の整数）が一致する。IPCイベントの意味・ペイロードの型・共有IDの意味も契約に含む。

未取得・不正・未対応の番号は、互換であると推測しない。

IPC契約番号は、項目の削除・型や意味の変更、共有IDの再割当て、**新たに追加した機能を相手が実装していることを必須にする変更**で上げる。見た目やバランスだけの変更では上げず、双方が従来どおり動ける任意項目の追加でも維持できる。番号が同じ組み合わせは、製品のリリース番号が異なっても連携できる契約とする。

IPCの完全一致方式は対応範囲の交渉より保守的であり、更新が必要な組み合わせは増える。複数世代の相手を同時に支える必要が生じた場合に、対応範囲や機能単位の交渉を検討する。

IPC Envelopeの `version: "1.0"` は、この判定の代用にはしない。特にEnvelopeの版とMMFのレイアウトは、互換性を照合するメッセージ自体を受け取るための前提である。契約番号はハンドシェイクの情報として扱い、Envelopeの文字列を単に置き換えて済ませない。

### 起動時の照合

1. コアは、都市をロードせずに取得できる読み取り専用の版情報APIを提供する。`GET /api/v1/system/version` とし、コアの版、ビルド識別情報を返す。
2. TauriとUnityは起動時に各自がコアの版情報を取得し、MAJORを照合する。TauriはRust側で版情報を一度取得し、全WebView・ゲーム開始・ロード・セッション監視が同じ結果を使う。Unityは初回マスター取得前に照合する。**フロントのMAJORがコアより小さければ、待っても版は変わらないので再試行せず、プログラム全体を終了する。** 版情報を取得できなかったとき（コアの起動準備中など）は、取得できるまで再試行する。
3. TauriとUnityは、起動通知と応答でフロントの版・IPC契約番号を交換する。双方の照合が済むまでゲーム用IPCを処理せず、新規開始・ロード・編集・エポック実行を解禁しない。
4. コアはアプリ実行中に再起動・別の版への差し替えを行わない。取得成功後の版情報はプロセス終了まで保持し、周期的な確認やウィンドウごとの再取得を行わない。起動準備中の通信失敗だけは初期取得を再試行できる。開発中にコアやマスターデータを変更したときはフロントも起動し直す。Unity自体が新たに起動した場合は、その起動時にコアの版とIPCの照合を行う。

IPC契約が一致しない場合は、操作側で理由を扱う。トップメニュー左下の小さな表示欄はコアの接続状況だけを示す（第9節）。設定・診断・終了は使えるようにしておく。起動情報の取得失敗を「互換性あり」にしたり、未対応のまま永遠にローディングを待ったりしない。

開発時のUnityなし起動は明示された開発モードでのみ認める。接続されたUnityのIPC契約不一致を「Unityなし」として迂回してはならない。モックも製品と同じ版の判定を通す。

## 5. セーブに記録する版情報

通常セーブ、シナリオテンプレート、手動セーブ、自動・緊急セーブは同じ規則を使う。

| 項目 | 意味 | 更新するタイミング |
| --- | --- | --- |
| `created_core_version` | その都市を新規作成したコアの版 | 都市作成時に設定し、別名保存でも維持する |
| `saved_core_version` | このファイルを最後に保存したコアの版 | 保存が成功したとき |
| `last_simulated_core_version` | 最後に完了したエポックを実行したコアの版 | エポックが正常完了したとき。未実行なら `null` |

一覧で常に表示するのは **「フォーマット v1」** のような `saved_core_version` のMAJORだけである(読み込めるかはMAJORの一致で決まり、MINOR・PATCHは読み込みに影響しないため)。作成時と最終シミュレーション時の版は、MINOR・PATCHまで含めて詳細情報(ツールチップ)に表示する。ロードできないセーブも一覧から隠さず、版と読み込めない理由を表示する。

ロードしただけでは元ファイルの版情報を更新しない。新しいコアで保存しても、それだけでは過去のエポックが新ルールで計算されたことにはならないため、`last_simulated_core_version` は書き換えない。

テンプレートから新しい都市を始めた場合、その都市の `created_core_version` は開始に使ったコアとする。テンプレート自身の作成・保存版は元ファイルに保持する。テンプレートに完了済みエポックがあればその最終実行版を引き継ぎ、新コアで再計算済みと誤表示しない。

### セーブ本体を正とする

版情報の正は `.cg` 内の `metadata.json` とする。高速な一覧表示用の `saves_metadata.json` には同じ情報を複製する。ロード時は本体のメタデータで再検証し、一覧のキャッシュだけで可否を決めない。一覧情報が欠けた場合は本体から再構築できるようにする。

セーブの互換性はコアのMAJORと最終保存版で判定する。互換変換の起点は保存版である。

## 6. セーブを開くときの判定

実行中のコアを `C`、セーブの `saved_core_version` を `S` とする。通信の互換性が成立していることを前提に、次の順で判定する。

| 条件 | 扱い |
| --- | --- |
| 版情報がない・不正、本体を正常に読めない | 読み込みを拒否し、「バージョン不明」または「ファイル破損」と理由を区別して表示 |
| `S > C` | PATCHだけ新しい場合も拒否。「より新しいコアで保存されています」と表示 |
| `S <= C` だがMAJORが異なる | 通常ロードを拒否。対応する旧版、または明示的な変換手段を案内 |
| MAJORが同じで `S <= C` | 互換性を保証する対象としてロード可能。必要な補完・変換と内容の整合性検証を行う |

MAJOR違いの自動変換は前提にしない。変換を提供する場合も独立した明示操作とし、元ファイルを残して新しいセーブへ出力する。

ロード可能なセーブについて、ルール変更の案内は `last_simulated_core_version`（未実行なら元データの `created_core_version`）と `C` のMAJOR・MINORを比較する。差があれば「この都市に適用されるゲームルール・バランスが変わる可能性がある」ことと対象の更新内容を示し、続行を確認する。セーブ時の番号だけで比較すると、ロードして保存しただけで案内が消えるためである。

同じセッション中に同じ変更を何度も確認させない。ただし、次回ロード時に版の移行が未完了なら再度案内する。PATCHだけの差ではバランス変更の確認を出さない。

**拒否や取消は、現在の都市・セッション・元ファイルを変更する前に完了させる。** 一覧のボタン無効化だけでなく、コアのロード入口でも必ず検証する。通常セーブ、シナリオのプレイ、テンプレート編集の全経路を対象とする。読み込みや変換が途中で失敗した状態はプレイ可能なセッションとして公開せず、緊急セーブの対象にもしない。

## 7. バランスとパラメータの引き継ぎ

セーブにはパラメータの一部が保存される一方、実行ロジックと配布マスターは起動したコアのものを使う。したがって、保存済みパラメータを復元するだけでは旧版の挙動は再現できない。

引き継ぎの原則は次のとおりとする。

- 都市の状態、プレイヤーが選んだ設定、保存済みのパラメータは維持する。新しい既定値で一括上書きしない。
- 追加された必須項目は、旧セーブに対する意味を定義したうえで補完する。名前が変わった項目や単位変更を、欠落値として黙って処理しない。
- 既存の保存値にも適用するバランス変更が必要なら、対象と変換規則を定め、リリース案内と確認に含める。保存されていないマスターやロジックの更新による影響も同じ扱いにする。
- 完了済みのエポックの履歴をロードだけで再シミュレーションしない。新しいシミュレーション結果が生まれるのはプレイヤーが次のエポックを実行したときである。ただし、ロード時の表示・派生値の再計算や編集時の判定には現行コアが使われる。

「読み込める」「過去と同一結果になる」「バランスが変わらない」は同義ではない。同一入力からのビット単位の再現性は、このバージョニング方針では保証しない。

## 8. 更新前のデータ保護

バージョン表示やロード拒否だけでは、更新後の上書きによる退避先の消失を防げない。保存元と異なるコアで初めて開くときは、PATCH更新も含め、**元ファイルを変更する処理より前に復元可能なバックアップを確保する。** 作成できなければ続行せず、保存場所や空き容量を確認できるエラーを返す。

- 元の `.cg` と、存在する外部サムネイルを保存する。版・保存ID・保存日時で識別できるようにする。
- 同じ元ファイルのバックアップを繰り返し作らない。内容が異なる旧データで既存バックアップを上書きしない。
- 手動保存・自動保存・終了時の緊急保存でも、更新前の保護を迂回しない。緊急保存の固定スロットを更新前バックアップの代用にしない。
- 新しいセーブは一時ファイルへ書き、完了後に置き換える。一覧メタデータも途中書き込みを避け、本体から復元できるようにする。
- バックアップの自動削除は当初行わず、一覧・保存先から確認して手動整理できるようにする。

元の都市を読み込むだけで新しい形式のファイルへ置き換えない。旧ルールで遊び続けたい場合は、バックアップと対応する旧コア・フロントの組を使用する。

## 9. トップメニューの表示

左下には次の2行を置く。番号は表示例で、コアの欄には実際に取得した版を使う。

```text
Core v1.0.0
Graphic v1.0.0
```

コアの欄はRust側が起動時に取得した版情報を `get_core_version` で受け取り、`Core v<core_version>` を表示する。TopMenu自身はHTTPで版を取得せず、タイマーも持たない。取得待ち・失敗時とセッション監視で接続失敗を検出した間は `Core 接続失敗`(各言語に翻訳)を表示し、ニューゲーム・ロード・シナリオ管理を無効にする。Rust側が配信する `session-state` の `coreVersion` と `backendConnected` で表示を更新する。TopMenu自身では版の比較や `get_frontend_status` の取得を行わず、詳細なエラー文もこの欄には出さない。

`Graphic` はフロント共通のリリース番号(`version.json` の `frontend_version`)を表示する。Unityの実際の版は診断コマンド `get_frontend_status` の `graphic_version` で取得できる。

中央のボタン群は上から **ニューゲーム・ロード・シナリオ管理**。右下は左から **設定・終了** の順に並べる。

## 10. 配布開始と検証の境界

互換性の保証を開始する境界は、早期アクセスや公開体験版を含む、プレイヤーが継続して遊ぶ最初の配布である。製品向けの基準版は `1.0.0` とし、その前の内部開発用データは保証対象に含めない。版情報がない開発用セーブへ、後から現在の番号を自動的に付けて互換とみなさない。必要な開発用データは複製に対して個別に検証・変換する。

配布時には、コアと対応フロントを検証済みの組として提供する。MAJOR更新を出す場合は、旧セーブへの影響と復帰手順を事前に示し、旧セーブを遊べる検証済みのコア・フロント一式を入手できる配布経路を用意する。新コアだけを差し替えて旧版の動作を維持できると約束しない。

リリースを判断する検証には、少なくとも次を含める。

- 同一MAJORの過去配布版で実際に保存したデータを、新コアで復元・操作・エポック実行・再保存できること。版文字列だけを書き換えたテストデータで代用しない。
- 新しい版のセーブ、MAJOR違い、版情報欠落を、都市の初期化前に拒否できること。
- ルール変更の案内、更新前バックアップ、保存中断からの復旧が、通常セーブとテンプレート、自動・緊急保存の経路でも成立すること。
- フロントのMAJORがコアより小さいときに起動しないこと、IPC契約の不一致・情報取得失敗・プロセス再接続で都市の変更が始まらないこと。
- PATCHとして出す変更が、ゲームルールやバランスを変えないこと。検証には制御した乱数など比較可能な条件を用いる。

## 11. 実装と運用

- フロントの版を変更したら `tauri/` で `npm run sync:version` を実行する。`npm run dev`・`npm run build` の前処理も同じ同期を行う。検査だけなら `node tools/sync-version.mjs --check`。Unityの `FrontendVersion.cs` は生成物。
- Rustビルドは製品番号の不一致を拒否し、UnityはPlay開始・Playerビルド時に定義と生成物・製品番号を照合する。公開リポジトリだけで同期できる。
- `GET /api/v1/system/version` は `core_version`、`build_kind` (`development` / `release` / `mock`)、`simulation_available` を返す。コアのビルド識別子は現時点では提供しない。
- UIはRust側で起動時にコアの版を照合し、フロントのMAJORがコアより小さければ終了シーケンス（Unityとコアへの終了通知を含む）でプログラム全体を終了する。WebViewの要求ごとに版確認を挟まない。
- Unityも初回マスター取得前にコアの版を照合し、フロントのMAJORがコアより小さければ終了する。`system:graphic_ready` / `system:ready` で各フロントの版・IPC契約・コアとの照合結果を交換し、Unityは応答確認前のゲーム操作を受け付けない。版情報を受信した後は再取得しない。
- `GET /api/v1/saves/{id}/validation?template=false` は本体を検査し、`save` と `compatibility` を返す。ロードAPIは `accept_balance_change=true` がないバランス変更を422 `SAVE_BALANCE_CONFIRMATION_REQUIRED` で拒否する。UIは共有の確認ウィンドウで承認を得てからこの値を送る。
- 互換性表示は `compatibility.loadable`・`code`、`balance_changed`、`balance_core_version`、`core_version`。版不明・新版・MAJOR違い・破損を区別する。
- バックアップは通常セーブディレクトリ内の `backups/` へ、元ファイル名とSHA-256を組み合わせた名前で保存する。同じ原本は重複退避せず、別内容のバックアップは残す。
- 拒否・取消は都市の初期化前に終了する。ファイル検査を通過した後の復元処理でエラーになった場合は、セッションを無効化して緊急保存も停止する。あらゆる復元エラーから直前の都市をメモリ上で復元するトランザクションは提供しない。

過去に配布した各版の実セーブを使うリリース試験、旧版の配布経路、更新案内は運用上の要件であり、ロード検証の実装だけで完了するものではない。
