# 通知レベル管理

## 概要

City Genesis では、プレイヤー(市長)に知らせるべき事象を「緊急度」で3つのレベルに分類し、レベルごとに異なるUIチャンネルで表現する。

| レベル | 定義 | 表現チャンネル |
|---|---|---|
| **L1** | 今すぐ対処しないと都市が壊れる重大事象。プレイヤーの対処が必要 | タスクバーの通知アイコン(点滅+件数バッジ)+通知一覧ウィンドウ+新規発生時のトースト |
| **L2** | 放置すると悪化する傾向。認識して中期的に対処すべき事象 | エポック結果ウィンドウ(天気マーク・矢印マークなどの傾向表現) |
| **L3** | 認識だけしておけばよい事象。位置(どこで起きているか)が主情報 | アラートフラグ(3D空間のビルボードアイコン。[[アラートフラグ管理]]参照) |

この分類の背後には2つの軸がある。

1. **緊急度**: 今すぐ対処が必要か(L1) / 放置すると悪化するか(L2) / 認識だけでよいか(L3)
2. **空間性**: アラートフラグ(L3)は「その場所をカメラで見ているときだけ」気づける空間ローカルな通知である。都市全体に関わる危機(資源の枯渇、インフラ供給網の停止など)はカメラの向きと無関係に伝える必要があるため、L1は常設のタスクバーで表現する

同じ事象でも深刻度によってレベルは変わり得る。例えば交通事故の発生自体はL3(アラートフラグ)だが、死者が出たときはL1へ昇格する。

## L1通知の仕組み

### データフロー

```
バックエンド                          Tauri
┌─────────────────────┐   ポーリング   ┌──────────────────────────┐
│ NotificationPhase    │◄─────────────│ Taskbar                   │
│ (エポック末尾で       │  GET /api/v1/ │  - 通知アイコン点滅+バッジ  │
│  city.l1_notifications│  notifications│  - 新規発生分をトースト     │
│  を毎エポック再構築)   │              │  - クリックで一覧を開く     │
└─────────────────────┘              ├──────────────────────────┤
                                      │ CityNotificationsWindow   │
                                      │  (通知一覧。行クリックで    │
                                      │   対象の詳細ウィンドウへ)   │
                                      └──────────────────────────┘
```

- バックエンドはエポック処理の最末尾(死者・倒壊カウンタ、アラートフラグ、資源残量履歴、公共施設の供給実績がすべて確定した後)に、当エポックのL1通知リストを全再構築する。「前エポックで出ていたが解消した通知」は再構築で自然に消える
- 通知リストはセーブ対象であり、ロード直後からタスクバーの通知表示が復元される
- Tauri のタスクバーは `GET /api/v1/notifications` を定期ポーリング(30秒)し、エポック実行終了(`epoch:executing` の false 遷移)でも即時再取得する

### ライフサイクル: 継続状態系とワンショット系

L1通知のライフサイクルは `id` の付け方で2種類に分かれる。

| 種類 | id の形式 | 挙動 |
|---|---|---|
| 継続状態系 | `resource_runway:12` のような安定ID | 状態が続く限り毎エポック同じ id で再生成される。解消すると消える |
| ワンショット系 | `collapse:8500` のように日付を含むID | 発生エポックのみ生成され、翌エポックの再構築で自然に消える |

タスクバーは前回取得時の id 集合との差分を取り、**新しく現れた id の通知だけ**を右下トースト(`showNotification`)でも知らせる。継続状態系は同じ id を保つため、毎エポック同じ危機で鳴り続けることはない。初回取得(セーブロード直後)の通知はトーストせず、アイコンの点滅・バッジだけで表現する(ロード済み状態の復元であって新規発生ではないため)。

### 通知の種類

| type | レベル分類の考え方 | params | entity |
|---|---|---|---|
| `resource_runway` | 天然資源の余命警告(継続状態系)。**残量ではなく「純減トレンド×余命」で判定する**: 直近数エポックの残量減少ペースが続いた場合に一定エポック数以内で枯渇が見込まれるときだけ点灯する。採取をやめれば純減が止まり自然に消灯するため、回復しない資源が永久にアラートし続けることはない | `name`(資源名), `remaining_epochs`(推定余命) | resource |
| `resource_depleted` | 資源が枯渇に到達したエポックに1回だけ出るワンショット。枯渇したままの資源は通知しない(打てる手がない不可逆状態を常設表示しない)。枯渇の継続的な影響は下流の施設側通知として現れる | `name` | resource |
| `facility_inoperative` | 稼働中の公共施設のうち、サービス供給実績が目標を大きく下回るもの(継続状態系)。人手不足・原料調達不可などの原因を問わず結果(供給率)で判定する。原因の内訳は施設詳細パネルで確認する | `name`, `supply_ratio` | agent |
| `infra_facility_down` | インフラ財を授受する施設(発電所・変電所など)が停止中/倒壊中(継続状態系)。1施設の停止が広範囲の停電・断水に波及するため「根本原因」を施設単位で知らせる | `name` | agent |
| `infra_disconnected` | インフラ網未接続の施設数の集約通知(継続状態系)。個々の未接続施設の位置はL3のアラートフラグ(`ALERT_AGENT_INFRA_DISCONNECTED`)が担い、L1では件数だけを1件に集約する(通知一覧が未接続施設で埋まらないようにする) | `count` | なし |
| `collapse` | 当エポックの建物・道路の倒壊(ワンショット)。火災由来の死者も倒壊死として計上されるため火災専用の通知は無い(火災の発生自体はL3) | `count`, `deaths` | なし |
| `deaths_traffic` | 当エポックの交通事故死(ワンショット)。事故の発生自体(死者なし)はL3のアラートフラグに留め、死者が出たときだけL1へ昇格する | `count` | なし |

### 文言化はフロントエンドの責務

バックエンドは通知メッセージの文言を組み立てず、`type` と `params` だけを返す。Tauri 側が i18n キー `notifications.types.<type>` へ params を差し込んで文言化する(表示言語の知識をバックエンドに持たせないため)。未知の type は汎用文言(`notifications.types.unknown`)へフォールバックするので、バックエンドが先行して新種の通知を返してもUIは壊れない。

例外として、対象エンティティの名前(資源名・施設名)は表示データとして params に含まれる(クエスト名と同じ扱い)。

## API

### `GET /api/v1/notifications`

現在有効なL1通知の一覧を返す。エポック未実行(新規ゲーム直後)は空リスト。

#### レスポンス

```json
{
  "notifications": [
    {
      "id": "resource_runway:12",
      "type": "resource_runway",
      "created_date": 8500,
      "params": { "name": "鉄鉱床", "remaining_epochs": 7 },
      "entity": { "type": "resource", "id": 12 }
    },
    {
      "id": "collapse:8500",
      "type": "collapse",
      "created_date": 8500,
      "params": { "count": 2, "deaths": 3 },
      "entity": null
    }
  ]
}
```

- `id` ... 差分検出用の安定キー(上記「ライフサイクル」参照)
- `created_date` ... 発生時点のゲーム内日付(1800年1月1日からの経過日数)
- `entity` ... 通知対象のエンティティ参照。通知一覧の行クリックで対応する詳細ウィンドウ(`agent` → 経済主体詳細、`resource` → 天然資源詳細)を開くために使う。集約通知では null

#### レスポンスは endpoints.yaml 自動生成フローから外す

`l1_notifications` はエポックごとに全再構築される揮発的な派生データであり、通常のエンティティスキーマには載せない。`app/controllers/notifications.py` で手書きの Pydantic モデルとして定義する(アラートフラグの `GET /api/v1/alerts` と同方針)。

## Tauri 側の消費

### タスクバー(Taskbar.tsx)

- システムトレイ左端に通知アイコン(`public/images/menu/tray_notifications.png`)を常設する
- `GET /api/v1/notifications` を30秒間隔でポーリングし、エポック実行終了でも即時再取得する(実行中はポーリングを止める)
- 通知が1件以上あるとアイコンを赤系パルスで点滅させ(`taskbar-tray-icon--alert`)、件数バッジ(`taskbar-tray-badge`)を重ねる
- 前回取得との id 差分で新規発生分だけを `showNotification` でトーストする(8秒で自動消去)
- アイコンクリックで `city_notifications` ウィンドウを開く
- セッション切断・別セーブのロード時は差分状態をリセットする(旧セーブの通知が新セーブの「新規発生」として鳴らないように)

### 通知一覧ウィンドウ(CityNotificationsWindow.tsx)

- window-registry の `city_notifications`(single ポリシー)として開く通常のポップアップウィンドウ
- マウント時に一覧を取得し、「アイコン+文言+発生日」の行として表示する
- `entity` を持つ行はクリックで対応する詳細ウィンドウを開く
- 一過性トースト(NotificationWindow)とは別物で、「未解決の危機が続いている限り表示され続ける一覧」を担う

## L2 / L3 の表現(参照)

- **L2(エポック結果ウィンドウ)**: 公共施設の逼迫・衛生状態・治安などの「傾向」はエポック結果ウィンドウの統計タイルが担う。現状は件数が非0の災害系タイルの警告色表示のみで、天気マーク・矢印マークによる傾向表現は将来の改修対象
- **L3(アラートフラグ)**: 建設調達不足・火災・犯罪・交通事故・インフラ未接続など「どこで起きているか」が主情報の事象。仕組みは[[アラートフラグ管理]]を参照

## 新しいL1通知の追加手順(拡張ガイド)

1. **バックエンド**: `genesis-core/app/services/simulation/notification.py` の `NotificationPhase` に収集メソッドを追加する。判定に使う状態が確定するフェーズより後であることを確認し(現状はパイプライン最末尾なので通常は問題ない)、`_append()` で type / params / entity を積む。継続状態系は安定ID、ワンショット系は日付入りIDにする
2. **フロントエンド**: `tauri/src/i18n/{ja,en}/notifications.json` の `notifications.types` に文言キーを追加する(両言語必須)。エンティティ参照で新しい種別を使う場合は `utils/cityNotifications.ts` の `NOTIFICATION_ENTITY_WINDOW_TYPES` に詳細ウィンドウとの対応を足す
3. **テスト**: `genesis-core/tests/test_notifications.py` に判定条件のテストを追加する

しきい値パラメータ(資源余命のエポック数など)は `GENERAL_PARAMS` の `NOTIFICATION_*` キーで調整できる(コード側デフォルトあり)。
