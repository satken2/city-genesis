# 通知レベル管理

## 概要

City Genesis では、プレイヤー(市長)に知らせるべき事象を「緊急度」で3つのレベルに分類し、レベルごとに異なるUIチャンネルで表現する。

| レベル | 定義 | 表現チャンネル |
|---|---|---|
| **L1** | プレイヤーの対処が必要で常設表示すべき事象。重要度2階調(warning=今すぐ対処しないと都市が壊れる / caution=放置すると成長が滞る)を持つ(後述) | コックピットのアラートアイコン(warningのみ点滅+赤バッジ、cautionは黄バッジ)+通知一覧ウィンドウ |
| **L2** | 放置すると悪化する傾向。認識して中期的に対処すべき事象 | エポック結果ウィンドウ(天気マーク・矢印マークなどの傾向表現) |
| **L3** | 認識だけしておけばよい事象。位置(どこで起きているか)が主情報 | アラートフラグ(3D空間のビルボードアイコン。[[アラートフラグ管理]]参照) |

この分類の背後には2つの軸がある。

1. **緊急度**: 今すぐ対処が必要か(L1) / 放置すると悪化するか(L2) / 認識だけでよいか(L3)
2. **空間性**: アラートフラグ(L3)は「その場所をカメラで見ているときだけ」気づける空間ローカルな通知である。都市全体に関わる危機(資源の枯渇、インフラ供給網の停止など)はカメラの向きと無関係に伝える必要があるため、L1は常設のタスクバーで表現する

同じ事象でも深刻度によってレベルは変わり得る。例えば交通事故の発生自体はL3(アラートフラグ)だが、死者が出たときはL1へ昇格する。

### 通知トレイの重要度2階調(warning / caution)

通知トレイ(L1チャンネル)に載る通知は、`severity` でさらに2階調に分かれる。

| severity | 定義 | コックピットでの表現 |
|---|---|---|
| `warning` | **今まで築き上げた都市が崩壊する差し迫った危機**。停電・道路寸断・倒壊など、放置すると既存の都市機能が壊れていく事象 | アイコンの赤系パルス点滅 + 赤バッジ(件数) |
| `caution` | **放置しても都市は壊れないが、成長が止まる・徐々に荒廃する問題**。教育機関の低稼働・区画サイズ不足による建設不能など | 点滅なし。黄バッジ(件数)のみ |

caution は「プレイヤーの対処が必要で常設表示すべきだが、緊急ではない」事象の置き場である。L2(放置すると悪化する傾向)に相当する事象のうち、エポック結果ウィンドウの一過性表示では見落とされやすい継続状態系がここに載る。caution を点滅させないのは、緊急でない問題で点滅が常態化すると、本当の危機(warning)の点滅シグナルが薄まるためである。

## L1通知の仕組み

### データフロー

```
バックエンド                          Tauri
┌─────────────────────┐   ポーリング   ┌──────────────────────────┐
│ NotificationPhase    │◄─────────────│ Cockpit                   │
│ (エポック末尾で       │  GET /api/v1/ │  - アラートアイコン点滅+バッジ│
│  city.l1_notifications│  notifications│  - クリックで一覧を開く     │
│  を毎エポック再構築)   │              ├──────────────────────────┤
└─────────────────────┘              │ CityNotificationsWindow   │
                                      │  (通知一覧。行クリックで    │
                                      │   対象の詳細ウィンドウへ)   │
                                      └──────────────────────────┘
```

- バックエンドはエポック処理の最末尾(死者・倒壊カウンタ、アラートフラグ、資源残量履歴、公共施設の供給実績がすべて確定した後)に、当エポックのL1通知リストを全再構築する。「前エポックで出ていたが解消した通知」は再構築で自然に消える
- 通知リストはセーブ対象であり、ロード直後からアラートアイコンの表示が復元される
- Tauri のコックピットは `GET /api/v1/notifications` を定期ポーリング(30秒)し、エポック実行終了(`epoch:executing` の false 遷移)でも即時再取得する

**L1通知はトーストを出さない。** アイコンの点滅と件数バッジで十分に気づけるため、プレイヤーの操作を遮るポップアップは表示しない(トーストは操作の結果を返す用途に限る)。通知の内容はアイコンをクリックして一覧ウィンドウで確認する。

### ライフサイクル: 継続状態系とワンショット系

L1通知のライフサイクルは `id` の付け方で2種類に分かれる。

| 種類 | id の形式 | 挙動 |
|---|---|---|
| 継続状態系 | `resource_runway:12` のような安定ID | 状態が続く限り毎エポック同じ id で再生成される。解消すると消える |
| ワンショット系 | `collapse:8500` のように日付を含むID | 発生エポックのみ生成され、翌エポックの再構築で自然に消える |

継続状態系は状態が解消するまで毎エポック同じ id で再生成されるため、通知一覧では危機が続いていることが一目で分かる。ワンショット系は翌エポックの再構築で自動的に消えるので、過去の事故が一覧に溜まり続けることはない。

`id` はフロントエンドが通知を安定して識別するためのキーでもある(React のリストキー等)。

### 通知の種類

| type | severity | レベル分類の考え方 | params | entity |
|---|---|---|---|---|
| `resource_runway` | warning | 天然資源の余命警告(継続状態系)。**残量ではなく「純減トレンド×余命」で判定する**: 直近数エポックの残量減少ペースが続いた場合に一定エポック数以内で枯渇が見込まれるときだけ点灯する。採取をやめれば純減が止まり自然に消灯するため、回復しない資源が永久にアラートし続けることはない | `name`(資源名), `remaining_epochs`(推定余命) | resource |
| `resource_depleted` | warning | 資源が枯渇に到達したエポックに1回だけ出るワンショット。枯渇したままの資源は通知しない(打てる手がない不可逆状態を常設表示しない)。枯渇の継続的な影響は下流の施設側通知として現れる | `name` | resource |
| `facility_inoperative` | warning / budgetのみcaution | 稼働中の公共施設のうち、実質運営できていないもの(継続状態系)。**対象は標準経済主体(市場生産をする施設)のみ**で、供給率という判定が意味を持たない教育機関などは対象外(教育機関の低稼働は `education_low_enrollment` が別途判定する)。サービス供給実績が目標を大きく下回る施設に加えて、供給率に現れない要因(高スキル人材不足による計画ゼロ化・公共予算不足による計画の大幅縮小)もアラートフラグ経由で検出する。原因は `reason` に `labor`(労働力不足) / `material`(原材料不足) / `high_skill`(高スキル人材不足) / `budget`(予算不足) / `unknown` のいずれかが入り、フロントは `notifications.types.facility_inoperative_<reason>` で文言化する(`unknown` と未知の reason は原因なしの汎用文言へフォールバック)。`budget` はプレイヤー自身の予算配分の帰結で施設も部分稼働はしているため caution、それ以外は公共サービスの機能不全として warning | `name`, `supply_ratio`, `reason` | agent |
| `education_low_enrollment` | caution | 稼働中の教育機関のうち、在籍者数が定員を大きく下回る低稼働のもの(継続状態系)。教育機関の「運営」は市場生産ではなく在籍なので、供給率ではなく在籍者数/定員で判定する。開校直後は就学年齢の市民が段階的に入学してくるため、稼働開始から一定日数は判定を猶予する。低稼働でも既存の都市は壊れない(成長が鈍るだけ)ため caution | `name`, `enrolled`(在籍者数), `max_students`(定員) | agent |
| `infra_facility_down` | warning | インフラ財を授受する施設(発電所・変電所など)が停止中/倒壊中(継続状態系)。1施設の停止が広範囲の停電・断水に波及するため「根本原因」を施設単位で知らせる | `name` | agent |
| `infra_disconnected` | warning | インフラ網未接続の施設数の集約通知(継続状態系)。個々の未接続施設の位置はL3のアラートフラグ(`ALERT_AGENT_INFRA_DISCONNECTED`)が担い、L1では件数だけを1件に集約する(通知一覧が未接続施設で埋まらないようにする) | `count` | なし |
| `rail_capacity_exceeded` | caution | 実交通量(列車の便数)が線路容量を超えた線路の本数の集約通知(継続状態系)。路線の新設・運行間隔変更は事前検証で容量超過を拒否するため、ここに来るのは線路の撤去・倒壊による迂回で便数が別線路に集中した場合などプレイヤーの直接操作ではない事後変化に限られる。運休や減便で罰さず警告に留めるため caution。該当線路の位置は線路の利用率(`utilization`=100%)で確認できる([[6_公共交通機関]]の「線路容量」参照) | `count` | なし |
| `tenant_blocked_by_parcel_size` | caution | 建設したい業種があるのに、その地区のどの土地区画でも必要な床面積を1棟で確保できず建設が止まっている状態(継続状態系)。入居待ちの一般施設テナントと、専用建物を建てる業種(工場・農場など)の両方が対象になる。プレイヤーの対処(より大きな土地区画を用意する)がないと恒常的に解消しないため常設表示するが、壊れるのは成長であって既存都市ではないため caution。地区×フロア種ごとに1件で、必要面積と地区内で建てられる最大容量を数値で示す | `tenant_name`(業種名), `zone_name`, `required`(必要m²), `max_capacity`(区画で建てられる最大m²), `count`(待機テナント数。専用建物の業種では1) | zone |
| `collapse` | warning | 当エポックの建物・道路の倒壊(ワンショット)。火災由来の死者も倒壊死として計上されるため火災専用の通知は無い(火災の発生自体はL3) | `count`, `deaths` | なし |
| `deaths_traffic` | warning | 当エポックの交通事故死(ワンショット)。事故の発生自体(死者なし)はL3のアラートフラグに留め、死者が出たときだけL1へ昇格する | `count` | なし |

### 文言化はフロントエンドの責務

バックエンドは通知メッセージの文言を組み立てず、`type` と `params` だけを返す。Tauri 側が i18n キー `notifications.types.<type>` へ params を差し込んで文言化する(表示言語の知識をバックエンドに持たせないため)。未知の type は汎用文言(`notifications.types.unknown`)へフォールバックするので、バックエンドが先行して新種の通知を返してもUIは壊れない。

例外として、対象エンティティの名前(資源名・施設名)は表示データとして params に含まれる(クエスト名と同じ扱い)。

## API

### `GET /api/v1/notifications`

現在有効なL1通知の一覧を返す。エポック未実行(新規ゲーム直後)は空リスト。

#### レスポンス

```json
{
  "notifications": [
    {
      "id": "resource_runway:12",
      "type": "resource_runway",
      "created_date": 8500,
      "params": { "name": "鉄鉱床", "remaining_epochs": 7 },
      "entity": { "type": "resource", "id": 12 },
      "severity": "warning"
    },
    {
      "id": "education_low_enrollment:34",
      "type": "education_low_enrollment",
      "created_date": 8500,
      "params": { "name": "スター大学", "enrolled": 3, "max_students": 120 },
      "entity": { "type": "agent", "id": 34 },
      "severity": "caution"
    }
  ]
}
```

- `id` ... 差分検出用の安定キー(上記「ライフサイクル」参照)
- `created_date` ... 発生時点のゲーム内日付(1800年1月1日からの経過日数)
- `entity` ... 通知対象のエンティティ参照。通知一覧の行クリックで対応する詳細ウィンドウ(`agent` → 経済主体詳細、`resource` → 天然資源詳細、`zone` → 地区詳細)を開くために使う。集約通知では null
- `severity` ... `warning` / `caution` の2階調(上記「通知トレイの重要度2階調」参照)。未知の値はフロントが安全側(warning扱い)へ倒す

#### レスポンスは endpoints.yaml 自動生成フローから外す

`l1_notifications` はエポックごとに全再構築される揮発的な派生データであり、通常のエンティティスキーマには載せない。`app/controllers/notifications.py` で手書きの Pydantic モデルとして定義する(アラートフラグの `GET /api/v1/alerts` と同方針)。

## Tauri 側の消費

### コックピット(hud/Cockpit.tsx)

- エポック実行ボタンの隣にアラートアイコン(`public/images/menu/tray_notifications.png`)を常設する
- `GET /api/v1/notifications` を30秒間隔でポーリングし、エポック実行終了でも即時再取得する(実行中はポーリングを止める)
- **warning が1件以上**あるときだけアイコンを赤系パルスで点滅させ(`cockpit-alert--active`)、右上に赤の件数バッジ(`cockpit-alert-badge`)を重ねる
- **caution** は点滅させず、右下に黄の件数バッジ(`cockpit-alert-badge--caution`)だけを重ねる(緊急でない問題で warning の点滅シグナルを薄めないため)
- アイコンクリックで `city_notifications` ウィンドウを開く
- **トーストは出さない**(点滅で気づける以上、プレイヤーの操作を遮る必要がないため)
- セッション切断時は一覧を空にし、別セーブのロードで旧セーブの件数バッジが残らないようにする

### 通知一覧ウィンドウ(CityNotificationsWindow.tsx)

- window-registry の `city_notifications`(single ポリシー)として開く通常のポップアップウィンドウ
- マウント時に一覧を取得し、「警告」「注意」の2セクションに分けて「アイコン+文言+発生日」の行として表示する(空のセクションは見出しごと出さない)。警告の行は赤系、注意の行は黄系の配色で区別する
- `entity` を持つ行はクリックで対応する詳細ウィンドウを開く
- 一過性トースト(NotificationWindow)とは別物で、「未解決の危機が続いている限り表示され続ける一覧」を担う

## L2 / L3 の表現(参照)

- **L2(エポック結果ウィンドウ)**: 公共施設の逼迫・衛生状態・治安などの「傾向」はエポック結果ウィンドウの統計タイルが担う。現状は件数が非0の災害系タイルの警告色表示のみで、天気マーク・矢印マークによる傾向表現は将来の改修対象
- **L3(アラートフラグ)**: 建設調達不足・火災・犯罪・交通事故・インフラ未接続など「どこで起きているか」が主情報の事象。仕組みは[[アラートフラグ管理]]を参照

## 新しいL1通知の追加手順(拡張ガイド)

1. **バックエンド**: `genesis-core/app/services/simulation/notification.py` の `NotificationPhase` に収集メソッドを追加する。判定に使う状態が確定するフェーズより後であることを確認し(現状はパイプライン最末尾なので通常は問題ない)、`_append()` で type / params / entity を積む。継続状態系は安定ID、ワンショット系は日付入りIDにする
2. **severity の選定**: 「築いた都市が崩壊する差し迫った危機」なら `warning`(既定値)、「放置しても壊れないが成長が止まる・徐々に荒廃する問題」なら `severity="caution"` を `_append()` に渡す
3. **フロントエンド**: 全対応言語の `tauri/src/i18n/<lang>/notifications.json` の `notifications.types` に文言キーを追加する。エンティティ参照で新しい種別を使う場合は `utils/cityNotifications.ts` の `NOTIFICATION_ENTITY_WINDOW_TYPES` に詳細ウィンドウとの対応を足す
4. **テスト**: `genesis-core/tests/test_notifications.py` に判定条件のテストを追加する

しきい値パラメータ(資源余命のエポック数など)は `GENERAL_PARAMS` の `NOTIFICATION_*` キーで調整できる(コード側デフォルトあり)。
