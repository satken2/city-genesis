# コンポーネント連携

City Genesis は3つの独立したプログラムで構成される。

- **バックエンド（genesis-core）**: Python / FastAPI。都市データの保持・経済シミュレーション・永続化を担う。
- **UI（city-genesis/tauri）**: Tauri / Rust + WebView。操作パネル・タスクバー・トップメニューなどの2Dインターフェースを描画する。
- **グラフィック（city-genesis/unity）**: Unity / C#。3Dワールドの描画・カメラ操作・ユーザーの空間入力を処理する。

これらはそれぞれ独立したプロセスとして動作し、HTTP またはメモリマップトファイル（MMF）で連携する。

## ロード画面のTips掲載データ

Tauriの `src/components/tips/TipsWindow.tsx` は `TIPS_LIST` からウィンドウ初期化時に1件を無作為に選び、選択されたIDに対応する `tips.items.<ID>.title` と `description` を表示する。文言は `src/i18n/<言語>/tutorial.json` にあり、日本語を原本として全7言語で同じIDを揃える。Tipsを追加する際は翻訳リソースと抽選リストの両方への登録が必要である。背景画像は任意で、画像を指定しない項目はテキストのみで表示する。

## 統計ウィンドウのタブ構成

Tauriの `src/components/statistics/CityStatisticsWindow.tsx` がタブ定義と表示切り替えを管理する。通常タブは人口（初期選択）、満足度、余暇、住環境、保健衛生、所得、経済、経済推移、教育、雇用、貿易、事故、事業所、移動、不動産、インフラ網、観光の順で、開店閉店履歴は含めない。`GET /api/v1/sessions` の `debug_execution` が真の場合だけ、末尾に開発者向けスポーンタブを追加する。

満足度は笑顔、余暇はパラソル、住環境は家、保健衛生は単色の十字、経済推移は折れ線グラフ、移動は車の自作インラインSVGで表す。アイコンの線色は共通CSSの選択・ホバー状態に従う。

### 満足度・余暇・住環境タブのデータ契約

3表示は `statistics/tabs/WellbeingTab.tsx` が共有し、`GET /api/v1/stats/wellbeing` から履歴を取る。履歴は都市全体か `zone_id` で指定した1地区分だけを返し（`scopes` が選択肢）、応答の `weights` が満足度の四軸の重みである。地区別の色分け地図は `GET /api/v1/stats/wellbeing/zones`（最新確定エポックの全地区の現在値を1回で返す。母集団世帯が0の地区は各指標が `null`）を使い、地区ごとにリクエストを分けない。

UI側の規則:

- 満足度の構成グラフは履歴の軸の値に `weights` を掛けた貢献点を積み上げる（等分の重みをUIに焼き込まない）。住環境は「4要素の平均×住宅充足度」の積で和に分解できないため、バックエンドが記録した乗数適用後の貢献値（`comfort_*`）をそのまま使い、UIで式を再現しない。
- 構成グラフを持つ表示は、評価済み世帯が0のエポックを推移・構成の両方から落とす（recharts の積み上げは欠測を0に丸め、総合指標が0になったように見えるため）。
- 地区別の値塗りは地区間の最小〜最大を両端に割り当てた相対値で、凡例に実値のレンジを併記する。
- 統計ウィンドウのエポック単位キャッシュ（`statistics/useEpochCache.ts`）は接続先・エポックの変更で破棄し、同一世代でも保持するレスポンスは最大32件。

## 起動順序

ユーザーのPC上でゲームが起動されると、以下の順序でプロセスが生成される。Steam経由での配布時、Steamが起動するのはバックエンド（`genesis.exe`）であり、UIとグラフィックはその子プロセスとして派生する。この構成により、権威データを持つバックエンドのライフサイクルとアプリ全体のライフサイクルが一致する。

1. バックエンドが最初に起動する。localhostの空きポートを自動的に確保し、FastAPIサーバーを立ち上げる。
2. サーバーの準備が整うと、バックエンドは **UIとグラフィックの両方を、それぞれ自身の直接の子プロセスとして** 起動する。
3. 子プロセスは中間シェルを介さず直接起動され、親（バックエンド）の環境変数を継承する。これは、Steamのオーバーレイ注入やSteam関連の環境変数を、実際に描画を行うグラフィックへ確実に引き継ぐために必要である。

バックエンドは、起動した子プロセスの生存を監視し、必要に応じて再起動やアプリ全体の終了を統括する。詳細は後述の「プロセス死活監視と統括シャットダウン」を参照。

各プロセスが通信するバックエンドのAPIサーバーアドレスは固定ではなく、起動時に動的に決定される。バックエンドは確保したポート番号を、子プロセスへ以下の形で伝達する。

- グラフィックへ: コマンドライン引数 `--api-base-url`（APIのベースURL全体）。
  Unityは採用したAPIベースURLだけをログに残し、起動引数全体は出力しない。Editorの引数にはUnity Hubの認証情報が含まれる場合があるため。
- UIへ: 環境変数 `GENESIS_API_PORT`（ポート番号）。あわせて、グラフィックが既に外部（＝バックエンド）によって起動済みであることを示す環境変数 `GENESIS_GRAPHIC_EXTERNAL=true` を渡す。これによりUIは自前でグラフィックを起動しない。

開発時は各プログラムを個別に起動することもでき、その場合UIは環境変数 `GENESIS_UI_API_BASE_URL` でAPIのベースURLを直接上書きできる。

## 通信方式

### UIとバックエンド、グラフィックとバックエンド

バックエンドに対する通信は、UIもグラフィックも共通でHTTP（REST API）を使用する。

UIは主に以下のエンドポイントを利用する。

- `GET /api/v1/sessions` — 現在のセッション状態（セーブIDや言語設定など）を取得する。
- `GET /api/v1/city` — 都市名や現在日付などの表示情報を取得する。
- `POST /api/v1/sessions` — 新規ゲームまたはセーブデータのロードを開始する。
- `DELETE /api/v1/sessions` — セッションを終了する。

グラフィックは主に以下のエンドポイント群を利用する。

- `GET /api/v1/agents`, `GET /api/v1/paths`, `GET /api/v1/parcels`, `GET /api/v1/buildings` など — 3D空間に配置するオブジェクトの形状・属性を取得する。
- `POST /api/v1/paths`, `POST /api/v1/buildings`, `POST /api/v1/parcels` など — ユーザーが確定した建設計画を登録する。
- `POST /api/v1/epochs` — エポックシミュレーションを実行する。実行は同時に1つだけで、別の実行の最中に届いた要求は409 `{"code": "EPOCH_ALREADY_RUNNING", "message": ...}` で断られる（未認証時の上限の判定から結果の集計までを1回の実行として排他にする。同時に走らせると、判定の後に別の実行がエポックを進めて上限を超えたり、集計中の都市が書き換わったりするため）。
- `POST /api/v1/system/verify` — 起動時にSteam認証チケットを送信して検証を依頼する（後述の「Steam認証」を参照）。

#### 一括取得エンドポイントのMessagePack対応

バウンディングボックス(BBOX)指定の一括取得エンドポイント(`GET /api/v1/buildings`, `GET /api/v1/paths`, `GET /api/v1/parcels`, `GET /api/v1/zones`, `GET /api/v1/nodes`)は、座標配列を大量に含む巨大なレスポンスを返すため、通常のJSONに加えて **MessagePack** バイナリ形式での応答に対応している。

- クライアントがリクエストの `Accept` ヘッダに `application/x-msgpack` を含めると、レスポンスは `Content-Type: application/x-msgpack` の MessagePack バイナリになる。含めなければ従来どおりJSONで応答する。
- レスポンスのデータ構造(プロパティ名・型)はJSONとMessagePackで完全に同一であり、シリアライズ形式だけが異なる。クライアントはレスポンスの `Content-Type` を見てデコーダを切り替える。
- ただし、辞書型プロパティの整数キー(例: `path_traffic` の商品ID)は、JSONでは文字列に暗黙変換されるのに対し、MessagePackでは整数のまま保持される。**受信側は整数キーを文字列キーとして扱うこと**(グラフィック側は `MsgPackDecoder` が、UI側は JavaScript のオブジェクトキー変換が自動的にこれを行う)。
- グラフィックは `ApiClient.GetBulk`、UIは `fetchApi` がこのネゴシエーションを自動で行うため、通常は呼び出し側が形式を意識する必要はない。
- 通信路はあくまでHTTPであり、この最適化はバックエンドをリモートサーバーで運用する構成でもそのまま機能する。

### ローカルAPIへの接続

バックエンドのHTTP APIは `127.0.0.1` だけで待ち受け、外部のネットワークへはポートを公開しない。認証やアクセス制限は無く、同じPCで動くプログラムは、UI・グラフィックに限らずサードパーティ製のものも、同じHTTP APIで都市の閲覧・編集ができる。

各クライアントの実装:

- **UI（Rust）**: 起動時にコアの版情報を取得してMAJORを照合し、フロントのMAJORがコアより小さければプログラム全体を終了する。取得成功後は版情報を全ウィンドウ・ゲーム開始・ロード・セッション監視で共有する。同時に要求されても実際の取得は1本にまとめる。起動準備中の取得失敗は再試行できるが、取得済みの結果に期限は設けない。`<ユーザーフォルダ>` は起動時に1回だけ決め（Windows は OS の既知フォルダより環境変数 `LOCALAPPDATA`・`APPDATA` を優先する。[ファイル配置](ファイル配置.md)）、セーブの置き場と地形エディタの作業コピーも同じフォルダを使う。
- **UI（WebView）**: `utils/api.ts` の `fetchApi` と置き換え後の `fetch` が、設定したバックエンドの `/api/v1/` 配下のURLへの要求を担う。各ウィンドウは版情報を取得しない。
- **UI（画像）**: APIの画像は `hooks/useApiImageUrl` が `fetchApi` で取得して Blob URL を作り、URLが変わったときとアンマウント時に解放する（`ScenarioThumbnail`）。画像のキャッシュは fetch のHTTPキャッシュに従う。
- **グラフィック（Unity）**: HTTPは必ず `ApiClient`（`Get`・`GetBulk`・`Post`・`Patch`、それ以外は `ApiClient.Request` が返す `ApiRequest`）を通す。`UnityWebRequest` を直接作らない。

CORSで許可するオリジンは `http://tauri.localhost`・`https://tauri.localhost`・`tauri://localhost`（TauriのWebView）と `http://localhost:1420`・`http://127.0.0.1:1420`（開発サーバー）だけで、資格情報（Cookie）は扱わない。メソッドと要求ヘッダーはすべて許可し、`X-Origin-X`・`X-Origin-Z`・`X-Grid-Rows`・`X-Grid-Cols` を応答ヘッダーとして公開する。CORSは他のミドルウェアより外側で処理するので、409・503 の応答にもCORSヘッダーが付き、UIは理由を読める。Unity と Rust の要求、およびブラウザ以外のサードパーティ製プログラムの要求はCORSの対象外である。

製品版・モックのバックエンドは、API仕様（`/docs`・`/redoc`・`/openapi.json`）と開発用の `/data/*` を提供しない。APIの一覧は本ドキュメントの API Reference を参照する。

UIのWebViewは Content Security Policy で読み込み元を制限する。製品版（`tauri.conf.json` の `csp`）ではスクリプトを自身のバンドルだけに限り（`eval` やインラインスクリプトは使えない）、画像は自身・`data:`・`blob:`・`http://127.0.0.1:*`・`http://localhost:*`、通信は自身・IPC・`http://127.0.0.1:*`・`http://localhost:*` に限る。スタイルは React の `style` 属性のためにインラインを許し、Tauri がスタイルへハッシュを足してインライン指定を無効にしないよう `dangerousDisableAssetCspModification: ["style-src"]` を指定する。デスクトップの `tauri dev` は `devUrl`（Vite の開発サーバー）を直接読むため、CSPは適用されない（TauriがCSPを付けるのは、組み込みのアセットを tauri プロトコルで配るときだけ）。CSP違反は `tauri build` の成果物で確認する。実行時に `new Function` を使うライブラリは使わない（チュートリアル定義のJSON Schema検証は事前生成したコードで行う。[チュートリアル基盤](チュートリアル基盤.md)）。製品版のビルドには開発者ツール（devtools）を含めない。CSPはIPv6のアドレスを書けないので、接続先に `[::1]` は使えない。

### UIとグラフィック

UIとグラフィックは、Windowsのメモリマップトファイル（MMF）を使ったIPCで連携する。双方が `CreateOrOpen` で同じ名前のMMFを開くため、どちらが先に起動しても接続できる。

UIからグラフィック方向には `genesis-ipc-ui-to-graphic` という名前のMMFが使用され、グラフィックからUI方向には `genesis-ipc-graphic-to-ui` が使用される。排他制御には `genesis-ipc-mutex-utg` / `genesis-ipc-mutex-gtu`、書き込み通知には `genesis-ipc-event-utg` / `genesis-ipc-event-gtu` を併用する。

MMFを使う理由は、同じPC内で低遅延かつ双方向のイベント通知を行うためである。HTTPは使用しない。

IPCでやり取りされる主なイベントには以下のようなものがある。

- `game:start` / `game:end` — ゲームセッションの開始・終了を通知する。
- `session:reload` / `session:reset` — 3Dワールドの再描画・クリアを指示する。
- `world:change_state` — グラフィックの操作モード（通常モード、道路敷設モード、建物建設モードなど）を切り替える。
- `world:select_object` — 3D空間でオブジェクトが選択されたことをUIに通知し、詳細パネルを開く。
- `system:shutdown` — アプリ全体の終了を相手プロセスへ通知する。UI・グラフィックいずれの向きにも送られ、受け取った側は自身を終了する。
- `system:graphic_ready` — グラフィックからUIへ、起動とIPC初期化の完了を通知する。毎起動時（初回・再起動を問わず）に送られ、UIは開いているポップアップウィンドウを一掃して表示をリセットする。グラフィックが再起動した際の再同期の起点となる。
- `system:graphic_stopped` — グラフィックからUIへ、正常終了（EditorのPlay停止を含む）を通知する。UIはグラフィックを未接続扱いに戻す。クラッシュ時は送られず、その場合はバックエンドによる自動再起動後の `system:graphic_ready` で整合する。
- `system:focus_gained` — グラフィックのウィンドウがフォアグラウンドになったことをUIへ通知する。グラフィックはモニタ全面を覆うボーダーレスウィンドウで動くため、活性化時にWindowsのシェルが「最前面」指定のUIウィンドウを裏へ回すことがある。UIはこの通知を受けて表示中の全ウィンドウの最前面指定を打ち直すため、UIが裏に隠れてもグラフィックをクリックすれば復帰する。

## UIのウィンドウ管理

UIは複数のWebViewウィンドウで構成され、その実体管理（生成・配置・ラベルの採番・二重起動の防止・閉じたときの後始末）はすべてRust側（`src-tauri/src/window.rs`）が持つ。Reactコンポーネントから別ウィンドウを開く操作は、最終的にTauriコマンド `open_window` の呼び出しに行き着く。

描画側は1つのReactアプリ（`tauri/src/App.tsx`）で、Tauriのウィンドウラベルによって描画内容を分岐する。常駐ウィンドウ（`main` / `icon-panel` / `cockpit` / `system-tray` / `display-tray` / `topmenu` / `notification` / `hintbar` / `tutorial` / `parameter-setup` / `tips`）はRustが直接生成し、それ以外のラベルはすべてポップアップとして扱う。

- **常駐HUDは4枚のウィンドウ**（`icon-panel`＝左端のメニュー、`cockpit`＝下部中央、`system-tray`＝右下、`display-tray`＝左下）に分かれている。3Dビューに重ねる透明なウィンドウは、見た目が透明な領域でもクリックをWebViewが吸ってしまうため、1枚の全画面ウィンドウにはできず、パネルの実面積ぴったりに分割する。ポップアップの配置計算は、HUDのあるモニターに置くときこれらの占有領域を避ける。
- **表示先のモニターは2系統**。HUD・ヒントバー・チュートリアル・トップメニュー・Tips・通知・初期パラメータ設定は、設定の「ディスプレイ」で選んだモニター（Unityのゲーム画面を置くモニター）に出す。ポップアップも通常は同じモニターだが、設定の「マルチディスプレイモード」ではHUDとは別のモニター（「ウィンドウの表示先」で選ぶ。HUDと同じモニターや接続されていないモニターを指していればHUDの次のモニター）に出し、そこではHUDを避けずに画面端まで使う。モニターが1台なら通常と同じになる。表示先が変わると、開いているポップアップ（閉じて再利用を待っているものを含む）は新しい表示先の初期配置へ移り、記憶していた位置・サイズは破棄される。
- **配置は物理座標で渡す**。拡大率の違うモニターが混在すると、論理座標はモニターをまたいで一意に定まらない。Tauriは論理座標の位置を、移動では今いるモニターの倍率で、生成では座標を含む最初のモニターの倍率で換算するため、別の場所や別のモニターに出る。Rustはモニター上の論理座標をそのモニターの倍率で物理座標に直してから渡し、ウィンドウは非表示で生成して配置してから表示する。
- **ポップアップは `config/window-registry.json` で定義する**（サイズ、ドック位置、single / multiple / single_per_entity のインスタンスポリシー）。同時に開けない組は `window-mutex-groups.json`（キーは開く側の種別。非表示から再表示するときにも適用する）。排他の相手を開くウィンドウは、自分を閉じる処理を持たずRustの排他に任せる。排他で非表示になった自分のWebViewがそのまま新しいウィンドウに転用されることがあり、後から届く自分の閉じる要求が新しいウィンドウを閉じてしまうため。各ポップアップは起動時にTauriコマンド `get_window_context` で自分のコンテキスト（ウィンドウ種別・対象エンティティ・params）を受け取る。常駐ウィンドウはコンテキストを持たない。
- タイトルバー(ドラッグ領域と×)を持たないポップアップは、レジストリの `chromeless` で指定する(システムメニュー `save_load`・ニューゲーム `new_game`・セーブデータ一覧 `save_list` など)。パネルがウィンドウ全体を描き、閉じる操作(メニューの「ゲームに戻る」・フッタの「閉じる」・Esc)もパネルが持つ。
- **閉じる操作は「破棄」ではなく「非表示にして再利用待ち」**。WebViewの再生成を避けるため、閉じたウィンドウは非表示のまま一定数まで保持し、同じ種別を開き直すときに再利用する。再利用時はラベルを変えずに `window-context-updated` イベントで新しいコンテキストを配り、世代番号 `open_seq` を増やす。Reactはこれを再マウントのキーに含めるため、再利用でもパネルの状態は必ず初期化される。
- 閉じたときの後始末（編集モードのウィンドウなら Unity を `STATE_NORMAL` へ戻す、詳細パネルならハイライトや強調を消す、対象IDを載せた打ち切りイベントを送る）は、Reactのアンマウント処理が走らないためRustが非表示化の時点で行う。閉じたら `STATE_NORMAL` を送るウィンドウ種別はRust側の一覧（`EDIT_MODE_WINDOW_TYPES`）で管理する。Unityの編集ステートは1つしかないため、この一覧の種別（公共交通の一覧・新設を含む）は `window-mutex-groups.json` で互いに同時に開けないようにする。併存させると、先に開いた側のパネルが別のステートに上書きされたまま残る。別の編集ツールを開くと表示中の編集ウィンドウは閉じ、そのときの `STATE_NORMAL` は新しいウィンドウが表示される前に送られる。
- 編集モードのウィンドウを開くと、Rustがイベント `hud:mode_changed`（`mode: null`）を全ウィンドウへ送り、HUDの常駐モード（ブルドーザ・地区編集）を解除する。HUDのアイコン・詳細パネルの「編集」ボタンなど、どこから開いても同じ処理を通る。
- ウィンドウの位置とサイズはプロセス起動中だけウィンドウ種別ごとに記憶し、開き直すと復元する（ドック配置のウィンドウはサイズのみ）。位置は物理座標で記憶する。永続化はしない。
- Unityはモニタ全面を覆うボーダーレスウィンドウなので、活性化時にシェルがUIの最前面指定を外すことがある。Rustは `system:focus_gained` / `system:graphic_ready` の受信、HUDの表示、UIウィンドウのフォーカス喪失のたびに、表示中の全ウィンドウの最前面指定を打ち直す。
- Unity→UIのイベントを受けてウィンドウを開く場合、内容はウィンドウのコンテキスト（`params.extra`）に載せて渡す。イベントを送ってからウィンドウを開くと、開いたウィンドウの購読が間に合わずイベントを受け取れない（地区統合の確定ウィンドウ `zone_merge` がこの形）。

## セッション状態の管理

ゲームの「セーブデータがロードされているかどうか」という状態は、バックエンドの `GameData3.current_save_id` が唯一の情報源である。この値が `null` の間はゲーム未開始、非 `null` の文字列が入っている間はゲーム進行中とみなされる。

UIはバックエンドのセッション状態を自前で保持せず、5秒ごとに `GET /api/v1/sessions` をポーリングして常に最新の状態を問い合わせる。ポーリング結果は `session-state` という名前のイベントとして、UI内の全WebViewウィンドウにブロードキャストされる。

`GET /api/v1/sessions` のレスポンスには、`current_save_id` のほかに以下のフィールドも含まれる。バックエンドからUIへ状態を伝える経路はこのポーリングだけなので、プッシュしたい状態はここに相乗りさせる。

- `shutting_down` — バックエンドがアプリ全体の終了シーケンスに入ったかどうか（後述の「プロセス死活監視と統括シャットダウン」を参照）。
- `verification_status` — Steam認証の状態（後述の「Steam認証」を参照）。

`current_save_id` が `null` の間に使えるのは、システム（`/api/v1/system`）・セッション・セーブ・シナリオ・パラメーター・テンプレート・マスターデータのAPIだけである。それ以外の都市のデータを返すAPI（地形を含む）は503 `NO_SAVE_LOADED` を返す。

シナリオの地形編集や標高ファイルからのシナリオ作成では、コアがゲームのセッションを使わずに一時的に都市を組み立てる。その間も `current_save_id` は `null` のまま返り、都市のデータを返すAPIは503 `NO_SAVE_LOADED` を返す。UIとグラフィックがこれをゲーム開始と誤認しないためである。処理の間は、システム・パラメーター・テンプレートへの書き換え要求（`GET`・`HEAD`・`OPTIONS` 以外。終了 `POST /api/v1/system/shutdown` とSteam認証 `POST /api/v1/system/verify` を除く）を409 `SESSION_ACTIVE` で断る。セッションの作成・変更・終了（`POST` / `PATCH` / `DELETE /api/v1/sessions`）とパラメーターの変更（`PATCH /api/v1/parameters`）は、この処理や保存と直列に実行される。

### ゲーム未ロード時の表示

`current_save_id` が `null` の間、UIはトップメニュー（`topmenu` ウィンドウ）を表示する。トップメニューには「新規ゲーム」「ロード」などのボタンがあり、ユーザーがゲームを開始するまでの入り口となる。

グラフィックは起動後にバックエンドのセッション状態を問い合わせ、ゲーム開始まで再試行する。未設定であればゲーム未開始状態を維持する。ワールドデータを受け取るまでは3D空間に都市オブジェクトを描画しない。

### 初期ロードとTips

ニューゲームのシナリオ選択画面は、トップメニュー・プレイ中のシステムメニューのどちらからでも、Unityの起動・リセットやデータ破棄の確認を行わずに開く。シナリオの閲覧・選択・開始設定中は現在の都市と3D表示を保持するため、「閉じる」・Esc・設定確認の「戻る」で取り消しても現在のゲームを続けられる。

「このシナリオを始める」で開くゲーム設定の確認ダイアログには、`GET /api/v1/sessions` の `current_save_id` が非nullの場合だけ「現在のゲームの未保存の変更は失われます」と表示する。未保存の都市にもIDがあるため、セーブファイルの有無では判断しない。表示中は共通監視の `session-state` にも追従し、セッションの確認が済むまで最終の「開始」を無効にする。チュートリアルも同じ確認を通す。最終の「開始」で `create_session` を呼び、版・保存データの検証後にUnityの起動・リセット、暗転、初期ロードへ進む。保存済みのセーブファイルはこの切替では削除しない。

`TipsWindow`の`mode`は`initial`（既定）または`epoch`。初期ロードでは描画準備が終わっても明示的な開始ボタンを待つ。エポック用は`index.html?tipsMode=epoch`で開き、初期ロード状態を問い合わせず開始ボタンも出さない。エポック実行側が完了時に自動で閉じる。エポック用の開閉では`game:reveal`や初期設定への遷移を行わない。

エポック実行は確定直後に裏で開始し、Unityの日没1.5秒・黒幕フェード0.5秒の完了通知を待ってから表示を進める。実行済みなら結果、未完了ならTipsを表示する。右下の実行中通知は使用しない。処理完了後はTipsを閉じて結果を表示し、結果を閉じるまでは背景を黒く維持する。結果画面はタイトルバーを持たず(`chromeless`)、閉じるボタンとEscがRustの共通終了処理を通り、0.5秒のフェードイン・1.5秒の日の出で復帰する。結果がない応答や失敗では待機を解除して復帰する。

初期ロードは `tips` ウィンドウに統合する。バックエンドへの開始要求中からTipsと回転アイコン付きの `Now Loading...` を表示し、文字は20px・太字で左から右へ光が移動する。動きを減らす設定ではアニメーションを停止する。

`begin_initial_loading` は要求ごとの `loading_id` と、空の都市を新規作成したかを保持する。POST成功後に `session:reload` と `game:start {loading_id}` を送り、同じセーブIDを再ロードした場合も初期描画を開始する。Unityの `game:loaded {loading_id}` が現在の世代と一致したら、Tipsを「ゲームを開始する」ボタンへ切り替える。TipsはRustの保持状態を問い合わせるので、WebView起動前の完了通知も取りこぼさない。

開始ボタンは `game:reveal {loading_id}` で黒画面を解除する。通常ロード・シナリオ・チュートリアル・テンプレート編集では初期設定を自動表示しない。空の都市を新規作成した場合だけTipsの次に `ParameterSetupWindow` を表示し、設定完了までHUDを抑制する。設定完了時に都市を再ロードしない。テンプレート編集から手動で開くパラメータ編集は従来どおり使用できる。

HUDとヒントバーは `current_save_id != null && !isLoading` を表示条件とする。`isLoading` は描画準備・開始ボタン待ち・初期設定中を含む。TipsのAlt+F4では待機を解除しない。開始APIの失敗時はTipsを破棄し、ロード状態を解除する。

カメラの視点はUIを経由しない。グラフィックは `game:start` を受けると `GET /api/v1/city` の `camera`（セーブに保存された視点。シナリオから始めた都市ではシナリオの初期視点）を読んでカメラを復元し、以後はカメラが静止するたびに `PATCH /api/v1/city` で視点をバックエンドへ送る。視点はセーブデータに含まれるため、ロード後は保存時の場所と向きから再開する。`camera` が `null` の都市はマップ中心（原点）の上空の既定視点で始まる。

### ゲーム終了時の表示遷移

セッションが破棄され `current_save_id` が `null` に戻ると、UIは開いている全ポップアップウィンドウを閉じ、タスクバーとヒントバーを隠してトップメニューを再表示する。同時にグラフィックに `game:end` を送信し、3Dワールドの描画を終了させる。

初期ロード中(Tips表示中・初期設定中)にセッションが破棄された場合も同じ終了処理を行い、Tipsと初期設定ウィンドウを閉じてロード状態を解除する。破棄された都市ではグラフィックが `game:loaded` を返せず、Tipsは自力で閉じられないため、ここで打ち切らないと操作不能になる。ただし開始要求のPOST応答前は新しいセッションがまだ無いのが正常なので、バックエンドの準備完了を確認した後に取得した `current_save_id` だけで判定する。

## プロセス死活監視と統括シャットダウン

バックエンドは子プロセス（UI・グラフィック）を単に起動するだけでなく、それらの生存を監視し、アプリ全体の終了を一箇所で統括する。

### グラフィックの死活監視と自動再起動

バックエンドはグラフィックの終了を監視する。

- グラフィックが **正常終了（ウィンドウの×ボタンなどによる正常なプロセス終了）** した場合は、ユーザーがアプリを終了しようとしたものとみなし、後述の統括シャットダウンを開始する。
- グラフィックが **異常終了（クラッシュ）** した場合は、バックエンドが自動的に再起動する。再起動後、グラフィックは自分から `system:graphic_ready` を送って再同期を主導し、3Dワールドを作り直す。ただし短時間に繰り返しクラッシュする場合（一定時間内に複数回）は、再起動をあきらめてアプリ全体を終了する。

UIプロセスが終了した場合も、バックエンドはこれを検知して統括シャットダウンを開始する。

### 統括シャットダウンの合流

以下のいずれの経路も、最終的にバックエンドの単一のシャットダウン処理へ合流する。この処理は冪等であり、複数の経路が同時に発火しても二重に走らない。

- UIの終了操作（終了ボタン、またはメインウィンドウの×ボタン）。UIはグラフィックへ `system:shutdown` を送り、バックエンドへ終了を要求する。
- グラフィックの正常終了、または短時間でのクラッシュの繰り返し。
- UIプロセスの消失。
- OSからの終了シグナル（SIGTERM / SIGINT）。

合流したシャットダウン処理は、おおむね次の順で進む。

1. セッション状態を「終了中」にする。これは `GET /api/v1/sessions` の `shutting_down` として公開される。UIはポーリングでこれを検知すると、グラフィックへ `system:shutdown` を送ったうえで自身を終了する。
2. 未保存のデータがあれば緊急オートセーブを行う（固定スロットに保存し、通常のセーブスロットは汚さない）。エポック実行中であれば、完了を一定時間だけ待つ。
3. 子プロセスの自発的な終了を一定時間待ち、残っていれば終了させる。
4. バックエンド自身を終了する。

さらに、バックエンドが強制終了された場合でも子プロセスが孤児として残らないよう、OSレベルの後始末機構によって子プロセスがまとめて終了するようになっている（この仕組みはWindowsでのみ有効で、他のプラットフォームでは何もしない）。

## 通信切断時の挙動

起動時の版の照合と、稼働中の通信確認は別に扱う。版情報は各プロセスの起動時に一度取得し、WebViewごとの取得や定期的な再取得は行わない。Tauriは共通のセッション監視で `GET /api/v1/sessions` を確認する。

| 状況 | 製品版のTauri・Unity | 開発版のTauri・Unity |
| --- | --- | --- |
| 通信確認が1回失敗 | 都市・セッション・編集中の画面を保持し、接続確認中の表示と更新操作の停止を行う | 同じ動作 |
| 次の確認が成功 | 連続失敗を解除し、状態を読み直して操作を再開する | 同じ動作 |
| 通信確認が2回連続で失敗 | TauriはUnityへ `system:shutdown` を送り自分も終了する。Unityも独立した確認で2回失敗したら自分で終了する | Tauriは都市表示・ロード・演出・ポップアップを片付けてトップメニューへ戻り、再接続を待つ。Unityは終了せず `game:end` で都市表示を終了する |
| 再接続時のセッション | 製品版ではコアを実行中に再起動しない | セッションがあれば初期描画から復帰し、なければトップメニューで待つ |

Tauriの開発版は `debug_assertions` と `dev` の両方が有効なビルド、Unityの開発版はEditorまたはDevelopment Buildである。製品版のUnityの独立監視は、Tauriの終了通知が届かない場合に終了を保証するための経路で、開発版では実行しない。通常の起動時にはUnityもセッション復帰用の確認を行い、ゲーム開始後に止める。

通信確認は5秒の待ち時間を挟み、各要求のタイムアウトは10秒。2回連続の失敗は、断絶から正確に10秒後を意味しない。都市情報 `GET /api/v1/city` の失敗や互換性不一致を通信断の回数に加えない。

通信待ちではTauriのゲーム画面を `inert` にし、Unityの入力ゲートでも編集を止める。HTTPの共通窓口とRust側の開始・保存コマンドも更新要求を拒否する。設定・クレジット・終了は利用できる。POST・PATCH・PUT・DELETEは保留や自動再送をしない。応答だけ失われた操作を二重実行しないため、復旧時は読み取り要求で現在の状態を確認する。セッションの消失・切り替えを画面へ反映してから操作を解禁し、古い都市のポップアップから再接続先の都市を変更させない。

開発中のコア再起動でも取得済みの版情報は再取得しない。コアやマスターデータを変更した場合はフロントも再起動する。明示的な終了操作・コアの `shutting_down` 通知・Job Objectとスーパーバイザによる子プロセスの後始末は通常どおり有効である。

UIとグラフィックの間のIPCが切断された場合、UIは開いているポップアップウィンドウを閉じる。HTTP通信断の終了判定とは別の経路であり、明示的な `system:shutdown` は終了要求として扱う。

## Steam認証

Steam経由での配布時、ゲームは起動チケットによる所有権の検証を行う。この検証はグラフィック（Unity）が担当する。グラフィックはSteamのAPIを介して認証チケットを取得し、`POST /api/v1/system/verify`（本文 `{app_id, ticket}`。チケットは16進文字列）でバックエンドへ送信する。

バックエンドはチケットを外部の検証サーバーへ転送し、検証サーバーが署名した結果だけを受け入れる。署名を確かめる公開鍵はバックエンドに組み込まれているので、偽の検証サーバーや改ざんした応答では認証を通せない。要求ごとに使い捨ての乱数を付けて、過去の応答の使い回しも防ぐ。クライアントが申告した `app_id` は信用せず、ゲームのApp IDと一致しなければ失敗にする。

検証に成功すると、バックエンドは認証済みになり、所有している追加パック（DLC）の鍵も受け取る（暗号化されたDLCのシナリオを開くのに使う。[セーブデータ仕様](セーブデータ仕様.md#暗号化されたファイル)）。成功した結果はOSのユーザーごとに保護して保存し、発行から30日間は、オフラインで起動しても認証済みとして扱う。保存した結果が読めない・壊れている・署名が合わない・期限が切れているときは、それを捨てて未認証として起動する（起動は止めない）。

検証状態は `GET /api/v1/sessions` の `verification_status` として公開される。

`POST /api/v1/system/verify` は、検証結果に応じて次のHTTPステータスを返す。グラフィックはこれを見て挙動を切り替える。

- **200** — 検証成功。
- **401** — 失敗（チケットが無効、検証サーバーの応答が不正、App IDが一致しない。確定的な失敗なので、グラフィックは再送しない）。
- **502** — 検証サーバーに到達できない、または一時的な障害（グラフィックは新しいチケットを取り直して再送してよい）。

認証状態を下げるのは、検証サーバーがチケットを無効と確定させたときだけである。そのときバックエンドは未認証に戻り、保存した結果と追加パックの鍵を捨てる。通信の失敗や不正な応答では状態を変えないので、オフラインで遊んでいる正規のユーザーが認証を失うことはない。ソースから起動した開発用のバックエンドは検証サーバーへ問い合わせず、常に認証済みとして扱う。

Steamが起動していない環境などで検証が完了しないままでも、ゲームは起動し続ける。ただしその場合、エポックを実行できる回数に制限がかかる。`POST /api/v1/epochs` の `count` は1〜10000で、未認証のまま実行すると上限を超える要求は、実行前に403 `{"code": "UNVERIFIED_EPOCH_LIMIT", "message": ...}` で拒否される。複数エポックの実行中も1エポックごとに判定し直し、途中で未認証になったらそこで打ち切って実行済みの分を返す。

製品版のバックエンドでは、神モード（`template_mode`）を `PATCH /api/v1/sessions` で有効にできない（403 `TEMPLATE_MODE_FORBIDDEN`）。無効にする操作はいつでもできる。製品版で神モードに入る経路は、シナリオ制作とチュートリアルの開始（`POST /api/v1/sessions` の `template_mode`・`is_tutorial`）だけである。

### 本番ビルド（exe）時の通信喪失による自動終了

Tauriのセッション監視（`GET /api/v1/sessions`）で通信切断・セッション消失を検出した場合は、都市の操作・ロード待ち・エポック演出を終了し、ポップアップ・HUDを片付けてトップメニューへ戻す。Unityには `game:end` を通知する。切断が続いている間は接続失敗を表示し、再試行のたびに設定などのウィンドウを閉じない。接続表示はこの監視結果を全WebViewへ配信して更新し、版情報の再取得には使わない。

コアはゲーム実行中に再起動・別の版への差し替えを行わない。開発中にコアを差し替えた場合はフロントも起動し直す。Unityから版確認や生存確認を周期的に重ねず、バックエンドからの統括シャットダウン要求は従来どおりアプリ全体の終了として扱う。

開発中（`tauri dev` 実行時および Unity エディタ実行・Development Build 時）は、一時的な通信切れで終了しないようにこの自動終了機能は無効になる。


### Unity単独起動時の接続先

`--api-base-url` が無い場合は `http://127.0.0.1:5000/api/v1` を使う。IPv4ループバックで待受ける開発サーバーに対し、localhostのIPv6接続失敗からのフォールバック待ちを避けるためである。起動引数で明示した接続先は書き換えない。


### 停留所の描画用参照

ノードHTTP応答のstation_path_idは、公共交通停留所の所属道路・駅パスを示す。Unityのバス停上屋はこのIDからロード済み道路を参照して配置する。これはノードの保存値の公開であり、Unityから装飾用の位置変更をバックエンドへ送ることはない。

初期設定またはTipsから通常操作へ進む際はUI内の `initial-loading:finished` イベントでHUDとヒントバーの描画を即座に解禁し、次回のセッションポーリングを待たない。


開発時のUnityなし起動: 通常の `npm run tauri dev`（Rustの `cfg(all(debug_assertions, dev))`）では、Unityが接続中でない場合に限り、バックエンドの開始要求成功とセッション確認後に描画待ちを省略し、Tipsを開始ボタンへ切り替える。接続中かどうかは `system:graphic_ready`（接続）と `system:graphic_stopped`（正常終了・EditorのPlay停止）で追跡し、「一度でも接続したか」では判定しない（それだとPlayを止めた後の再ロードで永遠に待つ）。接続中は描画完了を待ち、待機中にUnityが停止した場合はその時点で開始ボタンへ切り替える。待機中にUnityが接続した場合は開始要求を再送して描画待ちに戻る。`tauri build`（`--debug` を含む）およびリリースビルドには省略処理を含めない。環境変数やバックエンドのNuitka／uvicorn判定は使用しない。

## UIの多言語対応

- 対応言語は `tauri/src/utils/locale.ts` の `SUPPORTED_LANGUAGES` が唯一の正で、`ja` / `en` / `es-419` / `zh-Hans` / `zh-Hant` / `fr` / `ko` の7つ。日本語を原本として他言語へ訳す。中国語は地域ではなく字体(簡体字・繁体字)で分け、スペイン語はラテンアメリカ向けの `es-419` とする。設定ウィンドウ・ニューゲームの言語選択肢もこの配列の順で並ぶ(表示名は `settings.language.<コード>`)。
- 翻訳リソースは `tauri/src/i18n/<言語コード>/` にドメイン別のJSON(`agent.json`・`budget.json` など)で置く。各ファイルはトップレベル名前空間をそのまま含み、`i18n/index.ts` が `import.meta.glob("./*/*.json")` で全言語・全ファイルを読んで言語ごとに単一の `translation` 名前空間へ集約する。キーは `t("agent.foo")` のように名前空間付きで参照する。新しい名前空間は既存ファイルに入れるか、全言語に同名の新規ファイルを作れば自動で拾われる。
- 日本語を基準にしたキーの過不足と `{{変数}}` の食い違いは `tauri/tools/check_i18n_parity.py` で検査する。
- i18nインスタンスはWebViewウィンドウごとに独立している。各ウィンドウはマウント時に保存済み設定から言語を復元し、以後の変更は設定保存時にブロードキャストされる `settings-updated` イベントを受けて `changeLanguage` する。再マウントされない常駐ウィンドウ(HUD・トップメニュー)もこの経路で追従する。
- 数値・日付の整形に渡すロケールは `resolveIntlLocale(i18n.language)` で解決する。言語コードと `Intl` 用の地域付きロケールの対応表は `locale.ts` に集約している。ゲーム内の仮想暦(1ヶ月=30日・1年=360日)の整形は `utils/date.ts` が担当し、月名は `Intl` から引くため言語を追加しても月名の手当ては不要で、年月日の並びだけ言語系統ごとに分岐する。

## ニューゲームと舞台の地形

`tauri/src/components/taskbar/NewGameWindow.tsx` は `FlatTabs` で「シナリオを選択」と「シナリオを探す」の2タブを持つ。「シナリオを探す」は共有シナリオの閲覧用で、未提供のため無効にし、Coming soon の札を付ける。

ウィンドウはタイトルバーを持たず(`chromeless`)、閉じるのは左下の「閉じる」とEsc(確認ダイアログを開いているときはEscでダイアログだけを閉じる)。左カラムの上端に小見出しと見出しの大きさのタブを置き、その下に選択肢の一覧、右にウィンドウの右端・上端・下端まで届く固定幅の詳細を置く。一覧は「チュートリアル」（常に表示）と「シナリオ」（`GET /api/v1/scenarios` の全保存元（自作・コミュニティ・DLC））の2節に分け、`scenarios:changed` で取り直す。タイルはサムネイルを全面に敷いて名前・保存元の札だけを重ね、説明・達成条件・舞台の地形（大きさ・地表・気候）・版情報は詳細に集約する。詳細は選んだ対象の画像を上端いっぱいに敷き、その下端にタイトルを重ね、開始ボタンを下端に置く。地形から直接始める入口は無く、標高ファイルはシナリオ管理で取り込んでシナリオにしてから遊ぶ（[シナリオ制作と配布](シナリオ制作と配布.md)）。チュートリアルはゲームに同梱した都市から始まる（[チュートリアル基盤](チュートリアル基盤.md)）。読み込めないシナリオは開始できない。タイル・詳細の紹介文は多言語テキストを表示言語で引く(無ければ英語)。開始ボタンで選択画面の上に確認ダイアログ(ウィンドウ内のオーバーレイ。選択画面は幕の下に残り、幕を押すか「戻る」で閉じる)を重ね、そこで都市名・都市の言語・シミュレーション日数と、シナリオでは作者が固定していない開始設定(気候・地表・アセットの地域)を決める。都市の言語の既定はアプリ設定の言語で、シナリオの言語と違うときは名前を付け直すことを注記する([シナリオ制作と配布](シナリオ制作と配布.md#ゲーム開始時の言語と開始設定))。

シナリオの舞台の地形の属性(大きさ・地表・気候)は、ニューゲームのシナリオの詳細に共通部品 `common/TerrainFacts` で表示する。チュートリアルの詳細は教材の画像と説明だけを出し、地形の属性は出さない。シナリオの説明・達成条件は作成者のフリーテキストをそのまま表示する。達成条件の節は常に出し、達成条件を持たないシナリオでは「達成条件なし」と書く(達成条件が無いこともシナリオを選ぶ情報になるため)。画像を持たないシナリオはプレースホルダーを表示する(標高ファイルから作ったシナリオは作成時に地形から画像を描いてある)。

詳細欄の幅はウィンドウ幅の36%(380〜540px)とし、画像(16:10)・タイトル・本文をまとめてスクロールする。開始ボタンは下端に固定し、左カラムの「閉じる」と同じ高さの段に揃える。属性はマップサイズ・地表の種類・気候の3項目を1段に並べた諸元の帯で表示する(カードにせず、上下の細い罫線と項目間の縦の罫線で区切る)。

- サイズはシナリオ一覧の要素の `map_width` / `map_height` を1,000で割り、UIのロケールに従って `7 × 7 km` のように表示する。島の面積ではなくマップ範囲の幅と高さである。欠損・非有限値・非正数は不明として扱う。
- 地表はAPIの `ground_cover` を正規化して `GroundCoverIcon.tsx` の自作SVGで表す。草原・砂丘・濃い草地・雪・乾燥地を描き分け、翻訳された種別名をSVGの `title` と `aria-label` に残す。
- 気候はAPIの `climate` を `normalizeClimate` で正規化し、全7言語の `climate.<値>` で表示する。「未分類」にはしない。現行の気候データは7区分の `CLIMATE_*` であり、ケッペン記号を保持していない。UI側で地名から別の分類や記号を割り当てない。
- シナリオの地表・気候は、シナリオ一覧の要素に保存された `ground_cover`・`climate`（都市が持つ値で、地形エディタの保存で変わる）を表示する。要素に値が無ければ大きさ・地表を不明とし、気候はゲームと同じ温暖湿潤を表示する。

## UIの共通スタイル

- スクロールバー: WebView2(Chromium)の既定はコンテンツに重なるオーバーレイ式で、パネル右端の値やボタンが隠れて操作できなくなる。これを避けるため `tauri/src/App.css` で `*::-webkit-scrollbar` 系を定義し、全スクロール領域を従来型(レイアウト幅を占める)に切り替えている。個別に幅・色を変えたい要素だけ、そのセレクタで `::-webkit-scrollbar` を上書きする。標準プロパティの `scrollbar-width` / `scrollbar-color` は使わない。Chromiumではこれらを指定した要素で `::-webkit-scrollbar` が無効化され、オーバーレイ表示に戻ることがある。
- フラット意匠(`--flat-*`): トップメニュー系のウィンドウ(ニューゲーム・セーブ/ロード・シナリオ管理・エポック実行確認・エポック結果・設定)は、枠線・角丸・発光を使わず、ベタ塗りの面と落ち影だけで高さを表す意匠で統一している。強調は枠ではなく左端の実線ブロック(`box-shadow: inset 4px 0 0 var(--flat-accent)`)で示す。配色と影は `App.css` の `:root` にある `--flat-*`(面 `--flat-surface` / `--flat-raised` / `--flat-sunken`、選択 `--flat-selected`、文字 `--flat-text*`、状態 `--flat-good` / `--flat-warn` / `--flat-danger` とその面色、影 `--flat-shadow` / `--flat-shadow-sm`)が唯一の正で、直値では書かない。`App.css` の `.panel` / `button` などの旧来のグローバルスタイルは角丸・枠線を持つ別系統なので、この意匠のウィンドウでは `border: none; border-radius: 0` で明示的に打ち消す。

- 設定フォーム: アプリ設定・都市名の変更・システム統計の近似の節は `common/SettingsRow.tsx` と `common/SettingsForm.css` を共用する。グループ見出し、カード、設定行、Coming soon の札、セグメント選択、入力欄の意匠を統一する。システム統計では共通部品の入力契約を保ちつつ、カードの面を外して縦並びの設定行にする。未提供の行は文字の可読性を保ちつつ操作部を薄くし、各入力・ボタンの `disabled` でキーボード操作も無効化する。

- 文字サイズ: アプリ設定の文字サイズ(小10 / 中12 / 大14px、カスタムは8〜32px。既定は中)は本文の大きさで、`contexts/FontSizeContext.tsx` がルートの `font-size` に入れる(1rem = 本文)。コンポーネントの文字サイズは rem で書き、本文を 1rem、見出しや補足をその倍率にする。こうすると設定の変更で全ウィンドウが同じ比率で拡縮する。文字に連動する寸法(情報グリッドの行の高さ、統計・公共交通のタブ列の幅など)も rem で書く。グラフ(recharts)の目盛り・凡例・ツールチップにも `fontSize: "0.93rem"` のように rem の文字列を渡す(SVGの属性でも rem が効き、設定の変更に即座に追従する)。Y 軸の `width` のように px の数値しか受け付けない寸法は、`hooks/useRemPx` で rem から今の設定の px に換算する(縦に並べたグラフの横位置を揃える共通の軸幅も、この換算で文字と一緒に拡縮する)。px で固定するのは次の3つだけ。
    - Rust側でウィンドウ寸法を固定している常駐ウィンドウ(HUD4枚・ヒントバー・チュートリアル・通知・Tips)。文字だけが大きくなると切れるため。
    - 設定フォーム(`SettingsForm.css` を使うアプリ設定・都市名の変更・システム統計の近似の節)。値を変えた瞬間に設定画面自体のレイアウトが崩れないようにするため。
    - 図の一部として描く文字(canvas、viewBox で拡縮する SVG、地図の方位記号、道路の帯図)。

### 都市名の変更

コックピットの都市名をクリックすると都市名の変更ウィンドウを開く。ウィンドウ種別は `city_rename`、実装は `taskbar/CityRenameWindow.tsx`。入力欄1つと保存・キャンセルだけの小さなウィンドウ(460×210、リサイズ不可)である。

都市名は `GET /api/v1/city/` から取得し、変更時は `PATCH /api/v1/city/` に `name` のみを送る。成功後は `city:renamed` でHUDへ即時通知する。空白だけの名前・未変更の名前は保存できず、保存中は操作を無効化する。

### システム統計

システムトレイの左端のボタンからシステム統計を開く。ウィンドウ種別は `system_stats`、実装は `statistics/SystemStatsWindow.tsx`。内容は `GET /api/v1/stats/system` の1回の応答で、タブを持たず左右2列に並べる(初期サイズ1120×850、リサイズ可)。左列の上段にシステムステータスとエンティティ数の2列(システムステータスが左、エンティティ数が右)、下段にシミュレーション負荷、右列にシミュレーションの近似を置き、それぞれ独立してスクロールする。幅が70rem以下のときは縦並びに切り替え、本文全体をスクロールする。開いたときと、エポックの実行が終わったとき(`epoch:executing` の `executing: false`)に取り直す。都市の中で本格的な経済シミュレーションが動いていることを見せ、シミュレーションの近似を選ぶ目安にするためのウィンドウで、値の厳密さは求めない。

- シミュレーション負荷: 直近のエポックの計算時間を、1本の積み上げ横棒と内訳の表で示す。
    - 区分は大きな処理8つ(商品市場・不動産市場・労働市場・建物スポーン・経済主体スポーン・市民の経路探索・公共交通の経路探索・住環境)と「その他」。
    - 時間はコアがエポックの中で記録している処理ごとの時間を読むだけで、全体の時間はその合計である。エポックの前後の初期化・集計のような処理の外側の時間は含めない。
    - 複数のエポックを続けて実行したときは最後のエポックの値になる。
    - 計測値はセーブに含めない(実行したPCに依存するため)。ロード直後やまだエポックを実行していないとき、モックバックエンドでは応答の `epoch` が `null` で、「計測データなし」と表示する。
    - 処理件数は、各処理の主な比較の組み合わせ数(需要者×供給者、求職者×雇用主体など)を、ウィンドウを開いた時点の都市の規模から見積もった目安である。値にマウスを重ねると式と内訳が出る。
    - 表は処理・時間・処理件数の3列で、コンパクトな行間と右揃えの数値で表示する。処理件数は万・億などへ省略せず全桁を桁区切り付きで表示する(日本語ではコンマ区切り)。説明文は本文に置かず処理件数のツールチップで示す。区分の色はカテゴリごとに固定し、並びや件数が変わっても塗り替えない。色は暗色の面で色覚多様性とコントラストの検証を通した8色で、その他は無彩色。
- エンティティ数: 項目・件数の2列の表で、桁を揃えて表示する。プレイで増える総数だけを出す(経済主体、市民、地区、土地区画、パス、ノード)。応答の `entities` はコアのテーブルに入っている行数をそのまま数えた整数で、描画の可視・不可視やパスの種類で除外しない。分類別の内訳と人口、路線数や経過エポックは返さない。マスターの種類数のように変わらない値は出さない。
- システムステータス: 表やセルを使わず、CPU製品名、GPU製品名とVRAM、搭載RAM、GPUアクセラレーションの状態を左寄せのテキストで並べる。GPU製品名とVRAMは検出値を使い、取得できないときはGPUの行を省く。アクセラレーションは未対応のため「無効」と表示する。
    - その下の「[コアシミュレーター]」に現在と起動以降の最大メモリ使用量を、続く「[3D]」(Unity)にも同じ2つと現在のVRAM使用量をテキストで表示する。3Dのメモリはコアが3Dの子プロセスのメモリをPIDで読むだけで、UnityとのIPCは使わない。3Dが起動していない・読めないとき、VRAMが読めないとき(Windows以外を含む)は該当の行を省く。VRAMの使用量は現在値のみで、最大値は持たない。
    - その下にRAMとVRAMのメーターを1本ずつ並べる。バーの全体が搭載量(RAMは搭載メモリ、VRAMはGPUの専用メモリ)、グレーがPC全体の使用量、緑が本ゲームの使用量(RAMはコア+3D、VRAMは3D)で、緑はグレーの内側に重ねる。凡例を添え、値にマウスを重ねるとPC全体・本ゲーム・搭載量の数値が出る。VRAMのバーは搭載量とVRAM使用量がそろうときだけ表示する。
    - ハードウェアの容量は整数のGB、プロセスの使用量はMBまたはGBで表示する。文字サイズは通常の本文と同じ。
    - 最大値はOSがプロセスごとに記録している最大値で、エポック中の一時的な増加やロード・保存、先に開いていた都市の分も含む。取得できないメモリ・CPUの値は「—」で表示する。
- シミュレーションの近似: 商品の購入候補数、就職・転職の候補数、転居先の候補数、定期的な判断の間隔、似た市民・世帯の集約を表示する。
    - 全項目が Coming soon の表示専用で、数値は未定のプレースホルダー、集約はオフの表示とする。各項目はラベルと操作部品だけで構成し、説明文を並べない。これらの値を保存したり、シミュレーションへ適用したりする処理はない。
    - 設定領域の全体を、項目がほとんど見えない濃さの暗い半透明の板で覆い、中央に節の名前と「Coming soon」を重ねる。板はスクロールしない枠に重ねるので、縦並びの狭い幅でも、設定行がスクロールしても領域全体を覆い続ける。
    - 節には「ゲームバランスに影響がある可能性があります。元に戻せません」と表示する。提供時の設計方針は、近似による影響が後続エポックへ残るため、有効化した近似の解除や近似度の引き下げを認めないこと。
    - この節の行は設定フォームの共通部品で描く。
- 公開UIの文言は全7言語で揃える。

## シナリオ管理と版情報

トップメニュー中央の「シナリオ管理」から `scenario_manager` を開く。Unityは起動しない。システムメニューの「シナリオとして保存」は `scenario_metadata` を作成モード(`params.extra.create`)で開き、自作カードの紹介情報ボタンは `params.extra.scenarioId` を渡して開く。どちらも既存の遅延ロード・ウィンドウレジストリ・共通フラット色トークンを使う。タブは `common/FlatTabs`、保存元と公式の札・必要パックの所有状況は `common/ScenarioSource`（`ScenarioOriginBadges`・`RequiredPacks`）、版情報は `SaveVersionInfo`（必要パックも表示する。セーブ一覧・ニューゲーム・シナリオ管理で共通）、サムネイルは `ScenarioThumbnail`、紹介文・初期の都市名・クエストの名前と説明の多言語入力は `LocalizedTextFields`(言語のタブで切り替え、英語が先頭で必須)に集約する。変更通知は `scenarios:changed`。タブ・カードのボタン構成は[シナリオ制作と配布](シナリオ制作と配布.md#シナリオ管理)を参照する。

UIのHTTP取得は、起動時にコアの版を照合してから行う。通常保存・シナリオ開始・編集開始のロード確認は `utils/saves.ts` を通す。版の規則とAPIは[シナリオ制作と配布](シナリオ制作と配布.md)と[バージョニングと互換性](バージョニングと互換性.md)を参照する。

## パス建設パネルの一覧内タブ

パス建設はカテゴリのタイル、バリアントのカード一覧、建設画面の3段で選ぶ。カード一覧は、カテゴリに分類がある場合だけアイコンタブで切り替える。鉄道は「線路」「旅客ホーム」「貨物ホーム」の3分類とし、LRT専用軌道と橋梁は線路に含める。単線・複線によるタブは設けない。他のカテゴリは全候補を1つの一覧で表示する。

タブボタンにはアイコンだけを置き、選択中の分類名をタブの下、カード一覧の上に見出しとして表示する。各ボタンには同じ名前のツールチップと読み上げラベルを付ける。タブは折り返さず、横幅が足りなければ横スクロールする。左右矢印・Home・Endでタブを選べる。

分類は `pathBuildCategories.buildCategoryVariantTabs` に集約し、カテゴリ別のビルダーを登録する。描画側の `PathConstructionPanel` は分類条件を持たず、各タブのID・翻訳キー・アイコン・候補一覧を受け取る。道路などに分類を追加する際も同じ描画を使える。タブ未登録のカテゴリでは従来の一覧を使い、空の分類は省略する。

鉄道のホーム有無は `path_master.platform_width > 0` で判定する。貨物ホームは `transit_master.freight` が真の路線の `stop_path_variants` に含まれ、旅客路線の停車候補には含まれないものとする。旅客・貨物兼用のホームと停車用途が未設定のホームは旅客側に表示し、分類にバリアントIDを列挙しない。

カテゴリを選び直すと先頭タブから始まり、建設画面から一覧へ戻ると選んでいたタブを保持する。チュートリアルで特定のバリアントが指定される場合は、そのカードを含むタブを自動表示する。資金不足の判定は各カードに適用し、タブの分類には影響させない。

共通部品 `FlatTabs` は従来の文字タブに加えて `iconOnly` によるアイコン専用表示を持つ。`idPrefix` を渡す場合、タブIDは `<prefix>-tab-<id>`、対応するパネルIDは `<prefix>-panel-<id>` とし、`aria-controls` と `aria-labelledby` で関連付ける。パス建設の分類アイコンは `PathVariantTabIcon` 内の自作SVGである。
