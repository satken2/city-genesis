# 診断ウィンドウ

## 概要

経済主体(施設・公共交通路線)に出ている不調(アラート・運休・車両不足)について、「直接の原因 → その原因 → さらにその原因」と因果の順にたどって説明するウィンドウ。アラートフラグ([[アラートフラグ管理]])や L1 通知([[通知レベル管理]])は「何が起きているか」を知らせるが、「なぜ起きているか」はプレイヤーが自力で推理する必要があった。診断ウィンドウはその推理をバックエンドが肩代わりし、木構造で提示する。

例(鉄道車両基地):

```
鉄道車両基地が原材料を調達できていません
  ↳ 高圧電流の不足(必要 10 に対して受け取り 0)
     ↳ この網には生産施設がありません(発電所は別の網)
        ↳ 生産施設側の網と接続されていません(タップ接続が必要)
```

## データフロー

```
バックエンド                                   Tauri
┌──────────────────────────┐   GET /api/v1/    ┌──────────────────────────┐
│ 診断サービス               │◄────────────────│ DiagnosisPanel            │
│ (エポック確定後の状態から  │  agents/{id}/    │  - 因果木を縦に表示        │
│  因果木をその場で構築)     │  diagnosis       │  - 対象施設/パスへのリンク  │
└──────────────────────────┘                  │  - 3Dビューでハイライト    │
                                               └──────────────────────────┘
```

- 診断はリクエストのたびに **エポック確定後の状態** から構築される。シミュレーションのフェーズは結果(受領量・アラートビット・パスの流量)しか記録しないため、診断サービスがそれらを突き合わせて因果を再構成する。将来の予測はせず、現状の説明に徹する。
- 文言はバックエンドで組み立てない。ノードは `type` と `params` だけを持ち、フロントエンドが i18n キー `diagnosis.nodes.<type>.title` / `.description` で文言化する(L1 通知と同じ方式)。

## 開き方

| 入口 | 条件 |
|---|---|
| 経済主体詳細パネル(`agent_detail`)のアラートカード | カードをクリックすると、その経済主体を対象に `diagnosis` ウィンドウが開く |
| 路線詳細パネル(`transit_detail`)の「原因を診断」ボタン | 運休中、または車両の調達数が必要数を下回っているときだけ表示される。対象は路線エージェント |

ウィンドウ種別は `diagnosis`(`entity_type=agent`、単一インスタンス/対象)。

## API: `GET /api/v1/agents/{agent_id}/diagnosis`

```json
{
  "agent_id": 123,
  "name": "第1車両基地",
  "epoch": 42,
  "roots": [ <node>, ... ]
}
```

`roots` は症状ごとの根ノードの配列で、空なら「現在報告すべき問題は無い」。

### ノード

| フィールド | 内容 |
|---|---|
| `type` | ノード種別(下表)。i18n キー `diagnosis.nodes.<type>` に対応する |
| `params` | 文言に埋め込む値。`product_id` / `product_name`(製品名。UI 側で `products` マスターの表示名に置き換える)、数量(`demand` / `received` / `supply` / `required` など)、件数(`count` / `producers` / `hubs` / `depots`)、距離(`distance`、m) |
| `targets` | このノードが指す対象の配列。`{"kind":"agent","id","name"}` / `{"kind":"path","id"}` / `{"kind":"node","id","position":[x,z]}` |
| `children` | 原因ノードの配列(このノードの「なぜ」) |

### ノード種別

根(症状)は経済主体のアラートビット、または路線の運休/車両不足から決まる。

| type | 意味 | 主な params / targets |
|---|---|---|
| `material_shortage` | 原材料不足(`ALERT_AGENT_MATERIAL_SHORTAGE`)。子に製品別の `material_unmet` | |
| `material_unmet` | 特定の原材料が不足。子にその原因(インフラ財なら網の診断、それ以外は市場の診断) | `product_id`, `demand`, `received`, `ratio` |
| `material_unmet_unknown` | ビットは立っているが不足した製品を特定できない(需要縮小直後など) | |
| `infra_disconnected` | インフラ網未接続(`ALERT_AGENT_INFRA_DISCONNECTED`)。原材料不足の枝で既に扱った製品は重複しない | `product_id` |
| `high_skill_shortage` / `labor_shortage` / `budget_capped` / `construction_shortage` | 対応するアラートビットの症状。`labor_shortage` は子に `labor_market_tight`(失業率が低く働き手がいない)か `labor_unfilled`(求職者はいるが集まらない)を持つ | `quota`, `total_labor`, `unemployment_rate` |
| `line_paused_<reason>` | 路線の運休理由(`route_disconnected` / `return_leg_blocked` / `no_underlay` / `train_too_long`。[[6_公共交通機関]]) | |
| `line_vehicle_shortage` | 路線の車両調達不足。子に車両基地側の診断 | `required`, `received` |

インフラ財(高圧電流・高圧水道)が届かない原因([[26_インフラ網]]の配送規則に対応):

| type | 意味 | 主な params / targets |
|---|---|---|
| `infra_terminal_unconnected` | 接続端子にパスが1本も無い | node(端子) |
| `infra_link_not_active` | 端子に繋がるパスが建設中/未着工 | paths |
| `infra_link_incompatible` | 端子に繋がるパスがその財を流せない種類(非電化線路の引き込みなど) | paths, node |
| `infra_no_producer` | 都市にその財の生産施設が無い | |
| `infra_producers_inactive` | 生産施設はあるが全て非稼働。子に各施設の状態 | `count` |
| `infra_producers_unconnected` | 生産施設は稼働中だが全て網に未接続。子に各施設の端子側診断 | `count` |
| `infra_network_split` | 端子の網と生産施設の網が別の連結成分。子に `infra_gap_detected`(両網の端点が近接。途切れ箇所)/ `infra_link_under_construction`(網をつなぐパスが建設中)/ `infra_tap_missing`(タップ未接続)のいずれか | `producers`, `distance`, nodes |
| `infra_generation_shortage` | 同じ網の生産量合計が需要合計を下回る。子に不調の生産施設(`producer_ref` → その施設の診断) | `supply`, `demand`, `producers` |
| `infra_transmission_bottleneck` | 網の容量が飽和(流量 ≒ 容量のパスがある) | `count`, paths |
| `infra_unexplained` | 生産量・接続とも足りている(一時的な不足の可能性) | |

商品市場を通る財が届かない原因(構造的な要因だけを判定する):

| type | 意味 | 主な params |
|---|---|---|
| `market_no_supplier` | 稼働中の国内生産者も輸入拠点も無い。子に非稼働の生産者の状態 | `product_id` |
| `market_supply_insufficient` | 都市全体の供給が注文量を下回る。子に不調の生産者 | `supply`, `demand`, `producers`, `hubs` |
| `market_unmatched` | 都市全体では足りているがこの施設には届かなかった(距離・価格・供給範囲の可能性) | 同上 |

公共交通の車両が届かない原因(走行網の連結成分による配分。[[6_公共交通機関]]):

| type | 意味 | 主な params / targets |
|---|---|---|
| `line_off_network` | 路線の下地経路が走行網に乗っていない | |
| `transit_no_depot` / `transit_depots_inactive` | 車両基地が無い / 全て非稼働 | `count` |
| `transit_depots_unconnected` | 基地が走行網に未接続(鉄道は引き込み線の溶接が必要) | `count`, `is_rail`, agents |
| `transit_depot_other_network` | 基地は別の走行網の成分にある | `count`, agents |
| `transit_vehicle_insufficient` | 同じ成分の基地の供給が路線群の必要数を下回る。子に不調の基地 | `supply`, `demand`, `depots` |
| `transit_unexplained` | 供給・接続とも足りている | |

共通の補助ノード:

| type | 意味 |
|---|---|
| `producer_ref` | 供給元施設への参照。`targets` にその施設、`children` にその施設自身の診断結果 |
| `facility_inactive` | 施設が稼働していない(建設中・停止中・倒壊など)。`params.status` / `status_reason` |
| `no_alert` | 掘り下げた先の施設自身には症状が無い |
| `cycle` | 原因が循環している(既に上位で診断中の施設) |
| `depth_limit` | 再帰の深さ上限で打ち切った |

## フロントエンドの挙動

- `DiagnosisPanel` は木を深さごとに字下げして縦に並べる。根は警告色、深い階層ほど落ち着いた色にする。
- `targets` の施設は経済主体詳細ウィンドウ、パスはパス詳細ウィンドウを開くリンクになる。ノードは座標のチップとして表示する。
- 木に現れたパスと施設は `world:highlight_objects`(発信元 `diagnosis`)で3Dビュー上にハイライトされ、ウィンドウを閉じると Rust 側が `world:clear_highlights` を送って消す(ウィンドウは非表示になるだけで React のアンマウント処理が走らないため)。
- 「再診断」ボタンで再取得できる。対処後は次のエポックを実行しないと結果が変わらない旨を注記として表示する。
