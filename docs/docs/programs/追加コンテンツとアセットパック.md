# 追加コンテンツとアセットパック

## 概要と目的

Steam で配布するベース内容は「最小限のモデル」に留め、建物・道路の見た目を **後から追加できる**
仕組みを用意する。ねらいは3つ。

1. **最小配布**：各建物バリアント／建物タイプ、および各道路バリアントにつき、ベースにはモデルを1つだけ同梱する。
2. **DLC / Mod による追加**：公式アセットパック（DLC）やユーザー製 Mod を後から重ねられる。
3. **言語別ラインナップ**：セーブデータ単位の設定言語に応じて、生成される建物・道路モデルのラインナップを入れ替える。
   例：日本風建物アセットパックDLCを入れると、日本語セーブでは日本風の建物が生成される。「日本風道路」も同様。

本ドキュメントは、これを実現する **コンテンツパック方式** のアーキテクチャを定義する。
建物メッシュの組み立て・アセットのパス体系は [[F_建物メッシュの生成]]、ファイル配置とデータ管理責任は
[[ファイル配置]] を前提とする。

> **アセット形式の方針**：**base と公式DLC は FBX**（Editor でビルド時にパッケージ化）、**ユーザー Mod は glTF/glb**（実行時ロード）を用いる。パック種別でロード経路が異なるため、これを後述の「§ アセット形式とロード経路」で定義する。マテリアルの共有・重複対策とBlenderからのエクスポートは [[P_マテリアル共有とエクスポート]] を参照。

---

## 用語

| 用語 | 意味 |
|---|---|
| **コンテンツパック（パック）** | モデルアセット群＋マニフェストをまとめた配布単位。base / DLC / Mod の3種。 |
| **エントリ** | パック内の1つのモデル貢献。対象（target）・閾値（threshold）・言語（locale）・物理ディレクトリを持つ。 |
| **locale** | エントリが対象とする言語（`ja` / `en` / …）。全言語共通は `neutral`。 |
| **target** | エントリが差し替える対象の prefix。建物 `b{bd_type}` / `a{variant}`、道路 `p{path_variant}`。 |
| **threshold** | 外観バリアント閾値（`0`,`250`,…）。[[F_建物メッシュの生成]] §4 の閾値フォルダに相当するが、本方式ではメタデータとして持つ。 |
| **論理パス** | メッシュ生成器が要求するリソースパス（例 `Models/Buildings/b16/500/base-w1`）。物理配置とは独立。 |

> base / 公式DLC は FBX ベース（Editor でパッケージ化。実行時は base=`Resources.Load`、DLC=AssetBundle/Addressables）、ユーザー Mod は glTF/glb ベース（`persistentDataPath` から実行時ロード）。詳細は次節「アセット形式とロード経路」。

## アセット形式とロード経路

コンテンツパックは配布元によって最適なアセット形式が異なる。**base と公式DLC は FBX、ユーザー Mod は glTF/glb** を用いる。この差は「実行時（ビルド済み Player）に外部ファイルを読めるか」という Unity の制約に由来する。

| パック種別 | アセット形式 | パッケージ化 | 実行時ロード経路 | マテリアル共有 |
|---|---|---|---|---|
| **base** | FBX → prefab | Editor（本体に同梱ビルド） | `Resources.Load` | Editor インポート時に名前で共有（`materialSearch: RecursiveUp`）。詳細は [[P_マテリアル共有とエクスポート]] |
| **公式DLC** | FBX | Editor（AssetBundle / Addressables） | AssetBundle / Addressables ロード | Editor インポート時に共有。base のマテリアルも依存参照で共有可能 |
| **Mod** | glTF / glb | なし（ユーザーが生アセットを配置） | `GLTFUtility.Importer.LoadFromFile`（`persistentDataPath`） | 実行時生成のため名前ベース共有プールが必要（[[P_マテリアル共有とエクスポート]]） |

### なぜ形式が分かれるのか

- **Unity 純正の FBX インポーターは Editor 専用**。`UnityEditor.ModelImporter` / `AssetDatabase` と Autodesk FBX SDK ネイティブプラグインに依存し、ビルド済み Player には存在しない。したがって **ユーザーが後から置く Mod の生 FBX を実行時に読む手段が標準機能にはない** → Mod は実行時パーサー（`Siccity.GLTFUtility`）で読める glTF/glb に限定する。
- **公式DLC は開発側が Editor でビルドする**ため FBX を使える。FBX を Editor でインポートし、**AssetBundle または Addressables** に焼き込んで配布、実行時はバンドルからロードする。Editor 経由なので後述のマテリアル共有（同名 `.mat` への集約、base 側マテリアルの依存参照）がそのまま効き、**DLC で何十棟追加してもマテリアル・テクスチャが重複しない**。
- **base** は現状どおり FBX を prefab 化して `Resources/Models/` に同梱する。

### なぜ DLC を Mod と同じ glTF にしないのか

glTF/glb を実行時ロードすると、`GLTFUtility` はファイルごとに `Material` / `Texture2D` を新規生成し、`ModelManager` のキャッシュも**ファイル単位**（マテリアル名単位ではない）である。名前ベースの共有プールを別途通さない限り、同じ見た目のマテリアルでもパック内のファイル数だけ重複する。公式DLCは大量の建物を含みうるため、**Editor でマテリアルを正しく共有できる FBX + バンドル方式**を採る。Mod は実行時ロードが必須で glTF を避けられないため、共有プール（[[P_マテリアル共有とエクスポート]]）で重複を抑える。

## パックの配置

[[ファイル配置]] の「組み込み＋ユーザー追加を自動マージ」（テンプレート／マップの前例）を踏襲する。

| パック種別 | 配置 | 形式 | 削除可否 |
|---|---|---|---|
| **base**（同梱・最小） | `<インストール先>/content_packs/base/`（移行期は現状の `Resources/Models/` も併用） | FBX（prefab / Resources） | 不可（`assets/`・`city/template/` と同格） |
| **DLC**（同梱・追加） | `<インストール先>/content_packs/{pack_id}/` | FBX（AssetBundle / Addressables に焼き込み） | 不可（インストール管理） |
| **Mod**（ユーザー追加） | AppData `UrbanGenesis/content_packs/{pack_id}/` | glTF / glb（生アセット） | 可 |

AppData のベースパスは [[ファイル配置]] のプラットフォーム別定義に従う
（Windows `%LOCALAPPDATA%\UrbanGenesis\`、macOS `~/Library/Application Support/UrbanGenesis/`、
Linux/Steam Deck `$XDG_DATA_HOME/UrbanGenesis/`）。

> **移行期の注記**：既存の `Resources/Models/...`（threshold フォルダ）資産は、base パックが整備されるまで
> 最下層フォールバックとして併用してよい（後述 §「解決順」の第4層 `Resources.Load`）。

## マニフェスト仕様

**設計判断：threshold はメタデータ、フォルダ名は id/uuid。**
閾値をフォルダ名に埋め込まない。閾値は意味情報なのでマニフェスト側に持たせ、物理フォルダ名は安定した
`id`/`uuid` にする。これにより再編や多対応（1フォルダを複数 threshold/target に割当）が容易になり、
マジックナンバー的なフォルダ名を排除できる。

各パックのルートに `manifest.yaml` を置き、以下を宣言する。

| フィールド | 説明 |
|---|---|
| `pack_id` | パックの一意 ID |
| `display_name` | UI 表示名 |
| `version` | パックのバージョン |
| `type` | `base` / `dlc` / `mod` |
| `entries[]` | モデル貢献の一覧（下記） |

エントリのフィールド：

| フィールド | 説明 |
|---|---|
| `target` | 対象 prefix（建物 `b{bd_type}` / `a{variant}`、道路 `p{path_variant}`） |
| `threshold` | 外観バリアント閾値（`0`,`250`,…）。**フォルダ名ではなくここで宣言** |
| `locale` | `ja` / `en` / … / `neutral`（全言語共通）。**エントリ単位で言語割当** |
| `dir` | 物理アセット参照。**Mod（glTF）**: `base-w1.glb` 等の part ファイル群を含むディレクトリ名（id/uuid）。**公式DLC（FBX）**: AssetBundle 名／Addressables アドレスのプレフィックス（part は `base-w1` 等のアドレスで引く） |

part ファイルの命名（`base-w1`, `mid-c2`, `roofprop`, `ceil`, `floor`, `tile` 等）は
[[F_建物メッシュの生成]] §3 の partName 規約をそのまま使う（形式に依らず論理名は共通）。

配置例（Mod = glTF、生アセットをディレクトリに並べる）：

```
content_packs/jp_buildings/            # Mod パック
├── manifest.yaml
│     # entries:
│     #   - {target: b16, threshold: 500, locale: ja, dir: 7f3a-...}
│     #   - {target: p1,  threshold: 0,   locale: ja, dir: 91be-...}
├── 7f3a-.../            # フォルダ名は uuid。threshold はマニフェスト側
│   ├── base-w1.glb
│   ├── base-c1.glb
│   └── ...
└── 91be-.../            # 日本風道路 p1
    ├── body.glb
    └── ...
```

公式DLC（FBX）は Editor でビルドした AssetBundle / Addressables を配布する。マニフェストの `dir` はバンドル名／アドレスプレフィックスを指し、part は論理名（`base-w1` 等）をキーにバンドルからロードする。生の `.fbx` を配布フォルダにそのまま置くのではない点に注意（FBX は実行時に読めないため。§ アセット形式とロード経路）。

```
content_packs/jp_buildings_dlc/        # 公式DLC パック
├── manifest.yaml
│     # entries:
│     #   - {target: b16, threshold: 500, locale: ja, dir: jp_buildings}   # dir = バンドル名/アドレス接頭辞
├── jp_buildings.bundle               # AssetBundle（Addressables なら .bundle 群 + カタログ）
└── jp_buildings.bundle.manifest
```

> **Mod での個別建物追加**：Mod は1つのパックとして配布するが、言語割当は**エントリ単位**で行う。
> 追加する建物ごとに `locale` を選べるため、「この建物は日本語アセットに、あの建物は全言語共通に」といった
> 混在が可能。全言語で出したい建物は `locale: neutral` を指定する。

## ModelManager 解決層

**中心となる洞察**：アセットのパス体系（`Models/Buildings/{prefix}/{threshold}/{partName}`）と
メッシュ生成側（`BuildingMeshUtils` / 各 Generator）は **一切変更しない**。同じ論理パスに対して
「どの物理ファイルを返すか」を、`ModelManager` に追加する **パック解決層** がセーブ言語・有効パックに応じて選ぶ。
既存の閾値／位置フォールバック（[[F_建物メッシュの生成]] §4-5）はそのまま活き、変更範囲と破壊リスクが小さい。

### 解決順

`GetModel(resourcePath)` を、有効パック（`enabled` かつ現在セーブ言語にマッチ）を優先度順に探索するよう拡張する。

```
論理パス要求: Models/Buildings/b16/500/base-w1   （生成器からの要求。無変更）
        │
        ▼
 パック解決層（新規）
   ① Mod パック      （ユーザー、最優先）
   ② DLC パック
   ③ base パック
        │   各層の内部で locale マッチ：
        │     セーブ言語 == entry.locale を優先 → neutral → 次の層へ
        ▼
   ④ Resources.Load / persistentDataPath 直読み  （組み込みフォールバック、現行動作）
        │
        ▼
 見つかったファイル → 以降は既存の閾値/位置フォールバック（F §4-5）に接続
```

各層のローダーは**形式に応じて分岐**する：**① Mod** は `GLTFUtility` で glb を実行時ロード、**② DLC** は AssetBundle / Addressables からロード、**③ base / ④ フォールバック** は `Resources.Load`。論理パス（`Models/Buildings/b16/500/base-w1`）は全形式で共通であり、拡張子・バンドルアドレスへの写像は各ローダーが担う。解決層はどの形式でも同じ論理パス→ `GameObject` を返すため、生成器側（`BuildingMeshUtils` / 各 Generator）は無変更。

`SetActiveLanguage(lang)` の呼び出し、または有効パック集合の変更時に、キャッシュ
（`ModelManager._modelCache` / `_knownMissing`）を無効化する。

### 論理パス → uuid の解決（threshold のマニフェスト化）

生成器が要求する論理パス `Models/Buildings/b16/{threshold}/base-w1` は**そのまま**。
`BuildingMeshUtils.GetPart` / `ResolveVariantSuffix` / `HasPart` は無変更。

- パック層はこの論理パスを受け、マニフェストの `{target=b16, threshold=500}` から該当エントリの `dir`(uuid) を引き、
  `content_packs/{pack}/{uuid}/base-w1.glb` に解決する。
- 生成器の閾値プロービング（[[F_建物メッシュの生成]] §4.2、標準候補 `0,100,…,1000` を `mid-w1` の有無で走査）は、
  フォルダ存在チェックの代わりに **パック層のマニフェスト問い合わせ**（「その target に threshold=X のエントリがあるか」）で答える。
- 結果、物理フォルダ名は threshold を持たず、閾値選択ロジックは論理レベルで完全に維持される。

### 現在の実装は変えない

既存の `Resources/Models/Buildings/b16/500/...`（threshold フォルダ）と、`persistentDataPath/{論理パス}.glb` の
直読みは **最下層フォールバック（上図④）として現状維持**。uuid+マニフェスト方式はその上に乗る新レイヤであり、
既存アセット・既存コードパスには手を入れない。

## 言語の配線（責務の整理）

現状、言語は2箇所に分散している：UI・操作系の言語は Tauri 管理（[[ファイル配置]]）、
セーブのゲーム内言語は `gd3.language` / `saves_metadata.json` の `language`。本設計では次のように整理する。

- **モデルラインナップを駆動するのは「セーブの言語」**（`gd3.language` / `saves_metadata.language`）。
  これはゲームプレイ上の設定であり、UI表示言語（Tauri管理）とは**別概念**である。
- ゲームロード時・言語変更時に、Unity 側 `ModelManager.SetActiveLanguage(lang)` へセーブ言語を伝達する
  （既存の init/session 経路、または `MasterDataStore` 経由）。

これにより、「日本語セーブでは日本風建物が生成される」という挙動が、施設 display_name の翻訳
（[[F_建物メッシュの生成]] とは別系統の masterdata 翻訳プロファイル）と同じ「セーブ言語」に一元的に紐づく。

## 道路への適用

道路も同一機構で解決する。論理パス `Models/Paths/p{path_variant}/{partName}`（partName: `body`, `line`,
`sidewalk`, `tree`）を、建物と同じパック解決層・locale マッチに通す。エントリの `target` に `p{path_variant}` を
指定するだけで「日本風道路」パックが成立する。生成器（道路メッシュ生成、[[G_道路メッシュの生成]]）は無変更。

---

## パック有効/無効トグルUI

city-genesis/tauri の設定に **パック一覧の on/off トグル**のみを追加する。

- 永続化は **Tauri 設定**（UI・操作系はTauri管理、[[ファイル配置]] に整合）。
- 有効集合をバックエンド／Unity が参照し、解決層のパック探索対象を絞る。
- **確率（threshold）調整を含むフル管理パネルは本設計のスコープ外**（将来検討）。トグルのみに留める。

## 具体例トレース（検算）

`ja` セーブで、オフィス建物 `b16`（`visual_variant = 0.6`）をロードするケース：

1. 生成器が閾値を決定：`variant_number = floor(0.6 × 1000) = 600` → 候補 `0,250,500,750` のうち 600 以下で最大 → **500**。
   （[[F_建物メッシュの生成]] §4.2、`BuildingMeshUtils.ComputeVariantNumber` / `ResolveVariantSuffix` は無変更）
2. 生成器が論理パス `Models/Buildings/b16/500/base-w1` を `GetPart` 経由で要求。
3. パック解決層が探索：
   - **Mod → DLC → base** の順に、各層で `{target=b16, threshold=500}` かつ `locale=ja` のエントリを優先。
   - ヒットした層の形式でロード：**Mod** なら glb を `GLTFUtility` で、**DLC** なら AssetBundle / Addressables から、**base** なら `Resources.Load`。
   - 無ければ同層の `locale=neutral` を試す。
   - どのパックにも無ければ次層へ。最終的に `Resources.Load`（既存 `Resources/Models/Buildings/b16/500/base-w1`）にフォールバック。
4. 解決した glTF/prefab に対し、以降は既存の位置フォールバック（w3→w1、中層縮退、白い箱）が働く（[[F_建物メッシュの生成]] §5）。

日本風建物パックDLCが有効なら手順3で `locale=ja` エントリがヒットし、日本語セーブでのみ日本風モデルが選択される。
