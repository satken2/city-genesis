# 24. 達成クエスト

達成クエスト（quest / achievement）は、都市の発展に伴ってプレイヤーが目標を達成したかどうかを判定し、達成状況を管理する仕組みである。エポック実行の完了時に自動的に判定が行われ、新規に達成・失敗したクエストはフロントエンドに通知される。

## 24.1. クエストの設計思想

達成クエストは、プレイヤーに都市建設の方向性を示すガイドラインとして機能する。ゲーム開始時（シナリオテンプレート）には複数のクエストが設定されており、都市が発展するにつれて自然に達成されていく設計である。達成時にはファンファーレと紙吹雪と共にお祝いウィンドウが表示され、プレイヤーに達成感を与える。

クエストの判定条件はコードにハードコーディングされず、**パラメータの組み合わせだけ**で記述される。これにより、シナリオ作成者はテンプレート作成モードのエディタ（またはAPI）から、成長型・維持型・期限型・連鎖型・隠し型など多様なミッションを自由に定義できる。

## 24.2. クエストのデータモデル

各クエストは以下のプロパティを持つ。

| プロパティ | 型 | 説明 |
| --- | --- | --- |
| `id` | int | クエストの一意識別子 |
| `name` | string | クエストの表示名 |
| `description` | string | クエストの説明文 |
| `condition` | object | 判定条件の木（24.3節） |
| `latch` | bool | `true`: 永久達成型 / `false`: 再判定型（24.5節） |
| `notify` | string | 達成通知の方法。`"modal"`（お祝いウィンドウ）/ `"toast"`（通知ポップアップ）/ `"off"`（無通知） |
| `deadline_epoch` | int/null | 絶対エポック期限。このエポックを過ぎても未達成なら `failed` になる |
| `deadline_within` | int/null | 相対期限。`active` 化されたエポックからこのエポック数を過ぎても未達成なら `failed` になる |
| `prerequisites` | int[] | 先行クエストのIDリスト。全達成まで `locked` 状態で判定されない |
| `reward` | object/null | 達成報酬（24.6節）。例: `{"type": "grant_money", "amount": 100000}` |
| `category` | string | UI表示用の分類ラベル（例: "経済", "人口"） |
| `tier` | string | 演出強度。`"bronze"` / `"silver"` / `"gold"` |
| `hidden` | bool | `true`: 隠しクエスト。達成するまで名前・内容がUI上で「???」に伏せられる |
| `is_force_completable` | bool | `true`: API経由で強制的に完了可能（判定はスキップされる） / `false`: 自動判定型 |
| `status` | string | `"locked"` / `"active"` / `"completed"` / `"failed"`（24.7節） |

このほか、判定エンジンが使用する実行時状態（`activated_epoch` / `completed_epoch` / `achieved_values` / `reward_granted` / `metric_history` / `streak_counts`）がクエスト自身に保存され、セーブデータと共に永続化される。

クエストの生成は必ず `add_quest`（`POST /api/v1/quests`）を通り、そこで全フィールドのデフォルト補完と実行時状態の初期化が行われる。`notify` のデフォルトは永久達成型なら `modal`、再判定型なら `toast` である。

## 24.3. 判定条件の3層構造

判定条件 `condition` は「**メトリクス解決 × 時間派生 × 論理合成**」の3層で表現される。

```json
{
  "op": "all",
  "clauses": [
    {
      "metric": {"path": "population", "index": null, "agg": null},
      "mode": "value",
      "window": 1,
      "compare": ">=",
      "target": 10000,
      "target_metric": null
    },
    {
      "metric": {"path": "unemployment_rate"},
      "mode": "streak",
      "window": 5,
      "compare": "<",
      "target": 0.05
    }
  ]
}
```

### レイヤ1: メトリクス解決（metric）

`city` オブジェクトのどの数値を読むかを指定する。

| フィールド | 説明 |
| --- | --- |
| `path` | ドット区切りの属性/辞書パス。例: `"population"`, `"budgets.3"`（`city.budgets[3]`） |
| `index` | `path` の解決結果が辞書の場合のキー（商品IDなど）。ドット表記と等価な別記法 |
| `agg` | 辞書全体の集約方法。`"sum"` / `"mean"` / `"max"` / `"min"` / `"count"` |

辞書キーは int / str の揺れ（セーブのJSON化で文字列になる）を自動吸収する。`total_exports` のような `{"amount": x}` 形式の値は自動でスカラー化される。解決できないパスは判定不能（状態を変えない）として安全にスキップされる。

指標にできる値の例: `population`（人口）, `unemployment_rate`（失業率）, `gdp` / `real_gdp`, `city_score`（施政スコア）, `crime_count` / `fire_count` / `traffic_death_count`（治安・災害）, `household_tier_0_count`（世帯ティア）, `average_prices.<商品ID>`（物価）, `total_production` / `total_exports`（生産・貿易、`agg` で総量化可）, `budgets.<カテゴリID>`（予算配分）など。

### レイヤ2: 時間派生（mode）

そのメトリクスを「いつと比べて」評価するかを指定する。

| mode | 説明 | 例 |
| --- | --- | --- |
| `value` | 現在値そのまま（デフォルト） | 「人口10,000人に到達」 |
| `delta` | 前エポック値との差分 | 「1エポックで人口+500人」 |
| `delta_pct` | 前エポック値に対する変化率 | 「GDP前エポック比+10%」 |
| `moving_avg` | 直近 `window` エポックの移動平均 | 「物価の5エポック平均を目標内に」 |
| `streak` | 比較条件を連続で満たしたエポック数が `window` 以上 | 「失業率5%未満を5エポック連続維持」 |

時間派生に必要な履歴は、クエスト自身が条件節ごとに `metric_history`（`[epoch, value]` のリスト、最大120エポック）として保持する。cityのリングバッファに依存しないため、**任意のメトリクス**（辞書の集約値を含む）に対して時間派生を適用できる。履歴・連続カウントの更新はエポックが進んだ判定でのみ行われ、`GET /api/v1/quests` による再判定では二重カウントされない。

### レイヤ3: 論理合成（op）

複数の条件節を合成する。合成ノードは入れ子にできる。

| op | 説明 |
| --- | --- |
| `all` | 全ての子を満たしたとき成立（AND） |
| `any` | いずれかの子を満たしたとき成立（OR） |
| `not` | 子（1件）の否定 |

いずれかのメトリクスが解決不能で全体の真偽が確定できない場合、そのエポックの判定は状態を変えない（`all` は1つでも False が確定すれば False として確定する、といった短絡評価は行われる）。

### 比較の右辺: 定数 or 別メトリクス

各条件節の右辺は定数 `target` のほか、`target_metric`（metric と同形式）で**別のメトリクスの現在値**を指定できる。これにより「教育予算 ≥ 消防予算」のような相対比較のクエストが書ける。

## 24.4. 設定できるクエストの例

| ねらい | 設定 |
| --- | --- |
| 到達目標 | `population` ≥ 10000 |
| 成長スピード | `population` の `delta` ≥ 500（1エポックで+500人） |
| 経済の質 | `gdp` の `delta_pct` ≥ 0.1（GDP前期比+10%） |
| 安定運営 | `unemployment_rate` < 0.05 を `streak` window=5（5期連続） |
| 産業構成 | `total_production` の `index=<商品ID>` ≥ X |
| 貿易都市 | `total_exports` の `agg=sum` ≥ X |
| 安全都市 | `all[ crime_count < 10, fire_count < 5, traffic_death_count == 0 ]` |
| 財政の姿勢 | `budgets.2` ≥ `target_metric: budgets.4`（教育予算を消防予算以上に） |
| タイムアタック | `population` ≥ 5000 + `deadline_epoch: 100`（期限切れで failed） |
| クエスト連鎖 | `prerequisites: [先行ID]` で達成後に解放される段階的ミッション |
| 隠し実績 | `hidden: true`（達成して初めて内容が明かされる） |

## 24.5. 達成タイプ

クエストには2種類の達成タイプが存在し、`latch` フラグで区別される。

### 永久達成型（latch = true）

一度達成条件を満たして `status` が `"completed"` になると、その後どれだけ条件が悪化しても未達成に戻ることはない。例えば「人口100人に到達せよ」というクエストは、一度100人に到達した後に人口が減っても達成済みのままである。

### 再判定型（latch = false）

毎エポックの判定時に達成条件を満たしていれば `"completed"`、満たさなければ `"active"` に戻る。例えば「失業率5%未満を維持せよ」というクエストは、失業率が上昇すれば再び未達成に戻る。

達成時の通知方法は達成タイプとは独立に `notify` で指定する。再判定型は頻繁に達成・未達成が切り替わりうるため、通常は `"toast"`（ノンブロッキングな通知ポップアップ）か `"off"` を指定する。維持型の目標で達成の節目を祝いたい場合は、`streak` モードと組み合わせた永久達成型（「5エポック連続維持を達成」）にするのがよい。

## 24.6. 達成報酬（reward）

クエスト達成時に一度だけ発火する報酬を設定できる。強制完了（24.9節）による達成でも発火する。

| type | 説明 |
| --- | --- |
| `grant_money` | `amount` の交付金を市政府の現預金（reserves）へ注入する |

`grant_money` は量的緩和と同様のカウンターパートなき通貨創造であり、「都市外部（国など）からの交付金」という位置づけである。マネーサプライは増加する。

## 24.7. クエストのステートマシン

`status` は4状態を取る。

```
                     prerequisites 全達成
   [locked] ────────────────────────────▶ [active]
                                             │
                     条件を満たす             │      期限切れ(deadline)
        ┌────────────────────────────────────┼──────────────────────┐
        ▼                                    │                      ▼
   [completed]                               │                  [failed]
        │                                    │                  (以後不変)
        │ latch=false かつ 条件を下回る       │
        └────────────────────────────────────┘ (activeに戻る)
```

- `locked`: `prerequisites` の先行クエストが全て `completed` になるまでの待機状態。条件判定されず、UI上はロック表示になる。解放判定は条件判定より前の独立したパスで行われるため、先行クエストが達成された**次のエポック**に解放される（クエストの登録順に依存しない決定的な動作）。解放されたエポックはまだ条件判定されず、判定はさらに次のエポックから始まる。
- `active`: 判定対象。`deadline_epoch` / `deadline_within` を過ぎると `failed` になる。
- `completed`: 達成。永久達成型は不変。再判定型は条件を下回ると `active` に戻る。一度 `completed` になったクエストが期限切れで `failed` になることはない（永久達成型）。
- `failed`: 期限切れ。以後どの状態にも遷移しない。

## 24.8. 達成判定のタイミング

クエストの達成判定は以下の2つのタイミングで行われる。

### エポック実行完了時（自動）

`POST /api/v1/epochs` の実行完了後、シミュレーション内部で自動的に `check_quests_completion()` が呼ばれる。メトリクス履歴・連続達成カウントの更新はこのタイミングでのみ行われる。このエポックで新たに達成・失敗したクエストは、レスポンスの `completed_quests` / `failed_quests` フィールドに含まれてフロントエンドに返却される。

複数エポックを連続実行（`count > 1`）した場合、`completed_quests` / `failed_quests` は**全エポックの累積**（IDで重複排除）が返却される。途中のエポックで達成したクエストの通知が失われることはない。

### クエスト一覧取得時（手動）

`GET /api/v1/quests` を呼び出した際にも、内部的に `check_quests_completion()` が実行される。これにより、フロントエンドが任意のタイミングで最新の達成状態を取得できる。このパスではメトリクス履歴・連続カウントは更新されない（同一エポック内の再判定として扱われる）。

## 24.9. エポック実行レスポンスにおけるクエスト情報

`POST /api/v1/epochs` のレスポンスには `completed_quests`（新規達成）と `failed_quests`（期限切れ失敗）が含まれる。各要素は通知用ペイロードで、達成時の実測値・報酬・演出情報を持つ。

```json
{
  "completed_quests": [
    {
      "id": 1,
      "name": "人口10,000人到達",
      "description": "都市の人口が10,000人に到達する",
      "latch": true,
      "notify": "modal",
      "tier": "gold",
      "category": "人口",
      "hidden": false,
      "reward": {"type": "grant_money", "amount": 100000},
      "achieved_values": {
        "0": {"current": 10234, "target": 10000, "compare": ">="}
      },
      "completed_epoch": 42,
      "status": "completed"
    }
  ],
  "failed_quests": []
}
```

`achieved_values` は達成時点の各条件節の実測値（条件木内の位置をキーとする辞書）で、お祝いウィンドウが「実測値 10,234 / 目標 10,000」のような表示に使う。

## 24.10. フロントエンドの表示フロー

### エポック実行後の通知

1. **通知ポップアップ（toast）**: `notify="toast"` の達成クエストと、`failed_quests` の全件は、エポック実行完了直後にウィンドウを開かず通知ポップアップで軽く知らせる。
2. **エポック実行結果ウィンドウ（epoch_result）**: ヘッダ直下の**クエストストリップ**に、このエポックで達成したクエスト（tier色のチップ＝この後のお祝いの予告）、失敗したクエスト、および**達成間近**（進捗70%以上）のアクティブなクエストの進捗バーを表示する。達成間近の表示は次のエポックへの動機付けとして機能する。
3. **お祝いウィンドウ（quest_complete）**: 結果ウィンドウを閉じた後、`notify="modal"` の達成クエストがあれば開かれる。「結果で因果を確認してからお祝い」の連続演出である。ファンファーレ（tada.wav）と紙吹雪と共に、tier降順（gold→silver→bronze）に1件ずつページ送りで表示し、各ページには達成時の実測値と達成報酬を表示する。

### 達成目標ダッシュボード（achievements）

クエストカード一覧では、サーバ計算の進捗率 `progress`（`GET /api/v1/quests` が返す）と各条件節の現在値・目標値を表示する。`locked` はグレー+錠前、`failed` は赤系、`hidden` の未達成クエストは「???」で伏せられる。tierバッジ・カテゴリ・期限・報酬もカード上に表示される。

### クエスト編集パネル（quest_edit、テンプレート作成モード専用）

条件エディタは2モードを持つ。**フォームモード**では条件節のリストを all / any で合成する平坦な条件を編集でき、各節のメトリクス・時間派生・比較（定数 or 別メトリクス）を指定できる。**JSONモード**では条件木をそのままJSONで編集でき、`not` 演算子や入れ子の合成条件はこちらで記述する。条件以外にライフサイクル（永久達成/通知/期限/先行クエスト）・報酬・表示メタ（tier/カテゴリ/隠し）も編集できる。

## 24.11. API エンドポイント

| メソッド | パス | 説明 |
| --- | --- | --- |
| `GET` | `/api/v1/quests` | 全クエストを取得（達成判定後に `progress` / `clause_states` を付与） |
| `GET` | `/api/v1/quests/{quest_id}` | 特定のクエストを取得 |
| `POST` | `/api/v1/quests` | 新しいクエストを作成（テンプレートモードのみ） |
| `PATCH` | `/api/v1/quests/{quest_id}` | 既存のクエストを更新（テンプレートモードのみ。条件を変更すると履歴・連続カウントはリセットされる） |
| `DELETE` | `/api/v1/quests/{quest_id}` | クエストを削除（テンプレートモードのみ） |
| `PUT` | `/api/v1/quests/{quest_id}/complete` | 特定のクエストを強制的に完了（`is_force_completable = true` のみ。報酬も発火する） |
| `POST` | `/api/v1/quests/{quest_id}/complete` | 同上（POST/PUT両方対応） |

`GET /api/v1/quests` が各クエストに付与する表示用フィールド:

| フィールド | 説明 |
| --- | --- |
| `progress` | クエスト全体の進捗率 0..1（`all`=全節の最小、`any`=最大、`streak`=経過/window、達成済みは常に1.0） |
| `clause_states` | 各条件節の評価状態のリスト（現在値・目標値・比較演算子・mode・window・streakカウント・進捗率） |
