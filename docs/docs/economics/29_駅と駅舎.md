# 29. 駅と駅舎

駅舎パスと、その線に交差するプラットフォーム(駅パス)による「駅」の表現について。

## 29.1 概要

プラットフォームは駅パス([[6_公共交通機関]] 6.4)として表現され、経路探索・停留所の設置・建設ライフサイクルはすべてパスの仕組みで完結する。一方で、プレイヤーが「1つの駅」と認識する単位はパスと一致しない。通常の鉄道の複線の駅では上下線のホームが別々のパスであり、既存の駅を延長・分割すれば1つのホームが複数のパスに分かれる。

この乖離を埋めるのが**駅舎パス**である。駅は独立したエンティティではなく、**駅舎パスそのもの**として表現される。駅名は駅舎パスの名前(`name`)であり、駅舎パスを敷設することが駅を作ることに等しい。

| 概念 | 実体 | 持つもの |
| --- | --- | --- |
| ホーム(駅パス) | パス | 停留所ノード・編成長制約・建設/老朽化のライフサイクル([[6_公共交通機関]]) |
| 駅(駅舎) | 駅舎パス | 駅名(`name`)・ウェイポイント付き折れ線と、選択した終端の専有エリア(建屋) |

駅は経済主体ではなく、市場・会計には一切参加しない。

ロープウェイの乗降区間（[[30_人員搬送設備]]）は分岐もホームの束ねもないため、駅舎パスの対象外である（駅舎に所属しない）。

## 29.2 駅舎パス

駅舎はパスバリアントの1つ(パスマスターの type が駅舎種別=共有定数 `PATH_STATION_HOUSE` のバリアント)で、通常のパスと同じ操作(敷設・造り替え・撤去・名前変更)で扱う。形状は**ウェイポイント付きの折れ線**に限られる(曲線は不可)。

- **線**: 駅ごとの `passage_mode` により上空の連絡橋・地上通路・地下通路を選ぶ。地下通路は描画しない。線は道路・線路と物理的に干渉せず、交差してもノードや分割は発生しない。経路探索にも参加しない。
- **専有エリア(建屋、外側配置)**: `house_ends`で選択した終端に、バリアント別の寸法(`house_width`×`house_depth`)の矩形として置かれる。矩形は**終端から外側へ広がる**(内側の辺が終端の上に乗る)。線路と重なる場合は線路を避けてさらに線の外側方向へずれ、バリアント別の `house_offset` があればそのぶん横方向にもずれる(算出方法は[Q_駅舎パスのメッシュ生成](../geometries/Q_駅舎パスのメッシュ生成.md))。線が線路群を大きく越えて長く引かれていれば、建屋はそのぶん離れた位置に建ち、長い連絡橋が描画される(将来プラットフォームを増設するための余地になる)。
- **土地占有**: 地上を占有するのは選択した終端の専有エリアだけで、線(橋)の下には後からプラットフォームや道路を通せる。専有エリアは通常のパスと同じ着工フローで用地を確保し、区画作成・建物の直接配置の障害物になる。
- 駅舎パスは通常のパスと同じ建設ライフサイクル(計画→建設中→稼働)とコストを持つ。
- 駅名は敷設時に、都市の言語([セーブデータ一覧メタデータ](../programs/セーブデータ仕様.md#セーブデータ一覧メタデータsaves_metadatajson)の `language`)ごとのテンプレートで自動命名される。`{id}` には駅舎パスのID(再利用されないので駅名は重ならない)が入り、ja `駅{id}`・en `Station {id}`・es-419 `Estación {id}`・zh-Hans `车站{id}`・zh-Hant `車站{id}`・fr `Gare {id}`・ko `{id}번 역` となる。テンプレートの無い言語では日本語のものを使う。駅名は生成時点の言語で確定して駅舎パスの `name` として保存され、通常のパス名変更(`PATCH /api/v1/paths/{id}` の `name`)でいつでも変更できる。

## 29.3 プラットフォームの所属

プラットフォームがどの駅に属するかは、駅舎パスの敷設に応じて自動で管理される。

- **所属**: プラットフォームは、**駅舎パスの線(中心線)と交差していればその駅舎に所属する**。駅舎を先に作り、あとから橋の下にプラットフォームを敷いても所属する。
- **先勝ち**: 既にどこかの駅舎に所属しているプラットフォームは、後から作られた駅舎の線が交差しても奪われない。
- **駅舎の撤去**: 駅舎パスを撤去する(または駅舎以外のバリアントへ造り替える)と、所属していたプラットフォームは解放され、他の駅舎の線と交差していればそちらへ移る。
- プラットフォームを1本も持たない駅舎、およびどの駅舎にも所属しないプラットフォームは合法である。後者には「駅舎がありません」というアラートが立ち、プレイヤーが把握できる([[アラートフラグ管理]])。
- **分割への追従**: 交差点の発生などで所属プラットフォームが2本に分割されても、両方のパスは同じ駅舎に属したままになる。

## 29.4 データモデル

駅舎パスは通常のパスAPI(`GET /api/v1/paths/{id}` 等)で扱う。駅単位の集計は `GET /api/v1/paths/{id}/station-info` から取得する(駅舎パス以外のIDはエラー)。

| 対象 | プロパティ | 内容 |
| --- | --- | --- |
| パス | `house_path_id` | 所属する駅舎パスのID。どの駅舎にも所属していないプラットフォームはnull相当 |
| 駅舎パス | `house_ends` | 建屋の配置端。`both`=両端、`start`=A側のみ、`end`=B側のみ。省略した側は土地も占有しない |
| 駅舎パス | `passage_mode` | 通路の配置。`elevated`=上空（既定）、`ground`=地上、`underground`=地下（通路非描画）。全駅舎で選択できる |
| 駅舎パス | `name` | 駅名(自動命名され、通常のパス名変更で変更できる) |
| station-info | `house_path_id` | この駅舎パスのID |
| station-info | `footprints` | 選択した終端の専有エリア `[{end, center: [x, z], rotation, width, depth}]`(表示・デバッグ用。グラフィック側は同一アルゴリズムで自前計算する) |
| station-info | `paths` | 所属ホームの一覧(`path_id` / `path_variant` / `status` / `length` / `platform_side`) |
| station-info | `lines` | この駅に停留所を持つ路線の一覧(`line_agent_id` / `name` / `status`) |
| station-info | `ridership` | 駅単位の乗降統計(路線の乗車回数から求めた近似値) |

どのパスバリアントが駅パス(プラットフォーム)かは、パスマスターの `platform_width` が設定されているかどうかで決まる(プラットフォームの描画([N_線路メッシュの生成](../geometries/N_線路メッシュの生成.md) §7)と同じ条件)。LRTの走行網のバリアント(LRT付き街路・歩行者専用道路(LRT付き)・LRT専用軌道)は `platform_width` を持たないので駅パスにならない(設定すると、そのバリアントの道路・軌道がすべて駅パスとして扱われる)。LRT停留所のホームはグラフィックが停留所の位置に描く描画専用の設備で([[6_公共交通機関]]の「LRT停留所の3D表示」)、駅舎への所属・駅情報の対象外である。駅舎パスかどうかは、パスマスターの `type` が駅舎種別(共有定数 `PATH_STATION_HOUSE`)かどうかで決まる。

## 29.5 建屋の配置方式と操作

バリアントの `house_placement` は `outside`（通常）または `inside`（高架下）。通常型は建屋の内側辺が線路外縁に向き、線路との余白を確保して外側に建つ。高架下型は建屋の外側辺を線路外縁に合わせ、奥行き全体を線路側へ収める。2003・2013はinside、その他はoutside。既存の `house_width`・`house_depth`・`house_offset` を共用する。

建設パネルでは「両端／A側のみ（始点）／B側のみ（終点）」を選択でき、Unityの敷設プレビューに即座に反映される。Aは最初に置いた端、Bは最後の端で、プレビューにもA/Bを表示する。配置方式はバリアントから決まるため、個別の切替は不要。

建屋の配置端は `TrackConstructionPanel` の建設時だけ選択・表示する（簡易モードの駅パッケージと詳細モードの駅舎タブ）。パス詳細や形状編集には表示しない。APIも着工後の配置端変更を拒否する。着工前に追加する建屋の用地は区画・地上パスとの干渉を検証する。片側を省略しても所属ホーム・駅名は変わらない。建設コストは従来のパス計算を維持し、建屋数による割引は設けない。

高架下型の配置は平面上の外縁合わせであり、高架幅より深い建屋や高さ不足の高架への収まりを保証しない。地上線路との重なりは着工を妨げる。高架・地下の線路は従来の接地判定に従って扱う。2003・2013で地上通路を選んだ場合は専用通路モデルを使う。他の組み合わせも共通通路モデルによって選択できる。建屋モデルが無い場合だけ仮箱で代替する。

## 29.6 通路の配置

通路方式は建屋バリアントと独立した駅舎パスの保存属性である。全駅舎で上空・地上・地下を選択でき、建設後もパス詳細の「駅」タブから変更できる。任意高さの指定は行わず、パスのY座標は通路方式に使わない。建屋は常に地面へ配置する。

方式変更は表示の切り替えであり、追加工事・費用・ホーム所属・経路探索・建屋の土地占有を変更しない。地上通路も線路等との物理干渉を検証しない。建屋に固定された階段や開口と通路が一致しない組み合わせを許容し、接続部の補修や自動生成は行わない。
