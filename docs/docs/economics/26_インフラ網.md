# 26. インフラ網

電力や水道などの都市インフラは、専用のネットワーク（インフラ網）を通じて供給される。
本章では、インフラ財という商品分類、インフラパス、そしてインフラ財の配送の仕組みを説明する。

## 26.1. インフラ財（GOODS_INFRASTRUCTURE）

商品分類のひとつに **インフラ財**（`GOODS_INFRASTRUCTURE`）がある（[[8_商品市場]]も参照）。
高圧電流や高圧水道のように、専用のインフラ網を通じてのみ授受できる中間財である。

インフラ財は他の商品と根本的に性質が異なる。

- **商品市場では取引されない。** 需給マッチングの対象外であり、
  輸出入・自家供給の対象にもならない。
- **金銭の授受を伴わない。** インフラ財の生産施設（発電所など）と消費施設（変電所など）は
  いずれも市政府所有の公共施設であり、インフラ財の移動は市政府内部での財の移動にすぎない。
  したがって価格の概念を持たず、公共サービスの価格統制（[[9_生産活動]]）の対象にもならない。
- **蓄えられない。** 調達済み量（`remain_amount`）はエポック開始時に
  リセットされ、エポックをまたいだ持ち越し（蓄電など）はできない。
  生産側の売れ残り在庫も次エポックには持ち越されない。
  消費施設が受け取った分を使い切れなかった場合でも、その使い残しが翌エポックの
  需要から差し引かれることはなく、消費施設は毎エポック必要量を満額で需要する。

> 類似する仕組みに、公共交通の車両財（`GOODS_TRANSIT`、[[6_公共交通機関]]）がある。
> こちらも商品市場では取引されず専用網（下地の走行網＝線路/街路）の到達性で配送されるが、
> インフラ財と異なり、(a) 走行網の流量キャパは考慮しない（繋がっていれば調達可能）、
> (b) リース料の金銭授受を伴う、(c) 配送は最大流ではなく連結成分ごとの等比縮小で行う。

### 電力供給の2段階構造

電力を例にとると、供給は次の2段階で行われる。

```mermaid
graph LR
発電所 -- 高圧電流(インフラ財) --> 送電線網 -- 高圧電流(インフラ財) --> 変電所 -- 電力(サービス財) --> 需要家
```

1. **発電所** は高圧電流（インフラ財）を生産する。
2. 高圧電流は **送電線**（インフラパス）のネットワークを通って **変電所** へ送られる。
3. **変電所** は高圧電流を原料として電力（サービス財 `GOODS_SERVICE`）を生産し、
   通常の商品市場を通じて世帯や施設へ供給する。

このため、発電所を建てただけでは都市に電力は行き渡らない。
送電線を引き、変電所を設置して初めて電力が供給される。
送電網が未整備・分断されている、あるいは容量が不足している場合、変電所は高圧電流を
十分に受け取れず、都市は電力不足（停電）に陥る。

## 26.2. インフラパス（PATH_INFRASTRUCTURE）

インフラ網を構成するパスの種類として `PATH_INFRASTRUCTURE` がある（[[3_道路網]]も参照）。
送電線・水道管などのバリアントがあり、バリアントごとに「流せる製品」と「流量容量」が
マスターデータで定義される。

| path_master のキー | 内容 |
| --- | --- |
| `infra_products` | このバリアントが流せるインフラ財の製品IDリスト（例: 送電線 → 高圧電流） |
| `infra_capacity` | パス1本あたりの1日あたり流量上限 |

インフラパスは道路とは以下の点で異なる。

- **経路探索・交通に参加しない。** 自動車・歩行者・列車は通行できず、
  交通量や渋滞、交通事故の対象にもならない。
- **他種のパスと自由に交差できる。** 道路や線路と交差してもノードは生成されず、
  パスも分割されない。**同じ網に属する**（`infra_products` に共通の製品を持つ）
  インフラパスどうしの交差ではノードが生成され、網の分岐点として機能する。
  別網どうし（送電線×導水管など）は道路との交差と同様に自由に立体交差でき、
  ノード生成も分割も起きない。
- **端点には専用のインフラノードが作られ、通常の道路ノードとは接続されない。**
  ノードの種類（`type`）は「そのノードが受け入れる接続種別の集合」を表す
  **ビットフラグ**であり、インフラパスの端点ノードは流せるインフラ財ごとのビット
  （電力・水道など製品ごとに固有のビット）を持つ。端点の溶接（既存ノードへの接続）は
  ノードのビットとパスのビットの積が非空の場合にのみ行われるため、送電線の端点が
  普通の街路ノード・導水管のノード・水道施設の接続端子に繋がることはない。
  例外として、**電化線路**（後述）のノードは道路・鉄道ビットに加えて電力ビットを
  持つため、送電線の端点を溶接できる。
- **端点は垂直に高さを変えて結合できる（垂直結合）。** 道路や線路がスロープで
  高さを変えるのに対し、インフラパスの端点溶接では x,z 座標が一致（スナップ閾値内）
  していれば **Y座標（相対高さ）のズレを無制限に許容する**。パス端点はユーザーが
  指定した高さを保持したままノードに結合され、ノードのY座標も変更されない。
  これにより、高さ20mの高圧送電線を地表高さの接続端子ノードへ直接
  引き込んだり、地中の導水管を垂直に立ち上げて地表の網に接続したりできる。
  高低差に応じた建設コストの逓増が経済的な制約として機能するため、垂直距離
  そのものに上限はない。
  なお、これは端点とノードの結合だけの特例であり、パス中間部どうしの交差は
  従来どおり「同じ高さで交差した場合」にのみ分岐ノードが生成される
  （高さが違えば同一網でも立体交差として素通りする）。
  例外として、**インフラパスの端点を同一網のインフラパスの中間へ落とす引き込み（タップ）では、
  高さ差が一定の許容範囲（数m）以内なら接続の意図とみなして分岐ノードが生成され、
  端点の高さはタップ先のパスの高さへ自動的に揃えられる**。地面に敷いた導水管どうしを
  つなぐ操作が僅かな高低差で不成立になるのを防ぐための挙動で、許容を超える高低差
  （深い地下幹線の上を横切る地表管など）は従来どおり立体交差として素通りする。
  タップ先が電化線路（後述）のような**インフラ財のキャリアを兼ねる交通パス**の場合は
  この許容範囲は適用されず、端点とノードの垂直結合と同様に**高さ差を問わず接続される**
  （送電線は高架前提のため、地上の線路との高さ差は必ず数mを超える）。端点の高さは
  敷設時の値のまま保持される。
- **建設の仕組みは他のパスと共通。** 建設サービス財を消費して建設が進行し、
  `STATUS_ACTIVE` になって初めてインフラ網の一部として機能する
  （ステータス遷移は[[3_道路網]]を参照）。

### 電化線路（インフラ財のキャリアを兼ねる交通パス）

`infra_products` / `infra_capacity` はインフラパス専用のキーではない。
**線路・駅パスのバリアントに電力の `infra_products` を設定すると、そのパスは
「電化線路」となり、鉄道であると同時に送電線としても機能する**。
電化線路は列車が走行する通常の線路であると同時に、インフラ財の配送ネットワーク
（§26.4）に容量付きのキャリアとして参加し、線路網そのものが送電網を兼ねる。

- **タップ接続**: プレイヤーが送電線の端点を電化線路のどこかへ引き込むと、
  電化線路が分割されて接続ノードが生まれ（既存の端点・交差点ノードへの溶接も可）、
  そこから送電網と線路網が電気的につながる。以降、発電所の電力は送電線→電化線路を
  通って沿線の消費施設（鉄道車両基地など）へ届く。
  タップできるのは同じインフラ財を流せる組み合わせだけで、導水管を電化線路に
  つなぐことはできない。また接続は端点の引き込みでのみ成立し、送電線が電化線路の
  中間を横切るだけでは（他のパスとの交差と同様）接続されない。
  送電線と電化線路の高さ差は問わない（§26.2）。ただし**駅パス（プラットフォーム区間）
  へのタップはできない**。タップは線路を分割するため、ホーム長（[[6_公共交通機関]]の
  編成長判定に使う）が分断されてしまうからで、駅の前後の本線へ引き込めば同じ網に届く。
- **電化しても線路としての挙動は変わらない。** 線路どうしの交差・分割・列車の走行・
  転回制約は非電化の線路と同一である。
- **電化改修**: 非電化線路から電化線路への造り替え（[[3_道路網]]のバリアント変更）が
  できる。
- 電化網を駅で寸断させないため、電化する場合は本線の線路バリアントと駅パス
  バリアントの両方に `infra_products` を設定する必要がある（マスターデータの制約）。
- 電化線路を流れた電力量はインフラパスと同様に `infra_flow` に記録され、
  インフラ網統計（§26.5）で流量・容量として観測できる。

## 26.3. 施設とインフラ網の接続（接続端子ノード / infra_node_id）

インフラ財の生産施設・消費施設（発電所・変電所など）を設置すると、その施設が立地する土地区画（parcel）の道路に面する辺（`facade_edge_index`）の反対側にあたる辺、すなわち **面している道路から最も遠い辺の中点** に、区画の基準標高（`altitude`）の高さで **接続端子ノード**（`type` = その施設が授受するインフラ財ごとのビットの和）が自動生成される。これにより、施設の前面道路側の美観を損ねることなく、裏手からインフラ配線を引き込むような配線形状が実現できる。区画情報や道路面データが取得できない特殊な場合は、安全なフォールバックとして施設の中央（center_point）に生成される。
このノードのIDは経済主体のプロパティ `infra_node_id` に永続的に記録される。施設とノードの紐付けは**経済主体→ノードの片方向参照**であり、ノードAPI（`GET /api/v1/nodes` 系）は所属施設の情報を公開しない。グラフィック（Unity）はbbox取得した経済主体の `infra_node_id` から接続端子ノードを逆引きして識別する。

- **端子位置の移動制限**: 端子ノードにまだインフラパスが1本も接続されていない場合に限り、ノードの位置（座標）を PATCH API 等で移動させることができる。ただし移動先は**施設が立地する土地区画の範囲内**（境界線上を含む。XZ平面で判定し、高さYは制限しない）に限られ、区画外への移動はバリデーションにより拒否される。端子は施設の敷地内にある設備であり、建物から離れた場所へ引き回すことはできない。また、パスが1本でも接続されると、網の接続関係（トポロジー）の破壊や幾何学的な不整合を防ぐため、ノード位置の変更はバリデーションにより拒否される。
- **接続施設との重なりの扱い**: 端子ノードが施設の区画内にあるため、端子へ引き込むインフラパスは施設の建物と重なり得る。インフラパス（および電化線路などインフラ財を流せるパス）と、そのインフラ財を需要／供給する施設の建物との重なりは正常な配線形状であり、干渉（`POST /api/v1/paths/interference` 等が返す `building_ids`）として扱われない。
- プレイヤーは**インフラパスの端点を接続端子ノードに接続する**ことで、
  施設をインフラ網に参加させる。端子ノードには複数のパスを接続でき、
  複数の発電所からの送電線を1つの変電所へ束ねるような冗長な網も作れる。
  敷設中のパスが吸着できるのは**同一網（網互換）の接続端子ノード**だけであり、
  別網の端子（送電線敷設中の水道施設の端子など）には吸着できない。
  端子への接続でも垂直結合（§26.2）が使えるため、高架の送電線や地中の導水管を
  端子の高さまでスロープさせる必要はなく、端点の x,z を端子に合わせるだけでよい。
- 端子ノードに接続できるのは、その施設が授受するインフラ財を流せるパスだけである。
  電力施設の端子には送電線しか接続できず、水道施設の端子には導水管しか接続できない。
- 端子ノードは施設が立地する土地区画の内側にあるため、端子へ引き込むインフラパスは
  市有区画（施設自身の区画を含む）の上を通ることになる。市政府が所有する土地区画は、
  パスが**地下または高架**で通過する場合に限り、区画や建物を残したまま敷設できる
  （[[3_道路網]]の「土地区画の扱い」を参照）。端点が端子ノードで地表に達する
  ごく短い接地区間は許容されるため、地下配線から端子への立ち上げが可能である。
- 端子ノードに当該インフラ財を流せる稼働中パスが1本も接続されていない施設は
  配送の対象外になる。発電所が網に繋がっていなければ発電しても送れず、
  変電所が繋がっていなければ受電できない（＝停電・断水）。
- 施設を撤去すると、端子ノードにパスが接続されていない場合はノードごと消える。
  パスが接続されている場合はノードは通常の分岐点として残り（`owner_agent_id` は
  クリアされる）、既設の網の形状は壊れない。

### 共用接続ノード（走行網とインフラ網の両方に接続する施設）

鉄道車両基地のように、**公共交通の走行網への接続端子**（`depot_node_id`、
[[6_公共交通機関]]）と**インフラ網への接続端子**（`infra_node_id`）の両方の資格を持つ
施設には、端子ノードが2つではなく**共用接続ノードが1つだけ**生成され、
`infra_node_id` と `depot_node_id` が同じノードを指す。共用ノードの `type` は
走行網ビット（道路・鉄道）とインフラ財ビット（電力など）の和であり、
**引き込み線路（電化線路）をこの1点へ溶接するだけで、施設は走行網（車両の配送）と
送電網（電力の受電）の両方へ同時に接続される**。非電化の線路で引き込んだ場合、
車両の配送は成立するが電力は届かず、未接続アラート（§26.5）が表示される。

## 26.4. インフラ財の配送

各エポックの商品市場マッチングの直後に、インフラ財の配送が実行される。
インフラ財の製品ごとに、その製品を流せるパスだけからなるネットワークを通じて、
生産施設から消費施設へ**流せるだけ流す**。

- 各パスの流量は `infra_capacity ×  エポック日数` を超えられない。
  並行して複数のパスを敷設すれば、その分だけ容量が合算される。
- 生産施設からは在庫量まで、消費施設へは需要量までしか流れない。
- 供給や網の容量が不足する場合、**どの消費施設がどれだけ受け取れるかは
  ネットワークの構造で決まる**。網の末端や細い経路の先にある施設ほど不足しやすい。
  ただし、需要が小さな施設（車両基地など）は供給不足時でも極力満たされるよう
  配分される（大口消費者が供給を独占して小口需要が停電する「飢餓」を防ぐ）。
  ネットワークの到達性・ボトルネック制約自体は変わらないため、構造的に届かない
  施設は依然として停電・断水になる。
- 各パスを実際に流れた量はパスのプロパティ `infra_flow` に記録され、
  送電網の利用状況として可視化に利用できる。値は符号付きで、
  正はパスの始点ノード → 終点ノードの向きに流れたことを表す。

## 26.5. インフラ網の観測（アラートと統計）

プレイヤーがインフラ網の状態を把握するための手段が2つ用意されている。

### 未接続アラート（ALERT_AGENT_INFRA_DISCONNECTED）

稼働中（`STATUS_ACTIVE`）のインフラ施設のうち、接続端子ノードに
「その施設が授受するインフラ財を流せる稼働中インフラパス」が1本も接続されていない
ものには、アラートビット `ALERT_AGENT_INFRA_DISCONNECTED` が立つ
（[[アラートフラグ管理]]参照）。建設中の施設は配線の猶予期間として警告対象にならない。
パスを接続すると翌エポックの再計算で自動的に消灯する。

- アラートは `GET /api/v1/alerts` 経由で観測できる。
- あわせて、経済主体は全財共通の**当エポック獲得量**（`received_amount`。
  例: 高圧電流 100 MWh）を持つ（[[8_商品市場]]参照）。インフラ財については配送時に
  記録された実受領値であり、調達済み量（`remain_amount`）とは異なり生産で消費されても
  減らない表示専用の値である。

### インフラ網統計（GET /api/v1/stats/infrastructure）

`GET /api/v1/stats/infrastructure` は、インフラ財の製品ごとに以下を返す。
網の利用状況の可視化（2Dマップ表示など）に利用できる。

| フィールド | 内容 |
| --- | --- |
| `producers` | 生産施設の一覧（位置・供給在庫・当エポック出荷量・接続状態） |
| `consumers` | 消費施設の一覧（位置・残需要・当エポック受領量・接続状態）。需要ゼロでも接続状態を見せるため全インフラ施設を含む |
| `paths` | その製品を流せるインフラパスの一覧（`[x, z]` 折れ線ジオメトリ・当エポック流量 `infra_flow`〔符号付き。正 = 折れ線の並び順 = 始点→終点の向きに流れた〕・エポックあたり容量 = `infra_capacity` × エポック日数）。建設中パスも含む |
| サマリー | 供給在庫合計・出荷合計・注文量合計・受領合計・充足率 |

## 26.6. 水道など他インフラへの拡張

この仕組みは電力専用ではない。マスターデータに以下を定義するだけで、
任意のインフラ財を同じ仕組みで配送できる。

1. インフラ財の製品（例: 高圧水道）を `products_master` に定義する。
2. それを流せるパスバリアント（例: 導水管）の `infra_products` に製品IDを追加する。
3. 生産施設（例: 浄水場）の `supply` と、消費施設（例: 配水所）の `materials` に
   その製品を設定する。
