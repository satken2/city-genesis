# 6. 公共交通機関

都市内の公共交通（路線バス・メトロ）の仕組みについて。

## 6.1 概要

公共交通は、自動車を保有しない世帯の移動手段を提供するインフラである。世帯の移動（通勤・通学・買い物）は徒歩または自動車の2つの交通モードで行われるが、公共交通の路線は**徒歩モードの経路の一部**として機能する。つまり「徒歩で停留所まで歩き、公共交通に乗り、降りて徒歩で目的地へ向かう」という一連の移動が、徒歩での移動の選択肢として自然に選ばれる。

ロープウェイのように車両・運行主体・運行間隔の概念を持たない設備は公共交通ではなく、人員搬送パスとして徒歩経路に直接組み込まれる（[[30_人員搬送設備]]）。

公共交通は以下の要素で構成される。

| 要素 | 実体 | 役割 |
| --- | --- | --- |
| 停留所 | ノード | 乗客が乗り降りできる地点。路線ネットワークと道路ネットワークの接点 |
| 路線区間 | 公共交通パス（`PATH_TRANSPORT`） | 停留所間を結ぶ運行区間 |
| 路線 | 経済主体（非建物） | 路線バスの系統やメトロの路線。車両を調達し、運賃を受け取る運営主体 |
| 駅 | パス（例: 地上鉄道駅・高架鉄道駅） | 停留所を設置できる特殊な線路パス。建物ではなく経路探索グラフの一部 |
| 車両基地 | 経済主体（建物） | 車両を路線に供給する公共施設。下地の走行網（線路/街路）に接続端子ノードで接続する |
| 車両 | 商品（公共交通の車両財 `GOODS_TRANSIT`） | 路線が車両基地から毎エポック調達するリース財。商品市場では取引されず、走行網の到達性に基づいて配送される |

路線の種別（バス路線・メトロ路線・LRT路線など）は**公共交通マスター**（`transit_master`）で定義される。各種別は以下を持つ。

| 項目 | 内容 |
| --- | --- |
| `transit_path_id` | その種別の路線区間として使う公共交通パスのバリアント（`path_master`）。路線種別のキーとなる |
| `stop_path_variants` | 停留所ノードを設置できる下地パスのバリアント一覧 |
| `route_path_variants` | 路線の車両が走行（経由）できる下地パスのバリアント一覧 |

公共交通マスターは `GET /api/v1/master/transit` で取得できる。路線種別の表示名・アイコン・説明・設置制約はここから解決する。

他のシミュレーション要素と同様に、プレイヤーはエポック開始前に路線の計画（路線の敷設、運賃・運行水準の設定、車両基地・駅の建設）を行い、シミュレーション実行によってその結果（乗客数、収支、混雑）が確定する。

## 6.2 路線ネットワークの表現

### ノードとパス

路線の形状は、通常の道路網と同じノード・パスの仕組み（[[3_道路網]]）で表現される。ノードが停留所、公共交通パス（`PATH_TRANSPORT`）が停留所間の運行区間である。公共交通パスは通常の道路網から独立したネットワークレイヤーを構成するが、以下の設置制約によって物理的な交通網の上に重なる。

- **停留所ノードは、路線種別の `stop_path_variants` に属する稼働中パスの上にのみ設置できる**（バス路線なら街路の各バリアント、鉄道系の路線なら駅パスなど）
- 路線の車両は、路線種別の `route_path_variants`（および `stop_path_variants`）に属するパスの上だけを走行できる

### 停留所ノードは路線ごとに独立

停留所ノードは、その路線の専有物であり、複数の路線が1つの停留所ノードを共有することはない。同じ場所に複数路線が停まる場合でも、路線ごとに別のノードが置かれる。これにより「乗車」「降車」「乗り継ぎ」がすべてネットワーク構造上で明確に区別される（乗り継ぎは必ず「降車 → 徒歩接続 → 別路線に乗車」という経路をたどる）。

### 住民の移動経路への統合

稼働中の公共交通路線は、住民の徒歩での移動経路の一部として利用される。プレイヤーが停留所と道路を明示的につなぐ必要はなく、住民は最寄りの歩行者が通行できる道路から停留所を利用する。

住民が公共交通を利用するかどうかの判断には、移動時間だけでなく以下のコストが加味される。

- **待ち時間**: 路線の運行間隔が長い（本数が少ない）ほど、乗車時の待ち時間コストが大きくなる
- **運賃**: 路線に設定された運賃が、時間換算のコストとして乗車時に加算される

このため、運賃が高すぎたり本数が少なすぎたりする路線は、たとえ線路がつながっていても住民の移動手段として選ばれなくなる。運賃・運行水準の設定は住民の行動に直接跳ね返る（詳細は6.7）。

### 下地の交通網に沿った物理経路（迂回と運休）

停留所間の路線区間（公共交通パス）は概念上のつながりを表すが、路線の車両は実際には**下地の交通網**（路線種別の `route_path_variants` に属するパス群。バスは街路、メトロは線路・駅パス）の上を走行する。各路線は「その車両が物理的にどの道路・線路を経由するか」を、**順序付きのパス列**として保持する（`route_path_ids`）。この経路はエポックごとに最新の交通網に基づいて更新される。

路線は**常に往復運行する**。そのため、往路（先頭停留所→末尾停留所）と復路（末尾→先頭）の両方が下地の交通網でつながる必要がある。このとき下地パスの**通行方向**（[[3_道路網]]の `travel_direction`。単線を2本並べた複線では各線路が互いに逆向きの一方通行になる）が尊重され、往路は順方向の線路を、復路は逆方向の線路を通る。

この物理経路により、次のゲーム挙動が成立する。

- **迂回**: 経路上の道路が倒壊・取り壊しされても、残った交通網で別の経路が見つかれば、路線は自動的にその経路へ迂回して運行を続ける。
- **運休**: 連続する停留所間が分断され、どの経路でもつながらなくなった場合、その路線は**運休**となる。運休は路線全体に及び、路線エージェントの `status` が `STATUS_PAUSED` になって路線全体が住民の移動経路として使われなくなる。分断された道路が再建されれば、次のエポックで運行が再開される。
- **片方向の下地では往復できず運休**: 往路は通れても**復路が下地の通行方向で塞がれている**場合（片方向の線路1本の上に敷いた場合など）、往復が成立しないため運休になる。往復させるには**複線化**（逆方向の線路を敷く）か、双方向の単線が必要である。逆方向の線路を敷けば、次のエポックで運行が再開される。

### 交差点での進行方向の連続性（線路の折り返し制約）

線路・モノレールのような**案内軌条系**の交通では、車両は交差点や合流点で自由に向きを変えられない。現実の鉄道がY字合流点で折り返せず、平面交差（ダイヤモンドクロッシング）でも直進しかできないのと同じ制約が、下地経路の探索に反映される。

具体的には、ノードで軌道系のパスから別の軌道系のパスへ乗り移れるかどうかを、**それぞれの線路がノードに接する向き（端点の接線）のなす角**で判定する。到着した線路の進行方向と、次に進む線路の発進方向のなす角（＝偏向角。まっすぐ通り抜ければ0°、その場で逆戻りすれば180°）が一定の閾値を超える遷移は「物理的に曲がれない」として経路に使われない。

この結果、次のようなプレイヤーの意図がそのまま挙動になる。

- なめらかにY字合流するように線路を敷けば、合流する2本のどちらからでも本線へ滑らかに入っていける。
- 逆に、Y字の分岐で「片方の線路からもう片方の線路へ折り返す」ような鋭角の転回はできない。そういう向きでしか繋がっていない停留所どうしを結ぶ路線は、経路が見つからず**運休**になる（下地の分断と同じ扱い）。
- 線路どうしが直角に平面交差する箇所では、直進は通れるが90°の転回はできない。

進行方向の連続性が問われるのは走行の途中だけである。**停留所（駅）では車両がいったん停止するため、そこでの折り返しは許容される**。終端駅で来た方向へ引き返す運行や、スイッチバックのある路線は問題なく成立する。

この制約は軌道系（線路・モノレール）どうしの接続にのみ働く。街路を走るバスやLRTは交差点で自由に曲がれるため、この判定の対象にならない。

この判定は3D表示にもそのまま反映される。線路の交差点では、**通行可能と判定される線路ペアの間にだけレールが敷かれて描画される**ため、ポイント（分岐器）やダイヤモンドクロッシングの見た目と、実際に列車が走れる方向が一致する（[N_線路メッシュの生成](../geometries/N_線路メッシュの生成.md)参照）。

## 6.3 路線と路線エージェント

### 路線の作成

プレイヤーが停留所と区間を描いて路線（バス系統・メトロ路線）を作成すると、その路線に対応する**路線エージェント**が1つ生成される。路線に属する公共交通パスは `line_agent_id` プロパティで路線エージェントに紐づく。

路線エージェントは建物を持たない経済主体（[[2_経済主体]]）であり、道路建設の需要を代理する建設代理エージェント（[[12_建物]]）と同様の「代理主体」である。公共施設として扱われ、その支出は市予算の公共交通カテゴリ（`LEDGER_TRANSPORT`）の管理下に置かれる（[[22_予算管理]]）。

各路線エージェントは、その運営組織（○○市交通局の一系統に相当する存在）の所在地として**市庁舎（市政府建物）への入居**が紐付けられている（[[12_建物]] 12.11）。これは中央銀行と同様に所在を示す台帳上の参照であり、市庁舎のフロア占有や家賃は発生しない。路線自身の地図上の位置（最寄り地区・起点停留所）は別途保持される。

### 路線エージェントの役割

| 役割 | 内容 |
| --- | --- |
| 車両の調達 | 毎エポック、目標運行水準に必要な車両数を商品市場で車両基地から調達する |
| 運賃の収受 | 路線を利用した世帯から運賃を受け取る |
| 収支の観測単位 | 路線ごとの乗客数・運賃収入・車両リース支出（＝路線別の黒字/赤字）が統計として記録される |

### 路線のライフサイクル

路線を構成する公共交通パス（`PATH_TRANSPORT`）は概念上の運行区間であり、道路や線路のような物理的な建設ライフサイクル（[[3_道路網]]の `STATUS_TEMPORARY` → 建設 → 老朽化 → 倒壊）はたどらない。区間パスは作成時に即 `STATUS_ACTIVE` となり（建設サービス財を消費しない）、以後そのステータスは `STATUS_ACTIVE`（運行中）か `STATUS_PAUSED`（運休）のいずれかだけを取る。運休は下地経路の分断によって路線単位で発生し、その路線の全区間パスと路線エージェントが揃って `STATUS_PAUSED` になる（6.2節）。経路が復旧すれば `STATUS_ACTIVE` に戻る。

一方、メトロ路線が走行する下地の線路・駅パスは通常のパスであり、建設サービス財を消費して [[3_道路網]] の通常ライフサイクルで建設・維持される（区間パスとは別物）。路線の全区間が削除されると路線エージェントも清算・削除される。

## 6.4 停留所と駅

### 停留所

停留所は目に見えないノードであり、建物ではなく、土地区画も占有しない。停留所ノードは路線種別の `stop_path_variants` に属する稼働中パスの上にのみ設置できる。バス路線であれば街路上のどこにでも停留所（バス停）を置けるが、鉄道系の路線は駅パスの上にしか停留所を置けない。

### 駅の表現

駅は**特殊なパス**（`path_master` の「鉄道PF」「電化鉄道PF」など。地上/高架/地下はノードの高さで決まる）として表現される。プレイヤーは線路を敷くのと同じ操作で駅パスを建設する。駅パスは建物ではなく交通網の一区間であり、通常の線路と同様に建設・老朽化・修繕・取り壊しのライフサイクル（[[3_道路網]]）に従う。

駅パスの幅（線路コリドー）は通常の線路と同じで、プラットフォームは駅パスの敷地を**片側（または両側）に広げる**形で表現される。どちら側に設けるかは駅パスのプロパティ `platform_side`（外側/内側/両側を表す共有定数 `PLATFORM_SIDE_*`）で建設時に指定し、以後変更できない。「内側/外側」は都市の通行方向（`traffic_hand`）を基準に左右へ解決される（左側通行では複線の相手線路が進行方向右側に来るため、内側=進行方向右）。複線（単線2本）の上下線とも内側を指定すれば線路間にホームが向き合う島式ホーム、外側なら相対式ホームになる。プラットフォームを含む駅らしい見た目は、グラフィック（Unity）側が駅パスのバリアントと `platform_side` に応じて動的に描画する（[N_線路メッシュの生成](../geometries/N_線路メッシュの生成.md) §7）。

鉄道系の路線種別は駅パスのバリアントを `stop_path_variants` に持つため、「駅を建設しないと停留所を置けない＝開業できない」という制約が設置制約として自然に成立する。駅パスが取り壊し・倒壊で失われれば、下地経路の分断として路線は運休（6.2節）になる。

なお、複数の駅パス（複線の上下線ホームなど）は、それらを跨ぐ駅舎パスの敷設によって1つの**駅**として束ねられ、駅名・駅単位の統計を持つ。詳細は[[29_駅と駅舎]]を参照。

## 6.5 車両と車両基地

### 車両のリースモデル

公共交通の車両（路線バス車両・メトロ車両）は、**公共交通の車両財**（`GOODS_TRANSIT`）の商品として表現される。世帯の自動車（[[10_消費活動]]）と同じく買い切りではなく**毎エポック更新されるリース契約**としてモデル化される。ただし車両は**商品市場（[[8_商品市場]]）では取引されない**。インフラ財（[[26_インフラ網]]）が専用のインフラ網を流れるのと同様に、車両は**下地の走行網（メトロは線路、バスは街路）の到達性に基づいて車両基地から路線へ配送される**。調達できた車両数がそのエポックにおける路線の運行能力となる。車両は整数単位でのみ調達できる。

このため、地区間の距離減衰やトラック輸送（輸送サービス需要）は発生しない。「工業原料をトラックで路線の場所まで運ぶ」という不自然さ（路線エージェントは物理的な場所を持たない）を避け、車両は走行網の上を回送されるものとして扱う。

### 車両基地と走行網への接続

車両の供給者は**車両基地**（バス車庫・鉄道車両基地）である。車両基地は一般施設（`TYPE_STANDARD`）の建物経済主体で、市政府が建設する公共施設である。労働力を雇用し、原料を消費して車両を生産する。つまり車両基地の生産能力（敷地規模・従業員数・原料調達）が、都市全体で運行できる車両数の上限を規定する。

車両基地は、インフラ施設と同様に**接続端子ノード**（[[26_インフラ網]]の接続端子ノードと同型）で下地の走行網に接続する。

- **鉄道車両基地**は、本線から車両基地の接続端子ノードへ**引き込み線（線路）を敷いて**走行網に接続する。線路で本線網につながっていない車両基地は、どの路線にも車両を供給できない（未接続の発電所と同じ）。これにより「鉄道車両基地は線路につながっていなければ機能しない」という物理制約が自然に成立する。
- **バス車庫**は街路が偏在するため、近傍の街路への接続が自動的に成立する。

### 鉄道の電力（電化線路による給電）

鉄道車両基地の原料は**インフラ財の電力**（変電所が売るサービス財の電力ではなく、
発電所が生産する高圧電流）である。電力は[[26_インフラ網]]の配送の仕組みで、
**電化線路**（電力を流せる線路・駅パス。[[26_インフラ網]]の「電化線路」参照）を通って
車両基地へ届く。

```mermaid
graph LR
発電所 -- 高圧電流/送電線 --> タップ点 -- 高圧電流/電化線路 --> 鉄道車両基地
```

- プレイヤーが送電線を電化線路のどこかへタップ接続すれば、その線路網全体が
  送電網の一部になり、沿線の車両基地が受電できる。
- 鉄道車両基地の接続端子は、走行網とインフラ網の**共用接続ノード**
  （[[26_インフラ網]]参照）である。電化線路の引き込み線を1本溶接するだけで、
  車両の配送（走行網）と電力の受電（送電網）の両方が同時に成立する。
- 発電容量や送電網が不足すると、車両基地は電力不足で車両を十分に生産できなくなり、
  その走行網の全路線が一律に減便される（6.6節の調達不足と同じ帰結）。停電が続けば
  車両が調達できず運休に至る。鉄道の消費電力は高圧側（発電所・送電網）の容量を
  一般家庭向けの変電所と奪い合うが、変電所が売るサービス財の電力を食いつぶすことはない。
- バス車庫は電力ではなくガソリン系の原料を商品市場から調達する（燃料経済との接続）。

このため、路線収支を管理する仮想的な存在である路線エージェントが電力を消費することはなく、鉄道の電力消費は物理的な位置を持つ車両基地と電化線路網で表現される。

### 到達性による配分と車両基地の配置

車両は、走行網の**連結成分**（互いに線路/街路でつながった範囲）を単位に配分される。ある車両基地は、その接続端子ノードと同じ連結成分にある路線にだけ車両を供給できる。1つの車両基地が供給する路線の必要車両数の合計が、その基地の生産能力を超える場合は、**各路線の必要車両数に比例して等比縮小**される（全路線が一律に減便される）。したがって、都市の各鉄道網・各方面に車両基地を適切に配置し、線路でつなぐことが、公共交通網を拡大する上でのプレイヤーの計画課題となる。

## 6.6 運行能力と混雑

### 編成・車両数から運行水準へ

プレイヤーは路線ごとに、目標運行間隔（運行水準）と**1編成あたりの車両数**（`cars_per_train`）を設定する。路線エージェントは、路線の長さと目標運行間隔から必要な**編成数**（`train_count`＝目標運行間隔を満たすのに必要な列車の本数。副次的に算出される派生値）を求め、`編成数 × 1編成の車両数` だけの車両を調達する。実際に調達できた車両数に応じて、そのエポックの実効的な運行間隔と輸送容量（1日に運べる乗客数）が決まる。

- 車両が計画通り調達できれば、目標運行間隔どおりの本数（編成数）が確保される
- 1編成の車両数を増やすほど、必要車両数と1編成の輸送容量（＝1編成の車両数 × 車両定員）が増える
- 調達が不足すると運行間隔が伸び（減便）、待ち時間コストの増加と輸送容量の低下を招く。1編成を組めるだけの車両（＝1編成の車両数）に満たない路線は**運休**となる

### 編成長とプラットフォーム

1編成の長さ（＝`1編成の車両数 × 1車両の長さ`。1車両の長さは路線種別ごとに公共交通マスターで定義される）が、停留所が設置されている下地パス（駅パス等のプラットフォーム）の長さを超える路線は**運行不可**になる。長い編成を走らせたい場合は、駅（プラットフォーム）を延伸するか、1編成の車両数を減らす必要がある。この判定は停留所の追加時・1編成の車両数の変更時、および毎エポックに行われ、条件が解消されれば自動的に運行へ復帰する。

### 混雑（満員電車）

路線の輸送容量は、公共交通パスのキャパシティとして設定される。乗客数がキャパシティに近づくと、道路の渋滞と同じ仕組みで通過所要時間が増加する。これは満員による乗降遅延や積み残しの不快を表現しており、混雑した路線は移動手段として選ばれにくくなる。混雑の解消には、運行水準の引き上げ（＝車両の増備）が必要である。

### 道路キャパシティの共用

公共交通の車両自体も物理的な交通網を占有する。

- **バス**: 運行便数分のバス車両が、路線直下の街路の自動車交通量に加算される。バスは一般の自動車と道路キャパシティを共用するため、渋滞した道路を走るバス路線は所要時間が伸び、逆にバスの高頻度運行は道路の混雑を悪化させる
- **メトロ**: 運行便数分の列車が、路線直下の線路の列車交通量に加算される

乗客がゼロでも運行便数分の負荷は発生する（空のバスも道路を使う）。

## 6.7 運賃と資金循環

### 運賃の設定と徴収

プレイヤーは路線ごとに運賃（乗車1回あたりの均一運賃）を設定できる。公共交通を利用した世帯は、乗車回数に応じた運賃を路線エージェントに支払う。乗り継ぎは新たな乗車として運賃が発生する。

### 運賃は住民の行動に反映される

徴収される運賃は、必ず住民の移動手段の選択に反映される。運賃は「移動時間の機会費用」と同じ物差し（都市の平均賃金による時間換算）でコスト化され、乗車時のコストとして扱われる。このため次のフィードバックが成立する。

- 運賃を上げる → 公共交通の実効コストが上がる → 徒歩や自動車に経路が流れ、利用者が減る → 運賃収入は必ずしも増えない
- 運賃が高い都市では、徒歩モード（公共交通込み）の所要コストが自動車より不利になり、自動車保有世帯（[[10_消費活動]]の自動車保有判定）が増える

つまり「利用実態と無関係に運賃だけを吊り上げて収入を得る」ことは構造的にできない。運賃0円に設定すれば、無料の公共交通として運営することもできる。

### 資金循環

すべての金銭移動はゼロサム資金循環の原則（[[7_金融システム]]）に従う。

```mermaid
graph LR
世帯 -->|運賃| 路線エージェント
路線エージェント -->|車両リース料| 車両基地
車両基地 -->|賃金| 市民
車両基地 -->|原料費| 電力・燃料等の供給者
市政府 <-->|会計統合| 路線エージェント
市政府 <-->|会計統合| 車両基地
```

路線エージェントと車両基地はともに公共施設であるため、その収支はエポック末の会計統合（[[22_予算管理]]）によって市政府に一元化される。運賃収入が車両リース支出を下回る路線の赤字は結果として市政府が負担し（補填）、黒字は市政府に上納される。プレイヤーが個別に補填操作を行う必要はない。

### 公共交通予算

市予算に公共交通カテゴリ（`LEDGER_TRANSPORT`）が追加される。路線エージェントの車両リース調達と車両基地の運営費（賃金・原料費）は、このカテゴリの予算残額の範囲内に制限される（[[22_予算管理]]の予算執行制御）。予算が不足すると車両調達が等比縮小され、都市全体で減便が発生する。

## 6.8 データモデル

外部（UI・グラフィック）から観測できる主なプロパティは以下の通り。

路線の一覧・詳細は API（`GET /api/v1/transit/lines` および `.../lines/{id}`）から取得する。主な項目は以下の通り。

| 対象 | プロパティ | 内容 |
| --- | --- | --- |
| 公共交通パス | `line_agent_id` | 所属する路線エージェントのID |
| 公共交通パス | `status` | 区間パスの稼働状態。所属路線の運休と連動し、`STATUS_ACTIVE`（運行中）か `STATUS_PAUSED`（運休）のいずれかのみを取る |
| 駅パス | `platform_side` | プラットフォームの設置側（`PLATFORM_SIDE_OUTSIDE`=外側 / `PLATFORM_SIDE_INSIDE`=内側 / `PLATFORM_SIDE_BOTH`=両側）。内側/外側は都市の通行方向（`traffic_hand`）基準で左右へ解決される。建設時に指定し、以後変更不可（6.4節） |
| 停留所ノード | `station_path_id` | 停留所が乗っている下地パス（路線種別の `stop_path_variants` に属するパス）のID。停留所以外のノードはnull相当 |
| 路線 | `status` | 路線の稼働状態。下地経路が分断されて運休中の路線は `STATUS_PAUSED` |
| 路線 | `route_path_ids` | 車両が走行する下地パスIDの順序列。停留所間を下地ネットワークの最短経路で結んだもの |
| 路線 | `path_variant` | 路線の種別のキー。区間パスのバリアント（＝`transit_master` の `transit_path_id`）。表示名・アイコン・説明・設置制約はこの値から `transit_master` を逆引きして解決する |
| 路線 | `fare_price` | 乗車1回あたりの運賃（プレイヤー設定） |
| 路線 | `target_headway` | プレイヤーが設定する目標運行間隔 |
| 路線 | `cars_per_train` | 1編成あたりの車両数（プレイヤー設定）。編成長・輸送容量・必要車両数に効く |
| 路線 | `train_count` | 編成数（＝目標運行間隔と路線長から算出される派生値）。運行に必要な列車の本数 |
| 路線 | `vehicle_count` | 当エポックに調達できた車両数（両数） |
| 路線 | 乗客数・収支・混雑率 | エポックごとの乗車回数（`ridership`）、運賃収入、車両リース支出、平均混雑率 |

なお路線の種別は「バス／メトロ」といった固定の区分ではなく、`transit_master` に定義された路線種別（バス路線・メトロ路線・LRT路線など）で表現される。停留所ノードは目に見えない通常のノードであり、駅建物への紐付けプロパティは持たない（駅はパスとして表現されるため）。駅舎パスで複数の駅パスを1つの駅として束ねる仕組みとそのデータモデルは[[29_駅と駅舎]]を参照。


## 6.10 車両の走行と共通の所要時間

バス・メトロ・中距離鉄道の車両は、調達した編成数に応じて実際の道路・線路に沿って往復し、停留所で停止する。描画時計は経済時計を進めず、計画中も都市の経済状態を変えずに動く。

路線は方向付きの停留所間経路と、加減速・カーブ・停車を含む走行時間を持つ。必要編成数、実効運行間隔、乗車時間と描画はこの時間を共用する。停車は各到着で1回とし、終端駅を往復で重複して2回停車させない。鉄道の停止位置は編成中心で、ホーム内に収まる位置へ寄せる。

詳細な時間の考え方は [交通シミュレーションと走行描画の整合](../geometries/T_交通シミュレーションと走行描画の整合.md)、描画は [車両の走行描画](../geometries/O_車両の走行描画.md) を参照する。
