    24. 達成クエスト

    達成クエスト（quest / achievement）は、都市の発展に伴ってプレイヤーが目標を達成したかどうかを判定し、達成状況を管理する仕組みである。エポック実行の完了時に自動的に判定が行われ、新規に達成・失敗したクエストはフロントエンドに通知される。

    24.1. クエストの設計思想

    達成クエストは、プレイヤーに都市建設の方向性を示すガイドラインとして機能する。ゲーム開始時（シナリオテンプレート）には複数のクエストが設定されており、都市が発展するにつれて自然に達成されていく設計である。達成時にはファンファーレと紙吹雪と共にお祝いウィンドウが表示され、プレイヤーに達成感を与える。

    クエストの判定条件はコードにハードコーディングされず、パラメータの組み合わせだけで記述される。これにより、シナリオ作成者はテンプレート作成モードのエディタ（またはAPI）から、成長型・維持型・期限型・連鎖型・隠し型など多様なミッションを自由に定義できる。

    24.2. クエストのデータモデル

    各クエストは以下のプロパティを持つ。

    プロパティ 型 説明
    id int クエストの一意識別子
    name object クエストの表示名。多言語テキスト（{言語コード: 文}。英語が必須）
    description object クエストの説明文。多言語テキスト（英語が必須）
    condition object 判定条件の木（24.3節）
    latch bool true: 永久達成型 / false: 再判定型（24.5節）
    notify string 達成通知の方法。"modal"（お祝いウィンドウ）/ "toast"（通知ポップアップ）/ "off"（無通知）
    deadline_epoch int/null 絶対エポック期限。このエポックを過ぎても未達成なら failed になる
    deadline_within int/null 相対期限。active 化されたエポックからこのエポック数を過ぎても未達成なら failed になる
    prerequisites int[] 先行クエストのIDリスト。全達成まで locked 状態で判定されない
    reward object/null 達成報酬（24.6節）。例: {"type": "grant_money", "amount": 100000}
    category string UI表示用の分類ラベル（例: "経済", "人口"）
    tier string 演出強度。"bronze" / "silver" / "gold"
    hidden bool true: 隠しクエスト。達成するまで名前・内容がUI上で「???」に伏せられる
    is_force_completable bool true: API経由で強制的に完了可能（判定はスキップされる） / false: 自動判定型
    status string "locked" / "active" / "completed" / "failed"（24.7節）

    このほか、判定エンジンが使用する実行時状態（activated_epoch / completed_epoch / achieved_values / reward_granted / metric_history / streak_counts）がクエスト自身に保存され、セーブデータと共に永続化される。

    クエストの生成時に、フィールドの既定値と実行時状態を初期化する。notify のデフォルトは永久達成型なら modal、再判定型なら toast である。

    name・description はシナリオの紹介文と同じ多言語テキストで、言語コードは ja・en・es-419・zh-Hans・zh-Hant・fr・ko。UI は表示言語の文を出し、無ければ英語の文を出す。そのため英語は必須で、英語の無い名前・説明はテンプレート作成モードでも作成・更新できない（ほかの項目の検査はテンプレート作成モードで省かれる）。チュートリアル完了クエストは全7言語の文を持つ。

    24.3. 判定条件の3層構造

    判定条件 condition は「メトリクス解決 × 時間派生 × 論理合成」の3層で表現される。

    {
  "op": "all",
  "clauses": [
    {
      "metric": {"path": "population", "index": null, "agg": null},
      "mode": "value",
      "window": 1,
      "compare": ">=",
      "target": 10000,
      "target_metric": null
    },
    {
      "metric": {"path": "unemployment_rate"},
      "mode": "streak",
      "window": 5,
      "compare": "<",
      "target": 0.05
    }
  ]
}

    レイヤ1: メトリクス解決（metric）

    city オブジェクトのどの数値を読むかを指定する。

    フィールド 説明
    path ドット区切りの属性/辞書パス。例: "population", "budgets.3"（city.budgets[3]）
    index path の解決結果が辞書の場合のキー（商品IDなど）。ドット表記と等価な別記法
    agg 辞書全体の集約方法。"sum" / "mean" / "max" / "min" / "count"

    辞書キーは int / str の揺れ（セーブのJSON化で文字列になる）を自動吸収する。total_exports のような {"amount": x} 形式の値は自動でスカラー化される。解決できないパスは判定不能（状態を変えない）として安全にスキップされる。

    指標にできる値の例: population（人口）, unemployment_rate（失業率）, gdp / real_gdp, city_score（施政スコア）/ city_score_per_household（1世帯あたり施政スコア）, crime_count / fire_count / traffic_death_count（治安・災害）, household_tier_0_count（世帯ティア）, average_prices.<商品ID>（物価）, total_production / total_exports（生産・貿易、agg で総量化可）, budgets.<カテゴリID>（予算配分）など。

    レイヤ2: 時間派生（mode）

    そのメトリクスを「いつと比べて」評価するかを指定する。

    mode 説明 例
    value 現在値そのまま（デフォルト） 「人口10,000人に到達」
    delta 前エポック値との差分 「1エポックで人口+500人」
    delta_pct 前エポック値に対する変化率 「GDP前エポック比+10%」
    moving_avg 直近 window エポックの移動平均 「物価の5エポック平均を目標内に」
    streak 比較条件を連続で満たしたエポック数が window 以上 「失業率5%未満を5エポック連続維持」

    時間派生に必要な履歴は、クエスト自身が条件節ごとに metric_history（[epoch, value] のリスト、最大120エポック）として保持する。cityのリングバッファに依存しないため、任意のメトリクス（辞書の集約値を含む）に対して時間派生を適用できる。履歴・連続カウントの更新はエポックが進んだ判定でのみ行われ、GET /api/v1/quests による再判定では二重カウントされない。

    レイヤ3: 論理合成（op）

    複数の条件節を合成する。合成ノードは入れ子にできる。

    op 説明
    all 全ての子を満たしたとき成立（AND）
    any いずれかの子を満たしたとき成立（OR）
    not 子（1件）の否定

    いずれかのメトリクスが解決不能で全体の真偽が確定できない場合、そのエポックの判定は状態を変えない（all は1つでも False が確定すれば False として確定する、といった短絡評価は行われる）。

    比較の右辺: 定数 or 別メトリクス

    各条件節の右辺は定数 target のほか、target_metric（metric と同形式）で別のメトリクスの現在値を指定できる。これにより「教育予算 ≥ 消防予算」のような相対比較のクエストが書ける。

    24.4. 設定できるクエストの例

    ねらい 設定
    到達目標 population ≥ 10000
    成長スピード population の delta ≥ 500（1エポックで+500人）
    経済の質 gdp の delta_pct ≥ 0.1（GDP前期比+10%）
    安定運営 unemployment_rate < 0.05 を streak window=5（5期連続）
    産業構成 total_production の index=<商品ID> ≥ X
    貿易都市 total_exports の agg=sum ≥ X
    安全都市 all[ crime_count < 10, fire_count < 5, traffic_death_count == 0 ]
    財政の姿勢 budgets.2 ≥ target_metric: budgets.4（教育予算を消防予算以上に）
    タイムアタック population ≥ 5000 + deadline_epoch: 100（期限切れで failed）
    クエスト連鎖 prerequisites: [先行ID] で達成後に解放される段階的ミッション
    隠し実績 hidden: true（達成して初めて内容が明かされる）

    24.5. 達成タイプ

    クエストには2種類の達成タイプが存在し、latch フラグで区別される。

    永久達成型（latch = true）

    一度達成条件を満たして status が "completed" になると、その後どれだけ条件が悪化しても未達成に戻ることはない。例えば「人口100人に到達せよ」というクエストは、一度100人に到達した後に人口が減っても達成済みのままである。

    再判定型（latch = false）

    毎エポックの判定時に達成条件を満たしていれば "completed"、満たさなければ "active" に戻る。例えば「失業率5%未満を維持せよ」というクエストは、失業率が上昇すれば再び未達成に戻る。

    達成時の通知方法は達成タイプとは独立に notify で指定する。再判定型は頻繁に達成・未達成が切り替わりうるため、通常は "toast"（ノンブロッキングな通知ポップアップ）か "off" を指定する。維持型の目標で達成の節目を祝いたい場合は、streak モードと組み合わせた永久達成型（「5エポック連続維持を達成」）にするのがよい。

    24.6. 達成報酬（reward）

    クエスト達成時に一度だけ発火する報酬を設定できる。強制完了（is_force_completable）による達成でも発火する。

    type 説明
    grant_money amount の交付金を市政府の現預金（reserves）へ注入する

    grant_money は量的緩和と同様のカウンターパートなき通貨創造であり、「都市外部（国など）からの交付金」という位置づけである。マネーサプライは増加する。

    24.7. クエストのステートマシン

    status は4状態を取る。

                         prerequisites 全達成
   [locked] ────────────────────────────▶ [active]
                                             │
                     条件を満たす             │      期限切れ(deadline)
        ┌────────────────────────────────────┼──────────────────────┐
        ▼                                    │                      ▼
   [completed]                               │                  [failed]
        │                                    │                  (以後不変)
        │ latch=false かつ 条件を下回る       │
        └────────────────────────────────────┘ (activeに戻る)
    • locked: prerequisites の先行クエストが全て completed になるまでの待機状態。条件判定されず、UI上はロック表示になる。解放判定は条件判定より前の独立したパスで行われるため、先行クエストが達成された次のエポックに解放される（クエストの登録順に依存しない決定的な動作）。解放されたエポックはまだ条件判定されず、判定はさらに次のエポックから始まる。
    • active: 判定対象。deadline_epoch / deadline_within を過ぎると failed になる。
    • completed: 達成。永久達成型は不変。再判定型は条件を下回ると active に戻る。一度 completed になったクエストが期限切れで failed になることはない（永久達成型）。
    • failed: 期限切れ。以後どの状態にも遷移しない。

    24.8. 達成判定のタイミング

    クエストの達成判定は以下の2つのタイミングで行われる。

    エポック実行完了時（自動）

    POST /api/v1/epochs の実行完了後、達成を自動判定する。メトリクス履歴・連続達成カウントの更新はこのタイミングでのみ行われる。このエポックで新たに達成・失敗したクエストは、レスポンスの completed_quests / failed_quests フィールドに含まれてフロントエンドに返却される。

    複数エポックを連続実行（count > 1）した場合、completed_quests / failed_quests は全エポックの累積（IDで重複排除）が返却される。途中のエポックで達成したクエストの通知が失われることはない。

    クエスト一覧取得時（手動）

    GET /api/v1/quests を呼び出した際にも、達成を再判定する。これにより、フロントエンドが任意のタイミングで最新の達成状態を取得できる。このパスではメトリクス履歴・連続カウントは更新されない（同一エポック内の再判定として扱われる）。

    24.9. シナリオのクリアとプレイヤーの記録

    シナリオとチュートリアルは、都市のクエストが1件以上あり、そのすべてが completed になった時点でクリアとなる。failed や未達成のクエストが1件でも残るとクリアにならず、クエストを持たない都市はクリアにならない。判定は、エポック実行完了時の自動判定（24.8節）と、強制完了（is_force_completable のクエストの complete）のどちらで達成した直後にも行う。神モードはシナリオを作る用途なので、クリアの対象にならない。

    都市は、始めたシナリオのIDとクリア済みかどうかを持つ（city.json の scenario_id・scenario_cleared。セーブ・ロードで都市と一緒に保存・復元される）。scenario_id はシナリオ一覧の id（<保存元>~<名前>）、チュートリアルは tutorial~<教材ID> で、シナリオ・チュートリアルから始めるとき（POST /api/v1/sessions）に記録する。scenario_cleared はそのときに未達成へ戻り、クリアすると立つ。一度立てたら、再判定型クエスト（24.5節）が後から active に戻っても下げない。

    クリアしたとき、そのIDはプレイヤーのプロフィールにも記録される。プロフィールは都市とは独立したプレイヤー単位のファイル profile.bin（saves/ と同じ親フォルダ。ファイル配置）で、どのセーブを開いていても共有され、セーブを消しても残る。ファイルは暗号化され、書き換えを検出する。GET /api/v1/profile は復号後の情報をJSONで返す。セーブのロード前でも呼べる。

    フィールド 説明
    version プロフィールの形式の版
    level プレイヤーのレベル。項目だけで、今は更新も使用もしない
    tutorials_cleared クリアしたチュートリアルの教材ID（POST /api/v1/sessions の tutorial_id と同じ値）のリスト
    scenarios_cleared クリアしたシナリオのID（シナリオ一覧の id）のリスト 
    {"version": 1, "level": 1, "tutorials_cleared": ["basic"], "scenarios_cleared": ["local~sample"]}

    同じIDは1度しか並ばない。ファイルが無い、壊れている、または書き換えられているときは、クリア記録のない初期値を返す。平文のJSONファイルはクリア記録として読み込まない。

    表示・通知とAPIの契約は達成目標ウィンドウを参照する。
