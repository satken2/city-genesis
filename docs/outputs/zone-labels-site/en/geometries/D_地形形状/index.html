    D. 地形形状

    地形データを管理する Terrain シングルトンと、3段階のLOD（Level of Detail）を持つ標高マップについて。

    D.1. 何のためのデータか

    地形形状は、都市ワールドの標高をグリッドデータ（ラスター）として保持し、3D描画のLODや道路・建物の工事による地形変更を支える。遠景は常に描画し、視点周辺は近景で描画する。超近景はさらに細かく、道路の盛土・切土などランタイムでの地形変更を反映する。

    D.2. Terrainシングルトン

    地形データは Terrain クラス（app/entities/terrain.py）のシングルトンで管理される。CityやGameData3と同じ __new__ パターンで、プログラム起動時に1つのインスタンスが作られる。

    D.2.1. 設定値

    プロパティ 意味
    map_height マップの高さ(m)
    map_width マップの幅(m)
    cell_size セル分割サイズ(m)
    far_map_spacing 遠景グリッド間隔(m)
    near_map_spacing 近景グリッド間隔(m)
    dynamic_map_spacing 超近景グリッド間隔(m)

    これらの値は標高ファイルを取り込んで都市（シナリオ）を作るとき（§D.14.1）に決まり、都市を作った後は変えられない（シナリオの地形APIもマップの寸法を変えない）。読み込み時に check_settings_integrity で整合性が検証される。具体的には、全ての値が正の整数であること、マップの縦横がセルサイズの整数倍であること、遠景間隔が近景間隔の整数倍であることなど。

    D.2.2. 計算で導かれる値

    設定値から以下が計算される: - cells_x = map_width / cell_size（横方向のセル数） - cells_y = map_height / cell_size（縦方向のセル数） - far_map_shape（遠景マップのピクセルサイズ） - near_map_shape（近景マップのピクセルサイズ） - dynamic_map_cell_shape（超近景マップ1セル分のピクセルサイズ）

    D.3. 標高データと描画LOD

    初期自然地形near_mapと編集済みセルが標高の正となる。共通サンプラーが全域に固定した格子で補間し、編集標高を反映する。far/near/dynamicは保存・互換APIの名前であり、カメラ距離で別の地面へ切り替える描画ティアではない。

    Unityは同じ標高から作った513格子のTerrainタイルを使用する。地形自身の画面上の細分化はUnity Terrainに任せ、建物・道路・プロップの描画LODは独立に選択する。詳細は E_LOD処理。

    D.3.1. 配列の向きと方位

    ワールド座標は東が+X、北が+Z、上が+Yで、原点はマップ中心である。標高配列(近景・遠景・超近景・背景とも)は行0がZ最小の南端、列0がX最小の西端で、行が増えるほど北へ、列が増えるほど東へ進む。したがって配列の[0, 0]は南西隅に当たる。この並びはUnityの俯瞰(北を上にしたとき+Zが画面上)・コンパス・カメラyaw(北=+Zを0とする時計回り)と一致する。

    外部の標高データ(画像やDEMは北→南の行順)は、取り込みツールが行を並べ替えてからこの向きで保存する。ゲーム内に行を反転する処理は持たないので、新しい取り込み経路を足すときも保存前に並べ替えること。

    都市マップと地形エディタの2D表示は画面のY軸が下向きなので、+Zが画面の上に来るように変換する。Canvas2Dで描く都市マップと地形エディタのベクター層・カーソル層はビュー変換のY倍率を負にし(文字だけはその描画でY反転を打ち消す)、地形エディタの地形層(WebGL2)は画素の画面座標からワールド座標を求めるときに同じ向きで換算する(地形エディタの2D表示参照)。サムネイルも北上の平面図で、標高格子の行順を反転して画素へ変換する。地形エディタの3Dプレビューはthree.js(右手系)で描くので、ワールド座標のままでは東西が鏡像になる。地形・水面をZ倍率-1のグループに入れて鏡像を打ち消す。

    D.4. セル

    セルは標高データの保存単位であり、Unityが地形タイルを作る単位でもある。ゲームルール上の意味は持たず、道路・建物・土地区画・資源はマップ全域のどこにでも置ける。

    セルサイズは設定から取得する。バックエンドは左下原点の非負セル番号、Unityはマップ中心原点のため負の番号もある。変換はTerrainManagerの変換APIを使う。

    編集用のfloat32配列はセル単位で持ち、そのセルの地形が実際に編集されるときにだけ生成される（無ければ共通サンプラーから作る）。新規都市は編集用配列を1つも持たずに始まり、描画は全域共通の /terrain/surface が担う。編集セルの共有辺・角の格子点は隣接セルへ同じ高さで反映する。

    D.5. 任意範囲の切り出し

    バックエンドの extract_region は指定セル領域をfloat32で組み立てる。Unity描画には /terrain/surface を使用する。保存用配列やnear_mapをクライアントが独自補間して接地標高を作らない。

    D.6. 標高マップの更新

    update_dynamic_map は入力を検証後、編集セルと共有格子点を持つ隣接セルへ反映し、版を増やす。変更したセルを保存対象にする。描画APIは版と標高を同じ読取ロック内で取得する。

    D.7. フロントエンドとの通信

    API 内容
    GET /terrain/settings マップ寸法・セルサイズ・標高範囲
    GET /terrain/surface cell_x、cell_z、resolutionで指定する現在標高。little-endian float32、行Z・列X(行0が南端。D.3.1)
    GET /terrain/cell-versions 版を持つセルとその3x3近傍の描画版。一覧に無いセルは版0として扱う
    GET /terrain/far 現在標高の全域overview。互換形式float16
    GET /terrain/near 初期地形の互換・編集用取得
    GET /terrain/reclaimed-lands 埋立地の一覧。保存値（範囲・版）と、現在の海岸線と地形から求めた派生値（天端の高さ・岸壁区間・壁・帯）を返す。応答の形は §D.17.3

    surfaceは X-Grid-Rows、X-Grid-Cols、X-Cell-Version を返す。Unityは完成前のデータを公開せず、全帯の適用後に置換して高さキャッシュを無効化する。

    D.8. セーブ・ロード

    初期地形（近景・遠景）、都市外の背景地形、編集セルを保存する。編集セルは初期標高と違う格子点だけを差分として保存し、値は float32 のまま持つ（編集精度を float16 へ落とさない）。ゲームは標高マップを同梱せず、地形はすべてセーブの中身から戻す。表示用タイル・UnityのLODキャッシュは保存せず再生成する。形式はセーブデータ仕様。

    海岸線・湖・川（city.terrains）と埋立地（§D.17）はセーブデータの city.json に入り、ロードではそのまま戻す。海岸線をロード時に地形から抽出し直すことはしない。埋立で広がった海岸線は初期地形からは再現できないため、保存した値が正である。埋立地の岸壁・帯・天端の高さは保存せず、ロード後も現在の海岸線と地形から求める。

    D.9. 初期化

    初期標高を読み込み、地形設定とnear/far配列を生成する。ロード・設定変更時は共通サンプラーの派生キャッシュを初期化する。

    標高ファイルを取り込んで新しい都市（シナリオ）を作るとき（§D.14.1）は、標高と設定値だけを作る。水面・川・資源・プロップ・カメラを持たずに始まり、地表種別と気候区分は既定値（草原・温暖湿潤）で始まる（§D.15.2・§D.16.2）。水面・川・カメラはシナリオの作者が地形エディタで作り、資源とプロップは神モードのセッションで置く（§D.14.2）。

    海岸線（陸地ポリゴン）を地形から抽出するのは、新規都市の作成時と、シナリオの地形APIで標高・水面・川を保存したとき（§D.14.3）だけである。その時点のnear_mapの標高0mを境に陸地を取り出し、湖・川の範囲を穴として差し引く（§D.10.3・§D.11.5）。ゲーム中の海岸線は、埋立の完了で範囲が足されて広がるだけである（§D.17.4）。道路の盛土・切土や陸地の整地で地形が変わっても、海岸線は変わらない。

    D.10. 水面（海面以外の湖など）

    標高0mの海面（ワールドY=0の板ポリゴン）とは別に、任意の場所に「水面ポリゴン」を配置できる。山上湖や貯水池のように、海面とは異なる標高（水位）を持つ平らな水面を3D上で表現するためのものである。

    D.10.1. データモデル

    水面は1枚ごとに以下のフィールドを持つ、GeoJSONライクなオブジェクトである。

    フィールド 意味
    id マップ内で一意な識別子
    water_level 水面のY標高(m)。heightmap と同じ絶対標高フレームで、海面が0。湖はそれぞれの水位を持つ
    kind 種別ラベル（任意。"lake"）
    polygon 水面の平面形状。{"type": "Polygon"｜"MultiPolygon", "coordinates": [...]}。座標はワールド座標（マップ中心が(0,0)）のXZ平面。穴（内周リング）も表現可能

    水面はシナリオの作者が地形エディタで描く静的データで、near_map から導出できない。都市の city.terrains["water_surfaces"] に入り、シナリオ・セーブデータ（city.json）に保存され、ロード時に復元される。取り込む標高ファイルは水面を持たないので、取り込んだばかりのシナリオには水面が無い（§D.14）。

    D.10.2. APIとレンダリング

    フロントエンド（Unity）は GET /api/v1/terrain/water で水面一覧を取得し、各ポリゴンを water_level のY標高に置いた水平メッシュとして描画する（WaterSurfaceManager）。マテリアルとシェーダーは海面板と同じもの（Custom/DepthOffsetLit、Offset -1,-1）を用いるため、湖底（per-cellタイル）とのZ-fightingは海面と同じ深度オフセット階層で回避される。岸（水面より高い地形）では地形がワールドYの差で自然に手前へ描画される。詳細は E_LOD処理 の「海面・水面の描画と深度オフセット」を参照。

    D.10.3. 海岸線への反映（穴あき形状）

    水面は海岸線ポリゴンから差し引かれて「穴」になり、陸地として扱われなくなる。穴の上に作られた土地区画は海上区画（PARCEL_WATER）になり、陸地を要求する通常の建物は建てられない（B_土地形状 B.5）。

    このとき穴になるのは、オーサリングされた polygon（footprint）そのものではなく、footprint の範囲内で地形標高が water_level を下回る領域だけである。footprint はあくまで「その水面が存在しうる範囲の上限」であり、その内側でも water_level より高い地形は陸地として残る（例えば水面の中に頭を出す小島や、水位より高い岸辺は陸地のまま）。これは、海面（water_level に相当する標高が0）が海岸線を形作るのと同じ考え方を、湖ごとの水位に対して適用したものである。したがって水位を上げれば水面（穴）は広がり、下げれば狭まる。

    海岸線のGeoJSONは穴（Polygonの内周リング）とMultiPolygonを表現でき、Unity側の陸地内外判定（CoastlineStore.IsLand）も全リングへのeven-odd判定で穴を尊重する。

    湖の上を通るパスは、海と同じく橋（路面が water_level + WATER_BRIDGE_MIN_CLEARANCE 以上）か完全埋設トンネルでなければならない（J_パスの交差処理 の「海・湖の横断」）。Unity は敷設中の判定のために水面の範囲と水位を WaterSurfaceStore に保持する。

    なお、川（次節）は水面（water_surfaces）には含めない。水面の契約は「単一の water_level を持つ水平面」であり、流下方向に水面標高が変化する川とは互換性が無いためである。

    D.11. 川（rivers）

    地形エディタ（city-genesis/tauri の「川編集」タブ）で自動生成・作図する河川。川床の彫り込み自体はシナリオの標高データ（near_map）へ直接焼き込まれるため、ランタイムから見た「地形の谷」は通常の標高と区別されない。この節で定義するのは、その上に存在する「川」の実体、すなわち範囲ポリゴンと水面標高のプロファイル線である。流路スプライン（幅・深さ）は彫り込みのためのエディタ内部の中間データであり、ゲーム側には渡さない。

    D.11.1. データモデル

    川は1本ごとに以下のフィールドを持つ。

    フィールド 意味
    id マップ内で一意な識別子
    kind 種別ラベル。常に "river"
    polygon 川の範囲。{"type": "Polygon"｜"MultiPolygon", "coordinates": [...]}。座標系は水面の polygon と同じ（ワールド座標XZ、マップ中心が(0,0)）。中州・島は穴（内周リング）になる
    profile 水面標高のプロファイル線 [[x, y, z], ...]（上流→下流）。y は海面=0 の絶対標高(m)で、流下方向に単調非増加

    範囲内の任意地点の水面標高は「profile 折れ線上の最近点の y（線分内は線形補間）」で決まる。 この規則は地形エディタ（riverGeometry.ts の RiverProfileSampler）・バックエンド（geo_rivers.py）・Unity（RiverStore）で共通の契約であり、水面メッシュの頂点標高、パスの横断判定の水面標高はすべてこれで求める。

    D.11.2. 永続化

    水面（§D.10.1）と同じく、都市の city.terrains["rivers"] に入り、シナリオ・セーブデータ（city.json）に保存される。地形エディタの作業コピーでは meta.json の rivers フィールドに保持され、「シナリオに保存」で一覧全体を置き換える（§D.14.3）。未彫り込みの川（制御点だけで標高へまだ焼き込んでいない川）は保存されない。

    D.11.3. 生成（地形エディタ）

    流路はハイトマップと降雨範囲から自動生成するか、制御点で指定する。幅・深さは流量と横断地形に応じて変化し、平坦な場所では蛇行や中州ができる。湖への流入で流路は分かれ、支流は本流へ合流する。

    未彫り込みの川は制御点を編集でき、地形へ焼き込むまでは標高を変えない。彫り込み済み・保存済みの川はノード編集の対象外である。幅に下限はないが、格子間隔より細い川の溝・水面は1格子ぶんの幅になる。

    生成と彫り込みは terrainRiver.ts、操作と作業コピーは地形データ作成に定義する。

    D.11.4. レンダリング（Unity）

    Unity は GET /api/v1/terrain/rivers で川の一覧を取得し（RiverSurfaceManager）、川ごとに「範囲ポリゴンを覆う格子面」の水面メッシュを作る。格子間隔は 4m（RiverStore.GRID_STEP）。各頂点の Y は「その地点のプロファイル標高 + 微小な持ち上げ」で、湖の水平面と違い流下方向に沿って下る。ポリゴンを頂点ごとに三角形分割しないのは、細長く蛇行する川では外周頂点を結ぶ三角形が流下方向に長く伸び、頂点間の線形補間が実際の水面勾配から乖離するためである。描画は「4隅のいずれかが範囲内」のセルとその隣接1セルを採用し、岸線から最大2セルの余白を岸へ埋める。地形と水面の格子・三角形が異なる曲線区間でも水の板の端を露出させないためで、保存ポリゴン・川床マスク・干渉の占有範囲は拡大しない。Tauriの3Dプレビューも同じ描画規則を使う。

    マテリアルは海面板（Custom/WaterLit）の複製で、流れモード（_FlowEnabled）を有効にし、頂点の UV2 に載せた流下方向（プロファイル線の最近線分の接線）へさざ波と泡を流す。深度オフセットや水際の扱いは湖と同じ（E_LOD処理 の「海面・水面の描画と深度オフセット」）。

    川床と川岸の地表は地形シェーダー側で表現する。RiverSurfaceManager は同じ4m格子で全域マスク（R＝川床、G＝カーブ内岸の砂地）を生成してグローバルテクスチャとして渡し、地形シェーダーが川床を濡れた岩、内岸の岸帯を砂地として塗る（E_LOD処理 の「地表のスタイライズ表現」）。

    D.11.5. 海岸線への反映とパスの横断

    範囲ポリゴンは水面と同列に、海岸線の抽出（新規都市の作成時とシナリオの地形の保存時。Terrain.compute_coastline_polygon）の穴あけ入力になり、そのまま difference される（湖のような水位判定は行わない。範囲が既に「水面より低い領域」だからである）。造成は川・湖の範囲に掛けられないので、埋立で海岸線が広がっても川・湖の穴は残る。したがって川の上に作られた土地区画は海上区画（PARCEL_WATER）になって陸地を要求する建物は建てられず、パスの端点・ウェイポイントも置けず（over_water_allowed のバリアントを除く。A_パス形状 A.9）、プロップの範囲散布も除外される。

    川の範囲を跨ぐパスには追加の制約がある。範囲内の各地点で「路面の絶対標高が水面標高 + WATER_BRIDGE_MIN_CLEARANCE（consts.py、0.5m）以上（橋）」か「深さ（地形標高 − 路面標高）がバリアントのクリアランス高さを超える（完全埋設トンネル）」のいずれかでなければ敷設できない。地形追従スパンは路面が川床（水面より下）になるため必ず拒否され、既定の街路で川を渡ろうとすると警告になる（橋バリアントか非追従設定、または地下で渡す）。電線・導水管・パイプラインなどのインフラパスは地表を占有しないため対象外。判定の詳細は J_パスの交差処理 の「川の横断」を参照。

    海（標高0m）と湖（§D.10）の上を通る区間にも同じ制約がかかる。こちらは範囲ポリゴンではなく「陸地ポリゴンの外側で、地形が水面標高より低い地点」を水の上とみなし、水面標高は湖の範囲内ならその water_level、それ以外は0mとする（J_パスの交差処理 の「海・湖の横断」）。川の範囲内の地点は川の横断として扱う。陸地ポリゴンはその時点の海岸線（埋立で広がった後のもの。§D.17.4）で、埋立地の上は水の上に当たらない。埋立地の岸壁の天端（帯）を横切る区間には、別に帯の規則がかかる（J_パスの交差処理 の「埋立地の岸壁の横断」）。

    D.12. 天然資源エリア（resources）

    神モードのセッションの資源編集（city-genesis/tauri の resource_edit ウィンドウ）でオーサリングされる天然資源エリア（鉱脈・油田などのポリゴン領域）。天然資源は経済シミュレーションのエンティティ（../economics/21_天然資源 参照）で、その初期配置はシナリオが持つ。取り込む標高ファイルは資源を持たない。

    D.12.1. データモデル

    資源エリアは1件ごとに以下のフィールドを持つ。

    フィールド 意味
    id 識別子。シナリオの地形APIでは資源のDB IDの文字列。シナリオの地形APIへ知らないIDで送った資源は新規になり、コアがDB IDを振って応答の resource_ids で送ったIDとの対応を返す（§D.14.3）
    resource_type 資源種別（resource_master のキー）。提供物資（product_id）は種別からバックエンドが導出する
    max_amount 埋蔵量上限。配置直後の埋蔵量はこの値と同値（満タン）で初期化される
    recovery_rate 埋蔵量上限に対する1日あたりの回復割合。0.0 は回復しない非再生資源（鉱脈・油田など）
    polygon 資源エリアの平面形状。{"type": "Polygon", "coordinates": [...]}。座標系は水面の polygon と同じ（ワールド座標XZ、マップ中心が(0,0)）

    D.12.2. 永続化

    資源はシナリオの都市に天然資源エンティティ（Resource）として入り、シナリオ・セーブデータに保存される。地形エディタの作業コピーでは meta.json の resources フィールドに保持される。「シナリオに保存」では一覧全体を送り、コアがIDで差分を適用する（既存のIDは更新、知らないIDは新規、送られなかった資源は削除。新規の資源のDB IDは応答の resource_ids で返る。§D.14.3）。地形エディタは資源を編集しないので、読み込んだ一覧をそのまま送り返す。既存の資源の埋蔵量上限を変えたときは、残量の割合を保つ。

    D.12.3. 都市への反映

    シナリオから都市を始めると、シナリオの資源がそのまま都市の初期賦存になる。以後の埋蔵量の増減はセーブデータ側が正となる。

    資源を置くのは、シナリオ管理の「都市を編集」で開く神モードのセッションでの資源編集（POST /api/v1/resources、../economics/21_天然資源 §21.7）である。地形エディタでは資源を編集しない。

    D.12.4. 埋蔵量上限・回復率の初期値（目安）

    テンプレート作成モードの資源編集パネル（resource_edit ウィンドウ）は、資源種別を選ぶと埋蔵量上限と回復率に目安の値を入れる。値とその根拠は ../economics/21_天然資源 §21.9 を参照。

    • 目安は資源の提供物資（product_id）ごとに city-genesis/tauri/src/data/resourcePresets.ts に定義する。性質の違う型がある提供物資（水資源の河川・湖沼・地下水）は、「目安」のプルダウンで型を選べる。先頭の型が既定になる。
    • 面積比例の目安（油田・鉱床・湖沼・地下水）は、1m²あたりの量に作図中のポリゴンの面積を掛けて埋蔵量上限にし、頂点を足したり動かしたりするたびに追従する。河川は面積に依らない定量である。
    • 利用者が値を手で変えると、その値が優先される。種別や目安を選び直すと目安の値へ戻る。
    • 入力欄の下には、目安の説明と、入力値を読み替えた量（面積・埋蔵量・1日あたりの持続採取量・空から満タンまでの時間）を表示する。持続採取量は §21.9 の式でエポック長を30日として求める。

    D.13. カメラ初期状態（camera）

    地形エディタ（「カメラ」タブ）でオーサリングされる、そのシナリオで都市を始めたときの3Dカメラの位置と向き。都市に1つだけ持ち、未設定でもよい。

    D.13.1. データモデル

    フィールド 意味
    x, z カメラ位置のワールド座標XZ（m）。水面・資源の polygon と同じ座標系（マップ中心が(0,0)）
    y カメラの高さ（m）。標高と同じ絶対高さフレーム（海面=0）
    yaw 視線の方位（度）。北（ワールド+Z）を0とする時計回り。camera:state IPC の yaw と同じ
    pitch 見下ろし角（度）。正で下向き（90=真下）、0で水平。ロールは常に0

    5つの値はどれも有限の数値で、float32 の範囲に収まらなければならない（グラフィックが float32 で読むため）。NaN・Infinity・範囲外の値は、シナリオの地形APIでは422 TERRAIN_INVALID、PATCH /api/v1/city では400 VALIDATION_ERROR で拒否する。

    D.13.2. 永続化と都市への反映

    カメラは都市のカメラ状態（City.camera、GET /api/v1/city の camera）で、シナリオ・セーブデータ（city.json）に保存される。標高ファイルから作ったばかりのシナリオは未設定（null）である。地形エディタの作業コピーでは meta.json の camera フィールドに保持され、「シナリオに保存」で City.camera を置き換える（null を送ると未設定に戻る）。

    シナリオから都市を始めると、シナリオのカメラ状態がそのまま初期視点になる。以後はグラフィック（Unity）がカメラの静止時に PATCH /api/v1/city の camera で更新する。ロード時はグラフィックが game:start 受信後に GET /api/v1/city を読んで視点を復元する。camera が null の都市は、グラフィック側の既定視点（原点＝マップ中心の上空、シーン配置時の向き）で始まる。

    地形エディタの共通操作

    地形エディタは、シナリオに含まれる地形を編集するツールである。シナリオ管理の自作カードの「地形を編集」から開き、編集結果は「シナリオに保存」でそのシナリオへ書き込む（§D.14.3。手順は L_地形データ作成マニュアル）。取り込んだ元の標高ファイルと、DLC由来の暗号化されたシナリオ（§D.14.3）は編集しない。暗号化されたシナリオのカードでは「地形を編集」を押せなくし、理由をボタンのツールチップで示す。

    元の地形の名前・遠景グリッド間隔・セルサイズ・マップサイズ・地表種別・気候区分は編集対象から独立したメタデータである。「3Dプレビューを開く」の右隣にある「メタデータ編集」からモーダルダイアログを開く。編集できるのは地表種別と気候区分だけで、ほかは読み取り専用で表示する（マップの寸法は変えられない）。閉じるボタンまたはEscapeで編集画面に戻り、変更した値は保持する。

    編集対象には地形・水面・川・カメラがある。左パネルは幅300pxで、見出しに「{シナリオ名} の地形」を出し、残りの幅は地図へ割り当てる。地形は「自動編集」「手動編集」のタブで切り替え（初期表示は手動編集）、選択範囲と設定値は切り替えても保持する。その他も対象の編集カードを1列で表示する。

    標高がロックされたシナリオ（§D.14.4）では、地形（自動編集を含む）・水面・川のタブを選べなくし、ロックの理由を表示する。開いた時点でカメラのタブを選ぶ。

    保存対象を変える操作をすると、保存ボタンの上に「未保存の変更があります」を表示する。保存中に行った編集は未保存のまま残る。ウィンドウを×で閉じると未保存の編集は失われる。保存に成功すると scenarios:changed を送り、シナリオ管理の一覧・画像・版を更新させる。

    資源（§D.12）とプロップ（M_地形プロップ）は、地形エディタでは編集も表示もしない。シナリオの地形APIは保存で資源をID差分、プロップを全置換で受けるため（§D.14.3）、読み込んだ内容をそのまま送り返してシナリオに残す。

    地形エディタの2D表示

    2D表示は3枚のキャンバスを重ねて描く。下から、標高から決まる地形層（WebGL2）、確定済みの水面・川・カメラを描くベクター層（Canvas2D。マウス操作もここで受ける）、ブラシや作図中の図形・川のノードなどマウスに追従するものを描くカーソル層（Canvas2D）である。マウスを動かしただけのときはカーソル層だけを描き直し、パン・ズームや編集データの変更で全層を描き直す。

    地形層は作業コピーの標高を1格子点＝1テクセルの浮動小数点テクスチャに置き、画素ごとに双線形補間した標高から次の順に重ねて描く。等高線は画面上の勾配から最寄りの等高線までの画素距離を求めて描くので線分を組み立てる前処理が無く、マップの広さや等高線の間隔によらず1フレームの負荷は画素数で決まる。GPUのテクスチャの上限（通常16384）を超える格子数のマップは表示できない。

    • 地形色: 標高0m以下は海面色、陸地は読み込み時に固定した陸地の標高レンジで正規化し、地表種別のカラーランプで塗る（§D.15）。
    • 選択範囲・ポリゴン仮確定のハイライト: 選択の重みに比例した不透明度の水色。
    • グリッド: 100m間隔とセル境界（cell_size間隔。より濃く太く描く）。マップ南西隅を起点に引き、線の間隔が画面上で詰まりすぎる縮尺では描かない。
    • 等高線: 標高0mより上で間隔の倍数の標高に1画素幅の線を引き、陸地の最低標高以上の最初の等高線から数えて5本ごとを太い主曲線にする。間隔は、地形全体を表示したときに約25本以下になる最小の候補（10, 20, 25, 50, 100, 200, 250, 500, 1000, 2000m）を基準とし、その表示から6倍を超えてズームインした分だけ1-2-5系列で細かくする（最小1m）。勾配0の平坦地には線を引かない。線の間隔が画面上で2画素を切る所は、1本ずつの線から平均の濃さへ寄せる。

    地形エディタと3Dプレビューの同期

    3Dプレビューウィンドウは地形エディタとTauriのイベント（全ウィンドウへの送信＋作業コピーのID editor_id での絞り込み）で同期し、ディスクではなく編集中のメモリ上の状態を表示する。

    イベント 向き 内容
    terrain_3d_preview:request_state プレビュー→エディタ 表示されたとき（マウント時・非表示からの復帰時）に全状態を要求する
    terrain_3d_preview:detach プレビュー→エディタ 非表示・アンマウントになり、状態の送信が不要になったことを知らせる
    terrain_3d_preview:full_state エディタ→プレビュー 標高（float16）・選択範囲・水面・川・地表種別の全体
    terrain_3d_preview:selection_delta / selection_reset / elevation_delta エディタ→プレビュー 選択範囲・標高の矩形差分

    プレビューはマウントごとに sessionId を作って request_state と detach に付ける（イベントの到着順は保証されないので、どのマウントの接続・切断かを区別する）。プレビューは購読を張り終えてから request_state を送る。エディタは接続中のプレビューがあるときだけ状態を送る。全状態は標高全体を符号化するため、続けて起きた変更は落ち着くのを待って1回にまとめて送り、その送信待ちの間は差分を送らない。切断していた間に状態が変わっていなければ、再接続したプレビューへは全状態を送り直さない。

    D.14. 標高ファイルの取り込みとシナリオの地形

    ゲームは標高マップを同梱しない。地形はシナリオ（.cg）が自己完結で持ち、新しい地形は利用者が用意した標高ファイルを取り込んでシナリオにする。シナリオは地形に、シミュレーションに関わるデータ（水面・川・資源・プロップ・カメラ）を加えたものである。ゲームで遊ぶ都市は、必ずシナリオ（またはチュートリアル）から始まる。チュートリアルはゲームに同梱した都市（チュートリアル基盤）から始まる。

    D.14.1. 標高ファイルの取り込み

    シナリオ管理の「地形を取り込む」で、任意の場所に置いた標高ファイルを選んで新しい自作シナリオにする（POST /api/v1/scenarios/from-heightmap。§D.14.3）。取り込めるのは次の2形式である。

    形式 読み方
    グレースケールPNG（8bit・16bit） 画像の上が北。最も暗い色を「最低標高」、最も明るい色を「最高標高」（m）として線形に当てる
    .npy 数値の2次元配列。行0が南端・列0が西端（§D.3.1）、値はメートル
    • 寸法: 1画素の距離（m）を入力する。マップの一辺は元の範囲（（画素数−1）×1画素の距離）を1km（2×cell_size）単位に切り上げ、元の範囲を中央に置いて、はみ出す分は縁の標高を延ばす（海で埋めると内陸の地形の縁に偽の海岸ができるため）。一辺は30km以下。近景の格子（10m）へ3次スプラインで標本化し、遠景は近景を間引いて作る。
    • 海: 「海面の高さ」（m）以下を海にして、その高さを0mにする。海は海岸からの距離に応じて負の標高へ彫る（-50m × tanh(0.02 × 距離 / 50m)。地形エディタの自動編集の海底生成と同じ式）。0mのままの海は海面と地面が同じ高さになり描画されない。陸地が無いファイルは取り込めない。
    • できるシナリオ: 水面・川・資源・プロップ・カメラは空、地表種別・気候区分は既定値（草原・温暖湿潤）、背景地形は指定したときだけ付く。タイトルは入力した1つの文を英語にだけ入れる（何語で書いたかは尋ねない。ほかの言語は英語で表示され、後から紹介情報で書き分けられる）。元のファイル名が「元の地形」（terrain_source）として残る。サムネイルはUIがシナリオの地形から描く（§D.15.4）。
    • 変換できないファイル（形式違い・大きすぎる・陸地が無いなど）は422 HEIGHTMAP_INVALID で断り、シナリオを作らない。

    背景地形（任意）: 都市の外に広がる遠景（都市外の背景地形）も、.npy（詳細地形と同じ規約の数値の2次元配列。PNGは標高範囲を別に持てないので使えない）を選んで一緒に取り込める。1画素の距離は詳細地形とは別に入力し、海面の高さだけ詳細地形と共通にする。

    • 格子: 入力した間隔に関わらず、50m格子へ線形補間で直す。一辺は100km以下。
    • 位置: 格子の中心が都市の原点に来る。詳細地形も元の範囲を中央に置くので、2つの中心が揃う。背景は都市の範囲を広げない。
    • 海: 詳細地形と同じ式で海底を彫る。陸地が無い背景は取り込めない。
    • 遠景用海岸線: 背景の陸地の粗い輪郭を取り込み時に作り、背景と一緒に持たせる（ロードでは作り直さない）。

    プレビュー: UIは取り込み前に、選んだファイルの標高を POST /api/v1/scenarios/heightmap-preview（§D.14.3）で受け取って描く。詳細地形は標高で色分け、背景は淡い単色で重ね、標高0m以下（海）はどちらも透明にする。詳細地形の海の下に背景の陸地があれば透けて見えるので、境界のずれに気づける。

    地形の API（/api/v1/terrain/*）は都市の地形を返すので、ゲームのセッションが無い間とシナリオの地形の処理中（§D.14.3）は503 NO_SAVE_LOADED になる。シナリオの地形API（§D.14.3）と取り込みはシナリオのAPIなので、セッションが無くても使える。

    D.14.2. シナリオが持つ地形データ

    シナリオ（とそこから始めた都市）は、地形について次のデータを持ち、すべて .cg に保存する。シナリオから都市を始めると、これらがそのまま新しい都市に写る。

    データ 都市での持ち方 ゲーム中に読むAPI
    標高 近景・遠景・超近景セル（§D.3・§D.4） /api/v1/terrain/*
    水面 city.terrains["water_surfaces"]（§D.10） GET /api/v1/terrain/water
    川 city.terrains["rivers"]（§D.11） GET /api/v1/terrain/rivers
    資源 天然資源エンティティ（§D.12） /api/v1/resources
    プロップ 個別配置・範囲散布（M_地形プロップ） /api/v1/props/*
    カメラ City.camera（§D.13） GET /api/v1/city の camera
    地表種別 City.ground_cover（§D.15） GET /api/v1/city の ground_cover
    気候区分 City.climate（§D.16） GET /api/v1/city の climate
    背景地形 都市外の背景の標高と遠景用海岸線（都市外の背景地形） GET /api/v1/terrain/background・GET /api/v1/terrain/background/coastline

    背景地形・資源・プロップ以外を編集するのは、シナリオの地形API（§D.14.3）を通す地形エディタである。資源とプロップは、神モードのセッションの資源編集・プロップ配置で編集する。

    D.14.3. シナリオの地形API

    地形エディタの入出力。どちらもゲームのセッションを使わず、コアが一時的にシナリオを読み込んで処理する。対象は自作シナリオだけで、コミュニティ・DLCは422 SCENARIO_READ_ONLY、存在しない自作シナリオは404 NOT_FOUND、ゲームのセッション中は409 SESSION_ACTIVE になる。

    DLC由来の都市から作った自作シナリオ（暗号化されたシナリオ。セーブデータ仕様）も対象外で、GET・PUTとも409 SCENARIO_ENCRYPTED になる。コアはファイルを復号する前にこれを判定する。地形を平文で返すと、地形エディタの作業コピーとしてディスクに残るうえ、別の平文のシナリオへ保存すれば必要パックの記録を外してDLCの地形を持ち出せてしまうためである。こうしたシナリオの資源・プロップは、神モードのセッション（シナリオ管理の「都市を編集」）で編集する。

    GET /api/v1/scenarios/{id}/terrain の応答:

    {
  "settings": {"map_width": 7000, "map_height": 7000, "near_spacing": 10, "far_spacing": 200,
               "cell_size": 500, "grid_rows": 701, "grid_cols": 701},
  "near_base64": "<近景標高>",
  "water_surfaces": [],
  "rivers": [],
  "resources": [],
  "props": {"instances": [], "scatters": []},
  "camera": null,
  "ground_cover": 1,
  "climate": 1,
  "background": null,
  "terrain_source": "island.png",
  "title": "シナリオのタイトル",
  "locks": {"heights_locked": false, "reasons": []}
}
    項目 内容
    settings マップの寸法と格子。grid_rows = map_height / near_spacing + 1、grid_cols = map_width / near_spacing + 1
    near_base64 近景標高の float16 リトルエンディアンのバイト列（行優先、grid_rows × grid_cols、行0が南端。§D.3.1）を、パディング付きの標準 base64 にしたもの
    water_surfaces / rivers §D.10.1・§D.11.1 の形式
    resources §D.12.1 の形式。id は資源のDB IDの文字列
    props instances（id/prop_type/x/y/z/rotation/scale）と scatters（id/prop_type/polygon/density/seed/edge_fade_width/allow_water）。id はDB IDの文字列（M_地形プロップ）
    camera §D.13.1 の形式、または null
    ground_cover / climate §D.15・§D.16 の値
    background 背景地形の格子 {"origin": [x, z], "rows", "cols", "spacing"}（origin は南西隅のワールドXZ）、または null。背景は編集できないので参照用
    terrain_source / title 元の地形の名前（取り込んだファイル名など）と、シナリオのタイトル
    locks 標高のロック（§D.14.4）

    PUT /api/v1/scenarios/{id}/terrain の本文は {near_base64, water_surfaces, rivers, resources, props, camera, ground_cover, climate}。

    • near_base64・water_surfaces・rivers は null なら変更しない。ロック中にどれかを送ると409 TERRAIN_LOCKED。
    • 標高の格子数が今のシナリオと違う（寸法を変えようとした）ときは422 TERRAIN_SIZE_MISMATCH。マップの寸法は変えられない。
    • resources は一覧全体を送る。コアはIDで差分を適用し、既存のIDは更新、知らないIDは新規、送られなかった資源は削除する。新規の資源に振ったDB IDは応答の resource_ids で返る。次の保存でそのIDを送れば同じ資源として更新され、仮のIDのまま送り直すと、前回作った資源を削除して別のIDで作り直すことになる。
    • props は全置換で、送ったIDは保存しない（保存後はコアが新しいIDを振る）。
    • camera はそのまま置き換える（null なら未設定に戻す）。値の条件は §D.13.1。ground_cover・climate は必須で、既知の値だけを受け付ける。
    • 形の崩れた値と有限でない数値（NaN・Infinity）は422 TERRAIN_INVALID、資源・プロップの値の誤りは400 RESOURCE_VALIDATION_ERROR / PROP_VALIDATION_ERROR。

    標高・水面・川のどれかを保存すると、コアは遠景（far）を新しい近景から作り直し、海岸線を抽出し直し（§D.9）、土地区画の種別を新しい海岸線で判定し直し（B_土地形状 の「区画種別の自動判定」。埋立地の区画を除く）、勾配と基準標高を測り直し、サービスの効果範囲を計算し直す。種別の変わった区画を含む地区は形を作り直す（海上区画は地区の形に寄与しないため）。水面・川・海岸線は新しいオブジェクトに差し替えるので、それらを参照するキャッシュも作り直される。土地区画の形は変えない。

    保存はシナリオの通常の保存経路を通るので、出自（セーブデータ仕様）はそのまま保たれ、content_revision が1つ上がる。応答は {"success": true, "id": "local~<id>", "content_revision": <int>, "locks": {...}, "resource_ids": {"<送ったID>": "<DB ID>"}}。locks は保存前に判定したロック、resource_ids は今回新しく作った資源だけの対応表である。途中で失敗したときはファイルを書き換えない。

    POST /api/v1/scenarios/from-heightmap は本文に標高ファイルの生バイトを、クエリに spacing（1画素の距離 m。必須）・min_height / max_height（PNGの標高範囲 m。既定0 / 1000）・sea_level（海面の高さ m。既定0）・title（必須）・language・source_name（元のファイル名）を受け取り、新しい自作シナリオを作って {"id": "local~<id>", "map_width", "map_height"} を返す（§D.14.1）。ゲームは始まらない。背景地形を付けるときは、本文の末尾へ背景の .npy を続けて、その大きさを background_size（バイト）、1画素の距離を background_spacing（m）で渡す（この2つは対。multipart は使わない）。

    POST /api/v1/scenarios/heightmap-preview は本文に標高ファイルの生バイトを、クエリに min_height / max_height / sea_level（取り込みと同じ読み方）・background（真なら背景として読む。.npy だけ）・max_side（間引いた標高の長辺の最大画素数。既定1024）を受け取り、{"source_rows", "source_cols", "rows", "cols", "min_height", "max_height", "heights_base64"} を返す。heights_base64 は sea_level を引いた標高を長辺 max_side 以下へ間引いた float16 LE（行0が南）、source_rows / source_cols は間引く前の画素数、min_height / max_height は間引く前の全画素の標高の最小・最大（sea_level を引く前のファイルの値）である。シナリオも都市も作らず、ディスクにも書かないので、ゲームのセッション中でも使える。読めないファイルは422 HEIGHTMAP_INVALID。

    D.14.4. 標高のロック

    建設物のあるシナリオでは、標高・水面・川を変えられない。建設物は建てたときの地形に合わせて造成・接地しているので、下の地形だけを変えると食い違うためである。資源・プロップ・カメラ・地表種別・気候区分はロック中も編集できる。

    locks は {"heights_locked": bool, "reasons": [...]} で、reasons は次の理由コードをこの順に並べる。

    理由コード 条件
    PATHS_EXIST パス（道路・線路・インフラ）が1本でもある
    BUILDINGS_EXIST 形を持つ建物が1棟でもある（市庁舎を置く前の市政府のように、形の無い主体は数えない）
    TERRAIN_MODIFIED 超近景セル（造成や編集で書き換えた標高。§D.4）が1つでもある
    RECLAIMED_LAND 埋立地がある（§D.17）

    初期の地区・土地区画は建設物に含めない。標高・水面・川を変えたときは、区画の種別・勾配・基準標高を測り直す（§D.14.3）。

    D.15. 地表種別（ground_cover）

    都市ごとの地表の見た目（草原・砂漠など）を表す属性。描画だけに使い、経済シミュレーションは参照しない。都市に1つだけ持ち、マップ内で塗り分けることはない。

    D.15.1. データモデル

    値 定数（consts.py） 見た目
    1 GROUND_COVER_GRASSLAND 草原。ステップのような黄緑の草地。未指定時の既定
    2 GROUND_COVER_DESERT 砂漠。砂色の地面と近景の風紋、砂浜の海岸、砂岩色の崖
    3 GROUND_COVER_LUSH 濃い草地。温帯〜亜寒帯の鬱蒼とした深い緑
    4 GROUND_COVER_SNOW 雪原。白〜青白の地面。急斜面は灰色の岩
    5 GROUND_COVER_SEMI_ARID 乾燥地。地中海性・半乾燥気候の枯れ草と低木、砂浜の海岸

    D.15.2. 永続化と都市への反映

    地表種別は都市（シナリオ）が保存値として持ち（City.ground_cover）、シナリオ・セーブデータ（city.json）に保存される。標高ファイルから作った新しい都市は草原で始まる。

    値は GET /api/v1/city の ground_cover で読める。PATCH /api/v1/city では変更できず、変えられるのはシナリオの地形API（§D.14.3。地形エディタの「メタデータ編集」）・シナリオの紹介情報（開始設定）・シナリオから始めるゲームの確認画面（作者が固定していない場合）だけである（シナリオ制作と配布）。地形エディタの作業コピーでは meta.json の ground_cover に保持する。

    D.15.3. 描画

    Unityの TerrainManager がセッション開始時（FetchCoastline）に GET /api/v1/city から種別を読み、GroundCoverPalette の対応するプロファイルを地形タイル・超遠景の陸地メッシュ・都市外背景のマテリアルへ同じ値で設定する。描画の詳細は E_LOD処理 の「地表のスタイライズ表現」を参照。Tauriの2D表示（地形エディタの2D・3Dプレビュー・サムネイル・都市マップ）は、同じ種別で標高のカラーランプを切り替える。

    D.15.4. 地形サムネイル

    標高ファイルを取り込んでシナリオを作ると、UIがそのシナリオの地形（シナリオの地形APIの近景）からサムネイルを描き、シナリオの画像として保存する。画像は地図の全範囲を真上から見た平面図で、北が上・東が右。長辺512pxで実寸の縦横比を保ち、表示側もobject-fit: containで全域を収める。

    terrainThumbnail.tsは標高を双線形補間し、標高0m以下を透明にする。陸地はterrainData.tsのlandElevationRangeとcomputePixelRGBを使い、保存対象の標高範囲と地表種別で塗る。草原は低地の緑から高地の茶へ変化する。1画素を2×2点で評価し、陸地の被覆率をアルファにするため、海岸の縁にも海色は混ざらない。湖・川の水面、プロップ、選択範囲、等高線は重ねない。

    地形エディタはサムネイルを作らない。画像を差し替えたいときはシナリオの紹介情報から変える。

    D.16. 気候区分（climate）

    都市ごとの気候。季節ごとの天気の出方（晴れ・雨・雪の出現割合）を決める描画だけの属性で、経済シミュレーションは参照しない。都市に1つだけ持つ。天気の種類と、気候・季節ごとの出現割合の表は天気と環境光を参照。

    D.16.1. データモデル

    値 定数（consts.py） 気候
    1 CLIMATE_TEMPERATE 温暖湿潤。未指定時の既定
    2 CLIMATE_SUBTROPICAL 亜熱帯
    3 CLIMATE_CONTINENTAL 湿潤大陸性
    4 CLIMATE_MEDITERRANEAN 地中海性
    5 CLIMATE_STEPPE ステップ
    6 CLIMATE_DESERT 砂漠
    7 CLIMATE_SUBARCTIC 亜寒帯

    地表種別（§D.15）とは独立に選ぶ。地表種別は地面に何があるか、気候は空から何が降るかを表す。地表が砂漠でも雨季のあるステップ気候になりうるし、地表が同じ濃い草地でも、冬に雪が降る湿潤大陸性と雪が降らない亜熱帯がある。

    D.16.2. 永続化と都市への反映

    気候区分は都市（シナリオ）が保存値として持ち（City.climate）、シナリオ・セーブデータ（city.json）に保存される。標高ファイルから作った新しい都市は温暖湿潤で始まる。

    値は GET /api/v1/city の climate で読める。PATCH /api/v1/city では変更できず、変えられるのはシナリオの地形API（§D.14.3。地形エディタの「メタデータ編集」）・シナリオの紹介情報（開始設定）・シナリオから始めるゲームの確認画面（作者が固定していない場合）だけである（シナリオ制作と配布）。地形エディタの作業コピーでは meta.json の climate に保持する。

    D.16.3. 描画

    Unityの WeatherController がセッション開始時とエポック完了時に GET /api/v1/city から climate と current_date を読み、気候と季節に対応する天気の出現割合を選ぶ。Tauriはシナリオ管理とニューゲームの詳細に気候名（i18n climate.<値>）を出し、地形エディタのメタデータ編集で区分を選ばせる。

    D.17. 埋立地（reclaimed_lands）

    造成（造成）は、プレイヤーが描いた範囲の地形を目標の高さ H（海面基準の絶対標高。基準の高さ（地表の接道の路面の高さ。地表の接道が無ければ整地は範囲の現況の平均、埋立は SEA_GRADING_TOP（3m））に、整地だけプレイヤーが指定するずれを足した値。埋立は常に基準の高さ）にそろえる公共工事で、種類は区画種別の規則（B_土地形状 B.5）で決まり、範囲が陸地区画になるなら整地（variant 3006）、沿岸区画になるなら埋立（variant 3007）になる。陸だけの範囲でも海岸線に接すれば埋立で、海に面する辺が岸壁になる（海上区画になる範囲は発注できない）。どちらも完了すると範囲内の1m格子点の標高を H に書き換え（岸壁の直近と既存の岸壁の天端など、§D.17.2 の点を除く）、範囲の外に法面は付けない。整地は地形を書き換えるだけで、海岸線も埋立地も変えない。埋立は完了すると範囲が埋立地として登録され、海岸線に足される。埋立地のうち海に面する辺は岸壁になり、Unity はそこにコンクリートの天端と垂直の面を描く。

    工事中の範囲の見た目は 工事中建物のメッシュ生成 §7 を参照。

    D.17.1. データモデル（保存値）

    フィールド 意味
    reclaimed_land_id 都市内で一意なID。1からの連番で、採番はセーブをまたいで続く
    polygon 範囲 [[x, z], ...]。外周は反時計回り（CCW）の閉じたリングで、工事の区画のポリゴンをそのまま写したもの
    version 登録時は1。隣の埋立で岸壁の形が変わるたびに1増える

    保存するのはこの3つだけで、city.json に入る（§D.8）。埋立地を消す操作は無い。

    D.17.2. 岸壁・帯・壁・天端の高さ（派生値）

    次の値は保存せず、現在の海岸線と地形から求める。海岸線や埋立地の一覧が変わると求め直す。

    • 岸壁区間（quays） — 範囲の外周の各辺を外向きに QUAY_PROBE_DISTANCE（0.5m）ずらした線のうち、陸地ポリゴン（現在の海岸線）の外に出る部分を、元の辺へ戻した区間。つまり辺のうち海に面している部分で、ごく短い片は捨てる。都市の範囲の外（縁の上を含む）は陸とみなすので、マップの縁に沿った辺は岸壁にならない（海岸線は陸地をマップの矩形で切った形なので、縁の上では陸がマップの外へ続いていても陸地の外になる。区画種別の沿岸判定（B_土地形状 B.5）がマップの縁を岸としないのと同じ扱い）。後から隣を埋め立てると陸地が広がり、その区間は岸壁でなくなる。
    • keep 領域 — 範囲の内側で、岸壁区間から QUAY_KEEP_WIDTH（2.8m）以内。完了時に地形を書き換えず、元の高さ（多くは海底）のまま残す。
    • 帯（band） — 範囲の内側で、岸壁区間から QUAY_BAND_WIDTH（5.6m）以内（岸壁の端では丸く広がる）。コンクリートの天端で覆い、帯の中の地面の高さは max(地形, 天端) とする（§D.17.6）。
    • 壁（walls） — 範囲の外周のうち帯に掛かる部分。岸壁区間に加えて、岸壁の端で帯が陸側の辺に沿って出る「袖」を含む。岸壁と同じく、都市の範囲の縁の上の辺には張らない。Unity はここに垂直の面を張る。
    • 天端の高さ（top_height） — 帯の中で keep 領域の外にある1m格子点（完了時に H を書いた点）の、現在の地形の高さの中央値。通常は H そのものになる。岸壁が無ければ null。

    keep 領域と帯の2段にするのは、Unity の地形タイルの見た目のためである。地形タイルは格子点の間を補間して描くので、岸壁の直近まで H を書くと、その補間で岸壁の外の海の上に盛り上がりが漏れて見える。そこで岸壁の直近（keep 領域）は元の海底の高さのまま残し、残した海底と H の段差をそれより広い天端（帯）で覆って隠す。2つの幅は、地形の格子と岸壁がどの向きで交わっても盛り上がりが岸壁の外へ漏れない最小の値で、unity/Tests/Quay/run-unity.ps1 が実際の Unity の地形で検査する。

    帯と、岸壁の外側の海（道路の法面が届く範囲まで）は、ほかの地形の書き換え（道路の盛土・切土・交差点の平坦化・整地・ほかの埋立）で変えない。帯を書き換えると天端の先に溝が出て、岸壁の外の海底を道路の法面が持ち上げると溝の先に尾根ができるためである。岸壁の端の丸い範囲が陸（天然の陸や隣の埋立地）に掛かる所は守らないので、岸壁の端のすぐ脇の陸地も普通に整地・造成できる。新しい埋立では、陸地を新しい範囲まで広げた後の海岸線で「岸壁の外側の海」を判定するので、新しい範囲に入る部分は守られず H で書かれる。帯の中を地表で通るパスは拒否される（J_パスの交差処理 の「埋立地の岸壁の横断」）。

    D.17.3. API

    GET /api/v1/terrain/reclaimed-lands:

    {"reclaimed_lands": [
  {"reclaimed_land_id": 1,
   "polygon": [[x, z], ...],
   "version": 1,
   "top_height": 3.0,
   "quays": [{"a": [x, z], "b": [x, z], "normal": [nx, nz]}],
   "walls": [{"a": [x, z], "b": [x, z], "normal": [nx, nz]}],
   "band": [[[[x, z], ...], [[x, z], ...]], ...]}
]}
    フィールド 種別 意味
    reclaimed_land_id / polygon / version 保存値 §D.17.1
    top_height 派生値 天端の絶対標高。岸壁が無ければ null
    quays 派生値 岸壁区間。各要素は辺の一部の直線 a→b と、埋立地の外向きの単位法線 normal
    walls 派生値 垂直の面を張る区間（quays を含む）。形は quays と同じ
    band 派生値 帯の多角形の列。各多角形は [外周, 穴...] のリングの列（GeoJSON MultiPolygon の coordinates と同じ形。外周は反時計回り、穴は時計回り）

    座標はワールド座標のXZ（マップ中心が原点）。フロントエンドは岸壁・帯・天端の判定を再実装せず、この派生値を描いて判定に使うだけにする（CoastlineStore.IsLand で岸壁を求め直すと、端点や天端がバックエンドとずれる）。

    D.17.4. 海岸線の拡大

    埋立の完了では、まず地形を書き換える（隣の埋立地の岸壁でなくなった区間の溝を埋め、自分の範囲を H にする）。書き込みがすべて成功したときだけ、範囲を海岸線（city.terrains["coastline"]）に和集合で足し、埋立地を version 1 で登録し、岸壁が変わった隣の埋立地の version を上げる。地形が海底のままの陸地や埋立地を残さないためで、地形を書けなかった工事は（整地も）建設中のまま残り、次のエポックで書き直す（同じ書き込みは何度行っても同じ結果になる）。和集合の後の海岸線は頂点を間引かない（辺が動くと岸壁の判定がずれるため）。

    • 隣へ広げる埋立 — 新しい範囲が既存の埋立地の辺に面で重なると、既存の埋立地の辺の一部は海に面さなくなり、岸壁でなくなる。完了時に、その部分の keep 領域（元の海底のまま残していた溝）をその埋立地の天端の高さで埋める。新しい範囲と既存の埋立地の帯のあいだに海底の点は残らない。
    • 区画種別 — 海岸線が広がった後に作る区画は、その時点の海岸線で陸地・沿岸・海上が決まる。埋立地の内側の区画は陸地、岸壁に接する区画は沿岸になる。作成済みの区画の種別は変わらない（B_土地形状 B.5）。
    • フロントエンドの再取得 — Unity は session:reload のたびに海岸線・湖・川・埋立地を取り直す（TerrainManager.FetchCoastline）。海岸線に依存する描画（港の岸壁 F4、超遠景の陸地 E_LOD処理、船の航路 V_環境演出の乗り物）は取り直した海岸線を使う。

    D.17.5. 描画（Unity）

    ReclaimedLandManager が TerrainManager.FetchCoastline の中で、海岸線・湖・川の後に GET /terrain/reclaimed-lands を読み、ReclaimedLandStore に置く。区画・建物のロードより前に揃えるのは、接地（§D.17.6）と港の岸壁の判定がこれを参照するためである。

    • 差分での作り直し — 取得のたびに前回と中身を比べ、中身が変わった埋立地だけを作り直す。新しいメッシュを作ってから古いものを捨て、先に全部消さない（湖・川のように消してから取得すると、session:reload のたびにちらつく）。取得に失敗したら前回の表示を残す。ストアの版 ContentVersion は中身が変わったときだけ進み、港はこの版で作り直す（F4 §8）。セッションの切り替えではストアごと消す。
    • メッシュ — 埋立地1件につき GameObject 1つで、天端と壁を1つのメッシュにする。天端は band の多角形（穴あり）を三角形に分割して高さ top_height に置き、法線は上向き。壁は walls の各区間に沿った垂直の帯で、上端は top_height、下端は区間の外側 QUAY_PROBE_DISTANCE の地面の高さから1m下。下端は最大2m間隔の列ごとに外側の地面に合わせる。外側の地面が天端より高い所でも、天端の0.05m下より上には上げない（面を潰し切らない）。隣の埋立地に接する袖では外側の地面が隣の天端になるので、面は隣の天端の下に隠れる。UV はワールド座標で10mごとに1枚。top_height が null の埋立地は描かない。
    • マテリアル — Resources/COMMON_CONCRETE の共有 DepthOffset 版（建物と同じく地形より手前へ寄せる）。帯の内縁で天端と地形が同じ高さになっても Z-fighting しない（R_マテリアルの解決 §3.4）。
    • 地形の版への追従 — 壁の下端だけが地形に依存する。OnTerrainTileReady と全景のロード完了（OnAllTerrainLodLoaded）のたびに、埋立地の範囲の地形の署名（TerrainManager.GetTerrainSignature）を作成時の値と比べ、変わった埋立地を作り直しの待ち行列に積んで共通の描画予算（RenderWorkScheduler）で作り直す。
    • クリック・表示切り替え — GameObject は背景地形のチャンクと同じ構成（Ground レイヤー、MeshCollider、VisualTerrainObject、TerrainInputHandler。タグは付けない）で、地形としてクリック・ホバーされ、地形と同じ表示切り替えに従う（Unity入力制御 §2.1）。

    D.17.6. 接地

    Utils.GetGroundHeight は、点がいずれかの埋立地の帯の中なら max(地形, 天端) を返す（ReclaimedLandStore.TryGetBandTop。帯の多角形は穴を持つので全リングの偶奇で判定する）。バックエンドが区画の勾配を測るときやパスの帯の検証で使う地面と同じ規則で、天端の上に置く建物・プロップ・カーソルは天端に接地する。ストアの更新・消去は高さのキャッシュを捨てる。

    • パスのノードの相対高さも帯の中では天端から換算されるが、バックエンドは地形から換算する。このずれを起こさないよう、パスの始点・終点・経由点は高架・地下でも帯の中に置けない（J_パスの交差処理 の「埋立地の岸壁の横断」）。
    • 区画のデータ可視化の塗り（GPU の高さの移動窓。E_LOD処理 の「接地と依存順序」）は天端を含まないので、帯の中では塗りが天端の下に沈む。

    都市外の背景地形

    都市範囲は詳細標高マップの範囲と一致する。半島・大陸などは、都市の外側に任意の50m格子の背景地形を描いて表現する。背景は詳細地形と同じ実地形から作り、編集や造成の対象にはしない。境界の継ぎ目を補間する処理はない。詳細地形と背景は同じ実地形から作り、都市の範囲内にある対岸の陸地も詳細地形に陸として含める(島だけを切り出さない)。そうしないと境界で陸地が直線で途切れる。

    背景の標高・左下のワールドXZ座標（原点。指定が無ければ背景配列を都市原点の周囲に配置する）・遠景用海岸線は都市のデータで、シナリオとセーブが持ち続ける（.cg の terrain/background.npy・terrain/background.json）。背景つきの都市は、シナリオ管理の「地形を取り込む」で背景の標高ファイルも一緒に取り込んで作る（§D.14.1）か、開発者ツールで作る（チュートリアルの舞台）。地形エディタは背景を編集しない。背景標高は詳細地形へ焼き込まない。

    UnityのTerrainManagerは /api/v1/terrain/background のfloat32 little-endian配列を取得する。行数・列数・格子間隔・原点は X-Grid-Rows、X-Grid-Cols、X-Grid-Spacing、X-Origin-X、X-Origin-Z で受け取り、未設定の204では背景を生成しない。背景を分割メッシュとして描き、都市内のセルには従来の詳細地形を使う。背景はロードバッチとは独立した処理で取得・生成し、カメラ移動によるバッチの取消しでは止めない(止めるのはセッション切り替えなどの全消去だけ)。バッチは高さ配列の受信(または204)までだけ待ち、チャンクメッシュは共通の生成予算の範囲で並行して作る。取得に失敗したら次のバッチで再試行する。都市外の接地(Utils.GetGroundHeight)はこの背景の高さを使う。都市内の未常駐セルの接地は Unity の全Terrain一覧を走査せず、全景の高さマップから返す。カメラ移動範囲と遠方クリップ距離は背景を含め、都市外の道路・建物も必要な周辺セルで取得する。

    背景の地表は全景(UltraFar)と同じシェーダーで描き、都市内の詳細地形と同じ手続き色・色被せ・照明の値を直接設定する。手続き色などの値はシェーダーの Properties に宣言していないため、既存マテリアルを new Material(既存) で複製すると落ちて、草のテクスチャそのままの色になる。遠景用のマテリアルは複製せず、TerrainManager.ApplyFarTerrainMaterialSettings で設定する。

    背景には遠景用海岸線が付く。背景の陸地(標高0m超。陸に囲まれた海面下の窪地は穴)の輪郭で、マップ作成時に背景と一緒に作り、背景の .npy と同じ場所・同じ名前の .coastline.json に保存する。新しい都市を作るときに背景と一緒に都市へ写す。背景はプレイ中も地形エディタでも変わらないので、ゲーム中に作り直すことはない。都市マップ(2D)で遠くから眺めるための形なので粗く、0.1km²未満の島・池を省き、頂点を許容誤差100mで間引いてある。そのため都市の境界では、都市側の海岸線と最大100mずれる。GET /api/v1/terrain/background/coastline がワールドXZの MultiPolygon で返し、背景の無い都市では空を返す。都市マップはこれを都市の矩形の外だけ陸地の色で塗る(都市マップの検索と経路案内)。

    都市の範囲は、カメラが境界へ近づいたときに半透明の白い破線で示す(VisualHandlers/CityBoundaryOverlay)。背景の陸地が地続きに見えても、都市外はテンプレートモード以外では建設できないためである。線の各位置からカメラまでの高さを含む3D距離が1,000m以上では非表示、600〜1,000mでは滑らかにフェードし、600m以内では既定の濃さで表示する。透明度は OverlayLine シェーダーの OVERLAY_DISTANCE_FADE を境界線の専有材質だけで有効にして画素ごとに求め、チャンク間や微小なカメラ移動でも連続させる。範囲外のチャンクはメッシュ生成から省く。

    線は地表(海の上では海面)から少し浮かせて置き、太さは画面上のピクセル数で一定にする。破線の周期はカメラからの距離に応じて2の累乗メートルに丸め、境界に沿った距離が周期の倍数になる位置から描く。周期が2倍刻みでしか変わらないので、カメラを動かしても破線は地面に固定されたまま流れない。

    さらに近づくと、境界の地表・海面から高さ1kmの水色の格子壁を描く。壁の各位置からカメラまでの3D距離が300m以上では透明、100〜300mでは滑らかにフェードし、100m以内では既定の濃さになる。格子の間隔はワールド上で20m、線幅は画面上で約1.5pxとし、格子の間は透明にする。OverlayLine の OVERLAY_WORLD_GRID で矩形の各辺に同じワールド座標の格子を描くため、カメラ移動やチャンクの継ぎ目でも模様は固定される。壁の下端は破線と同じ高さの更新に追従し、壁の高さを含む範囲でカリングする。描画専用でコライダーは持たない。

    都市外への道路・線路・建物・土地区画の配置はテンプレートモード専用。背景地形の上もクリックとカーソル位置の対象になる（Unity入力制御 §2.1）。道路は完成時に都市境界で分割され、都市外部分は共通の都市外地区に所属する。経路は境界を越えて接続できる。都市外地区は道路網が離れても分割されない。都市外では建物の自動発生や自動入居、道路の自動延伸、設備の老朽化・修繕は行わない。

    variant 4「国境検問所」はテンプレート専用の建物で、TYPE_DEFAULT・is_bd=Trueとして扱う。都市境界のすぐ外で、都市から延びる道路の突き当たりに置く想定の既成モデル(間口110m×奥行き70mの固定底面。F3_既成建物のメッシュ生成)で、通常の建物描画と区画所属を使い、火災・倒壊・自動閉鎖・自動解体の対象にはしない。建物自身は輸出入や観光の発生機能を持たず、入居する陸路輸送・都市外旅客輸送拠点が担う。
