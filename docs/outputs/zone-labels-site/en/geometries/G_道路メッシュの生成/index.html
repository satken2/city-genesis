    道路メッシュの生成

    地上・地下のパスは PathManager の同じ生成・更新・キャッシュ・LOD・セル退避経路を使う。地下表示は TunnelSectionUtil.GetDrawSections が返す表示区間に完全埋設区間を含める。点列は CalculatePathPoints、モデルは PathMeshFactory を共用し、描画物はワールド座標を保った Paths コンテナへ配置する。区間の PathSection は地上／地下の表示と材質の扱いを区別し、独立した更新や寿命を持たない。地下のモデル・材質は元のままで、ホバーは既存の青い HighlightMaterial、解除時は元材質へ戻る。モデルを持たない埋設インフラは共通ファクトリで通常道路のフォールバックを選ぶ。施工中も同じ進捗別生成器を使い、未施工の地下の土は設計標高に置く。表示切替・コライダーの扱いは Unity表示モード を参照。

    送電線の専用描画（1101・1102）

    送電線は PowerLinePath がバリアント固有生成器として描画する。道路用のbody反復・柱の両端配置を使わず、アンカー間を pillar_spacing 以下へ均等分割し、鉄塔と同じ支持点から電線を張る。各径間の電線は両端を保持する放物線で、中央たるみを径間長の4.5%（最大6m）とする。モデルは実寸配置し、シミュレーション用の帯幅へ縮小しない。base_height を引いた描画基準と、バックエンドの標高・幅・接続判定は従来どおり分離する。

    大型1101は高さ38m、3段の腕と懸垂碍子、2回線6組の二導体と頂部の架空地線。小型1102は高さ17mの細身格子柱と3相・架空地線。通常は pillar_cap、接写は PathDrawContext.ResolvePrefab により pillar_cap_close を選ぶ。Farは主脚・腕・粗い斜材と簡略電線をコード生成し、地面の道路帯へ置換しない。body のFBXは制作見本で、専用生成器では使わない。

    共有ノードの姿勢・高さ・型は接続パスの逆引きから決める（大型優先、同型はpath_id順）。すべての接続電線が同じ取付点を参照する。PowerLineSupport は表示中の候補から最も詳細な支持構造を1基だけ表示し、所有パスのアンロード・LOD交換・破棄では残る候補へ引き継ぐ。ノード未確定のプレビューや中間支柱はパス固有。接続変更時は隣接する送電線を再生成する。

    電化線路・モノレールとの共有ノードと、発電所・変電所などのインフラ施設の接続端子は、大型1101・小型1102とも通常の鉄塔に代えて PowerLineRailGantry が四本の格子柱と四辺の格子梁を持つ受電架構（かご型）を生成する。施設端子は BuildingManager.TryGetInfraTerminalOwner の逆引きで識別し、ノードのインフラ財ビットだけでは判定しない。施設では端子ノードの絶対標高と共有送電線の水平接線を使い、柱の横位置は中心から大型5m、小型4mとする。

    線路接続の対象は送電線と同じ infra_products を流せる軌道パスで、単なる立体交差には配置しない。接続線路の最小path_idを基準に、未切断の中心線の高さと水平接線を使う。施設端子と線路接続が重なる場合は線路の配置を優先する。施設・線路の高さには送電線の base_height を差し引かない。

    線路接続の柱は道床・ホームの外縁から1.2m外側（中心線から最低でも大型5m、小型4m）に立て、前後の柱間を5mとする。近接線路の結合幅は線路と同じ TrackAdjacency の規則で架構の中央と前後を調べ、並走する線路の外側まで広げる。隣接候補も未切断の中心線を使い、交差点内の幅を含める。

    格子梁の下弦は基準面から大型8.4m、小型6.6m、梁の高さは0.72m。懸垂碍子の取付点は下弦から0.84m下で、前後の梁をたるみ0.39mのジャンパ線で結ぶ。線路接続ではジャンパ線を鉄道の門型梁下弦より0.5m以上上に保つため、下弦高さを最低8mとする。架空地線の取付点までの高さは大型9.54m、小型は施設7.74m・線路9.14mとなる。送電線の各導体と架空地線は架構の取付点へ張り、柱は各足元の地盤まで伸ばす。通常・接写・遠景で配置と取付点を揃え、格子と碍子の詳細度だけを変える。材質は既存の送電鉄塔と共有する。

    接続線路や近接線路の追加・幅や高さの変更・撤去でも、ノードの逆引きと既存の近接セル索引で関係する送電線を再生成キューへ積み、架構と電線の取付点を更新する。遠景も同じ再生成の対象である。

    施工中は橋脚期間に相当する最初の25%で鉄塔を順に表示し、その後の進捗に応じて径間単位で電線を張る。Normal・Close・Farで同じ配置計画を使う。検証は unity/Tests/PowerLines/run.ps1。

    LRT付き道路222・242・歩行者道303

    LRTの線路（道路上の222・242・303と専用軌道431）は、1本のパスが上下線2本の軌道を持つ左右対称の複線である。通常鉄道の軌道数2の複線（まとめた複線。線路メッシュの生成 §1.1）と同じ方式で、往路と復路が同じパスの左右の軌道を走る（通常鉄道は一方通行の単線2本を並べても複線を作れる。同 §8）。431の通行方向は双方向に固定される（通行方向）。軌道の横位置・レール踏面の高さ・停留所ホームの寸法はLrtRoadPartsを唯一の正とし、車両（車両の走行描画）・交差点のレールコネクタ・沿道設備・歩行者の帯（歩行者の描画）もここを参照する。

    222は幅24m・合計4車線、242は幅32m・合計6車線で、両側歩道各3m・中央分離帯1mを持つ。中央寄りの左右1車線は自動車とLRTの共用であり、車線数に別の専用軌道を加算しない（lanesは車線数で、軌道数ではない）。軌道中心は双方向のRoadLaneLayoutの最内車線中心（222は±2.5625m、242は±2.541667m）とする。一方通行へ変更しても軌道の物理位置は変えない。

    303は幅12mのトランジットモールで、中心から±1.75m（軌道中心間隔3.5m。431と同じ）に複線を埋め込む。舗装は段差のない平坦な帯で、中心から左右に、石畳の軌道帯（0〜3.25m。車体が通る範囲は3.02mまで）、白い境界帯（3.25〜3.45m）、暖色レンガの歩行帯（3.45〜5.8m）、縁（5.8〜6.0m）が並ぶ。架線柱は両側の歩行帯（±5.4m）に立てる。

    概要

    路上駐車の車両は道路メッシュへ結合せず、ParkedVehicleManager が既存車両モデルを別途描く。道路と共通の交差点切断済み中心線、マスターの全幅・歩道幅・中央分離帯幅、RoadPartHeights.BODY_ABOVE_SPLINE を使い、エポックによる台数の増減だけで道路本体を再生成しない。配置と表示上限は 車両の走行描画 を参照する。

    バックエンドの Path データから、道路の外観メッシュを組み立てて配置する仕様。

    道路の経路は始点・終点・ウェイポイントというアンカー点と、それらの間を結ぶ三次ベジエ曲線で定義される。フロントエンドではこのベジエ曲線を多数の点にサンプリングし、その点群をもとにメッシュを生成する。

    カーブを含む道路の描画には Dreamteck Splines ライブラリを使用し、サンプリング点群からスプラインを構築してメッシュパーツを配置する。

    パスの種類とジェネレータの対応

    PathMeshFactory がジェネレータの振り分けを行う。ジェネレータの選択は path_master の model_type で決まる（path_type ではない）。まず path_variant に固有のジェネレータがあれば最優先し、なければ model_type で切り替える。

    model_type ジェネレータ 生成方式
    default RoadPath スプライン + SplineMesh
    track TrackPath スプライン + SplineMesh（線路構成）
    none （なし） メッシュ生成なし（経路探索専用パス・公共交通の路線等）

    model_type が未指定の場合は、鉄道・モノレールを track、その他を default として扱う。

    本ドキュメントでは主に RoadPath（道路のスプライン方式）の詳細を説明する。線路・モノレール向けの TrackPath は同じ仕組みの上に線路固有のパーツ構成を持ち、N_線路メッシュの生成 で説明する。

    1. データフロー

    PathSummary の始点・終点・ウェイポイントと制御点から描画用点列を作り、地形追従を適用する。PathMeshFactory はバリアント固有・model_typeの順に生成器を選び、RoadPath が寸法・部品・材質を解決してスプラインに沿って配置する。描画メッシュとは別にクリック用コライダーを作る。

    polygon は占有領域で、描画には直接使わない。形状データの意味はパス形状、取得と描画の更新はデータロードに定義する。

    2. 三次ベジエ曲線による点群生成

    2.1 アンカー点と制御点

    パスの形状はアンカー点と制御点の組で定義される。アンカー点は曲線が必ず通過する点であり、制御点は曲線の入り・出りの方向と張りを制御する。

    各セグメントは三次ベジエ曲線 B(t) = (1-t)³·P0 + 3(1-t)²·t·P1 + 3(1-t)·t²·P2 + t³·P3 で表現される：

    • P0 = セグメント始点の位置
    • P1 = セグメント始点の出口制御点（control_out または自動計算）
    • P2 = セグメント終点の入口制御点（control_in または自動計算）
    • P3 = セグメント終点の位置

    制御点が未指定の場合は自動計算する。ウェイポイントのないパスは始点と終点を 1/3・2/3 に内分した位置（実質的に直線）、ウェイポイントを挟むアンカーは Catmull-Rom スプラインの接線（T_i = P_{i+1} − P_{i-1}、テンション 1/6、端点は片側接線）から計算する。これはバックエンドの制御点自動補完（A_パス形状.md の「制御点の自動補完」参照）と同一ロジックであり、バックエンドが永続化したウェイポイントの制御点（control_in / control_out）が API に含まれる場合はそれを優先使用する。

    2.2 セグメント構成

    ウェイポイントがない場合は始点→終点の単一セグメント、ウェイポイントがN個の場合はN+1セグメントになる。

    始点 → ウェイポイント0 → ウェイポイント1 → ... → 終点
  セグメント0    セグメント1       ...      セグメントN

    2.3 サンプリングと地形追従

    PathManager.CalculatePathPoints() は各セグメントを約1m間隔（TERRAIN_SAMPLE_INTERVAL）でサンプリングする。相対Y=0のアンカーで挟まれた区間では、サンプリングされた各点のY座標を地形標高＋RoadPartHeights.ROAD_SPLINE_OFFSET（0.1m）に追従させる。これにより、道路の中心線が地形の起伏に沿うようになる。相対Y≠0（高架・地下）の区間は地形追従せず、アンカーと制御点のY座標をそのままベジエ補間する。

    中心線サンプリングは1m間隔を基準とし、Extrudeタイル長は曲率適応（§4.3。急カーブ・起伏では1mまで詰まる）で、Dynamic地形の格子間の小さな尾根を長い弦でまたぐことによる埋没を抑える。これは描画用近似の密度であり、保存されたアンカー・制御点や相対高さの意味は変更しない。高架・地下・single_spanの追従除外規則も維持する。

    地形の高さキャッシュは同一XZ座標のみを共有する。1m単位に座標を丸めて別地点の高さを使い回すと、傾斜地で問い合わせ順によって路面が変わるため行わない。道路全幅の横断方向の造成はバックエンドが担い、描画側で縁石や断面を地形へ個別に吸着させることはしない。

    3. LOD（Level of Detail）

    道路中心線までの距離でClose / Normal / Farを選ぶ。Normalは無印、Closeは存在する _close パーツ、Farは簡易帯である。生成済みルートはデータ版・形状revision・LODをキーにLRUへ退避する。

    長さ256m以上の通常道路は、連続するスプラインパーツを SplinePartLod で区間化する。区間数は全長÷128mの切り上げ、境界は全体の固定パラメータ比率とし、カメラで動かさない。曲線上の実長は各区間で多少異なる。各区間が距離でLODを選び、戻ったときは生成済みGOを再使用する。Farの路面は同じ曲線を17点でサンプルした帯、細部パーツは非表示になる。区間のLODは、全区間で共有するカメラ移動の世代(4m以上の移動で進む)が変わるまで再評価しない。静止中の区間ワーカーは予算外のネイティブ待機で眠るので、共通予算を消費しない。路面本体を区間化した道路は、親を通常LODに固定して区間だけを切り替える(E_LOD処理「道路」)。

    保存された道路・経路探索・編集単位は分割しない。single-span、破線、折り返しなど独自の配置規則があるパーツはこの分割対象外。モデルがない場合の既存フォールバックを先に判定する。SplineMeshの生成は即時Rebuildとして共通生成予算へ計上する。

    遠景の帯・詳細区間外の残り帯・ノードの円柱は、Z-fighting 防止用の DepthOffsetLit シェーダーに差し替えた共有マテリアルを使う(Renderer.materials で個別に複製すると誰も解放せずに蓄積するため)。色の上書きは VisualModeObject がマテリアルの差し替えとプロパティブロックで行うので、共有しても他の道路へ波及しない。

    生成スケジューラー、区間ごとの8MiBキャッシュと全体512MiB上限は E_LOD処理 を参照する。

    4. スプラインによる道路形状の定義（RoadPath）

    4.1 描画点列と補間

    CalculatePathPoints が保存された三次ベジエをサンプリングする。交差点の切断は、この点列上の経路距離で行う。保存されたアンカー・制御点を移動して曲線を作り直すことはしない。

    4.2 スプラインの構築

    RoadPath.BuildSpline は曲線の点列を明示的な三次ベジエハンドルで補間する。内部はCatmull-Rom相当の接線、両端は残存点列の最初・最後の区間方向を使う。交差点も同じ区間方向を参照するため、別々の再補間による入口の回転を防げる。折れ線はLinearを使う。Dreamteck の Linear スプラインは各点の方向を前後の区間の平均で決める(linearAverageDirection)ため、角を含む折れ線を1本のスプラインに載せると角の後ろの区間全体の向きがずれる。GenerateLinearPathWithCorners がセグメントごとに独立したスプラインを作るのはこのためである。single_span は交差点計算でもアンカー間の直線として評価する。

    点列はワールド座標で渡し、UniformサンプリングとRebuildImmediateで直後の長さ・位置評価を確定する。この補間は描画用の近似であり、バックエンドの保存曲線や占有ポリゴンを変更しない。構築後の SplineComputer は無効化して返す(点を後から変えない前提。Evaluate・Project・CalculateLength は無効でも使える)。無効なので、生成後にスプラインの点やコンテナのワールド座標を変えても自動では再構築・再サンプルされない。形を変えるときは作り直す。

    4.3 SplineMesh によるパーツの配置

    スプラインが構築できたら、各パーツ（道路本体、区画線、歩道）をスプラインに沿って配置する。これには Dreamteck Splines の SplineMesh コンポーネントを使用する。

    SplineMesh も RebuildImmediate で構築した後に RoadPath.SealSplineMesh で無効化し、生成メッシュを IntersectionMeshOwner に所有させて GameObject の破棄と一緒に解放する(Dreamteck は生成メッシュを自分では破棄しない)。無効化により毎フレームの更新処理が走らない。

    SplineMesh の考え方は以下の通り：

    • メッシュパーツをスプラインに沿って並べる という基本的なアプローチ
    • パーツはスプラインの形状に合わせて自動的に変形（曲げ）される
    • 1つのパーツが短すぎてスプライン全体を覆えない場合、タイリング（繰り返し配置） される
    • SplineMesh はタイル内の頂点Z位置でしかスプラインを評価しないため、Z方向の分割が粗いパーツはタイルが弦（直線）近似になる。縦カーブ（尾根・谷）でパーツ同士が上下にずれて貫通・浮きが起きないよう、タイル長に上限を設けてタイル数を明示的に決める（メッシュ実寸ベースの autoCount は使わない）。
    • 曲率適応タイル長: 上限は一律ではなく、スプラインの最大曲率（水平・縦断とも。1m間隔のサンプルから折れ角÷区間長で推定）から、弦誤差 ≈ κL²/8 が許容値 0.02m（PathDrawContext.CHORD_ERROR_TOLERANCE）以下になるタイル長 L を選ぶ（PathDrawContext.ComputeAdaptiveTileLength。生成器が BuildSpline 直後に SetAdaptiveTileLength で設定する）。直線・平坦なら最大8m（ADAPTIVE_TILE_MAX。地形の微小起伏の取りこぼしを抑えるため無限には伸ばさない）、急カーブや起伏の大きい地形追従では MAX_EXTRUDE_TILE_LENGTH（1m）まで詰まる。一律1mだと直線道路でも著作長の数倍の頂点を敷き、道床のような密なパーツで頂点上限に当たるため。CreateSplineMesh の maxTileLength を既定（MAX_EXTRUDE_TILE_LENGTH）のまま呼んだパーツだけが適応値に置き換わり、明示的に 0（上限なし＝著作長のまま）を渡すパーツ（軌道・ホーム・駅舎の桁）には適用されない。
    • 頂点予算: SplineMesh 1個の生成頂点数は「パーツの頂点数 × タイル数」で決まり、Unity標準メッシュの上限（65535）を超えると Dreamteck が毎フレームエラーを出し続ける。RoadPath.SPLINE_MESH_VERTEX_BUDGET（60000、public const）を上限に、上限なし（著作長）のパーツは整数タイル単位で複数の SplineMesh（{パーツ名}_Sections）へ分割し、それ以外はタイル数をクランプする。パーツ1個で超える場合は生成を中止してエラーを出す。線路ノードのレールコネクタ（TrackPath.CreateRailConnectorObject）も同じ予算でタイル数をクランプする。

    4.4 スケールとオフセット

    SplineMesh に渡すパーツは、元のメッシュの寸法と道路の設計寸法が異なるため、適切にスケールを調整する必要がある。

    • X 方向のスケール: 設計幅 / メッシュの元の幅 を計算する。body は最上面から2mm以内の頂点の横幅と中心を使い、下部の桁やスカートの張り出しを除く（GetBodySurfaceBounds）。他パーツは全体の bounds を使う。body の上面は生成用の共有メッシュで Y=0 に補正するため、FBX の微小な原点誤差も接合に持ち込まない。ただし base_height を持つバリアント（送電線）はスプラインが地表に置かれ、モデル自体が電線の地上高を持つ規約なので、この補正を掛けず（normalizeBodySurface: false）全体 bounds で幅を測る（補正すると電線が地面に落ちる）。歩道とラインも、実際に採用したモデル系列のbody上面Yを引く（GetRoadPartMesh）。p2のように路面高0.5mが付属パーツにも含まれるモデルで、路面だけが下がって付属パーツが浮くことを防ぐ。フォールバック時は採用したパーツ側の系列を参照する。
    • 横方向オフセット: スプラインの中心線から左右にどれだけずらすかを、パーツの中心の位置として指定する。プレハブのピボットが中心にない場合（縁石原点の歩道など）は、メッシュ bounds の中心が指定位置に一致するよう生成側（RoadPath.CreateSplineMesh）が自動補正する。このため、プレハブのピボット位置が配置結果に影響することはない
    • Y 方向オフセット: スプラインからの高さ。値は RoadPartHeights の定数に集約されている（下表）

    高さの層構造（RoadPartHeights）

    道路は「スプライン点（地形+0.1m）」の上に各パーツをオフセットで重ねる2層構造で描画される。

    定数 値 意味
    ROAD_SPLINE_OFFSET 0.1m 地形追従スプライン点の地形からの浮かせ量（地形メッシュへの埋没回避）
    BODY_ABOVE_SPLINE 0.1m 道路本体のスプラインからの高さ。bodyプレハブの上面＝ピボット平面の規約なので、路面上面はこの平面（地表道路なら地形+0.2m）になる
    LINE_ABOVE_SPLINE 0.12m 区画線・センターラインの高さ（body上面の2cm上）
    CENTER_LINE_EXTRA 0.005m 中央の線を側線よりさらに浮かせる量
    SIDEWALK_ABOVE_SPLINE 0.1m 歩道の下端の高さ（body上面と同一平面。縁石の立ち上がりはプレハブ形状）
    WALL_ABOVE_SPLINE 0.1m 防音壁・ガードレールの下端の高さ

    交差点メッシュもこの体系に従う（§11）。

    5. マスターデータと寸法パラメータ

    5.1 寸法の取得

    道路の寸法は MasterDataStore のパスマスターデータ（PathMasterItem）から取得する。path_variant をキーにしてマスターデータを検索し、以下のパラメータを得る。

    パラメータ フィールド 単位 デフォルト
    道路幅 width m 4.0
    歩道幅 sidewalk_width m 0.5
    区画線幅 side_width m 0.5
    防音壁・ガードレール幅 wall_width m null（配置なし）
    中央分離帯幅 center_width m null（配置なし）
    街路樹の標準間隔 tree_spacing m null/0なら20m（設置有無はPathの選択）

    歩道幅・区画線幅・防音壁幅・中央分離帯幅・街路樹間隔は null 許容であり、null の場合はデフォルト値を使用するか、その機能をスキップする。街路樹の有無は間隔とは独立し、Pathの保存値で決まる（§8.6）。

    5.2 オフセットの計算

    道路は中心線に対して左右対称に構成される。各パーツの配置位置は以下の考え方で計算する。

    width は道路全体の幅である。歩道は道路の端に覆いかぶさるように配置する（歩道幅を道路幅に足すのではなく、道路幅の中に歩道が含まれる）。

    中心線
    │
    ├──────────── width ────────────┤
    │                               │
    区画線  歩道    道路本体    歩道  区画線

    各パーツのオフセット（中心線からパーツ中心までの距離）：

    パーツ オフセット計算 値の例 (width=4, sidewalk=0.5, side=0.5, wall=0.3, center=0.6)
    道路本体 0 0
    中央分離帯 0 0
    歩道 (width/2) - (sidewalkWidth/2) 1.75
    区画線 (width/2) - sidewalkWidth - (sideWidth/2) 1.25
    防音壁・ガードレール (width/2) + (wallWidth/2) 2.15

    オフセットは絶対値で計算し、左右それぞれに +オフセット と -オフセット で配置する。オフセットは常にパーツの中心の位置を表す（プレハブのピボットが端にあっても生成側で bounds 中心基準に補正される）。

    左右非対称パーツのミラーリング規約

    歩道は左側用（縁石＝道路中心側が +X）で、左側が原型・右側がXミラー。壁は右側用（道路中心側が -X）で、右側が原型・左側がXミラー。交差点内でもこの向きを維持する。

    5.3 歩道付き道路橋（p223）

    幅12m、両側歩道各2.5mの2車線コンクリート桁橋。model_type=default の RoadPath で組み立て、single_span=false として曲線を維持する。height_editable=true、follow_terrain=false が既定で、橋脚間隔は40m。接道可否は frontage_allowed=false とし、地表に置いても沿道区画生成や接道指定の対象にはしない。Unityはマスターの同属性を参照し、沿道生成モードのクリック・ホバー対象から除外する。

    パーツ 構成・著作寸法
    body 幅12mの舗装・床版と4本の縦桁。路面上面が原点、最下部は-1.05m
    sidewalk 幅2.5m、歩道上面0.20m、車道側縁石0.23m。左側用（中心側+X）
    line 幅0.5mの区画線。既存街路の区画線マテリアルを共有
    wall 幅0.3mの地覆と金属製高欄。路面から約1.3m、右側用
    pillar 左右2本のコンクリート柱。天端0mから下へ4mの一様断面で、地盤まで高さ倍率を掛ける
    pillar_cap 幅10mの受け梁。路面原点から下へ1.9mまで、実寸のまま配置

    連続パーツは進行方向2.5mのタイルとし、既存の PATH_ASPHALT・PATH_CONCRETE・PATH_METAL を共有する。道路設備（街路樹・街灯・柵・電柱）の個別設定は許可しない。高欄は道路設備の柵ではなく、常設の wall パーツである。

    制作元は blender/paths.blend の p223/* コレクション。Unityのミラープレハブは通常の自動生成に従う。

    5.4 歩行者専用道路301・歩行者吊り橋302

    301にはランタン型街灯と3本横桟の柵を用意し、新設時は両方を標準で有効にする。道路詳細の設備設定で個別に「なし」へ変更できる。既設道路の保存済み設備値は自動変更しない。柵は専用のfenceパネルで、支柱は描画時に生成する。独立した歩道のない301では舗装端から内側0.12m、街灯は内側0.3mに置く。

    両方とも幅4m、type=3の歩行者専用パスで、車道の区画線や追加の歩道は持たない。301の路面代表材質はPATH_PAVING_STONE、302はPATH_CONCRETE。301は地形追従する舗装道で、既存のランタン型街灯を個別設定で選べる。bodyは厚さ0.2mの箱で、body_closeも同じ12三角形。石と目地はテクスチャで表現し、個別の石のポリゴンは持たない。

    302は高さ編集可能・非地形追従の直線吊り橋で、single_spanによりアンカー間を床版1枚で結ぶ。最大径間300m、最大勾配15%、建設費係数3を初期値とする。bodyはコンクリート床版と2本の金属縦桁、wallは常設の高欄でwall_width=0.2m。設備としての柵や街灯とは独立し、個別設備は許可しない。接道による沿道区画は生成しない。

    主塔は専用towerパーツで、柱中心は±2.8m、著作時の塔頂は12m。既存のSuspensionBridgeGeneratorが各径間の20%・80%に配置し、高さを径間長へ合わせる。ケーブル・吊材・地盤までの脚は同生成器の共通寸法で生成する。8m未満の短い区間には主塔とケーブルを置かない。

    舗装は通常・接写とも12三角形、302の高欄はNormalで40頂点/m以内に収める。近景では同じboundsのbody_close・wall_closeへ切り替える。302のbodyは長手方向の横目地を持たず、single_spanによる伸長でも大きな目地模様にならない。Unityのプレハブは通常の自動生成に従う。

    6.4 パーツプレハブのモデリング規約

    ロープウェイ乗り場602と鉄道・モノレール駅451/461・462・502の完成時Farは、共通の道路帯に代えてFarPlatformPathが簡易立体を生成する。通常モデルの材質と屋根・壁の輪郭を保ち、小物を省く。詳細はN文書のLOD節を参照。

    ロープウェイ乗り場602のstation_shellもCreateSplineMeshの接写解決に対応し、station_shell_closeで中央のベンチ・ごみ箱、壁付き照明、配管、ガラスの金具を表示する。通常版とbbox・原点・材質構成・8m周期を共通にし、中央設備は幅1m内へ収める。黄線と搬器の通過空間を空け、ケーブル・滑車・橋脚には通常版を使う。

    生成側はプレハブメッシュの bounds を実測して配置を補正するため、横方向のピボット位置は自由だが、以下の規約は守る必要がある。

    7. フォールバック機能

    7.1 基本考え方

    建物のフォールバックと同様に、まずバリアント固有のパーツを探し、見つからなければタイプのパーツにフォールバックする。

    交差点のbody厚さ参照と歩道コネクタも同じ順序で解決する。バリアント固有パーツの不在だけでは警告せず、タイプ側へのフォールバックも失敗した場合にモデル不足を警告する。

    7.2 フォールバック階層

    パーツごとに以下の順序で検索し、最初に見つかったものを使用する。

    1. バリアント固有パーツ: Models/Paths/p{path_variant}/{position}
   （描画LODが Close なら同フォルダの {position}_close を先に試し、無ければ無印）
       ↓ ない場合
2. タイプパーツ: Models/Paths/p{path_type}/{position}
   （同じく Close なら {position}_close → 無印）
       ↓ ない場合
3. そのパーツをスキップ（道路本体以外）

    ここで、path_type は PathMasterItem.type から取得する。この解決は PathDrawContext.ResolvePrefab に集約されており、順序は close → 無印（バリアント）→ close → 無印（タイプ）である。バリアントに _close が無くても無印のバリアントパーツがあればそれを使い、タイプ側の _close へは進まない（バリアントの外観を優先する）。

    道路本体（body）が見つからない場合は、道路形状（スプライン）に沿った白い板（ストリップメッシュ）を動的生成して描画し、ゲームプレイが継続できるようにフォールバックする。その他のパーツはオプショナルであり、パーツがなくても道路本体（または白い板）だけでも機能する。

    中央分離帯（center）の特別なフォールバック

    中央分離帯のパーツ（center）が見つからない場合、センターラインのパーツ（line）を代わりに使用する。これにより、中央分離帯の3Dモデルを用意しなくても、区画線で中央の分離を表現できる。

    8. 各パーツの生成詳細

    8.1 道路本体（body）

    スプラインの中心線に沿って、道路全体の幅で配置する。

    • リソースパス: Models/Paths/p{variant}/body（フォールバックあり）
    • 幅: マスターデータの width
    • オフセット: なし（中心）
    • 高さオフセット: BODY_ABOVE_SPLINE（0.1m）。bodyプレハブはピボット＝路面上面の規約なので、路面上面がスプライン+0.1m（地表道路なら地形+0.2m）になる
    • SplineMesh の設定:
    • X スケール = width / メッシュの元の幅
    • タイル数 = クリップ後のスプライン長 / min(メッシュZ長, 曲率適応タイル長)（§4.3。縦カーブの弦誤差を抑えるため明示指定）

    single_span モード（single_span = true）

    single_span が true のバリアントでは、body の配置方法が変わる。地形追従で曲率適応タイルごとに細分化配置するのではなく、柱（アンカー点）間を1枚のbody引き延ばしで接ぐ。高架橋や桁橋のように、路面が地形の起伏に関わらず支柱間で水平に架かる構造物を表現するために使う。

    • スプラインの構築: アンカー点（始点・ウェイポイント・終点）のみでスプラインを構築し、地形追従の細分化（SubdividePointsWithTerrain）を行わない。曲線パス（curved=true）も single_span の場合は直線セグメント化して扱う（ベジエ曲線の水平形状は無視され、アンカー点間の直線になる）。
    • body のタイル数: count = 1。SplineMesh はメッシュのZ頂点をスプライン始点・終点に写像するため、body は両端を結ぶ弦（直線スパン）になる。Z方向の分割を持たないプレハブ（bodyは10mの箱）では、アンカー点間の直線的な床板として描画される。
    • その他のパーツ（line / sidewalk / wall 等）: body と同じスプライン（アンカー点のみ）に沿って配置されるため、body と一貫して地形に追従しない。タイル数は通常通り曲率適応タイル長に基づく。
    • ウェイポイントがある場合: セグメントごとに独立したスプラインが作られ（GenerateLinearPathWithCorners と同じフロー）、各セグメントの body が count = 1 で柱間を接ぐ。

    8.2 中央分離帯（center）

    道路の中央に配置する分離帯。中央分離帯がある場合、センターラインは省略され、代わりに中央分離帯と側線の間にレーン境界の点線が配置される。

    • リソースパス: Models/Paths/p{variant}/center（フォールバックあり。パーツがない場合は line を代用）
    • 幅: マスターデータの center_width
    • オフセット: なし（中心）
    • 高さオフセット: 0.1m
    • レーン境界線: 中央分離帯の端から側線までの距離を片側レーン数で等分し、各境界に点線を配置する。例えば4車線なら片側2レーンなので1本、6車線なら片側3レーンなので2本の点線を配置する。

    8.3 路面標示

    PATH_STREET / PATH_MOTORWAY かつ side_width > 0 の道路は、Custom/RoadSurface がbodyの上面へ標示を合成する。白線用の板・SplineMesh・Rendererを追加しないので、路面と標示の深度競合や勾配上の浮きは生じない。元の路面の色・テクスチャ・法線・ライティングを使い、標示部分の色と粗さを変更する。line FBXとその高さ定数は他の生成経路の互換用に残すが、対象道路では読み込まない。

    RoadMarkingContext はスプラインごとに距離座標sと横断座標tを保持する。bodyの生成時にUVチャンネル3へ(s,t,上面フラグ,0)を設定し、元の材質のUVは維持する。側面・底面には標示を描かない。交差点ではノード原点からのXZを使用し、上面と追加した桁殻を区別する。

    Custom/RoadSurface の色描画パスは Offset 0, -1 で一定量だけ深度を補正する。傾きに比例する補正は使わない。bodyは端面を持つ部品の反復なので、縦面の深度まで傾きに応じて手前へ出すと、内部の端面が舗装を覆って横筋になる。路面の頂点や部品の端面は変更しない。

    • 側線・中央線・車線境界線はシェーダーで距離から計算する。幅はmax(0.1m, side_width * 0.3)、側線の位置は±((width/2) - sidewalkWidth - sideWidth/2)。
    • 点線は2m描画・4m周期。画面微分による被覆率で縁をなじませ、周期が画素より細かくなると平均の被覆率へ移行する。
    • 横断歩道・停止線・方向矢印・幅移行の線はRoadMarkingPlanの二次元三角形群から画像へ焼き込む。このメッシュは生成用であり、シーン上の道路には重ねない。
    • 線ごとに描く距離の範囲（_RoadBandSpans）を持ち、路側線を区間ごとに描き分けられる。高速道路の本線とランプの結合区間（§11.7）では、本線のランプ側の路側線をその区間だけ点線にし、ランプの本線側の路側線をその区間だけ描かない。描き分けは body の生成時にシェーダーへ渡すので、body より先に決める。
    • side_width == 0 の道路には標示を生成しない。

    舗装路と未舗装路・石畳が混在し、交差点の代表材質にCustom/PathDirt / Custom/PathPavingが選ばれた場合、交差点内部はその専用描画を維持して標示を省く。接続する舗装道路の標示は通常どおり描く。

    車線境界と車線中心の共有定義

    RoadLaneLayout（RoadPath.cs）は、歩道と側線を除いた走行帯の外側境界を計算し、区画線と車両描画の両方へ供給する。道路全幅を車線数で割る方式は使わない。車線中心の詳細は車両の走行描画 §O.4 を参照。

    • 双方向の1車線道路には中央線を引かない。
    • 双方向の2車線道路は中央に点線、偶数4車線以上は中央に実線と片側の車線境界に点線を引く。
    • 中央分離帯がある場合は中央線を省き、分離帯と側線の間を等分した境界に点線を引く。分離帯モデルの取得成否で車線位置を変更しない。
    • 奇数3車線以上の双方向道路は中央の転回用帯を確保し、その両端と通常車線の境界に点線を引く。
    • 一方通行は走行帯全幅を全車線で等分し、各境界へ点線を引く。

    交差点の進入部

    RoadMarkingRules は完成済み道路の接続、一方通行、左右通行から進行可能な方向を求める。完成済み道路が3本以上接続する街路で、描画区間が16m以上あれば停止線を配置する。接続先にも歩道付き街路がある場合は、切断端から1〜3.5mに横断歩道を置き、中央分離帯を避ける。停止線は横断歩道ありで5m、なしで1.5m。交差点手前の最大18m（区間長の40%まで）の車線境界を実線へ変え、横断歩道内の内部線を省く。

    25m以上の区間には切断端から10mに方向矢印を置く。左右通行に応じ、外側車線を近い側への転回、内側車線を対向車線を横切る転回へ割り当てる。片方向2車線では外側を直進兼用、3車線以上では中間を直進用にする。該当方向がない車線には可能な方向を割り当てる。一方通行の退出側には停止線と矢印を描かない。短い区間やトンネルの描画用分割端・折れ線の内部端には進入部を追加しない。

    矢印の基準点に対し、直進の先端は前方1.65m、左右の先端は前方0.35m・横1.05mに置く（狭い車線では全体を縮小）。左右の枝は基準点の手前0.2mから分岐し、先端三角形の底辺中央へ短い横向きの軸で接続する。直進と左右の先端を離して、兼用矢印の内側に閉じた穴を作らない。直進を許可しない矢印の中央軸は分岐点で止め、方向指定なしでは図形を生成しない。

    これは既存の車線への進行方向の割り当てであり、交差点手前の道路を拡幅して車線を増やす処理ではない。信号の現示・優先道路の判定や任意の交差点全体への誘導線生成は行わない（交差点の信号機は装飾として置く。§11.8）。一般車とバスは同じ方向割り当てを参照する（車両描画）。

    PathManager は接続道路ID・種別・バリアント・完成状態・通行方向・接線・左右通行の署名を比較する。切断位置が変わらない接続変更でも隣接道路を再生成し、古い矢印を残さない。標示画像は内容署名で再利用し、都市全域を焼き直さない。

    画像の保持と検証

    RoadMarkingSurface が既存Rendererの共有材質とMaterialPropertyBlockを管理し、RoadMarkingAtlas が32m四方のページを保持する。解像度・メモリ・固定区間LODとの関係は LOD処理 を参照。標示画像が未生成・容量不足の間も側線などの解析的な線は表示する。

    unity/Tests/RoadMarkings/run-unity.ps1 は独立したURPプロジェクトで実FBXの道路・交差点・勾配を描画する。真上・斜め・低い視点の道路を、内部端面だけを除いた参照画像と比較して横筋を検出する。矢印は全7種の方向組み合わせの描画画像から、先端と軸の連結、閉じた穴の不在、転回専用の中央軸を検査する。シェーダー、表示モード復元、キャッシュ再利用、容量超過時の縮退、長い道路の距離座標、セッション終了時の解放も検証する。

    8.4 歩道（sidewalk）

    道路の端に配置する。歩道は左右で形状を対称にするため、右側はメッシュを X 軸で反転させる。

    • リソースパス: Models/Paths/p{variant}/sidewalk（フォールバックあり）
    • 幅: マスターデータの sidewalk_width
    • 左側オフセット: -(width/2) + (sidewalkWidth/2) = -(width/2 - sidewalkWidth/2)
    • 右側オフセット: +(width/2 - sidewalkWidth/2)
    • 高さオフセット: SIDEWALK_ABOVE_SPLINE（0.1m）。下端がbody上面と同一平面に接し、縁石の立ち上がりはプレハブ形状で表現する

    歩道のミラーリング

    歩道パーツは左側用（縁石＝道路中心側の面が +X 側）として作り、左側はそのまま、右側は X 軸で反転（ミラー）して配置する。壁の右側用規約とは異なる。

    ミラーリングの処理内容： 1. 頂点の反転: 全頂点の X 座標を -1 倍する 2. 法線の反転: 全法線の X 成分を -1 倍する（面の向きを正しく保つ） 3. 三角形の反転: 三角形インデックスの順序を反転させる（カリング方向を修正する）

    この3つの処理を組み合わせることで、反転後も面が正しい向きを向く。頂点反転で裏返った面を、三角形反転で元に戻すという考え方である。

    8.5 防音壁・ガードレール（wall）

    地上・開削区間の左右端に配置する壁または柵。歩道の外側に設置される。

    • リソースパス: Models/Paths/p{variant}/wall（フォールバックあり）
    • 幅: マスターデータの wall_width
    • オフセット: ±((width/2) + (wallWidth/2))
    • 高さオフセット: WALL_ABOVE_SPLINE（0.1m）
    • 左右対称: 右側用パーツの規約。右側はそのまま、左側は X 軸で反転（ミラー）して配置する
    • オプショナル: wall_width が未設定（0以下）の場合は描画しない

    地下専用の側壁（wall_underground）

    完全埋設区間では地上用の wall を省き、wall_underground を道路の両外側へ敷く。区間は PathTunnelParts が坑口と同じ TunnelSectionUtil の深さ・地形追従規則から求める。地上で壁を持たない道路も対象とし、壁幅は正の wall_width、未設定なら0.3mを使う。

    専用モデルは Models/Paths/p{variant}/wall_underground → p{type}/wall_underground の順で解決し、接写は通常の _close 規約を使う。モデルは下端を原点とする右側用の壁だけを持ち、高さをパスのクリアランスに合わせる。通常用の wall へは戻さない。未定義なら既存の PATH_CONCRETE 材質で、路面からクリアランス高さまでのコンクリート壁を生成する。壁の内面を道路外縁に合わせ、左側をXミラーする。連続パーツの曲率適応・頂点数予算・LODは他の壁と共通である。

    本線とランプ・並走線路の結合部では、通行口をふさがないよう既存の側別の壁省略区間を使う。駅ではホーム外縁より外側へ置く。施工済み区間にも同じ地下壁を敷き、未施工部分の土には壁を加えない。

    ceiling_underground は同じ区間のクリアランス高さで、ホームを含む左右の壁の内面間へ張る。原点高さ0の片面モデルとし、法線と三角形の表向きを下へそろえる。材質は裏面をカリングするので、見下ろしでは内部が見え、トンネル内からは天井が見える。解決順と接写規約は地下壁と共通で、専用モデルが無ければ PATH_CONCRETE の下向きの面を生成する。

    地下壁の高さ・天井の上下からの描画・地上壁との切り替え・屋外設備の省略は unity/Tests/Underground/run.ps1、LRT各種の地下壁・軌道・架線柱・ホーム上屋の省略は unity/Tests/Lrt/run.ps1 で検証する。

    8.6 道路ごとの付帯設備

    完全埋設区間には街路樹（中央分離帯を含む）・街灯・電柱とその配線・地上機器ボックスを置かない。保存済みの設備選択は維持し、地上・開削区間だけで使用する。LRTの架線柱も同じ深さ規則で省き、軌道と架線は残す。

    付帯設備は Path の streetlight_type（街灯）、fence_type（歩車道境界の柵）、street_tree_type（街路樹）、utility_mode（配線方式）で選択する。各値は保存対象で、0は明示的な「なし」。種類は現在0/1（なし/標準）、配線方式だけ0/1/2（なし/架空/地中）を持つ。費用・治安・電力供給への効果はまだ持たない。

    道路マスターは各項目の *_allowed と default_* を持つ。未舗装路201は街灯を設置不可とし、設備値が残っていても描画しない。配線方式は選択可能で、架空配線では電柱と電線を描画する。地中配線でも地上ボックスは配置しない。初期値は新設時にエンティティへ確定保存し、以後のマスター初期値変更で既存道路の設備は変わらない。tree_spacing は有無ではなく標準の配置間隔で、未設定または0なら20mを使う。基本断面（歩道幅など）と外側の構造壁 wall は従来どおり道路マスターで決まる。

    RoadEquipmentGenerator は切断済みスプラインの両端から3mを空け、距離に基づいて配置する。街灯は24m間隔・開始位相6mで、極小路地211と1車線生活道路212は右側のみ、それ以外は両側、電柱は32m間隔で右側、地上機器ボックスは64m間隔で右側、街路樹は標準間隔の半分だけ開始位相をずらして両側に配置する。ここでの右側はパスの始点→終点を基準とする。個別の左右指定は持たず、向きを反転して結合した場合は再配置される。

    電柱/ボックス→街灯→街路樹の順に位置を確定する。3mグリッドの近傍検索で既存設備から2m（街路樹は3m）未満の候補を省略する。歩道がある道路では歩道中央、なければ道路端から0.3m内側に置き、接地高さは路面原点へ補正済みの床メッシュを使い、設置する横位置で三角形の上面を求める。bodyの未補正bounds上面や、歩道全体の最高点（縁石）を使ってはいけない。歩道の原点補正は採用モデルと同系列のbodyで行い、道路本体と同じ GetRoadPartMesh を使う。スプラインからの高さオフセットはワールド上方向、歩道の立ち上がりは断面法線方向に加える。設備は道路の勾配によらずワールド上方向へ直立する。長さ6m以下の描画区間には配置しない。

    柵は歩道に含めず、歩道がある場合は歩車道境界から歩道側へ0.12m、歩道がない場合は舗装端から内側へ0.12mの位置に独立生成する。設置可否はfence_type_allowedで決め、歩道の有無だけでは制限しない。支柱は最大2m間隔で直立し、横桟は支柱間を結ぶ。支柱(0.07m角)は中心位置の歩道上面へ接地するので、歩道幅へ伸縮した後の縁石と歩行面の段差が歩車道境界から0.085〜0.155mの範囲に来ると支柱の片側が浮く。歩道パーツの段差位置はこの範囲を避けて著作する(p222/p242は歩道3mで0.16m)。終端では支柱と桟を閉じ、交差点内部の歩道コネクタへは接続しない。交差点・折れ線の角・地下道の描画区間分割では、それぞれの描画区間に端部余白を設ける。既存の外側 wall の交差点接続は変わらない。

    モデルは Models/Paths/p{variant}/{part} → p{type}/{part} の順で解決する。点配置パーツは streetlight / utility_pole / utility_box / tree。点設備は接地面を原点に実寸で著作する。Blenderでは右側用として灯具を-Xへ向けるが、FBXの軸変換でUnityのX符号が変わるため、配置時は読み込み後のbounds中心Xから張り出し側を判定し、道路内側へ向ける。左側はさらにヨー180度回転する。旧共通モデルの原点ずれも考慮し、点設備のメッシュ下端を床へ合わせる。fence は支柱を含まない横桟/パネルで、高さ・横幅を保持しZ方向だけ支柱間長へ合わせる。標準支柱はコード生成される。

    モデルがない設備は簡易形状で表示する。簡易形状は道路・材質ごとに結合し、生成Meshは IntersectionMeshOwner が解放する。専用マテリアルは PATH_EQUIPMENT_METAL / CONCRETE / LAMP / LEAVES（いずれも接頭辞 PATH_EQUIPMENT_）で差し替え可能。設備にクリック用Colliderやリアルタイム光源は追加しない。遠景は従来の簡易道路表示のみ。

    架空配線の電線は同一描画区間内で隣接する実配置電柱の接地点+7.6mを結び、中央で0.4m垂らす。専用電柱もこの接続高さに合わせる。交差点を跨ぐ接続、建物への引き込み線、地中配線との接続設備は生成しない。地中配線では電柱と電線を省き、ボックスだけを別間隔で置く。

    道路詳細パネルの「道路設備」タブで選択し、「適用」でPATCH後に差分リロードする。変更は設備選択のみに作用し、道路の基本断面・経済値を変えない。分割時は両側に設定を継承し、異なる設備設定の結合は拒否する。造り替え先に設置できない設備がある場合は、先に設備を外す必要がある。

    道路詳細は経済主体詳細と共通のタブ表示を使う。「基本情報」に所属地区・線形指標・状態(耐久度・騒音・大気汚染)と交通・速度設定(制限速度・利用率・路上駐車量・交通量)を、「道路設備」に設備設定をまとめる。設備非対応で既設設備もないパスでは設備タブを表示しない。駅舎には「駅情報」、計画中・建設中・解体中には「建設工事」を追加する。着工前は基本情報・設備を省略し、着工前・建設中の初期選択は建設工事とする。タブ切り替えだけでは設備の未保存の入力と制限速度の反映待ちの入力を破棄しない。基本情報タブの表示内容は3_道路網の「パス詳細での表示」を参照。

    8.7 柱（pillar）とキャップ（pillar_cap）

    高架道路など、路面が地面から離れているパスに対して、路面を支持する柱（およびキャップ）を配置する。これらは height_editable=true のバリアントに対してのみ配置される。

    • リソースパス:
    • 柱: Models/Paths/p{variant}/pillar（フォールバックあり）
    • キャップ: Models/Paths/p{variant}/pillar_cap（フォールバックあり）
    • 配置対象: height_editable=true かつ pillar_spacing が設定されているバリアント。地下パスには配置しない。「路面と地表の差 + base_height」が0.1m以下の地点（地上区間・切り通し）には柱もキャップも置かない。base_height を持つ送電線はスプラインが地表にあってもキャップ（鉄塔）を置く。

    配置間隔

    スプラインに沿って配置する。各セグメント（始点→ウェイポイント、ウェイポイント→ウェイポイント、ウェイポイント→終点）について以下のルールで配置する。

    • パス全体の開始点と、各セグメントの終点に配置する（これにより、開始点・中間アンカー点・終了点のすべてに配置される）
    • セグメントのスプライン上の長さが pillar_spacing を超える場合は、その間隔で追加配置する

    他の道路・線路との干渉回避

    配置候補の柱本体または上部キャップが他の道路・線路の通行空間に重なる場合、通常橋脚を置かず、門型用の柱と横梁があれば門型橋脚で通行帯をまたぐ。門型パーツが無い場合や門型も干渉する場合は、その候補を省く。進行方向の配置位置と間隔は変えず、始終点・中間アンカーも同じ判定に従う。省略により pillar_spacing より長い無柱区間が生じることは許容する。道路・線路・工事中の柱は共通の RoadPath.GeneratePillars の内部処理を使う。

    PillarClearance は、子メッシュの変換と配置時の回転・スケールを反映した柱／キャップの bounds を別々に評価する。水平面は外接円、道路側は中心線＋半幅の帯として近似し、水平距離に0.25mの余裕を加える。高さは道路の描画路面からマスターの height までを通行空間とし、柱／キャップの高さ範囲との重複を調べる。斜路は線分上で高さが重なる区間だけ距離を評価する。低い道路の上方にあるキャップだけの張り出しや、十分深いトンネル、橋脚より上の道路では省略しない。同じ高さで接続する道路の路面はキャップ上端より上にあるため、接続だけを理由に柱を省略しない。

    PathManager.GetPillarObstacles が通過セルと隣接セルから候補を絞り、最新データの切断前中心線から通行空間を作る。道路幅は歩道込みの全幅、駅はホームの左右張り出しの大きい方を両側に加えた保守的な幅を使う。自分自身、インフラや描画なしのパスは対象外。計画・工事中の道路もデータが登録されていれば対象になる。描画用点列キャッシュやコライダーには依存せず、相手が未描画・Farでも判定する。

    新規登録・版／状態変更・削除時は、変更前後の近隣にある橋脚付きパスの描画revisionを無効化し、同一フレームのデータ更新とLODバッチの終了後に既存の再生成キューへ送る。下の道路の追加で柱が消え、移動・撤去で柱が戻る。通過セルの登録は描画前のデータ登録時に済ませ、曲線はアンカー間の直線ではなく既存の平面ベジエ点列から求める。

    この判定は描画上の近似であり、パスの保存形状・接続・建設可否は変更しない。外接円・ホーム幅の近似により、実メッシュが触れていなくても近接する柱が省かれる場合がある。検証は unity/Tests/Pillars/run.ps1 と run-unity.ps1。

    門型橋脚の組み立て

    PortalPillar は通常橋脚が干渉したときだけ、pillar_leg（柱1本）を左右に1個ずつ、pillar_crossbeam（横梁）を1個配置する。各パーツはバリアント→タイプの順で解決し、両方がそろったときに有効になる。現行モデルでは鉄道共通の p4 に用意する。道路やモノレールのタイプ既定には用意していない。レンガアーチ高架は専用生成器を使うため、この置き換えを行わない。

    • 柱1本は1.5m幅・1.8m奥行き・著作高さ8mの一様断面で、天端を原点にする。横幅・奥行きは保ち、各柱の設置位置の地面まで高さだけを伸縮する。
    • 横梁は著作長12m・奥行き2m・厚さ1.2mの一様断面で、上面を原点にする。横方向だけ柱の外端間へ伸ばし、厚さ・奥行きは保つ。門型全体の一様拡大や実行時の形状生成は行わない。無印のみを使う。
    • 横梁の上面は、通常の pillar_cap の最上部（配置倍率込み）へ合わせる。キャップが無ければスプライン高さに置く。通常の柱とキャップを置き換えるので、二重に重ねない。
    • 左右の柱は通常キャップの幅を支えられる位置を初期値にし、通行空間を抜ける方向へそれぞれ外へ移す。移動量は左右で異なってよい。横梁の中心は柱間の中央になり、片側へずれた道路も支える。
    • PillarClearance.FindPortalOffsets は、柱の外接円と0.25mの余裕で通行帯を広げ、線分を柱の高さ範囲と横断面の前後範囲で切って、横方向へ投影する。重なる帯を順に抜け、離れた道路まで一つの梁でまたがない。歩道込みの道路幅・駅のホーム幅・斜路の高さは通常橋脚と同じ通行空間から取得する。
    • 横梁と左右の柱を、配置後の bounds で個別に再検査する。一つでも通行空間に干渉する場合、柱を地面から立てる高さが無い場合、柱の外端間が PortalPillar.MaxSpan（描画上の上限40m）を超える場合は、一式とも置かない。低い高架の梁を通行空間へ押し込まない。

    完成時と施工中は同じ門型を使い、施工中は左右の柱と梁の3パーツで1つの施工単位になる。下の道路の追加・変更・撤去による既存の再生成通知が、通常橋脚と門型の切り替えにも働く。保存形状・建設可否・通行容量には影響しない。モデル原本は blender/paths.blend、実FBX・幅8/24/32m・低い高架・長すぎる梁・左右で異なる地面高・施工単位の検証は unity/Tests/Pillars/run-unity.ps1。

    柱とキャップの配置とスケール

    • 垂直保持: 柱・キャップとも地形の傾斜に追従して斜めに立たず、常にワールド上方向に対して垂直に立つ。回転は進行方向の水平成分から導出したYawのみ（ピッチ・ロールは0）とする。
    • キャップ（pillar_cap）の配置:
    • プレハブが存在する場合、スプライン上の路面位置（sample.position）にYスケールを変更せずにそのまま配置する。
    • 原点（ピボット）は路面原点（上端）とし、モデルは -Y 方向に厚みを持つものとする。
    • キャップの厚み capThickness は、プレハブの MeshFilter の bounds から -bounds.min.y として動的に計算される。
    • 柱（pillar）の配置:
    • プレハブが存在する場合、キャップがあるときは capThickness 分だけ下方向（常に Vector3.down）にオフセットした位置に配置する。
    • 柱の原点（ピボット）も路面原点（上端）とする。
    • Yaw-only 回転でローカルY軸がワールド上方向と一致するため、Yスケールにオフセット後の位置からその位置の地面標高までの高さをそのまま適用し、柱の下端が地面に接するようにする。
    • 残りの高さ（柱を配置すべき高さ＝路面と地表の差。base_height は含めない）が 0.1m 以下の場合は、柱（pillar）本体は配置せず、キャップのみを配置する。

    プレハブの著作規約（Yスケールの帰結）

    Yスケールは「柱を配置すべき高さ（m）」そのものを倍率として掛ける。著作寸法がそのまま倍率になるため、モデル側は次の作法で作る必要がある。

    • 柱（pillar）の天端は必ず原点（ローカル Y=0）に置く。 天端を原点より下に著作すると、そのオフセットにも倍率が掛かって沈むため、天端Y × 高さ < −高さ が常に成り立ち、どんな高さの高架でも橋脚が丸ごと地面より下に潜って一切描画されなくなる。
    • 柱の下端は、想定する最大の高架高さぶん（既存アセットは 2〜8m）だけ下方向へ伸ばしておけばよい。 倍率で伸びすぎたぶんは地中に隠れるだけで実害が無い。柱は一様断面（またはゆるいテーパー）にしておくと、倍率が変わっても見た目が破綻しない。
    • Yスケールを掛けたくない造形（橋脚梁・パイルキャップ・ハンチ・門型ラーメンの横梁）は pillar_cap 側へ分ける。 キャップは実寸のまま路面位置に置かれ、その厚みぶん柱が下げられるので、キャップの最深部と柱の天端（Y=0）が自動的に噛み合う。

    base_height（3D描画用の高さオフセット）

    base_height は3D描画用の高さオフセット(m) で、経路探索・交差判定には影響しない。バックエンドで唯一これを参照するのは建設コストの高さ倍率で、描画と同じ relY - base_height を実効高さとして評価する（12_建物 12.10）。

    パスの相対高さ(relY)から base_height を引いた値を「3D描画用の実効高さ」として扱い、CalculatePathPoints が返す全サンプル点のY座標から base_height を引く。これにより、スプライン・メッシュ・柱がすべて relY - base_height の高さで描画される。

    3D描画用の実効高さ = relY - base_height
    • base_height = 0（既定）: シフトなし。従来動作。
    • base_height = 20（例: 高圧送電線）: relY=20 で敷いたパスは3D上は高さ0m（地面）として描画される。プレハブモデル自体が20mの高さを持つことで、送電線が地上を這わずに適切な高さに見える。relY=25 にすれば3D上は5mの高さとして描画され、柱が5m分伸びる。

    base_height を持つバリアントのモデルは「スプライン＝地表」を前提に地上高を持つ。このため body には上面を Y=0 へ揃える補正（§5）を掛けず、pillar_cap は鉄塔本体（原点＝接地、上方向へ実寸）として著作し、pillar は relY > base_height のときだけ路面と地表の隙間を埋める部材になる。柱・キャップの置く／置かないの判定（§8.7 配置対象）も base_height を足した構造物の高さで行う（p1102: body は電線 y=8.3〜10.4m、pillar_cap は鉄塔 y=0〜10.5m、pillar は天端原点の角柱）。

    バックエンドの経路探索・交差判定は CalculatePathPoints を使わず、パスデータの relY をそのまま使用するため、base_height の影響を受けない。建設コストの高さ倍率だけは描画と同じ relY - base_height 基準で評価する。

    8.8 地下パス（トンネル）の描画区間分割

    負の相対Yを持つアンカーがあるパス（地下パス）は、点列をそのまま1本のスプラインにせず、サンプル点ごとのトンネル判定で「描画する連続区間」に分割してから、区間ごとに通常のメッシュ生成器（RoadPath / TrackPath）を呼ぶ（PathManager.GenerateUndergroundPathMesh / TunnelSectionUtil）。

    • トンネル判定: サンプル点で 現在の地形標高 − 道路Y > クリアランス高さ（マスターの height） ならトンネル区間。両端点がともに地表に張り付いている（|地形−Y| ≤ 0.5m）区間は地形追従区間とみなし、深さ0（描画対象）として扱う。
    • 開削区間との整合: バックエンドは着工時に開削区間（深さ ≤ height）の地形を道路標高まで掘削する。掘削後の地形ではその区間の深さが約0になるため、Unity側の判定は自動的に「開削区間＝描画、トンネル区間＝非描画」となり、バックエンドの区間分類（3_道路網参照）と整合する。建設前（PENDING・プレビュー）は元地形に対する判定となり、これもバックエンドの分類と一致する。
    • 境界と坑口: 区間の境界は深さがちょうど height になる位置を隣接サンプル間の線形補間で求める。各境界には portal パーツ（バリアント→タイプのフォールバック）を、トンネル内部方向を向けて配置する。プレハブ未整備時はスキップされる（オプショナルパーツ）。
    • コライダー: 描画区間のストリップメッシュを結合したものになる。トンネル区間はクリック判定を持たない。
    • 描画LOD=Far（遠景の帯）: 地下パスは遠景の帯を描かない。帯は埋設区間を無視して地表を横切ってしまうため、遠景では非表示とする（丘を貫く非追従パスも同様）。
    • 柱（pillar）: 地下パスには配置しない。

    9. マテリアルの割り当て

    SplineMesh でパーツを配置する際、プレハブに設定されたマテリアル情報を引き継ぐ。ただし、FBX からインポートされたマテリアルは Unity 内のマテリアルアセットと対応が取れない場合があるため、以下の再割り当てロジックを使用する。

    1. プレハブの MeshRenderer.sharedMaterials から元のマテリアル配列を取得する
    2. 各マテリアルについて、その名前で Resources.Load<Material>() を試みる
    3. Resources に同名のマテリアルがあればそちらを使用し、なければ FBX 由来のマテリアルをそのまま使用する

    これにより、Blender 等の DCC ツールで設定したマテリアル名と同名の Unity プロジェクト内マテリアルが自動的に対応付けられる。Resources 側にマテリアルを置くことが、コードを変更せずに路面の見た目（シェーダーを含む）を差し替える唯一の口である（未舗装路の PATH_SAND はこの仕組みで専用シェーダーを当てている。§16 参照）。

    10. コライダーメッシュの生成

    10.1 目的

    SplineMesh は子オブジェクトとして生成されるため、親オブジェクトの MeshCollider には自動的には反映されない。クリック判定等の物理用途のために、道路全体を覆う簡易的なコライダーメッシュを別途生成する。

    10.2 RoadPath の場合

    1. 構築済みの SplineComputer に沿って等間隔（1m間隔）でサンプリングし、List<Vector3> を得る
    2. PathMeshFactory.BuildStripMesh() にサンプリング点と道路幅を渡してストリップメッシュを生成する

    10.3 BuildStripMesh のアルゴリズム

    ポイント列を折れ線とみなし、各点で進行方向に垂直な方向に左右 width/2 ずつ頂点を置いてストリップ状のメッシュを構築する。各点での方向ベクトルは、前後の点とのベクトルを平均してスムージングする。UV座標は累積距離に基づいて割り当てる。

    10.4 返却

    生成されたコライダーメッシュは PathMeshResult.Mesh として返される。PathMeshResult.ModulesCreated は true（SplineMesh が視覚的メッシュを担当しているため親の MeshRenderer は不要）、GeneratedObject は道路のルートコンテナである。PathManager.CreateOrUpdatePath() で MeshCollider コンポーネントにこのメッシュが設定される。

    11. 交差点と断面の接合

    11.1 共通の切断断面

    PathManager は交差点の影響を受けない描画点列を CalculatePathPoints(path, false) で生成し、NodeMeshFactory に渡す。IntersectionPolygonUtil はこの点列上に PathEndSection（ワールド位置、外向き接線、法線、全幅、切断距離）を作る。点列が供給されないテストや仮想ノードでは SamplePlan が端点制御点・ウェイポイントを評価する。

    ConnectionPoints はこの断面の中心を返す。本線は Trim によって元の点列の必要区間だけを保持する。車道・歩道・壁・レールは同じ切断断面を参照し、保存データの端点を移動しない。

    ウェイポイントのない直線も、地形追従のサンプリングを切断前に行う。描画時に切断後の長さでサンプリングし直さない。折れ線道路の角は前後のアンカーから仮想入口を作り、各スパンの45%を上限に接合する。歩道がない場合も壁・中央分離帯のコネクタを生成する。

    11.2 外周と路面

    入口断面を外向き方向の角度順に並べ、隣接する入口の外縁を結ぶ。両側の道路の縁を交差点へ延ばした直線が入口より内側で交わる場合は、その交点から両側へ同じ距離だけ戻して角を丸め、入口から丸め始める点までは直線を保つ。丸め半径は最大道路幅の1/4を基準に、両側の入口までの距離に収まるように縮める。丸め部分は円弧を近似する端部接線付きの三次ベジエとする。四車線道路と一車線道路のように幅が違っても、太い道路の直線の縁を細い道路へ引き込まず、角で逆向きに曲がるくびれを作らない。直線の交点が得られない幅移行部などは入口間を端部接線付きの三次ベジエで結ぶ。

    IntersectionCorner の点列・方向を路面、歩道、壁が共用する。凸包で外周を塗り潰さないため、曲がった壁の外に余分な舗装が残らない。

    一直線の2本でも移行区間を生成する。異幅の入口間では外周が滑らかに変化し、幅変更を1点の段差にしない。三角形化は耳切り法で行い、失敗時に凹多角形をファンで埋めることはしない。耳切りが作る細い三角形の扇は、内部の辺をDelaunay条件で張り替えて解消する。入口の高さが揃わない、または縦断勾配を持つ交差点では、外周から1m以上内側に2m間隔（LocalConstants.INTERSECTION_SURFACE_VERTEX_SPACING）の正三角形格子の頂点を加え、間隔の2倍より長い外周の辺（入口断面など）も分割する。外周の頂点だけでは勾配のある路面を大きな三角形の平面でしか近似できず、三角形の対角線が折れ線として見えるためである。全ての入口が同じ高さで勾配の無い交差点は路面が平面なので、内部頂点を置かない。

    路面高さは本線の切断断面を境界条件として補間する。入口では本線と同じワールド上方向の BODY_ABOVE_SPLINE を適用し、坂道でも境界を合わせる。モデル自体の厚みは断面法線方向に向ける。bodyプレハブの全高から底面・外周の小口も作る。これは汎用の厚み補間であり、橋桁の内部構造を再現するものではない。

    補間は、各入口の本線の縦断勾配を交差点の内側へ延ばした高さを、入口断面までの距離の2乗に反比例する重みで混ぜる。延ばした高さは入口断面からの距離に応じて変わり、断面の横方向には変えない（本線の横断が水平なため）。入口では高さも勾配も本線と一致するので路面が折れず、一様な斜面に沿う道路どうしの交差点はほぼその斜面になる。延長は入口からノードまでの距離の2倍を尺度に滑らかに頭打ちにし、遠い入口の勾配で山や谷を作らない。路面の法線はこの高さの曲面から求め、三角形の向きを平均しない。陰影が三角形の形によらず、入口では本線の断面法線と一致する。高速道路の本線（§11.7）を持つノードでは、本線の路面の上を本線の縦断そのものの高さにし、外側だけを本線の路面の縁と他の枝の口から補間する。

    11.3 歩道・壁・中央分離帯

    幾何情報は互換性のため SidewalkConnectorSpec に集約し、Part が sidewalk / wall / center / line を区別する。RoadPath.CreateSidewalkConnectorObject は通常道路と同じプレハブを細かいタイルとして変形して生成する。

    • 歩道は共通外周の内側、壁は外側に配置する。幅を滑らかに補間し、端の向きは本線の断面に合わせる。
    • 歩道幅の補間はX方向だけに適用する。SplinePoint.sizeで縁石の高さまで拡大縮小しない。
    • 歩道が途切れる場合は、切断面の道路外縁を中心に、半径＝歩道幅の四分円の扇形を作る。縁石を道路外側へ90度回し、幅をゼロに絞った尖端にはしない。本線の歩道を別距離で後退させない。壁・中央分離帯の片側終端は先細りとする。
    • 異なるプレハブ間では開始側の形状を使用し、高さを相手側のbounds高さへ補間する。異なる装飾や断面トポロジーの完全な形状モーフィングは行わない。
    • ほぼ対向する2本道路の中央分離帯は接続し、多叉交差点では各入口で先細り終端にする。
    • 2本道路の移行部では側線を接続する。中央分離帯が無い場合は車線境界の横位置を対応付け、車線数の変化を表現する。
    • 駅ホーム側の壁は生成しない。交差点内のレール通路に干渉する壁コネクタも除外する。

    生成メッシュは IntersectionMeshOwner が所有し、オブジェクト削除・再生成時に解放する。

    11.4 線路と踏切

    レールの配置位置も共通断面から求める。軌道数が異なる場合は、横位置順を保つ多対一対応で実際の各軌道端へ接続する。中心線1本への置き換えは行わない。曲線端部には本線の方向と勾配を適用し、軌間は伸縮しない。

    転回可否は保存された論理端点の接線で判定し、切断後の描画接線とは区別する。曲線は端点制御点を優先し、折れ線は隣接アンカー方向を使う（バックエンド path_end_tangent と同じ）。線路とモノレールの間、LRT（222/242/303/431）と通常鉄道の間にレール接続は作らない（TrackIntersectionMeshGenerator.RailsConnect。LRT付き道路）。道路×線路では道路の路面材質を優先し、その上に通行可能な線路ペアのレールを配置する。線路だけのノードでの板なしの直進接続と、軌道の位置が違う線路のつなぎ目のS字は N_線路メッシュの生成 §4.6・§4.7 に従う。

    11.5 接合距離と縮退配置

    切断距離は幅・進入角度・外周の移行余裕から求める。反対側にも交差点があるパスでは、各端に全長の45%までを予約して切断区間の逆転を防ぐ。反対側が終端なら95%まで使用できる。折れ線・single_spanでは次のアンカーを越えない。

    この範囲に入口断面が収まらず外周が自己交差する場合、RequiresMoreSpace として接合を見送る。無効なポリゴン修復で入口を欠落させず、古い切断情報を解除して本線を元のノードまで描く。幅に対して極端に短い枝や同方向の重複パスではパーツ同士の重なりが残り得る。

    11.6 材質と検証

    材質は道路を線路より優先し、同分類では最大variantの body_material、bodyプレハブ、共通路面の順に解決する。交差点を複数材質へ領域分割する処理はない。UVに依存する路面テクスチャには従来の制限が残る。頂点カラーは白（α=1）を明示する。

    unity/Tests/Intersections/run.ps1 はUnity生成csprojで本体をビルドしてから、実際の幾何計算を.NET上で検証する。幅・角度・枝数・長さの組合せ、入口の境界一致、入力順への非依存性、切断による内部点の保持、保存制御点の優先順位、空間不足時の安全な失敗を確認する。幅24mと3mの十字路・T字路では、回転・遠方座標・保存方向の反転を含め、太い道路の外縁の直線部分と角の接線の単調な回転を検査する。

    run-unity.ps1 は独立した検証用Unityで実際の描画コードとFBXを使い、傾斜三叉路の路面・付属パーツの端を本線の頂点と比較する。幅24mと3mの十字路も生成し、路面端の一致と真上からの描画画像を確認する。道路と線路の混在、複線→単線、歩道なしの折れ点の壁も検査する。全モデル・全地形・全LODを網羅するものではない。実行条件と出力先は同ディレクトリのREADMEを参照する。

    11.7 高速道路の本線とランプ

    高速道路（PATH_MOTORWAY）では本線を優先して描く。本線はランプ（path_master.ramp）でない高速道路、ランプは ramp が真のバリアントである。IC/JCTの凸包や名前ラベルには依存しない。一般道路どうしの交差点・並走には適用しない。すべて描画専用で、保存中心線・制御点・縦断・接続ノード・道路占有ポリゴン・交通容量・経路探索は変えない。

    結合区間

    本線とランプが近接して並走・合流する区間は、一つの路面として描く（RoadAdjacency）。複線の線路の結合描画（§12）と同じく、各道路が自分の点列に沿って相手を探して判定する。結合する点の条件は次のとおり。

    • 路面の縁どうしの隙間が2m以内（ROAD_MERGE_MAX_EDGE_GAP。路面が重なる場合は負の隙間）
    • 向きの差が30度以内（ROAD_MERGE_MAX_ANGLE_DEG）
    • 高さの差が、路面が重ならず隣り合う点では1m以内、路面が重なる点では4m以内（ROAD_MERGE_MAX_DY / ROAD_MERGE_OVERLAP_MAX_DY）。重なるのはノードで接続するランプの取り付け部で、ランプの保存縦断が本線から離れていても同じ路面として扱う。

    本線は、ランプの路面が縁に隣り合う・一部重なる区間を結合区間とする。ランプの路面が本線の縁の内側へ入りきった区間は本線の路面そのものなので、本線の描画を変えない。ランプは本線の路面の内側へ入った区間も結合区間とする。

    結合区間では次のように描く。

    • 両者の間の壁（wall）を立てない。相手の路面が壁の位置に掛かる区間も立てない。1m未満に残る壁の断片は省く。
    • 路面の隙間は本線が舗装する（RoadMergeFiller_*。二重に作らないよう本線だけが生成する）。舗装は本線の路面より ROAD_MERGE_SINK の2倍（4cm）下げ、両側の路面の下へ0.3m潜らせる。bodyの材質を使い、標示は描かない。
    • 本線のランプ側の路側線は、結合区間だけ合流車線との境界を表す点線にする。ランプの本線側の路側線は結合区間では描かない（§8.3の区間ごとの描き分け）。
    • 路肩の設備（街灯など）は結合区間に置かない。

    ランプの描画高さ

    ランプは、結合区間の高さを本線の路面へ寄せて描く。本線は自分の縦断を保つ。PathManager が切断前の点列を作るとき、ランプの点列を本線と照合し、結合区間の点を「本線の路面の高さ − ROAD_MERGE_SINK（2cm）」に置く。本線と重なるランプの路面を本線の下へ隠し、深度の競合を避けるためである。結合区間の外は、寄せた量を滑らかに0へ戻してランプ本来の縦断へつなぐ。戻す長さは高さの差に比例させ、加わる勾配が最大4%（ROAD_MERGE_MAX_ADDED_GRADE）になるようにする（20〜120m）。戻しきれない短い区間は、両側の寄せ量を補間するか、道路の端で0になるよう縮める。

    寄せた点列は、路面・橋脚・交差点の切断断面・車両の走行位置・遠景の帯が共通に使う。寄せ先の本線が追加・変更・削除されたときは、近くのランプの点列を捨てて作り直し、ランプの両端の交差点も計算し直す。本線とランプの結合区間の描画も、相手側のデータ変更で作り直す。

    合流ノード

    ノードでは MotorwayMergeLayout が本線を判定する。稼働中の本線のうち、ノードから最も一直線に続く2本（外向き方向の内積が−0.8未満）が本線である。本線がノードで2度以内（ROAD_MERGE_MAX_MAIN_BEND_DEG）の折れで同じ幅に続き、本線以外の枝がすべて取り込めるランプなら、交差点の板を作らない。取り込めるランプは次をすべて満たす。

    • 稼働中で、近い方の本線との向きの差が30度以内
    • 本線より幅が狭い
    • ノードからたどると、ランプの路面の外縁が本線の縁を越える位置が切断距離の上限内にある
    • その区間で本線との高さの差が4m以内

    板を作らないノードでは、本線の2本をノードまで描いてつなぐ（切断しない）。つなぐ端では中央分離帯の端を丸めず、つなぎ目の橋脚はpath_idの小さい方だけが立てる。ランプは路面の外縁が本線の縁を越える位置で切る。そこから先のランプは本線の路面の下にあるので描かない。ランプの外縁の路側線と壁は切断位置まで続き、本線の縁の路側線・壁へ合流する。

    浅い角度で接続したランプは、本線との角度に応じた長さで路面が本線の縁へ絞られる。ランプを本線に沿って並走させてから接続すると、並走区間が結合区間になって合流車線の見た目になる。並走距離や絞りの長さはプレイヤーが引いたランプの形状で決まり、描画側で車線を追加しない。

    条件を満たさないノード（本線が折れる、角度の大きい枝・一般道路・工事中の道路が残るなど）は、全ての枝で通常の交差点の板を作る。本線があれば板の高さを本線優先にする。本線の路面の上は本線の縦断そのものの高さとし、本線の口は補間に使わない。外側は、本線の路面の縁（縁からの水平距離）と他の枝の口から補間する（§11.2）。本線が無い高速道路のノード（ランプどうしなど）は通常どおり全ての口から補間する。

    車両

    取り込まれたランプから本線へ入る車両は、ランプの側に最も近い本線の車線へ入る。左右は通行側と独立に、ランプの切断位置が本線の進行方向のどちら側にあるかで決める。ランプの走行点列は切断位置で終わり、そこから本線の車線への移動は通常の交差点と同じ接続曲線で描く。一般車・乗車中の車・バスの描画だけを調整し、シミュレーターの経路探索や移動時間は変更しない。

    検証

    unity/Tests/Intersections/run.ps1 は結合区間の判定（並走・離れた並走・高さの異なる隣接・重なり）、ランプの高さの寄せと戻し、合流ノードの板の有無とランプの切断位置、本線優先の板の高さを.NET上で検査する。run-unity.ps1 は実FBXと本編生成器で、板を作らない合流ノードと切断位置、進入車線、本線優先の板、並走してから合流するランプの壁・隙間の舗装・路側線の描き分けを検査し、描画例 merge-top.png / merge-perspective.png を出力する。

    11.8 交通信号機

    交差点の信号機は描画専用の装飾で、経済・経路探索・車両や歩行者の走行には影響しない。灯火は点灯状態（現示）を持たず、車両の信号待ちもない。

    設置条件

    ノードに接続する完成済みの道路（PATH_STREET / PATH_MOTORWAY）の腕が3本以上あり、そのうち2本以上がセンターライン（または中央分離帯）で上下線の分かれた双方向の街路であるとき、一律に設置する。センターラインの有無は §8.3 の RoadLaneLayout と同じ定義で、双方向・lanes 2以上・片側の走行帯を持つ道路が該当する（2車線道路221以上）。センターラインの無い1車線道路どうしの交差点、センターラインのある道路が1本だけで他が細街路の交差点、2本だけのつなぎ目、一方通行ばかりの交差点には置かない。工事中の腕は数えない。

    配置

    車両が流入できる完成済みの道路の腕ごとに1基を置く。配置は日本式で、灯器は交差点の向こう側・通行側（左側通行なら左、右側通行なら右）に置く。

    • 直進先の腕がある流入路: 流入方向から45度以内で最も向きの近い腕（線路は除く）を直進先とする。直進先の腕の切断面から0.5m外側の、流出方向を向いて通行側の歩道に柱を立てる。柱の軸は縁石から0.5m（歩道幅の半分が0.5m未満なら歩道の中央）で、歩道の無い腕では路端から0.5m外側の地表に立てる。アームは道路の中心側へ伸ばし、灯器を流出する向きの車線群の中央の上に吊る（双方向なら通行側の走行帯の外側境界と中央境界の中間、流出する一方通行なら道路の中央、1車線の双方向・流入専用の一方通行なら通行側の半分の中央）。
    • 直進先の腕が無い流入路（T字路の突き当たりなど）: 流入車線群の中央線を延ばした先にある角の外周（§11.2）の歩道に柱を立て、灯器を流入車線群の正面に置く。アームは通行側と反対へ最短長だけ伸ばす。正面に角が無い変形交差点では、流入方向へ90度未満で最も近い腕を直進先として扱う。
    • 灯器は流入路の外向き方向（流入してくる車の側）を向く。柱の軸から灯器までは最短0.9m（灯器の半幅と柱の取付バンドの半径に余裕を足した値）。
    • 柱がいずれかの腕の車道（切断面の外側・縁石の内側）に入る配置は省く。1m未満に近い柱は1本にまとめてアームを足し、1m未満に近い灯器は重ねて描かない。
    • 柱は立てる横位置の歩道の上面（縁石ではなく歩行面）に接地する。歩道が無ければ地表に立て、高架の交差点で歩道が無ければ置かない。

    モデルと描画

    モデルは固定名のプロップ Models/Props/traffic_signal_{様式}_{pole|arm|head}（地形プロップ §M.5.1 の固定名モデル）で、3部品とも原点を柱の接地面の高さに揃え、取付高さはモデルが持つ。

    部品 規約
    pole 柱。接地点が原点で地中へ1m延ばす。回転対称。アームの高さに取付バンドを持つ
    arm アーム。柱の軸（ローカルZ=-0.5）から先端（+0.5）までの単位長で、配置時に長手だけを伸縮する
    head 灯器。吊り金具の真下の地面が原点で、表示面はローカル+Z。下端は接地面から4.5m以上

    様式は TrafficSignalStyle が持ち、現在は日本式（jp。横型3灯を左から青・黄・赤、片持ちアーム）に固定している。アームは柱の軸から灯器の外側の端まで伸ばす。

    TrafficSignalLayout は交差点メッシュの生成（RoadIntersectionMeshGenerator）と同じ切断断面・外周・歩道のセットバックから配置を求め、NodeMeshResult.TrafficSignals で返す。PathManager は交差点の板の更新時に TrafficSignalBuilder で NodeMesh_* の子 Signals を作り直す。全信号機の部品を材質ごとのサブメッシュへ焼き込んだ1メッシュで、1基ごとのGameObjectやColliderは作らない。交差点の再生成・非表示・破棄に従い、入力は交差点の入力署名（接続道路の版・状態、左右通行、地形）に含まれる。材質は RoadPath.GetOrCreateRoadMaterial の共有プールを使う。遠景では道路の付帯設備と同じく省き、LODGroupで交差点の信号機群の投影比が建物の遠景降格と同じ0.03を下回ると描かない。

    unity/Tests/TrafficSignals/run.ps1 は独立したUnityで実FBXと本編生成器を使い、設置条件（置く11配置・置かない5配置）、左右通行、灯器の車線上の位置と向き、柱の接地と車道外への設置、灯器の下端高さ、結合メッシュの頂点数・材質・LODを検査し、交差点の俯瞰と運転席視点の画像を出力する。

    12. 線路・モノレール（TrackPath）

    14. max_span バリデーション

    14.1 概要

    始点・終点・ウェイポイント間の1区画のうち、非追従スパン（両端の相対Yがともに0ではない区画、または実効非追従パスの全区画）の長さが max_span を超えないように制限する。これは柱（pillar）や桁で支える構造上の制約であり、地形に張り付く地表スパンには掛からない。

    14.2 計算方法

    バリデーションでは水平距離（XZ平面）を計算する。高さ方向（Y軸）の差分は距離計算に含めない。曲線の長さは考慮せず、アンカー点間の直線距離で判定する。

    14.3 フロントエンド（Unity）

    道路エディタ（RoadPlanManager）では、ユーザーがポイントを移動した時点でリアルタイムに max_span をチェックする。max_span を超えるセグメントが存在する場合は以下のフィードバックを行う。

    • 視覚的フィードバック: 違反セグメントを赤色の太線でハイライトする
    • テキスト警告: 画面上部に「セグメントの長さが制限を超えています（最大 {max_span}m）」という赤色のテキストを表示する

    14.4 バックエンド（Python）

    パスの作成（POST /api/v1/paths）と更新（PATCH /api/v1/paths/{path_id}）時に max_span バリデーションを行う（crud_paths._validate_max_span。非追従スパンのみ）。

    15. 工事中（STATUS_CONSTRUCTING）のパス表示

    PathManager.GenerateConstructingPathMesh は ConstructionPathBuilder に施工表示を委譲する。道路・線路は、取得済みの建設進捗に応じて始点から終点へ施工が進む。交通の通行方向やカメラの向きには依存しない。model_type=none は工事中も描画しない。

    15.1 地上道路・線路

    全長の累積距離に進捗率を掛けた位置を施工先端とする。先端までには完成モデルのbodyと歩道、線路なら道床と実寸軌道を敷き、先端より先だけに土を残す。点列の途中で境界を補間するので、アンカー数やセグメント長が不均一でも施工速度は長さ基準で一定になる。施工済み区間には道路・線路とも完成時の配置条件に従ってwallも置く。線路はTrackPath.CreateConstructionPartsを通し、完成時と共通の区間判定で地表のbody/trackと高架のbody_elevated/track_elevated（未配置なら無印へフォールバック）を使い分ける。線路のwallは高架区間のみとし、隣接線路との結合側・ホーム側の省略条件も完成時と共通にする。区画線・中央分離帯・街路樹・架線などの仕上げ設備は、稼働状態へ移ったときに通常生成器が配置する。

    舗装機は先端側、ローラーは施工済み側、ショベルはその先の土工側へ実寸で配置する。車両は毎フレーム動かさず、進捗を取得した時点の位置に固定する。短い経路では端へ押し込んで車両を重ねず、収まる車両だけを置く。狭幅の経路とFar表示には車両を置かない。

    15.2 高架道路・高架線路

    height_editable と正の pillar_spacing を持ち、相対高さが正の区間を含む経路が対象。地形追従する地上道路を、描画上の浮かせ量だけで高架と判定しない。高架と地上をつなぐランプを含む1本のパスは、高架側の施工段階に従う。

    進捗 表示
    0〜25% 始点から順に橋脚を建てる。施工中の1本は接地位置を固定して高さを伸ばす。0%では何も表示しない
    25〜90% 橋脚は完成状態で、始点から橋脚間の桁を順番に載せる
    90〜100% 仕上げ期間。橋脚・橋桁・工事車両の見た目と配置を固定する

    橋脚モデルの著作高さでスケールを正規化し、柱の下端を地表に合わせる。1mとは限らない実寸モデルを、そのまま必要高さ倍して地中へ突き抜けさせない。橋脚候補、完成高さ、キャップ、周辺道路との干渉判定は完成時の RoadPath.GeneratePillars と同じ内部処理を使う。干渉で除外された位置には施工中も柱を置かない。進捗を柱の本数へ割り当てるため、候補を進行順に並べ、未着手の施工単位は非アクティブにする。高架の下には施工用の土を生成しない。

    桁は有効な橋脚と両端の橋台を区切りとした単位で架設し、区間の途中に桁端を浮かせない。single_spanの一体モデルも支持点間ごとに生成し、複数のアンカー区間を1枚に引き伸ばさない。橋脚の施工中はショベルをパス中心線上の地表に置く。架設段階は移動式クレーンとショベルを架設済みの路面上へ置き、路面の高さと勾配に合わせる。配置基準は連続的な進捗位置ではなく、橋脚間の施工単位で確定した桁端とする。車両の実寸に基づいて桁端と先行車両から余白を確保し、架設済み区間や道路幅に収まらない車両は表示しない。桁がまだ無い場合も車両は表示しない。道路幅の外への横オフセットは加えない。90%以降は配置を固定し、稼働状態へ移った際に撤去する。

    15.3 土の形状と材質

    ConstructionMeshUtil.BuildDirtStripMesh は、幅に1mの余白を加え、左右別の低周波ノイズで輪郭を揺らす。断面は地表の外縁と内側の盛り土からなる台形で、横断方向の各頂点で地形標高を取得する。地形の横断勾配があっても片側の縁が浮かない。多オクターブの DirtNoise で高さを変え、共有頂点から法線を計算する。

    道路工事専用の Resources/ConstructionPathDirt.mat は、既存の Custom/PathDirt を使う。茶色の土の色むら、砂利、粗い表面の微細法線をワールドXZ座標から生成し、頂点カラーのα（中核1・外端0）で縁だけを侵食する。ForwardLit・ShadowCaster・DepthOnly・DepthNormalsは同じ切り抜きを共有する。既存の建物用土マテリアルは変更しない。

    15.4 トンネル・遠景・クリック

    地下区間の除外と坑口は完成時の TunnelSectionUtil と共通。進捗は地下部分を含む経路全体で計算し、施工済み区間と土工区間をそれぞれ可視区間へ切り分ける。深いトンネル内部やその地上には車両を置かない。

    クリック用メッシュは土と施工済み面を結合する。高架は0%でも選択できるよう、非表示の設計面の当たり判定を保持する。全長が深いトンネルで見える面が無い場合は空の表示を返す。Farはモデルを読み込まず、施工済み面と土の帯だけで進捗を示す。高架のFarでは橋脚と桁単位の離散化を省き、25〜90%の間に帯を連続的に伸ばし、90%以降は固定する。高架のFarにも土は生成しない。地下パスのFar非表示は完成時と同じ。

    交差点自体の生成は通常のままで、工事中でも交差点の舗装が見える。施工の段階表示はパス本線に適用する。

    15.5 進捗の取得とキャッシュ

    GET /paths/ の各項目に construction_progress（0〜100、未設定はnull）を描画拡張として付ける。計算式は詳細画面と共通の取得済み建設体積÷必要体積。Unityの独自 ConstructionPathSummary が自動生成型を継承して受け取る。生成済みスキーマやマスターデータを手で編集しない。

    PathManager は一覧取得前後の進捗も比較し、形状versionが同じでも施工表示を再生成する。再利用キーにも進捗を含め、地形追従の再開記録を無効化する。単体の FetchPath も同じ拡張型を使う。進捗は0〜1へ正規化し、null・非数は0、不正な範囲はクランプする。statusが稼働へ変わると通常の完成メッシュへ戻る。

    15.6 工事車両の制作と検証

    コレクションとFBXの名前は construction_paver / construction_roller / construction_excavator / construction_crane。配置原点は接地0・水平中心、Unityの+Zが前方。既存の車両用材質と黄色塗装を共有する。施工表示は固定名で読むが、飾りとして自由に置けるよう数値ID 201〜204 の別名FBX(メッシュ共有)も prop_master に登録している(地形プロップ §M.7.2)。

    library.py export --category props --only construction_ で書き出し、Propsバリデータと build_gallery.py --only construction_ を実行する。Unityへのミラーは ModelPrefabGenerator が生成する。unity/Tests/ConstructionPaths/run-unity.ps1 は実FBXとURP材質で0・12.5・25・57.5・90・99・100%の描画、曲線、地下、クリック面、進捗の受信とキャッシュキーを検証する。橋脚の干渉回帰は unity/Tests/Pillars/run-unity.ps1。

    16. 未舗装路の路面表現（Custom/PathDirt）

    未舗装路（path_variant 201）の body は、舗装路のような「端までベタ塗りの帯」ではなく、地面に踏み固められた土の道として描く。テクスチャは使わず、ワールドXZ座標の手続きノイズと頂点カラーだけで表現する。

    • シェーダー定義: Assets/Resources/Shaders/PathDirt.shader（パス構成）
    • 本体: Assets/Shaders/PathDirt.hlsl（シェーディング）
    • マテリアル: Assets/Resources/PATH_SAND.mat

    16.1 3つの層

    層 内容
    土の色ムラ 大スケールの fbm で主色↔副色を混ぜ、細スケールの fbm で明るい砂利の斑を散らす
    細かい凹凸 同じ細スケールノイズの勾配で法線を微小に傾け、平面のノッペリ感を消す
    縁の侵食 頂点カラーのアルファを縁マスクとして、ワールド座標のノイズでアルファクリップし、路肩をギザギザに溶かす

    ノイズの入力はすべてワールドXZ座標なので、UV・タイリング・頂点密度に依存しない。SplineMesh の Extrude はタイル（曲率適応、1〜8m。§4.3）ごとに UV を繰り返すため、UV ベースの模様だとタイル周期の反復が目に見える。

    16.2 頂点カラーの規約（モデル側の契約）

    body プレハブは、路面の外側に下向きに垂れる「なじませスカート」を持ち、その頂点にアルファを塗る。

    頂点カラーのα 意味
    1.0 路面の中核。絶対に抜けない
    0.0 スカートの外端。ほぼ完全に抜ける
    中間 スカートを横断する線形グラデーション

    路面上面は地形+0.2m（§4.4 / RoadPartHeights）にあるため、スカートの外端をローカルY −0.3m 程度まで垂らすと平地でも確実に地形へ潜る。これにより見える境界が「スカートと地形の交線」になって直線でなくなり、その上にノイズの侵食が乗って砂利が草に食われるような縁になる。

    Dreamteck の SplineMesh は元メッシュの頂点カラーをそのまま出力へ透過するため（SplineMesh.cs のチャンネル書き込み）、Extrude されたタイル列でも規約が保たれる。

    body の公称幅は最上面の幅（§4.4）であり、下向きのスカートや桁の張り出しは含めない。スカートを広げても路面幅は変わらない。

    16.3 アルファブレンドではなくクリップである理由

    路面は地形から浮いた板なので、半透明にすると板の下の隙間が透ける。クリップ（cutout）なら抜けた部分は地形がそのまま見えるだけで済み、不透明キューのままなので GetOrCreateRoadMaterial の renderQueue 補正や ZWrite の前提も壊れない。キューは AlphaTest（RenderType は TransparentCutout）。

    16.4 パス構成と切り抜きの一貫性

    ForwardLit / ShadowCaster / DepthOnly / DepthNormals の4パス構成。DepthNormals は PC_Renderer の SSAO（Source = DepthNormals）が前段パスとして要求するため必須で、省くと未舗装路だけ SSAO と深度テクスチャから抜け落ちる（水面シェーダーの深度参照にも影響する）。

    全パスが同じ切り抜き関数（PathDirtClip）を通る。 パスごとに輪郭が食い違うと、抜けたはずの路肩が影や SSAO に残る。

    16.5 遠景でのチラつき対策

    プロジェクトは MSAA 無効（PC_RPAsset）のため、クリップ境界はアンチエイリアスされない。遠景ではノイズの粒がピクセル以下になってチラつくので、カメラ距離に応じてノイズを平均値（0.5）へ寄せて縁を滑らかな線に戻す（_EdgeDetailFadeDistance）。侵食量そのものを0へ戻すのではなく平均へ寄せるため、縁の平均位置が変わらず、遠近で道路幅が太った／痩せたように見えるポップが起きない。

    16.6 適用範囲の制限

    このシェーダーは規約どおりに頂点カラーを持つメッシュ専用で、他の道路 body へ流用してはいけない（頂点カラーのない body に適用すると縁マスクが不定になる）。

    交差点ポリゴン（§11）はこのマテリアルを共有しうる（未舗装路と舗装路が接続するノードでは variant 番号が大きい未舗装路側が代表に選ばれ、そのマスターの body_material＝PATH_SAND が交差点にも適用される）。ConvertGeometryToMesh は依存を明示するため白（α=1＝侵食なし）を明示設定する。既定値に依存すると交差点が丸ごと切り抜かれて消える事故になりうる。

    maxTileLengthを0以下にして著作周期を保つ連続パーツは、頂点数上限時に整数タイル単位で別SplineMeshへ分割する。区間全体のタイル数を減らして造形を引き伸ばさない。通常の道路用タイル上限やsingle_spanにはこの分割を適用しない。

    計画表示と非同期区間生成の同期

    敷設・形状編集時のプレビュー

    敷設中は、配置済みアンカーまでを詳細メッシュで保持し、最後のアンカーからカーソルまでを軽量な帯で表示する。曲線モードではホバーを仮終点としてCatmull-Rom接線を計算し、直前の1区間とホバー区間をベジエ曲線の帯で表示する。それより前の詳細区間はホバー移動だけでは再生成しない。打点時にも自動制御点を更新するため、配置済み区間が折れ線へ戻ることはない。打点によって形状が更新された詳細区間は、本番と同じ生成器で作り直す。

    形状編集のドラッグ中は、変更の影響を受ける区間だけを帯にする。直線のアンカーと曲線の制御点は両隣、曲線アンカーは隣接アンカーの自動接線まで変わるため前後2区間を対象とする。影響範囲の前後は詳細表示を保持し、ドラッグ終了時に全体の詳細表示へ戻す。

    RoadRenderer.Sections.cs が3つの表示を独立して管理する。帯のMeshと出力バッファを再利用し、道路幅・複線オフセット・ホームの設置側と高さを表示する。柱・柵・架線などの細部は詳細表示で確認する。地形追従する直線とホバー区間は約2m間隔で標高と盛土を反映し、高架・非追従区間は設計高さを補間する。曲線区間は制御点から再標本化し、制御多角形長を基準に約2m間隔・最低16分割・最大4096分割で帯を構築する。手動制御点は維持し、ホバー用の制御点は保存データへ書き込まない。これらは表示専用の処理であり、保存するアンカー・制御点と干渉判定の形状を変更しない。

    プレビューの点列は設計空間（地面＋設計相対高さ＋盛土）で保持し、base_height を持つパス（送電線）は生成器へ渡す直前と帯の頂点で base_height を引く。確定後の描画と同じ位置に出るため、送電線は地面の鉄塔として表示される。地形追従区間の判定も、設計相対高さが標準の敷設高さ（base_height）に一致するかで行う。ウェイポイントは確定後のパス要約と同じ {position: [x, 相対Y, z]} の辞書で詰める。素の配列は読み取られず捨てられるため、アンカーから経路を組む送電線が始点と終点を結ぶ直線になってしまう。

    線路のプレビューは、確定済みの形（敷設中は仮終点を除いたアンカーまで）を完成前の仮の相手として既存線路の描画に参加させ、既存線路は一時的に形を変えてプレビューとつながる（N_線路メッシュの生成 §8.5）。登録は詳細表示を作る前に行い、ドラッグ中は更新しない。

    詳細化は打点・ドラッグ終了時に同期的に行うため、長い計画の詳細生成時には負荷が残る。保持・解除・復帰の回帰検証は unity/Tests/RoadPreview/run-unity.ps1 で実行できる。送電線のプレビューが地面に載り、置いたウェイポイントすべてに鉄塔が立つことも同じ検証に含む。

    設置後のパスは、Renderer収集と統計値の設定を済ませてからステータス表示を適用する。SplinePartLod が後から生成・復元する区間にも、表示するフレームで VisualModeObject.RefreshMaterials() を適用する。既存Rendererの元マテリアルを保持し、白い計画表示を復元用の材質として再記録しない。

    パスの再利用キーにはstatusを含め、一覧のversionが同じでも表示中オブジェクトとstatusが異なれば再生成する。エポック後のデータ取得で着工・完成を検出した際も、カメラ移動なしで更新する。固定区間は共通フレーム予算内で生成を進め、完成した新パスへ旧表示から一括で切り替える。通信・メッシュ生成に必要な時間はかかるが、区間ごとに固定の1フレーム待ちは入れない。

    区間の切り出し（PathDrawContext.SlicePolylineByFraction）は、境界の重複頂点と浮動小数点誤差による0.1mm未満の連続点を統合する。ゼロ長の終端接線でSplineMeshの断面が回転し、施工先端から舗装が張り出すことを防ぐ。

    301の石畳テクスチャ

    ambientCGのPaving Stones 033（CC0）の色・NormalGL画像を使用する。PATH_PAVING_STONEとCustom/PathPavingが上面を描画し、石の形状やディスプレイスメントは生成しない。ワールドXZへ2m周期で投影するため、道路タイルの伸縮・回転・分割で石の大きさが変わらない。石の配列方向はワールド方向に固定され、道路に沿って回転しない。通常・接写は同じ単純なメッシュである。ForwardLitとDepthNormalsのUV・接線を揃え、標準のShadowCaster・DepthOnlyを併用する。色画像はsRGB、法線画像はNormalMap、Repeatとミップマップを有効にし最大1024px・異方性4で取り込む。Tests/Paving/run-unity.ps1が回転前後の画素一致、法線マップの効果、FBXの12三角形、各描画パスを検証する。素材の出所はゲーム内クレジットとAssets/Models/Paths/Textures/PAVING_STONE_SOURCE.mdに記録する。

    ケーブル接続部の描画

    ロープウェイ（PATH_CONVEYOR）とインフラパス（送電線 PATH_ELECTRICITY・導水管 PATH_WATER・パイプライン PATH_PIPELINE）は路面を持たないため、道路交差点の充填メッシュと切断断面の生成対象から除外する。ウェイポイントの折れ点と駅を含む実ノードの接続点の両方で適用し、ケーブルのスパンは元のアンカー位置まで描画する。支柱・ケーブル・駅設備のモデルは通常のパス生成で配置する。

    施設への接続

    RoadAccessPlan は BuildingRoadAccessIndex に登録された施設側の開口を、道路の左右別の弧長区間へ変換する。道路の生成が先でも、後から届いた建物の登録通知で再生成する。一般道路（PATH_STREET）の稼働中の区間が対象で、車線・中央分離帯・交通グラフは維持する。

    間口から敷地外向きに投影し、幅全体が同じ側の道路外縁に6m以内で届く場合に接続する。約1m刻みで、道路に向き合うこと、投影が折り返さないこと、舗装高の差が−0.03〜0.8mに収まることを検査する。交差点用に切断済みの道路を使い、道路端をまたぐ開口・交差点内部の開口は作らない。高速道路・線路や、大きな高低差のある道路へは接続しない。

    接続側の歩道・壁・旧式の路側線メッシュを区間で分割し、手続き路側線にも同じ非表示区間を渡す。交差点の歩道セットバックと開口の両方を適用する。街路樹・街灯・電柱・設備箱・ベンチ等は占有幅を考慮して省き、柵は開口をまたぐパネルも省く。反対側の歩道や設備、中央の樹木は残る。

    歩道を除いた部分の路面には既存のbodyを使う。追加の BuildingAccessSurface は道路外縁から間口までと、敷地内2mまでのすり付け部分だけを描く。ロータリーでは敷地内の実舗装形状でクリップし、既成建物と港の施設モジュールではモデルの間口の内側を使う。路面高から施設本来の舗装高へ補間する。施設より道路が低い段差は、既存施設の舗装の下へ潜るため許容値を超えると接続しない。接続面は描画専用で、選択コライダーは追加しない。

    開口索引は建物の描画LODに依存しない。PathManager は建物更新の前後の開口に近い道路をデータのセル逆引きで抽出し、中心線との距離で絞ってから geometryRevisions を進め、既存の再生成キューへ送る。退避中の道路も古いLODキャッシュを復元しない。建物削除・解体開始では元の歩道へ戻り、全消去では索引を消す。

    実FBXによる接続形状・片側の歩道と樹木・曲線・道路方向反転・高架除外・LODと登録削除の回帰検証は unity/Tests/BuildingAccess/run.ps1。接続点の定義は F_建物メッシュの生成 §16、モデルの著作は 道路間口マーカー。
