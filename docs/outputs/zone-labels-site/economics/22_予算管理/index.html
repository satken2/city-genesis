    22. 予算管理システム

    都市の財政運営を管理するシステムである。市政府（プレイヤー）の歳入・歳出の仕組みと、予算の配分・執行・制御のルールについて述べる。

    22.1. 予算関連プロパティ

    プロパティ 説明
    city.category_ratio プレイヤーが設定するカテゴリ別「必要額に対する比率」。プレイヤーが入力するのは金額ではなくこの比率である。全カテゴリ共通で 0〜1.5。1.0 で生産計画どおりの運転に必要な満額の予算になる。基準額は前エポックの実績支出を参照しないため、設定はプレイヤーが変えるまで恒久的に有効（自動リセットはない）。比率を下げると予算がキャップとなり、そのカテゴリの公共施設は比率にほぼ比例した実効稼働率まで絞られる。余力運転する公共施設（9_生産活動の余力倍率参照）では比率が生産計画への乗率として双方向に働き、100% 超に設定すると標準余力の上にさらに待機生産・雇用を上乗せできる。
    agent.utilization_target / path.utilization_target 施設・道路ごとに設定する稼働率目標。公共施設の実効稼働率はこの施設別の値のみで決まる。稼働中の施設では 0〜1（稼働率）、建設中の建物・道路では 0〜5（建設スピード倍率。最大5倍速）。予算とは独立に効く（）。
    city.prev_total_expense 前エポックの実績支出のスナップショット。「前実績」の表示に使える参考値であり、予算導出の基準ではない。エポック終了時に city.total_expense からコピーされる。
    city.projected_required カテゴリ別の「必要額」。各公共施設が生産計画どおり稼働した場合の1エポック見込み費用であり、予算導出の基準額になる。生産計画は需要・稼働率目標・雇用の状況・原材料の調達状況を織り込んでいるため、高度人材が揃わず稼働できない施設の原材料費のように、実際には支出されない費用は含まれない。
    city.savings_target 貯蓄目標。配分前に現預金からこの額を確保する（実効的により保守的な運営になる）。
    city.budgets 当エポックの予算配分（円額）。プレイヤーが直接入力するのではなく、budgets[cat] = 必要量[cat] × category_ratio[cat] として毎エポック導出される。希望合計が現預金を超える場合は Tier 順に自動調整される。
    city.budget_auto_adjusted 直近の配分で資金不足による自動調整（比率の強制減）が発生したか。UI が「資金不足のため予算が自動調整されました」と通知するのに使う。
    city.effective_category_ratio 自動調整後の実効比率（budgets[cat] / base[cat]）。表示・通知用。
    city.savings 配分後に貯蓄として現預金に残った額（＝どのカテゴリにも割り当てなかった余剰現金）。
    city.prev_budgets 前エポックの予算配分。エポック終了時に city.budgets からコピーされる。
    city.total_expense 前エポックのカテゴリ別実績支出。エポック中のシミュレーション処理で加算され、次エポック開始時にリセットされる。各カテゴリは自身の予算枠内でのみ執行される（共有プールによる補填は廃止）。
    city.total_revenue 前エポックのカテゴリ別収入。エポック中のシミュレーション処理で加算され、次エポック開始時にリセットされる。
    agent.reserves 市政府の現預金。予算配分後の残額が貯蓄となる。
    city.city_reserves_history 市政府の現預金のエポック末スナップショット（リングバッファ）。経済主体の reserves は現在値しか持たず過去を遡れないため、市政府ぶんだけを都市側で時系列として保持する。エポック終了時に確定し、GET /api/v1/city/budgets の reserves_history（[{epoch, reserves}] の古い順リスト）として予算ウィンドウの現金推移グラフに供給される。

    22.2. 予算のライフサイクル

    1エポックにおける予算は、以下の段階を経て循環する。

    1. 比率の設定 ... プレイヤーはユーザー操作フェーズで、各支出カテゴリの「必要額に対する比率」（city.category_ratio、0〜1.5）、貯蓄目標（city.savings_target）、削減優先度（city.budget_tiers）を設定する。金額そのものは入力しない。比率 1.0 = 生産計画どおりの稼働に必要な満額であり、都市が成長して施設が増えれば必要量も自動的に伸びるため、毎エポック調整し直す必要がない。設定はプレイヤーが変えるまで維持される。
    2. 予算の導出 ... budgets[cat] = 必要量[cat] × category_ratio[cat] として予算額が導出される。必要量は「各公共施設が生産計画どおり稼働した場合の1エポック見込み費用」である。希望合計（Σ desired）が配分可能額（現預金 − 貯蓄目標）を超える場合は、Tier 順に比率を自動的に削減して収める（）。導出はエポック開始時（シミュレーション処理の直前）に行われるため、ユーザー操作フェーズ中の操作（修繕の開始、建設の発注、稼働率目標の変更など）で変動した必要量・現預金は必ずそのエポックの配分に反映される。比率変更API（PATCH /budgets）でも即時に再導出される。
    3. 予算の執行 ... シミュレーション処理の中で支出が行われ、執行額が city.total_expense に加算される。運営カテゴリ（1〜7・11）の支出（商品調達・賃金・家賃）は執行時に予算枠でカットされず、計画された支出は必ず全額実行される（予算は次項の生産計画への反映だけに効く。計画を超過した分は市の貯蓄の取り崩し、貯蓄が尽きれば市政府の債務になる）。建設・修繕・用地買収は残予算の枠内でのみ執行され、案件の実行ペースを予算で直接制御できる。使い残しは市の現預金に貯蓄として残る。
    4. 必要量の捕捉 ... 同じエポックのシミュレーション処理の中で、次の予算導出に使う必要額が city.projected_required に記録される。
    5. 実績の確定 ... エポック終了時に city.budgets が city.prev_budgets に、city.total_expense が city.prev_total_expense にコピーされ、そのときの市政府の現預金が city.city_reserves_history に記録される（履歴スナップショットのみで、ここでは予算の導出は行われない）。この記録はエポック終了時点の値なので、その後のユーザー操作フェーズでの現金変動（収用・建設発注など）は当エポックの点には含まれず、次エポック末の点に現れる。city.total_expense・city.total_revenue・city.projected_required は次エポック開始時にリセットされる。

    22.3. 歳入

    市政府の歳入は主に税収である。各税目はエポック内のシミュレーション処理で徴収され、city.total_revenue にカテゴリ別に蓄積される。

    税目 概要
    消費税 小売財（GOODS_RETAIL）の取引に対して外税として課税。
    輸入関税 輸出入拠点からの輸入調達に対して商品単位で課税。
    所得税 賃金支払い時に内税として控除される。
    法人税 一般施設（TYPE_STANDARD）の利益（収入 − 支出）が正の場合に課税される。

    税率は city のプロパティとして保持され、フロントエンドから変更可能である。

    税外収入

    税収以外にも、市政府には次の税外収入があり、いずれも city.total_revenue に計上される。

    税外収入 計上先のキー 概要
    公営事業収入 施設のコストカテゴリ（LEDGER_CITYHALL 〜 LEDGER_OTHER） 公営施設の事業収益（公共サービスの売上）と、公営住宅・公共ビルの家賃収入。支出側と同じ予算カテゴリで計上されるため、カテゴリごとに「その事業がどれだけ稼いだか」を歳出と対比できる。

    なお、市有地を民間の建物着工へ売却したときの土地代（払い下げ）は市政府ではなく中央銀行が受け取るため、市政府の収入には含まれない（7_金融システム・12_建物）。

    22.4. 歳出と予算配分

    支出カテゴリ

    市政府の支出は、目的別に以下のカテゴリに分類される。各カテゴリは定数で識別される。

    カテゴリ 定数 用途
    市政 LEDGER_CITYHALL 市役所の運営費
    医療 LEDGER_MEDICAL 病院・診療所の運営費
    教育 LEDGER_EDUCATION 学校の運営費
    治安 LEDGER_SECURITY 警察署の運営費
    消防 LEDGER_FIRE 消防署の運営費
    インフラ LEDGER_INFRASTRUCTURE インフラ施設の運営費
    その他 LEDGER_OTHER その他公共施設の運営費
    建設 LEDGER_CONSTRUCTION 新規建設（道路・建物）の資金
    修繕 LEDGER_MAINTENANCE 既存施設の修繕資金
    貯蓄 LEDGER_RESERVE どのカテゴリにも配分しなかった余剰現金。支出カテゴリではなく、savings_target で意図的に積み増すこともできる。
    公共交通 LEDGER_TRANSPORT 公共交通（車両基地・路線）の運営費
    社会保障 LEDGER_WELFARE 世帯への現金給付（失業給付・年金・生活扶助）
    用地買収 LEDGER_LAND_PURCHASE 道路計画と重なる民間の土地区画の自動用地買収（3_道路網）の買収金

    予算制御の仕組み

    支出は大きく3つの目的に分類され、それぞれ異なるタイミングで予算制御が適用される。

    運営予算（LEDGER_CITYHALL 〜 LEDGER_OTHER） 市が運営する公共施設のランニングコスト。商品調達・賃金支払い・家賃支払いのタイミングで支出される。各公共施設の variant に設定された cost_category により、どのカテゴリの予算から支出されるかが決まる。

    建設予算（LEDGER_CONSTRUCTION） 新規の道路や建物の建設資金。建設中の建物または建設代理エージェントが建設サービス財に支出する際に使用される。

    修繕予算（LEDGER_MAINTENANCE） 既存の道路や建物の修繕資金。稼働中の建物または修繕代理エージェントが建設サービス財に支出する際に使用される。

    用地買収予算（LEDGER_LAND_PURCHASE） 道路計画と重なる民間の土地区画の自動用地買収（3_道路網の「民間区画の自動用地買収」）の買収金。必要額は買収交渉中の全区画の買収金見積の合計であり、比率 1.0 なら資金がある限り全交渉が成立できる。比率を下げると 1 エポックに成立する買収が予算内に絞られ（残りは持ち越し）、比率 0 で買収を停止できる。

    社会保障予算（LEDGER_WELFARE） 市政府から世帯への現金給付。給付は次の3種で、いずれも世帯単位で支払われる。

    • 失業給付: 就労可能年齢以上・退職年齢未満で、雇用主も就学先もない市民1人あたり「所属地区の標準賃金 × 失業給付率 × エポック日数」。
    • 年金: 退職年齢以上の市民1人あたり「所属地区の標準賃金 × 年金給付率 × エポック日数」。
    • 生活扶助: 世帯の現金残高に失業給付・年金を加えても最低生活費（必需品の最低需要と家賃）に届かない世帯への差額補填。借金（負の残高）は補填しない。

    必要額は当エポックの給付必要額そのものであり、都市の失業・高齢化・困窮が増えれば自動的に増え、好況で減れば自動的に減る（歳出側の自動安定化装置）。比率を下げると全給付が同率で按分され、比率 0 で給付を停止できる。退職年齢と各給付率（retirement_age、unemployment_benefit_ratio、pension_benefit_ratio、livelihood_assistance_ratio）はプレイヤーが設定する都市の政策で、規制設定（/api/v1/city/regulations）の一部として保持・変更される。

    貯蓄（LEDGER_RESERVE） 支出カテゴリではなく、どのカテゴリにも配分しなかった余剰現金を指す。予算は「必要額 × 比率」で 導出されるため、比率を満額（1.0）にしても現預金に余りがあればその分が貯蓄として残る。 savings_target を設定すると、配分前に現預金からその額を確保でき、意図的に貯蓄を積み増せる （その分だけ配分可能額が減り、より保守的な運営になる）。

    支出カテゴリの判定

    公共施設が支出を行う際、その支出がどのカテゴリに計上されるかは、支出元の公共施設の variant に設定された cost_category により一意的に決まる。

    社会保障の給付は実体のある施設を持たない。予算パネルの施設一覧では給付種別（失業給付・年金・生活扶助）の3行として示され、行の合計がカテゴリの必要額と一致する。

    建設・修繕のカテゴリ判定は、需要を処理する代表エージェントの種類によって決まる。建設代理エージェント（VARIANT_ZONE_CONSTRUCTION）の支出は建設カテゴリ、修繕代理エージェント（VARIANT_ZONE_CONSTRUCTION_MAINTENANCE）の支出は修繕カテゴリとして扱われる。

    予算枠外の支出（収用補償）

    上記の予算カテゴリとは別に、市が民間所有の土地区画を収用したとき、所有者へ支払う土地代（収用補償。市 → 所有者）が LEDGER_LAND_ACQUISITION のキーで city.total_expense に計上される。これは歳出側にのみ現れる台帳キーであり、予算カテゴリではないため予算の配分・制御には関与しない。収用補償は予算枠であらかじめ計画する支出ではなく、実際に収用が発生したときに実支出として事後記録される。

    22.5. 予算の執行制御

    予算がどう支出を制御するかは、運営カテゴリと建設系カテゴリで異なる。

    継続的支出（商品調達・家賃・賃金）は執行時にカットしない

    商品調達・家賃・賃金は、公共施設の運営に不可欠な継続的支出である。これらは執行時に予算枠でカットされず、生産計画（雇用枠・生産目標・調達量）が立った支出は必ず全額実行される。予算の制御は生産計画への事前反映（後述の「予算に基づく雇用枠の調整」）だけに効かせる方式であり、これにより「計画上は稼働できるはずの施設が、執行時の予算切れで一部の資材だけ調達できず稼働不能になる」事態は起きない。

    計画を超過した支出（物価上昇による資材費の期中変動など）は市の貯蓄の取り崩しとして吸収され、貯蓄が尽きれば市政府の債務（現預金のマイナス）になる。債務超過に陥ると次のエポックの予算導出で全カテゴリの予算が 0 になり、生産計画が全面縮小されて雇用・調達が止まる。つまり借金はできるが、その代償は翌エポック以降の公共サービスの縮小として払うことになる。

    建設は残予算の枠内で執行され、「建設サービス財の部分発注 → 工期が延びる」形で1エポックあたりの支出が減る（総額は不変）ため、予算比率を下げるだけでも建設を減速できる。

    社会保障も残予算の枠内で執行される。必要額が枠を超える場合は全世帯への給付が同率で按分され、枠が 0（比率 0 または債務超過）なら給付されない。

    施設別の稼働率目標

    公共施設の実効稼働率は、施設・道路ごとに設定する稼働率目標（utilization_target）のみで決まる。稼働率目標は予算とは独立に効くため、予算が潤沢でも特定の施設を低稼働で運転して支出を抑える、といった操作ができる。

    • 稼働中の施設 ... 稼働率目標（0〜1、標準1.0）が生産計画に反映され、その施設の雇用枠・生産目標・資材需要が比率に応じて絞られる。
    • 建設中の建物・道路 ... 稼働率目標が「建設スピード倍率」（0〜5、標準1.0、最大5倍速）として働き、1エポックあたりの建設サービス財需要に乗算される。スピードを下げると1エポックの支出が減る分だけ工期が延びる（総建設費は不変）。
    • 修繕 ... 稼働率目標による調整はない。修繕のペースを落としたい場合は修繕予算の比率を下げる。建設サービス財の部分発注により修繕完了までのエポック数が延びる形で1エポックあたりの支出が減る（総修繕体積は不変）。

    予算に基づく雇用枠の調整

    公共施設の雇用枠（quota）は、生産計画（9_生産活動）で市場需要に基づいて計算された後、「次エポックに配分される予算の見込み額」（必要額 × 実効比率 effective_category_ratio）と照合される。照合先が当エポック予算の使い残しではないのは、この計画が実行されるのは次エポックであり、次エポックには「必要量 × 比率」で新しい予算が配分されるためである。実効比率を使うため、資金不足による自動調整や債務超過（全予算 0）は、この照合を通じて計画の縮小として反映される。各カテゴリの計画支出がこの見込み額を超過する場合、そのカテゴリに属する全公共施設の以下の計画値が追加で等比縮小される。

    • quota（雇用枠）
    • supply_target_amount（生産目標）
    • demand_amount（原材料・投資財の需要量）

    縮小の際、現雇用者への賃金・現占有面積の家賃のように計画を縮小しても直ちには減らない「確定分」は温存され、追加採用や調達予定のような「変動分」が優先的に削られる。予算見込みが確定分にも満たない場合は計画値が 0 まで縮小される。運営支出は執行時にカットされないため、この計画キャップが運営カテゴリの支出を抑える唯一の制御点であり、確定分と実支出のズレは市の貯蓄・債務が吸収する。

    これにより、比率を満額（1.0）にしていれば雇用枠・生産目標・調達量は市場需要どおりに維持され、比率を下げるとそれらが比率にほぼ比例して縮小されて、次エポックの労働マッチングフェーズで過剰人員の解雇が自然に発生する。余力運転する公共施設では比率を 1.0 超に上げると雇用枠・生産目標・調達量が同率で拡大され（生産目標は施設の生産能力が上限）、標準余力を超える待機体制を予算で購入できる。

    予算変更時の即時反映

    プレイヤーがユーザー操作フェーズで予算を変更した場合、変更直後に生産計画が再計算される。これにより、予算増額に伴う雇用枠の回復や、予算削減に伴う雇用枠の縮小が次エポックの開始までに確定し、プレイヤーの予算操作と実際の雇用調整の間にラグが生じない。

    予算の読み書きは GET /api/v1/city/budgets と PATCH /api/v1/city/budgets で行う。PATCH で設定できるのは比率（category_ratio）・貯蓄目標（savings_target）・維持優先度（budget_tiers）で、存在しないカテゴリIDは無視され、範囲外の値はクランプされる。変更は即座に予算額へ再導出され、上記の生産計画の再計算を伴うため軽い処理ではない。応答は GET と同じ形で再導出後の値を返す。

    予算の対象一覧 GET /api/v1/city/budgets/agents（category_id で絞り込み可）は、カテゴリに寄与する対象ごとの前エポック実績（actual_expense）と次エポック見込み（projected_expense）を返す。行の kind は agent（公共施設）・path（道路等の建設・修繕）・parcel（用地買収）に加えて、実体のエンティティを持たない welfare（社会保障の給付種別。welfare_kind=unemployment/pension/livelihood）がある。社会保障の前実績は給付種別に分けて記録されないため、カテゴリ合計が失業給付の行にまとめて載る。

    公共工事の発注時の資金審査

    市政府が発注する公共工事（公共建物の新設、道路などパスの新設、パスの造り替え）は、発注の時点で事業費の全額を「未拘束の現金」で賄える場合にだけ受理される。自治体が事業費を歳出予算に全額計上してから着工するのと同じ考え方で、資金が無いまま発注して永遠に進まない案件を最初から作らせない。

    未拘束の現金 = 市政府の現預金 − 貯蓄目標 − 既存案件の拘束額
受理条件     = 新規案件の推定総額 ≤ 未拘束の現金
    • 拘束額は、発注済み・計画中（確定前の計画を含む）・建設中の公共建物と、計画中・発注済み・建設中・造り替え中のパスの「残り事業費（残り体積 × 建設サービス財の地区平均価格。パスは面ごとに半分ずつ、その面の地区の平均価格）」に、買収交渉中の土地区画の買収金見積を加えたもの。確定前の計画も含めるため、同じ現金を1回の計画フェーズ中に複数の工事へ二重に当てることはできない。
    • 推定総額は建設サービス財の費用に、直接配置で民間区画の自動買収を伴う場合はその買収金見積を加えたもの。
    • 対象外: 体積0の工事（未舗装路など建設コスト係数0のパス）は資金に関わらず受理される。取り壊しは審査しない（資金不足で止めると土地が永久に塞がるため）。修繕は自動開始のため対象外で、民間建物はプレイヤーが発注しないため対象外（与信枠で制御される）。テンプレート作成モードでも審査しない。
    • 市政府が債務超過（現預金が0以下）の間は、未舗装路以外の公共工事は発注できない。
    • 審査は発注時点の地区平均価格で行うため、着工後に価格が上がれば調達不足は起こり得る。それは建設サービス不足のアラートが受け持つ。

    資金不足の発注はAPIがエラーコード INSUFFICIENT_FUNDS で拒否し、必要額・利用可能額・不足額を併せて返す。建物・パスのコストプレビューAPIも同じ判定結果（affordable / required_total / available_funds / funds_shortfall、審査なしのときは unlimited: true で available_funds は null）を返すため、UIは確定前に不足を表示できる。パスの造り替えの dry_run も同じ項目を返す。

    さらに、形状を描く前の目安として、バリアント（規格・施設）ごとの基準費用と現在の利用可能額での可否をまとめて返すAPI（GET /api/v1/paths/variant-affordability・GET /api/v1/buildings/variant-affordability）がある。基準費用はパスなら「平地・標高ゼロ・基準延長（100m）」の建設費、建物なら「既定の底面（default_width × default_height）・最小階数（min_floors）・平地・最も安い許可構造」の建設費で、これを賄えない規格・施設は建設パネルの選択肢から選べなくなる。あくまで先回りの目安であり、実際の受理可否は発注時に形状の総額で審査される。

    建設買収の可否判定

    建設時の土地買収は一括的な支出であり、按分による部分実行が意味を持たない。そのため、予算が不足する場合は買収自体が失敗し、着工がスキップされる。

    22.6. パス需要を肩代わりする代表エージェントの分割

    道路は経済主体ではないため、市場での需給処理には直接参加できない。そこで、道路の建設・修繕需要は事前に地区の代表エージェントに付け替えられる。道路は左右の面ごとに地区を持つ（4_地区と土地区画）ので、需要は面ごとに半分ずつその面の地区の代表エージェントが受け持つ（2地区の境界の道路は両側の地区が半分ずつ）。

    パス需要を肩代わりする代表エージェントは、需要の種類によって2種類に分かれている。

    • 建設代理エージェント（VARIANT_ZONE_CONSTRUCTION）... 新規建設・解体の需要を処理する。建設中・解体中パスの需要がこのエージェントに移管される。
    • 修繕代理エージェント（VARIANT_ZONE_CONSTRUCTION_MAINTENANCE）... 修繕の需要を処理する。既存パスの修繕需要がこのエージェントに移管される。

    両エージェントとも public_facility 属性を持ち、マスターデータの cost_category によって建設予算・修繕予算の制御対象となる。なお、転居時の一時入居先は独立した転居補助エージェント（VARIANT_ZONE_RELOCATE）が担い、こちらは予算制御には関与しない（4_地区と土地区画 参照）。

    22.7. 公共施設の会計統合

    公共施設は市政府の下部組織として位置づけられ、その収支は市政府の収支に統合される。エポック末尾の処理で、全公共施設の reserves（現金残高）が市政府に付け替えられ、公共施設側はゼロにリセットされる。黒字は市政府が吸収し、赤字（reserves が負）は市政府が肩代わりする。運営支出は執行時に予算枠でカットされないため、公共施設は一時的に赤字残高で支払いを続けられ、その赤字はこの統合を通じて市政府の現預金（場合によっては債務）に反映される。

    付け替えは施設のステータスを問わない。建設中・解体中・停止中の施設も対象で、建設・解体の工事費は支払ったエポックのうちに市政府の現預金へ反映される（発注時の資金審査が、支払い済みの工事費を使える現金と見誤らない）。公共施設が削除されるとき（着工前・建設途中での取りやめ、取り壊し後の清算）に残っていた残高も、中央銀行ではなく市政府へ移る。民間の主体の清算とは異なり、公共施設の支出を中央銀行経由で経済全体に肩代わりさせることはない（7_金融システム）。

    この処理により、公共施設が独自に資金を蓄積することはなく、すべての収支が市政府に一元化される。この付け替えは会計上の内部整理であり、支出や収入の記録には影響しない。

    ただし、輸出入拠点はこの会計統合の対象外である。拠点の現金残高は都市の貿易収支を表現する台帳であり（7_金融システム 7.2）、市財政に統合すると輸入代金がそのまま市の収入になってしまう。拠点の残高は市政府へは付け替えられず、拠点間の均等リバランスのみが行われる。

    22.8. 予算の維持と自動調整（スケーリング）ルール

    予算はプレイヤーの比率（category_ratio）と、カテゴリ別の必要額から導出される（エポック開始時、および比率変更API）。

    導出と資金充足時

    1. カテゴリごとの基準額（必要量）を求める。必要量は「各公共施設が生産計画どおり稼働した場合の1エポック見込み費用」である:
      • 運営(1〜7・11): 生産計画どおりの賃金・物資・投資財・テナント家賃。賃金は現在の雇用者と雇用枠の多い方（採用予定の分を含む）で、物資は現在の雇用者で生産できる量の原材料費で見積もる（高度人材が不足して生産が止まっている施設は原材料費 0）。生産能力いっぱいの費用ではないため、稼働できない施設や需要に比べて大きすぎる施設が他カテゴリの予算を圧迫することはない。教育機関など一般施設以外の公共雇用主の運営費も含まれる。
      • 建設(8): 全建設案件（発注済み・建設中・解体中・造り替え中の建物と道路）を現在の建設スピード設定で進めた場合の1エポック支出。基準には施設別の建設スピード（utilization_target、0〜5）が含まれるため、「比率100% = 設定した建設スピードに必要な額」となる。
      • 修繕(9): 修繕中の公共建物・道路の1エポック修繕需要（設定済みの修繕需要どおり進めた場合の見込み額）。
      • 社会保障(12): 当エポックの失業給付・年金・生活扶助の必要額の合計。
      • 用地買収(14): 買収交渉中の土地区画の買収金見積の合計。
    2. カテゴリごとの希望額を desired[cat] = 必要量[cat] × category_ratio[cat]（比率は 0〜1.5 にクランプ）で求める。基準額は実績を参照しないため縮小スパイラルは構造的に発生せず、比率はプレイヤーが変えるまで恒久的に有効である。
    3. 配分可能額 available = reserves − savings_target（0 未満は 0）。
    4. Σ desired ≤ available の場合は希望どおり全額を budgets に配分する。配分しなかった余剰現金（available − Σ desired と貯蓄目標分）はどのカテゴリにも積まず現預金に残し、貯蓄（city.savings）とする。
    5. まだ必要量が捕捉・検出されていない初回エポック等（Σ base ≈ 0）は、全カテゴリに現預金を均等配分してブートストラップする。

    資金不足時（自動調整）

    Σ desired > available の場合は、budget_auto_adjusted を立て、設定された維持優先度（Tier）の低い順に希望額を削減して available に収める。Tier は数字が小さいほど優先的に維持され、数字が大きいほど先に削減される（削減は Tier 4 → 1 の順）。既定の割り当ては以下のとおり。

    • Tier 1（最優先維持）: 市政 (LEDGER_CITYHALL), 医療 (LEDGER_MEDICAL), インフラ (LEDGER_INFRASTRUCTURE), 修繕 (LEDGER_MAINTENANCE), 社会保障 (LEDGER_WELFARE)
    • Tier 2: 教育 (LEDGER_EDUCATION), 治安維持 (LEDGER_SECURITY), その他 (LEDGER_OTHER), 消防 (LEDGER_FIRE)
    • Tier 3: 建設 (LEDGER_CONSTRUCTION)
    • Tier 4（最初に削減）: 貯蓄 (LEDGER_RESERVE)（希望0のため実質は Tier 3 から削減される）

    削減の適用フロー：

    1. 不足額（Deficit = Σ desired − available）を解消するため、まず最も維持優先度の低い Tier 4 のカテゴリから削減する。
    2. 特定の Tier に属する全カテゴリを 0 にしても不足額が残る場合は、1つ上の Tier へ削減処理が移行する。
    3. 特定の Tier 内で不足額をカバーできる場合は、その Tier に属する各カテゴリを元の比率を維持したまま均等（比率均等）に削減する。
    4. 市政府が債務超過（reserves <= 0）となった場合は、すべての予算が 0.0 に設定される。実効比率が 0 になるため生産計画（雇用・調達）が全面縮小される。現雇用者への賃金など確定分の支出はすぐには消えないため、債務は数エポックかけて拡大が止まり、収入の回復とともに返済される。

    これにより、資金が潤沢なら比率どおり満額を配分して余りを貯蓄し、資金が逼迫すると建設 → 低優先の運営サービスの順に自動的に絞られ、医療・市政・インフラなどの必須サービス（Tier 1）は最後まで維持される。プレイヤーは金額を毎エポック調整する必要がなく、優先度と比率を一度設定すれば都市が成長しても機能し続ける。なお、API で budgets を直接上書きして自動導出を回避することもできる（上書き額は次のエポック開始時の再導出を1回だけスキップさせ、そのエポック限り有効）。

    優先度（Tier）のカスタマイズ

    これらの維持優先度（Tier 1 〜 Tier 4）は、各カテゴリについてプレイヤーがいつでも自由に変更可能である。設定は city.budget_tiers に保存され、API（/api/v1/city/budgets）を介して永続化される。
