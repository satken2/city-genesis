# 共通部品と実装範囲

この表は27ステップを実装するための部品表。**「利用可」だけが現在JSONに書ける契約**。拡張項目の型やIDを推測してJSONへ追加しない。全チュートリアルの全ステップを新基盤で書く。

## 全体の構成

| 部品 | 責任 | 状態 |
| --- | --- | --- |
| 定義・検証 | JSON Schema、型、操作名・定数・束縛名・重複IDの検査 | 利用可 |
| 進行管理 | Tauriの専用ウィンドウに1つ。段階の再評価、読了確認、失敗・再試行 | 利用可 |
| UI案内 | 各WebViewで強調、関係するウィンドウだけ許可、個別操作だけ許可 | 利用可 |
| Unity案内 | 地面相対の点マーカー、直線の予定線、クリック範囲・吸着 | 利用可 |
| 都市判定 | 対象の属性、予算比率、ノード間の連結、名前付き対象 | 利用可 |
| 初期配置・代行 | 道路・矩形探索区画・地区・建物の作成、対象指定の完成、再描画 | 利用可 |
| 都市内の選択対象限定 | 指定建物・道路・区画・ノードだけ選択可能にする | 共通部品として追加が必要 |
| 面と既存物の案内 | 複数区画の輪郭、名前付き物体から座標を取得して追従するマーカー | 共通部品として追加が必要 |
| 高架・端子間の配置 | 実ノードへの接続、複数点・線路平行間隔の制約(始終点の高さは `world.path` で指定できる) | 共通部品として追加が必要 |
| 集合・路線の判定 | 新規作成集合の束縛、2駅・ホーム所属・往復経路・運行可能状態 | 共通部品として追加が必要 |
| 初期都市 | 支援の町・教材の区画・資源・既存施設 | 利用可(コアが作り、`support.` / `lesson.` の名前で束縛に入る) |
| カメラの案内 | 段階ごとの注視点・距離・方位・俯角 | 利用可 |

新部品は `tauri/src/tutorial/` と `unity/Assets/Scripts/Tutorial/` に置く。通常画面への変更は安定した操作名の属性と入力・確定の接点に限定する。シナリオIDによる分岐を通常の建設ロジックへ追加しない。

## JSONに書ける項目

トップレベルは `version: 1`、`id`、任意の `setup`、`steps`。座標が前提とする舞台の地形は、コアの教材JSON(`stage`)と同梱の都市が決める。ステップには安定IDの `id`、既存ステップとの対応番号 `legacyStep`(1始まりの並び順)、段階列 `phases` を書く。段階は `id`・7言語へ登録した `textKey`・`ui`・`world`・`until` を持つ。実ファイルは `tauri/src/tutorial/definitions/basic.json` と `scenario3.json` を読む。

| 分類 | 契約 |
| --- | --- |
| `ui.policy` | `highlight` は制限なし、`related` は許可ウィンドウ内も操作可能、`strict` は個別操作のみ |
| `ui.allow` / `highlight` | 許可対象と強調対象の配列。別々に指定する |
| `world.mode` | `observe` は制限なし、`blocked` はワールド編集停止、`path` は指定パス(道路・プラットフォーム)の配置 |
| `world.markers` | `[x, 地面相対y, z]` の配列。保存されない描画物 |
| `world.camera` | `target`(地面相対の `[x, y, z]`)、`distance`、`yaw`(北=0の時計回り)、`pitch`(5〜89度)。直前と違う案内先のときだけカメラが滑らかに移動する |
| `world.path` | `points` は始終点2点(`[x, 地面相対y, z]`)、`radius` は地表上のクリック許容半径m、`variant` はバリアント、`bind` は保存IDの格納名。この項目がある段階では、パス建設パネルで `variant` 以外のカテゴリ・カードを選べない |
| パスの範囲 | v1は直線・盛土0・線路1本。始終点の相対高さは点ごとに書ける(地上は0、高架の高速道路は正の値。高さ編集ができるバリアントだけ)。円は地表に描き、吸着した点は指定の高さに置かれる。道路と同じ敷設エディタで敷くプラットフォームにも使える(ホームの側は検証しない)。水色の始点と黄色の終点を左クリックし、右クリックで形状確定。確定の右クリック位置は問わない。普通の建設可否も通る必要がある |
| `$constant` | 共有定数名、または `TUTORIAL_STREET`。後者は街路・2車線・高さ編集不可・接道可のマスター候補が1件のときだけ解決 |
| `$ref` | 名前付き対象の数値ID。文字列埋め込み・任意式・コード実行は不可 |
| コアの対象名 | `support.<名前>`・`lesson.<名前>` はコアが作った初期都市の対象。定義内の `bind` なしで `target` 等から参照できる |

利用できるHUD操作名は `hud.road`、`hud.construction`、`hud.land`、`hud.district`、`hud.execute`、`hud.visibility`、`hud.transport`。区画作成パネル(`hud.land`)は `parcel.mode`(作成方法のタイル。値は方法の名前で、`parcel.mode:along_path`=道路沿いに作成)、`parcel.clear`、`parcel.confirm`。道路・鉄道・インフラはすべて `hud.road` のパス建設パネルで敷き、パネル内は `path.type`(カテゴリのタイル)、`path.variant`(バリアントのカード)、`path.followTerrain`(地形追従の選択肢)、`path.platformSide`(ホーム設置側。値=`0`外側・`1`内側・`2`両側)、`path.back`(カテゴリ・カード一覧へ戻る)、`path.confirm`、`path.cancel`。建物建設パネル(`hud.construction`)は `building.category`(分類のタイル)、`building.variant`(建物のカード)、`building.back`(分類・カード一覧へ戻る)、`building.cancel`(仮決定した設置位置の取消)、`building.confirm`(確定)。公共交通(`hud.transport`)は `transit.new`(路線の新設ボタン)、新設パネルの `transit.type`(路線種別の選択。`<select>` なので選択肢は絞れない)・`transit.fare`(運賃)・`transit.headway`(運行間隔)・`transit.confirm`・`transit.cancel`。ウィンドウ単位の許可は `window.path_build`、`window.agent_detail`。新しい対象は実要素に `data-guide` を付け、`definitions.ts` の登録表・テスト・本表を同時に更新する。

タイルとカード(`path.type`・`path.variant`・`building.category`・`building.variant`)と地形追従の選択肢(`path.followTerrain`)は `名前:値` で1つだけを指せる。値はカテゴリ(`path_type`・`bd_category`)・バリアントの番号・地形追従の設定値(`0`=非追従、`1`=追従)で、例えば `["hud.construction", "building.category:7", "building.variant:1054"]` は建設アイコン・発電所の分類・太陽光発電所のカードを順に強調する。値の無い名前はその名前の要素すべてを指す。押せない(`disabled`)タイル・カードは強調しないので、`world.path` で選べるバリアントが1つに絞られる段階は値の無い名前でもその1枚だけが光る。建物・道路・鉄道・インフラを建てさせるステップは、全段階を `strict` にして、HUDのアイコンに加えてパネル内で選ぶタイルとカード(`allow` に `名前:値` で書く)を強調し、他のタイル・カード・階数などの設定を押せなくする。段階は「パネルを開く(`window`)→ 種別とカードを選ぶ(`pathVariant`。建物は選択が観測できないので選ぶ段階と確定の段階を分けない)→ 敷設・確定」の順で、同じ説明のまま続ける。カードを選んだ後の段階の `allow` には、戻る(`path.back`・`building.back`)・取消・確定と、そのステップの案内が使う設定(ホーム設置側・地形追従)だけを書く。公共交通の路線の新設も同じ規則で、「管理ウィンドウを開く→ 新設ボタン→ 種別・運賃・運行間隔・確定」の3段階にする。建物は確定するとパネルが閉じるので、複数段階のステップは達成条件(`complete`)を満たした時点で最終段階として扱い(`findPhase`)、「次へ」は最終段階でなくても達成条件そのものを確かめる。

ウィンドウ移動・閉じるための `.titlebar` と明示した `data-guide-escape`、チュートリアル・通知・Tipsは操作制限の対象外。システムトレイと設定・クレジット・セーブ/ロード・セーブ一覧・新規ゲーム・確認ダイアログも常に操作できる。除外一覧は `dom.ts` が管理する。スクロールとカメラは保持する。通常のdisabledは解除しない。別WebViewはそれぞれ同じ案内を受け取り、自分のDOMへ適用する。

アイコンパネルは方針に関わらず、その段階の `allow` と `highlight` にあるボタンだけを押せる(強調だけの段階でも他のボタンは無効になる)。段階をまたいで押せる必要があるボタン(地区編集の切り替えなど)は `allow` に書く。

## 判定と代行

| 条件 `type` | 合格条件 |
| --- | --- |
| `ack` | 説明の読了。最終段階は完了ボタンが必要 |
| `all` / `any` | 子条件のAND / OR |
| `window` | 指定 `window` が実際に表示中。`target` を付けるとその対象IDの詳細に限定 |
| `pathVariant` | 編集パネルで指定した `value` が選ばれている |
| `pathPoints` | `count` 以上の頂点がある。任意の `phase` により確定前の編集状態も指定 |
| `hudMode` | HUDの常駐モードが `mode`(`district`=地区編集、`bulldozer`=ブルドーザ)。HUD間で共有される `hud:mode_changed` を購読して知る。通常状態は未設定で、どの `mode` にも合致しない |
| `entity` | `resource` の `where` を満たす対象がある。`target` で既存束縛を指定、`bind` で対象IDを記録 |
| `budgetRatio` | `category` の配分が全配分の合計に対して `min` 以上 |
| `connected` | `from` / `to` の対象の `terminal` ノード間に、`where` を満たすパス列が存在 |

`where` は項目名 `field` と `equals` / `notEquals` / `oneOf` / `greaterThan` のいずれか。`notEquals` は項目が無い行を合格にしない。`field` はドット区切りで辞書を読める。一覧に無い項目は単体APIで補う。対象のIDは種類ごとに読むため、建物の区画IDを建物IDとして扱わない。条件は都市を書き換えず、束縛だけを更新する。ノードのそれぞれに別々の線があるだけでは `connected` を満たさない。

道路の `curved` はAPIの数値0/1を読み取り時にbooleanへ正規化するため、定義では `false` / `true` と比較する。それ以外の項目で文字列・数値・booleanを同一視する変換は行わない。

アクションは `create`、`completeConstruction`、`reload`。`create` は1アクション1対象で、道路・地区・区画・建物を `bind` へ保存する。区画は現行APIの `mode: empty_area` と中心座標・幅・高さを用いる。`completeConstruction` は `target` だけを完成し、結果を読み直す。新規作成の成功はすぐ記録する。応答が失われて作成結果を特定できない場合は自動再POSTしない。新しい都市での再開始を案内する。

順番は `setup` → 各段階の `until` → 次へボタン → `beforeCheck` → `complete` → `afterCheck` → 進捗保存。例えば、接続確定のための完成が先に必要な条件は `beforeCheck`、発電所の工期を省略する説明は `afterCheck` へ書く。条件未達やアクション失敗ではステップを進めない。

## 設計書と実装の差

設計書の「共通部品として追加が必要」な部品(都市内の選択対象限定、面と既存物の案内、端子間の配置制約など)は未実装で、該当するステップは強調だけの案内・マーカー・コアの判定で代える。

| シナリオ | 現在の書き方 |
| --- | --- |
| 基本5 | 道路配置・区画・集合住宅は指定操作だけ許可(区画と建物は、アイコンでパネルを開く段階のあと、パネル内の必要な操作だけを許す段階へ進む)。区画は `basic.road` を接道とするもの、集合住宅は支援町の住宅以外を `notEquals` で判定する |
| 地区7 | 道路網と鉱脈はコアの教材が作る(沿道区画は「道路沿いに作成」と同じ処理)。step1 は地区編集モードに入るまでとその後(カメラがマーカーへ寄る)の2段階。地区の分割は `lesson.right_top` の地区IDを `notEquals` で、天然資源の表示は資源の詳細ウィンドウで、規制は元の2地区以外の地区で判定する |
| インフラ6 | 端子の位置は固定座標のマーカーで示す |
| 鉄道9 | 2駅・駅舎・本線・基地・電源・路線・乗車回数をコアの判定(`platform`・`station`・`linked`・`line`・`ridership`)で確かめる |

部品を追加するときも既存の型の意味を変えず、必要な型をSchema・両ランタイム・試験へ一緒に足す。未対応機能を強調だけへ黙って置き換えたり、合格条件を「何か1つある」へ弱めたりしない。

## 検証

- `cd tauri; npm run test:tutorial`: 段階進行・戻り・正しい対象・接続・操作制限・解除・作成の再試行・定義と7言語を検証する。`check:tutorial` は同じ検証入口。
- `cd unity; ./Tests/Tutorial/run-unity.ps1`: 隔離したUnityで本編アセンブリのIPC・道路入力・吸着・解除・描画メッシュを検証する。
- `npm run build`、Rustの `cargo check`、既存の翻訳整合スクリプトも通す。
- 完成したシナリオの手動確認では、各段階で閉じる・取消・Unity再起動・通常都市への切替を含める。基盤試験の成功は、未移植のステップを含む全体の通しプレイを意味しない。
