# docs

Unity・Tauri の OSS 開発者向け公開ドキュメント。日本語原本は `docs/ja/`、英訳は `docs/en/`。GitHub 上で Markdown を直接読み、各言語の `README.md` が本文の目次である。

## 文書の配置

| 配置 | 内容 |
| --- | --- |
| `docs/{ja,en}/economics/` | シミュレーションの概念。フロントが表示・操作する対象が何を意味するか |
| `docs/{ja,en}/geometries/` | 形状データの表し方と、Unity の描画の全体構成・共通の仕組み |
| `docs/{ja,en}/programs/` | フロントの全体構成と共通基盤、コア・Unity・Tauri の間の通信の仕組み |
| `docs/{ja,en}/contributing/` | 翻訳用語と素材の扱いなど、公開リポジトリへの参加者が共有する約束 |
| `docs/api/` | 自動生成の API 資料。項目の説明の正はコアのスキーマ定義 |
| `docs/images/` | 両言語で共有する画像と図 |

## 共通ルール

- 日本語原本を先に編集し、対応する英訳を同じ変更で揃える。仕様や意味は日本語を正とし、翻訳だけに説明を追加しない。図・生成 API 資料は言語ディレクトリの外で共有する。リンクは各言語内の Markdown ファイルを相対参照する。
- 書くのは、Unity や Tauri の開発者が知る必要のある全体的な考え方だけ。シミュレーションの概念、フロントの全体構成と共通の仕組み、座標・単位・命名などモジュール間で共有する約束を書く。API・IPC の項目は網羅せず、読み違えやすい重要な項目だけを考え方の説明の中で書く(項目の一覧は API 資料、IPC はソースのコメントで読む前提)。
- コアの処理ロジック、内部の変数名・関数名・ファイル名を書かない。名前を出してよいのは、API・IPC の項目、フロントが読むマスターの項目、同期される共有定数のように、フロントから見える名前だけ。
- 個別の機能・画面・パネル・イベント・バリアントの仕様、閾値や係数などの値、クラスやメソッドの説明は書かない。それらはソースのコメントに書く。
- 実装を日本語に置き換えただけの説明、コードの写し、TODO、構想、作業記録、変更経緯、旧仕様との比較を書かない。
- 同じ説明は1か所に書き、他のページからは参照する。
- ソースを変えても、上の基準で書くべき内容が変わらなければ更新しない。
- ページを追加・削除したら両言語の `README.md` の目次と関連リンクを揃える。生成 API 資料は手編集せず取得スクリプトで更新する。
- 見出しリンクは GitHub のアンカーに合わせる。リンク先の見出しを一意にし、推測した連番アンカーを使わない。
- 文書の移動では本文・画像・API仕様の保持と、相対リンクの参照先を確認する。サイトのビルド環境は使わない。
