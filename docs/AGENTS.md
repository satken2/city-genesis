# ドキュメントフォルダ構成

```
genesis-docs/
├── mkdocs.yml              # MkDocs 設定ファイル
├── requirements.txt        # Python 依存パッケージ
├── fetch_openapi.py        # バックエンドから openapi.json を取得するスクリプト
├── docs/                   # 公開対象（MkDocs のビルドソース）
│   ├── index.md            # トップページ
│   ├── overrides/          # MkDocs テンプレート上書き
│   ├── economics/          # 経済シミュレーションの概念・データモデル（アルゴリズム不含）
│   ├── geometries/         # 形状データの仕様＋フロントエンドのレンダリング実装仕様
│   ├── programs/           # コンポーネント間連携仕様（IPC、起動順序、入力制御）
│   ├── api/                # OpenAPI 3.1 仕様
│   └── images/             # ドキュメント内の画像アセット
└── site/                   # ビルド出力（.gitignore 対象）
```

# 分類ルール

## ルール1：「What」vs「How」

| 基準 | `docs/`（公開） | genesis-corereレポジトリの`docs/`（非公開） |
|---|---|---|
| 視点 | 「何があるか」「どういう概念か」 | 「どう計算するか」「どう実装するか」 |
| 例 | 「市場には供給者と需要者がいて、価格で取引される」 | 「マッチングスコア = (price + transport) / attraction + noise」 |

概念の定義、データモデル（プロパティ名・型・取り得る値）、ステートマシン（statusの遷移）、ゲームルールとしてプレイヤーが知覚できる挙動は `docs/` に置く。スコア関数の数式と係数、マッチングの貪欲法の詳細手順、賃金・家賃調整の具体的な増減率、ペナルティコストの掛け方等の計算詳細は genesis-corereレポジトリの`docs/` に置く。

## ルール2：観測可能性

| 基準 | `docs/`（公開） | genesis-corereレポジトリの`docs/`（非公開） |
|---|---|---|
| 観点 | APIレスポンスやIPCイベントとして外部から観測できること | バックエンド内部の計算過程（結果しか見えないこと） |
| 例 | エージェントの status（PENDING, ACTIVE等）、パスの座標データ | マッチングのスコアリング、賃金調整の内部計算 |

## ルール3：コンポーネント帰属

| 実装先 | `docs/`（公開） | genesis-corereレポジトリの`docs/`（非公開） |
|---|---|---|
| Unity / Tauri（オープンソース） | その実装に必要なすべての仕様 | — |
| バックエンド（クローズドソース） | 外部インターフェースとデータモデルのみ | 内部アルゴリズムの詳細 |
| 両方にまたがる | インターフェース契約（IPC、API） | 各自の内部処理 |

フロントエンド（Unity）のレンダリング実装（LOD処理、メッシュ生成、データロード・差分同期、アート制作仕様）は `docs/` に置く。バックエンドの内部処理（スポーンロジック、経路探索、市場マッチングの計算式）は genesis-corereレポジトリの`docs/` に置く。

## ルール4：プログラム間連携の帰属

| 種類 | 場所 | 理由 |
|---|---|---|
| IPCプロトコル仕様 | `docs/` | 両コンポーネントの開発契約 |
| 起動順序・セッション管理 | `docs/` | 各コンポーネントの責務範囲 |
| 入力制御（Unity） | `docs/` | Unity開発者の実装対象 |
| ビルド・梱包の運用手順 | genesis-corereレポジトリの`docs/` | 内部開発プロセス |
| スタブパターン等の開発手法 | genesis-corereレポジトリの`docs/` | 内部開発プロセス |

## ルール5：経済ドキュメントの概念とアルゴリズムの分離

`docs/economics/` には概念レイヤーのみを記載する。計算アルゴリズムは対応する genesis-corereレポジトリの`docs/economics/` のファイルに記載する。

**`docs/economics/` に書く内容:**
- 「市場には商品種別がある」「賃金は労働力に応じて決まる」「家賃は需要過剰で上がり、空室で下がる」等の概念
- データモデル（プロパティ名、型、取り得る値）
- ステートマシン（statusの遷移図）
- ゲームルールとしてプレイヤーが知覚できる挙動

**genesis-corereレポジトリの`docs` に書く内容:**
- スコア関数の数式と係数
- マッチングの貪欲法の詳細手順
- 賃金・家賃調整の具体的な増減率
- 生産目標の計算式
- ペナルティコストの掛け方

対応関係は、`docs/economics/8_商品市場.md` に対して genesis-corereレポジトリの`docs/economics/8_商品市場マッチング詳細ロジック.md` のように、同じ番号で対応付ける。

## ルール6：ジオメトリ・グラフィック関連の帰属

| 種類 | 場所 | 理由 |
|---|---|---|
| データ形式の定義（Bezier曲線の構造、ポリゴンの座標系） | `docs/` | フロントエンドがデータを解釈するためのインターフェース仕様 |
| メッシュ生成パイプライン | `docs/` | Unity開発者が実装するもの |
| LODシステム | `docs/` | Unity開発者が実装するもの |
| データロード・差分同期 | `docs/` | Unity開発者が実装するもの |
| アート制作仕様（建物パーツ等） | `docs/` | オープンソースのアーティストが参照するもの |
| パス交差の世界モデルルール | `docs/` | ゲームの概念定義 |

## ルール7：ゲームロジックの帰属

| 種類 | 場所 | 例 |
|---|---|---|
| ゲームのルールとして表現される挙動 | `docs/` | 「道路には論理長があり、渋滞で増える」「地区は連結性を保つ」 |
| その計算の内部実装 | genesis-corereレポジトリの`docs/` | 論理長の3段階計算式、地区切断のグラフ理論的検出アルゴリズム |

ゲームルールとしての概念説明は対応する `docs/economics/` のファイルに含め、計算アルゴリズムは genesis-corereレポジトリの`docs/game-logic/` に置く。


## ルール8：書いてはいけないもの（economics/ で特に厳守）

`docs/economics/` は「フロントエンド実装者が知る必要のある、外から見たシミュレーション仕様」だけを書く場所である。以下は書いてはいけない。

- **操作説明書・UI挙動の描写**: 「〜パネルで確認できる」「〜ウィンドウが表示される」「グラフは実線/点線で表示」「マーカーがアニメーションする」等。プレイヤー操作の手順一覧（「プレイヤーの操作」節など）も不要。UIの実装仕様が必要なら programs/ か UI 側のドキュメントに書く。
- **APIに露出しない内部変数・定数名**: 名前を書いてよいのは、APIレスポンス/リクエストに現れるプロパティ（`genesis-corere/app/schemas.py` で確認）、マスターデータのキーgenesis-corecore/consts.py` から Tauri/Unity に同期される共有定数のみ。バックエンド専用の定数（例: `MIN_PROFIT_RATE` の類）は「一定の閾値」等の定性表現にし、ゲームルール上意味のある**値**（0.5/1.5 の教育境界など）だけを残す。
- **内部の計算手順・関数名・実装ファイル名**: 「◯◯フェーズが捕捉する」「`masterdata.py` の〜」等は genesis-corereレポジトリの`docs/` の対応する「詳細ロジック」ファイルへ書く。
- **旧仕様との比較・変更経緯**: 「かつては〜だったが廃止」等は書かない。現在の仕様だけを書く。経緯が重要なら genesis-corereレポジトリの`docs/` に書く。

# ドキュメントの追加・変更手順

1. 内容が `docs/`（公開）か genesis-corereレポジトリの`docs/`（非公開）かを上記ルールで判定する
2. 該当するmdファイルを追加・編集する
3. `docs/` に新規ファイルを追加した場合は `mkdocs.yml` の `nav` にも追記する
4. `mkdocs serve` でローカル確認する
5. commit & push → Cloudflare Pages が自動デプロイ

## 見出しへのリンク

見出しのアンカーは `mkdocs.yml` の `toc.slugify` に `pymdownx.slugs.slugify`(case: lower)を指定して生成している。日本語はそのまま残り、英字は小文字化され、`\w`・`-`・空白以外の文字(`.`・括弧・全角記号など)は消え、空白は `-` になる。

- 例: `### 9.1. ステート別の表示プリセット` → `#91-ステート別の表示プリセット`、`## 8.7 柱(pillar)とキャップ(pillar_cap)` → `#87-柱pillarとキャップpillar_cap`
- `_1`・`_4` のような連番IDは既定の slugify(非ASCIIを捨てる)の形式で、この設定では生成されないのでリンク先に使わない。手元の `site/` にこの形式が残っていたら再ビルド前の出力である。
- 同じページに同名の見出しがあると2つ目以降は `_1`, `_2` が付くので、リンク先の見出しは一意にしておく。

## 判定に迷った場合

以下の質問に「はい」と答えられるなら genesis-corereレポジトリの`docs/` に入れる。

- この情報はバックエンド（クローズドソース）の計算手順を説明しているか？
- フロントエンド開発者はこの情報を知らなくても実装できるか？
- この情報が公開されても問題ないか？（アルゴリズムの秘匿性）

以下の質問に「はい」と答えられるなら `docs/` に入れる。

- この情報はフロントエンド（Unity / Tauri）の実装に必要か？
- この情報は「何があるか」「どういう概念か」を説明しているか？
- この情報はAPIやIPCのインターフェース仕様か？
